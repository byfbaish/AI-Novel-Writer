# S3 第 0 步：人类对照语料来源方案（24 小时内答复件）

> 授权：只读研究 + 新增本文件；未导出语料、未改代码、零模型调用
> 对应裁定：`.batch/night/staging/res-s3/s3-gate-ruling.md`（admin 2026-11-25 06:2x）
> 这件的用途：把「取数 ≥20 章」从愿望变成**谁在什么时间交什么文件**。语料不到线，S3 不开。

---

## 0 结论先说

- **主路径只有一条：作者库内其他成稿章（同作者）**。它是唯一能同时满足「同作者、同体裁、同人称」三条的来源。
- 备路径（主人指定书单）**只能做跨作者稳健性复核**，不能当主基线——admin 已定「不得混用不同作者凑数」，理由我认：作者基线一换，四条候选的 `P95_author` 全部失效。
- 公开授权语料：**不可行，不排期**（理由见 §1-C）。
- 现状差额：A-1.1 基线只有**同一作者 11 章 / 15,862 字 / 1,194 句**，距 20 章差 **≥9 章**；这 9 章只能从作者本人成稿里出。

## 1 三种来源逐项（哪来 / 许可 / 谁出 / 什么时候出 / 能否达标）

### A 作者库内其他成稿章（推荐，唯一满足同作者）

| 项 | 内容 |
|---|---|
| 哪来 | 作者库中状态为「成稿/定稿」的正文，导出为纯文本（一章一文件，不带元数据、不带批注） |
| 许可 | 作品版权属作者本人；用途限于**内部研究读数**：不入库（`.runtime/` 已被 gitignore）、不进产品、不外传、不用于训练、不做再分发 |
| 谁出 | **主人一句授权**（哪几本书、哪几卷算成稿）＋ **developer** 执行导出与 manifest（复用现有导出，不改 `src/`） |
| 什么时候出 | 授权到手后 **4 小时内**（导出 1h、清洗与人称核对 1h、manifest 与三行报告 2h） |
| 同作者 | ✅ 天然成立（同一作者名写进 manifest 的 `author` 字段，导出时核对） |
| 同体裁 | ✅ 同一丛书系（番茄向长篇连载），非短篇、非番外混入 |
| 同人称 | ⚠️ 需筛：同一本书内人称必须一致；跨书混用会引入人称混杂，**只取与主基线同一人称的那几本** |
| 风险 | 成稿章可能不足 20 章（现状 11 章，差 ≥9）；若确实不够，见 §3 的降级分支 |

### B 主人指定书单（参考书，只能当复核）

| 项 | 内容 |
|---|---|
| 哪来 | 主人指定 1–2 本当代中文网文，主人提供合法副本 |
| 许可 | 主人须确认持有合法副本；**不落全文**，只落派生特征（计数、比率、窗口读数），快照用完即删；不入库、不进产品、不外传 |
| 谁出 | 主人给文件 → developer 清洗并只导出统计 |
| 什么时候出 | 拿到文件后 **半天** |
| 三条是否达标 | 同体裁 ✅、同人称需筛 ✅、**同作者 ✗** |
| 结论 | **不能替代 author-v1**。若用它，等价于换基线，四条候选全部失效重来；只能作「换作者后结论是否还成立」的稳健性复核，且必须单列一节、不得与主基线合并统计 |

### C 公开授权语料（不排期）

| 项 | 内容 |
|---|---|
| 现状 | 当代中文网文**没有**可再分发的公开授权集；公有领域中文小说是古典白话（体裁、句式、篇幅都不对，且用它会把我方判据带向文言/半文言的伪特征）；研究用网文数据集多为爬取、无再分发许可、质量不可控 |
| 三条是否达标 | 同作者 ✗、同体裁 ✗、同人称 ✗ |
| 结论 | **不可行**。写进本件是为了不再被反复提出——它连「凑数」都做不到，因为一凑就混作者 |

## 3 不足 20 章时怎么办（先说清，不留空）

1. **首选**：补同作者成稿章到 ≥20。差额写明「差 N 章、需要哪几本」，由主人决定给不给。
2. **次选（降级，须 admin 批）**：用现有 11 章 + **bootstrap 1,000 次重采样**报 P95 区间，四条候选全部标注 `baselineN<20`，**一律只进报告、不出命中判定**——这正是现在的状态，等于 S3 不开。
3. **不接受**：拿别的作者的书把 n 凑到 20（混作者 ⇒ 基线失效，结论不可用）；拿短篇/番外凑（体裁变）。

## 4 验收判据（谁跑、跑什么、阈值、输出）

① 章数与字数（developer）：
```bash
node scripts/res/corpus-manifest.mjs --dir .runtime/res-corpus/author-v1 --json
```
输出 `{chapters, words, person, author, files:[{name, sha256, words}]}`。

② 五条硬判据（QA 复核，可逐条打勾）：
1. `Test-Path .runtime/res-corpus/author-v1` 为 true，且**快照内无子目录、无元数据文件**；
2. `chapters ≥ 20`、`words ≥ 40,000`（20 章 × 2,000 字下限，实际应远高）；
3. `person` 唯一值（`第三` 或 `第一`），且与主基线一致；混合即作废；
4. `author` 唯一值，且等于主基线同一作者；出现第二个作者名即作废；
5. `git status --porcelain` 里**看不到**该目录（快照不入库）。

③ 三行报告（我报群，格式固定）：
```
chapters=20  words=52,140  person=第三
author=<作者名>（与主基线同一作者）
snapshot=.runtime/res-corpus/author-v1  manifest_sha256=<总表 sha256 前 16 位>
```

## 5 红线（写在这里，免得开工时忘）

- 不混作者、不混体裁、不混人称；
- 不下载、不转载正文；语料只落 `.runtime/`，不进 git、不进 `docs/`；
- 不把语料贴进任何 `.md`（含本件）；报告只报章数、字数、人称、sha；
- 不因为「想开 S3」而降低章数门槛——门槛是结论强度的来源，不是手续。
