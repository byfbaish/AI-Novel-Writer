# Bot 主身 vs 群分身：Session ID 身份锚定规则

> 适用范围：本仓库所有 Bot 之间、Bot 与外部 agent（豆包 / WorkBuddy）之间的跨会话通信、handoff-relay watch 配置、bridge 投递。
> 起因：2026-11-15 主人发现同名的「大肥鱼」有两个，跨域通信时极易绑错；当日起为硬约束。

## 1. 两个同名条目，别绑错
查 Session ID 时会看到：

- `大肥鱼` — **主身（main）**。只属于与主人的私聊，上下文长期不变。
- `大肥鱼 · AI writer项目组` — **这个群里的分身（clone）**。群里所有的活、上下文、记忆都在它这里。

**要联系在群里干活的那一方，必须绑带群名后缀的分身，不是原名。**
`AI writer总负责人 · AI writer项目组` 才是群里那个；`AI writer总负责人` 是主身。全员同理。

## 2. 为什么绑错代价很高
主身与群分身是两个独立会话，**不共享上下文**。投给主身＝把一个长会话从冷缓存整体重建，费用最高，且对方在群里积累的上下文全部作废。

2026-11-15 实据：
1. 误投总负责人**主身** 7 次（日志 1.74 MB），其**群分身**（2.27 MB）收到 **0** 条——任务执行了，但群内上下文白积累、缓存不命中。
2. `daeb834f`：不属于任何现存 Bot/分身，孤儿，11-14 02:14 后无写入 → 两封卡死的信。
3. `33494f59`：workbuddy 的**旧分身**，11-15 00:57 停写 → 发给 workbuddy 的信号**一直静默失败**。
4. 「伪造授权」误会：豆包**群分身**说「负责人已裁定」，豆包**主身**确实没说过——同一 Bot 两个会话互不知情，不是撒谎。

## 3. 判定这是插件缺陷（记录在案）
- 主身与分身放在同一命名空间，**只靠名字后缀区分**，分身条目没有 `parentBotId` / `roomId` / `isClone` 显式字段，无法程序化判断身份；
- 没有「给定 Bot + 群 → 返回该群分身 Session ID」的解析接口；
- Session ID 每次 DSH 重启整批刷新，硬编码必然失效，而工具层**不报错**（`agent-not-found` 只落日志）。

推论：任何按名字找人的自动化都有约一半概率绑错，且错得静默。插件作者大概率没设想过跨域通信直接写死 session id 的用法。

## 4. 硬规则
1. **锚点用「Bot ＋ 群」，不用 session id。** P54 第二档「投递时现场解析分身」为必做项；绑主身直接判不合格。
2. 认身份看「角色 ＋ 所属项目/群」，不认 session id 本身。
3. 投递必须有可判定证据（relay 日志 `resolved` / `delivered` 留痕），不许「发了就算」。
4. 改 relay watch 配置：先备份 `cordis.patch.yml`，改后 js-yaml 校验并打印 watch 清单（目标 id 前 8 位＋目录）留证。
5. 发现绑定失效或绑错 → **报主人裁决**，不自行改配置。
6. 定期核对：解析每个 watch 的 Session ID 身份，核对是否指向群里干活的那一方。
