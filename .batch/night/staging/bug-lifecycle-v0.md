> 依据：用户 2026-11-16「搞得乱糟糟的，结束后一起制定标准流程，按业内标准，结合群内人员配置」。
> 本文件只写**状态机 + 门禁 + 角色映射**；执行通道/凭据/回读/台账/回执格式由 大肥鱼 出另一半。

## 1. 状态机（7 态）

```
open ──triaged──> fixing ──fixed──> in-review ──verified──> closed
  │                 │                  │
  └─rejected        └─blocked         └─reopened ──> fixing
```

| 状态 | 含义 | 谁能进 |
|---|---|---|
| `open` | 已起票、未判定 | 任何人（含用户） |
| `triaged` | 已复现、已定级、已定归属 | 大肥鱼（管家，唯一 triage 权） |
| `fixing` | 有唯一执行人正在改 | 派卡后由负责人置位 |
| `fixed` | 提交/产物已落、等验 | 执行方交付即置位 |
| `in-review` | QA 首验中 | QA 领取时置位 |
| `verified` | 首验通过、待终审 | QA 出结论即置位 |
| `closed` | 终审通过并已对外关闭 | 负责人终审后，执行方关闭 |
| `blocked` | 依赖未就绪，写清阻塞点与解封条件 | 执行人或 triage |
| `reopened` | 验过又不成立 | **任何人**，但须贴反例 |

## 2. 每跳门禁（缺一不得进下一态）

1. **open → triaged**：① 最小复现（命令/步骤）② 环境版本（宿主版本 + 插件版本/提交）③ 影响面（会不会丢数据/崩溃）④ 复现值（能稳定复现 / 偶发几成）。
2. **triaged → fixing**：① 归属明确（插件侧 / 宿主侧 / 用法问题）② **唯一执行人**（同一时刻只一个）③ 估时与验收时点 ④ 卡面落盘、派验单登记。
3. **fixing → fixed**：① 提交 SHA 或产物路径 ② 与起点 diff 范围（`git show --numstat`）③ 自测读数 ④ 报告末行 `<!-- DONE -->` ⑤ A 类卡须落信号。
4. **fixed → in-review**：派验单齐、产物在盘。
5. **in-review → verified**：① QA 重跑点名套件（不采信自测）② 禁改区未动 ③ 新增红为零（全量可带既有红，须附基线同套件同失败对照）。
6. **verified → closed**：① 负责人终审 PASS ② 关闭评论含「修复提交 + 验的哪个版本 + 日期」③ 执行方先回「我领这条」，第三方回读确认。
7. **reopen 门禁**：贴反例（能复现的最小步骤 + 当前版本读数），不写「我试了不行」。

## 3. 角色映射（按现状）

| 角色 | 在流程里做什么 | 不得做什么 |
|---|---|---|
| 主人 | 拍板对外动作（close/tag/publish）、改方向 | — |
| 大肥鱼（管家） | 起票判定与定级、对外执行与回读、台账、逾时提醒 | 不判技术质量、不代替 QA 出结论 |
| 总负责人（我） | 派卡、终审、状态推进、冲突裁决 | 不复跑测试、不亲自改码 |
| QA | 首验（`in-review → verified`）、依据核对 | 不关闭 issue、不判优先级 |
| 产品经理 | 规格与验收口径 | 不判 bug 是否成立 |
| developer | 环境/工具链取证、配置类改动 | 不改业务代码 |
| 联络人 | 派卡投递、回执完整性 | **不执行对外写动作**（11-16 事故后明确） |

## 4. 三条硬规则（本次事故直接得来）

1. **一票一执行人**：对外写动作前，执行方群里回「我领这条」，无人反对再动；同一对象同一时刻只一个执行方。
2. **不信自我报告**：状态变更以第三方回读（REST/外网）为准，回读内容含 state + 评论 id + 评论数。
3. **不可逆动作最小化**：关闭优先于删除；要改文字就编辑，不删评论。

## 5. 执行通道（大肥鱼 补）

| 通道 | 能做什么 | 凭据来源 | 边界 |
|---|---|---|---|
| 浏览器（bsk 会话，本机已登录 Chromium） | 读 issue 列表/详情、close、发评论、**编辑**评论 | 本机浏览器的 byfbaish 登录态，无需额外取 token | 首选。写入能力已于 2026-11-16 20:04（close+评论）、20:19（编辑评论）实测成立 |
| REST（`api.github.com`） | 回读 state/评论/时间；写入 | 仅 WorkBuddy 侧可用：`git credential-manager get` 取得的 `gho_…`（40 位，属 byfbaish，`permissions.push=true/admin=true`） | 本机**无 gh、无 GH_TOKEN**；匿名 API 有速率限制（触发时返回 reset 时刻）。只作回读与兜底 |

选择规则：
1. **能回读的通道优先**：做写动作的人必须同时能回读，否则动作不可审计。
2. **同一对象同一时刻只用一个通道**，另一通道只读。
3. 任何通道**禁止 `--force`**；参数按渠道文档默认值，不凭记忆覆写（护栏报警即停并上报）。
4. 浏览器通道的已知坑：GitHub 新版 UI 无 `details-menu`；评论编辑入口是卡内 `[data-testid="comment-header-hamburger"]` → `Edit`；提交用焦点后 `Control+Enter`（"Update comment" 按钮常在视口外，坐标点击打不中）。页面相对时间会重绘，导致 strict observation 失效，须重新 sync 再动作。

## 6. 回读与留证格式

关闭/编辑后，执行方必须交**第三方回读**，格式固定为（负责人 11-16 补：加作者、长度、关闭人、回读时刻与标题校验）：

```
#N <标题> state=<closed|open> · comments=<条数> · closed_by=<login|-> · closed_at=<ISO> · updated_at=<ISO> · read_at=<ISO+08:00>
  - id=<评论 id> author=<login> len=<字符数> 末40字：「…」      ← 每条评论一行，两条就写两行
```

为什么这几项是必需的：
- `author` + `len`：11-16 事故中两条评论一长一短、作者不同，只有这两项能一眼分开。
- `closed_by`：关闭归属必须能落到人；本次 #5 的教训就是「谁关的」被写反。
- `read_at`（带时区）：与台账行对齐，否则同步时间对不上。
- `<标题>`：防止编号错配（同号不同仓库、issue 被改名）。

纪律：
- 回读用**与写入不同的通道**（浏览器写 → 最好 REST 读；反之亦然）；只有一个通道时，须回读刷新后的页面原文，不得复述自己的请求体。
- 回读原文落台账一行；**自我报告不作为结案依据**（11-16 事故：两条评论 13 秒内两次写入，只有回读能发现谁先落）。

## 8. 群内回执模板（三句，不长）

1. **领单**：`我领 #N 的<动作>｜通道=<浏览器|REST>｜估时 <n> 分`（无人反对才动）
2. **完成**：#N `<动作>` 已落 + 第 6 节六项回读 + 评论末 40 字
3. **失败/停**：`#N 停在第 <k> 步｜原始响应：<原文>｜已回滚=<是/否>`（一步失败即停，不继续下一步）

## 9. 超时与升级

- 派单必须带**估时 + 缓冲**；到兜底时点未回执 → 管家群里 @ 一次并记台账；再过一个缓冲 → 升级总负责人。
- 出现下列任一情况立即停手交总负责人裁定：两个通道同时有人动、凭据失效、护栏报警、回读与自我报告不一致。
- 对外不可逆动作（close / tag / publish）**publish 前必须单独找主人点头一次**（npm 不可撤回）。

## 10. 凭据纪律

- 凭据只在使用时由工具读取，**不落盘、不进群、不写报告、不转贴**；`gho_…` 是个人身份，等同密码。
- 需要长期凭据时走 `request_secret` 的密钥通道，不贴在对话里。
