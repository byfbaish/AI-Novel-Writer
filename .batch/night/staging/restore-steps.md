# 恢复插件开关：执行脚本（P13 通过后使用）

原则：能不开主实例就不开。方案 A 优先，A 不可行才走方案 B（会短暂失联）。

## 方案 A · 独立实例加载（首选，主实例不受影响）

目的：把修好的插件装进一个**独立 profile 的 DSH 实例**里启动一次，看加载期是否 fatal。
崩了只死这个进程，当前群、当前会话、当前 7 条 watch 全部不受影响。

步骤（developer 执行，全程只读主实例）：

1. 建独立 profile 目录：`$env:TEMP\dsh-selftest-<时间戳>\profile`。
2. 在该 profile 里安装插件（不碰 `~/.dsh/profiles/desktop`）：
   `dsh plugin --profile <该目录> add C:\develop\workspace\dsh-handoff-relay`
3. 用独立端口启动一次该实例（端口取一个空闲值，例如 61001），等待 20 秒。
4. 判据四条：
   - 进程存活，退出码不是 1；
   - 日志里没有 `fatal load failure`；
   - 日志里有启动行（watch 数量行）或「无 settings 服务，跳过设置卡」的 warn；
   - **设置页必须出现 Handoff Relay 那张卡**（看不到即 FAIL：不崩只是及格线，卡片静默失效同样不算过）。
5. 记录证据（命令原文 + 日志尾部 30 行），然后关闭该实例、删除临时 profile。
6. 失败即停：把日志贴回群，不重试第二次。

只有方案 A 通过，才允许主人打开 desktop 的插件开关。

## 方案 B · 主实例重启（A 不可行时的回退，群会短暂消失）

> 分步交互脚本见 `restart-interaction-script.md`（主人每答一句走一步，重启后先读 `restart-progress.md` 恢复现场）。

由主人执行，每步做完说一句，我方按顺序推进：

1. 主人在群里说「我关了」，然后关闭 DSH。
2. 主人双击 `.batch\night\staging\arm-probe.cmd`（把探针放进 watch 目录）。
3. 主人启动 DSH，回群说「起来了」。
4. 我方核对：插件加载无 fatal、7 条 watch 启动、探针被投递（恰好 1 条、带绝对路径）、源文件已移走。
5. 若第 4 步任一不成立：立刻让主人关掉插件开关，回复「已关闭」，不再试探。

## 红线（两方案共同）

- 一次只验证一件事：先加载，再投递，不改配置。
- watch 目录只放一个探针，验完清理。
- 任何一步失败，停止并向主人报告，不自行重试。
