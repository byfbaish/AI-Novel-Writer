# WB-20 WebDAV 备份服务空 catch 成因取证（只读）

需要说明的口径差：这三处是**渲染层面的面板**，且都带 `error` 形参（不是空 catch）。本卡要判的「WebDAV **备份服务**」实现不在这三个文件里，而在 `electron/services/webdav-backup-service.ts`（该文件 `catch` 命中 25 行，`git grep -n catch` 编号到 `:676`）。本报告只判这一处服务，不扩面。

## 1. 目标空 catch 的精确锚点

**`electron/services/webdav-backup-service.ts:442-444`**

```ts
440:    } finally {
441:      if (handle) await handle.close().catch(() => {})
442:      try { fs.unlinkSync(temporary) } catch (error) {
443:        if ((error as NodeJS.ErrnoException).code !== 'ENOENT') { /* Preserve the operation error. */ }
444:      }
445:    }
```

这是本服务里**唯一**「`catch` 有形参但函数体为空、只留一句注释」的形态（DB-12 普查 S1 的定义就是这一类：`catch (e) { /* 注释 */ }`）。同文件其余 24 处 `catch` 全部有实质动作（`fail(...)` / `throw` / `uncertain` 标记），不属空 catch。

相邻的第二类（**不同形状，另行登记**）：`.catch(() => {})` 吞掉 `response.body?.cancel()` 的 rejection，共 8 处 —— `:271`、`:355`、`:506`（`ensureCollection` 内 `await response.body?.cancel().catch(() => {})`）、`:524`、`:549`、`:562`、`:594`、`:607`。它们连形参都没有，是「真·完全静默」，但不是本卡主判对象。

## 2. 被吞掉的异常类型与触发条件（上下游取证，不猜）

**异常类型**：`fs.unlinkSync(temporary)` 抛出的 `NodeJS.ErrnoException`，且被 `:443` 的判据**排除 `ENOENT` 之后**的全部：Windows 上典型是 `EBUSY`（文件被其它进程占用）、`EPERM` / `EACCES`（权限或杀软锁）、`ENOTDIR` 等。也就是说：**只有「文件本来就不存在」被显式放过，其它删除失败一律静默丢弃**。

**触发条件（顺调用链取证）**：

1. 这个 `try/catch` 在 `putBytes` 的 `finally` 里（`:440-445`），所以它**只在该方法退出时**执行，且此时 `temporary` 是 `:511` 之后由本方法创建的临时归档文件。
2. `finally` 进入有两条路：
   - **成功路**：`:437` 已经 `fs.unlinkSync(temporary)` 删过一遍，`finally` 再删 → 得 `ENOENT` → 被 `:443` 排除，**不触发静默**；
   - **失败路**：`:428-430`（校验不符 → `WEBDAV_REMOTE_INVALID`）、`:432-436`（`linkSync` 失败 → `WEBDAV_TARGET_EXISTS` / `WEBDAV_PUBLISH_FAILED`）、`:423-427`（流读失败 → `WEBDAV_NETWORK` / `WEBDAV_CANCELLED`）中任一条 `fail(...)` 抛出后，`finally` 尝试删临时文件；若此刻文件仍被占用（Windows 上 `EBUSY` 很常见，例如同一路径的句柄没释放干净），删除失败 → **进入 `:443` 的空分支 → 异常凭空消失**。
3. 旁证：`:441` 的 `handle.close().catch(() => {})` 在同一 `finally` 里就是这种"清理失败一律吞"的写法，说明 `:442` 的静默不是笔误，而是**清理段整体「不因清理失败覆盖业务错误」的设计取向**。

## 3. 后果判定：是否导致备份静默失败？

**对「备份成败」：否。** 证据：备份的成功/失败在 `:428-439` 已经定型 —— 校验不符走 `fail('WEBDAV_REMOTE_INVALID')`（`:428-430`）、发布失败走 `fail('WEBDAV_PUBLISH_FAILED')`（`:432-436`）、成功则 `return { generationId, targetArchivePath, archiveSha256, archiveByteSize }`（`:438-439`）；`:442` 的 catch **位于 `finally`、在 `return`/`throw` 之后**，改不动返回值，也吞不掉 `fail(...)` 抛出的 `WebDavBackupError`（`fail()` 在 `finally` 之外抛出，先于 finally 生效）。所以不会把「失败」伪装成「成功」。

**对「清理残留」：是，完全静默。** 后果是：一次失败的归档发布可能在本地留下 `temporary` 文件，而**日志、返回值、界面状态里都没有任何痕迹**。这不是"备份静默失败"，是"磁盘静默泄漏" —— 两者的严重度不同，不能混为一谈（DB-12 的 S1 关注的是「无任何记录/上报」，这一处符合 S1 的形式定义，但后果档位要单独评）。

**不确定**：`temporary` 的确切落点（是否在项目 `.runtime/` 下、OS temp 下，还是用户可感知的目录）本次未逐行追 `:511` 之前的构造；若它落在系统 temp，泄漏的实际影响更低。

## 4. 分档修法（两档，各给要改的 `文件:行`）

### 档 A：确属刻意忽略 → 只补注释（最小改动）

- 改点：**`electron/services/webdav-backup-service.ts:443`**
- 现状：`if (... !== 'ENOENT') { /* Preserve the operation error. */ }` —— 注释只说了「保留业务错误」（即"不覆盖"），**没说清另外三件事**：① 为什么清理失败可以不管；② 残留文件由谁收（下次备份？启动清理？手工？）；③ 只放过 `ENOENT` 而其它 code 也一并静默，是有意还是图省事。
- 修法：把 `:443` 的空块注释扩成「为什么不覆盖 + 残留由谁收 + 其它 code 也允许静默的原因」，**代码零改动**，`try/catch` 结构不变。
- 适用判断：如果作者认为「归档临时文件的清理失败不影响任何用户可见结果」，选这一档。

### 档 B：吞错 → 加最小日志（留痕，不改控制流）

- 改点：**`electron/services/webdav-backup-service.ts:442-444`**（在 `:443` 的 `if` 分支内加一行 warn）
- 建议写法与同仓先例一致（先例在**同一个仓库、同一类"删临时文件失败"场景**里已经这么做）：
  - `electron/services/skin-service.ts:163`：`console.warn('[AI Novel Skin] Unable to remove temporary skin file.', error)`
  - `electron/services/skin-service.ts:446`：`console.warn('[AI Novel Skin] Unable to clean up a previous skin asset.', error)`
  - 本处对应写法：`console.warn('[AI Novel Backup] Unable to remove temporary archive.', error)` —— 只加一行，`fail()` 不被调用、返回值不变，所以**不会把"清理失败"升级成"备份失败"**。
- 若同时要治理 `.catch(() => {})` 那 8 处（`:271`、`:355`、`:506`、`:524`、`:549`、`:562`、`:594`、`:607`）：**不建议**逐处加日志（body `cancel()` 失败通常是连接已断，噪声大且无信息量），建议按档 A 在每处补一句「为何可忽略」注释；这一族是否要动由作者裁定，本卡不代裁。
