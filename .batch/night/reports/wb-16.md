## 3. 为什么「A + B」就够、而「D」才是被卡书提醒的那种改动

- `resolveCallDeadline` 的第二个参数**已经存在且已经是默认参数**（`src/shared/generation-call-timeout.ts:31`），所以纯函数侧**零改动**即可接受一个外部 cap。
- 但值必须有来源：deps 里没有配置通道（`:54-61`），所以**至少**要加一个 deps 字段 —— 这已经不是「一行」，是「两处（接口 + 调用点）+ 一处值来源」。
- 若要求 cap 与 run 一起落库（跨重启、跨复现一致），则 `RootBudget` 的 4 字段（`generation-contract.ts:52-55`）必须扩，且 `generation-run-repository.ts:331` 的白名单校验要同步登记 —— 那时「扩 `RootBudget` 是一行改动」这个说法就是错的。

## 4. 明确回答：`capMs` 能否在不扩 `RootBudget` 契约的前提下接进 `resolveCallDeadline`？

**能** —— 前提是 cap 的来源**不走 `RootBudget`**（走 deps 注入 / 设置读取），因为 `resolveCallDeadline(budgetRemainingMs, capMs)` 的第二参数已存在（`src/shared/generation-call-timeout.ts:31`），`RootBudget` 的 4 个字段（`generation-contract.ts:52-55`）一个都不用动。

**但不能说成「一行改动」**，理由三条（都可指行号）：

1. deps 没有配置通道（`electron/services/generation-run-service.ts:54-61`）⇒ 至少要加字段；
2. 值来源在本次读取范围内不存在（§2-C）⇒ 要新增读取点或写死；
3. 若 cap 需要随 run 冻结/可复现 ⇒ 必须扩 `RootBudget` 并同步 `electron/repositories/generation-run-repository.ts:331` 的字段白名单，那时这条路径**不是「不扩契约」**。

还有一条语义副作用必须写进验收：`generation-call-timeout.ts:37` 用 `budgetRemainingMs > capMs` 决定失败码归属 —— **cap 调小后，更多情形会落到 `GENERATION_CALL_TIMEOUT`（界面说「调用超时」），而不是 `ROOT_BUDGET_EXHAUSTED`**。换句话说调 cap 会同时改变「是谁的错」的呈现口径，不只是改变时长。
