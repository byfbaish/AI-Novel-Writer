## 1. 场景

**结论：手填 `targetSessionId` 不可行——它是一个运行时标识，重启即变；现在的配置把一次性运行时值写进了持久文档，后果是「配置看起来有理、实际静默不投递」。**

展开：

1. **标识的生命周期就是一次运行。** 配置里存的是 session id，而插件每次投递都要用它去 `agents.get()` 再兜底 `roots()`（F8）。会话 id 在重启后不保证复用，所以「昨天填的 id」今天多半解析不到。
2. **失败是静默的，不在配置面上。** 解析不到时只写一条 warn 到日志（F9），文件不投递、不排队、无重试；配置界面里那行字仍然正常显示，用户看到的是「配置好了」。真正发现问题的时刻是「文件早就该处理完却没动静」。
3. **每次重启要重填 N 条。** 一个 watch 一条 id，多目录就要重复填多次；同一目标被多个 watch 共用时，同一串 id 要手抄多遍，错一个字只坏一条 watch——最难排查的那种坏法。
4. **id 不可记认。** 文档示例都是 `session-xxxx…` 这种占位串（`README.md:46`、`README.zh-CN.md:40`），用户只能从别处复制；界面上没有任何「这串 id 现在指向哪个会话」的确认位。
5. **没有校验位。** 保存时不做存在性校验，写进去的可能是早已结束的会话——这与 F6 提供的 `validate` 能力（可拒绝写入）是现成的空档。

**因此本需求的目标不是「让输入框更好看」，而是把「运行时才存在的会话」变成「选择时就能看见的会话」，并且让失效状态在配置面上可见。**

### 2.4 完成规则（每条 watch 一列，四态）

**结论：每条 watch 一行三列 = 目录 / 目标会话 / 完成规则；完成规则四态——省略（默认）、文本、正则、关闭。**

| 交互点 | 行为 | 备注 |
|---|---|---|
| 控件 | 三个互斥选项「文本」「正则」「不使用」；未动过时显示「默认」态 | 写入映射见下表，不写 `mode` / `enabled` 键 |
| 文本形态 | 单行输入，精确子串、区分大小写 | `done: { text: "…" }` |
| 正则形态 | 单行输入，固定按 `m` 标志编译 | `done: { regex: "…" }`；支持 `^…$` 按行锚定 |
| 正则框下的三句约束（常驻，不折叠） | ① 只扫文件尾部 4KB，不全文扫描（日志类大文件不会每轮重读全文）；② 固定带 `m` 标志；③ 禁嵌套量词，超限即拒 | 用户配置的正则是不可信输入：回溯失控会卡住事件循环，插件跟着卡住 |
| 校验时机 | 输入时只做本地编译与长度检查，不写配置；保存时再走 `validate` | 与 §2.3 的保存流程一致 |
| 失败表现 | 编译失败 / 超限 → **只标红该行** + 行内一句原因；该行不写入；其他 watch 照常保存、照常工作 | 「不影响其他 watch」是硬要求 |
| 语义提示（列头 tooltip 必写） | 完成规则只是**加速判据**：未命中仍按 `stableMs` 稳定投递，不等于「必须命中才投」 | 不写这句，用户会以为没有标记就不投递 |
| 关闭选项 | 「不使用」= 写入 `done: null`，只按 `stableMs` 投递 | 11-13 已定；不新增 `enabled` 开关 |

**四态与写入值**（界面只负责把用户所选映射成这四个值之一，不做二次解释）：

| 界面态 | 写入 | 行为 |
|---|---|---|
| 默认（未配置） | 省略 `done` | 等价于 `text: "<!-- DONE -->"`，命中即投 |
| 文本 | `done: { text: "…" }` | 精确子串、区分大小写 |
| 正则 | `done: { regex: "…" }` | 尾部 4KB 内、`m` 标志 |
| 不使用 | `done: null` | 关闭完成规则，只按 `stableMs` 投 |




## 3. 边界

**结论：四条边界都能给出可执行行为，但其中三条属产品口径，标注「待主人裁定」。**

### 3.1 多个 watch 共用同一目标

结论：**应当允许**，且不改变现有隔离语义。

- 现状允许：`watches[]` 里两项写同一个 `targetSessionId` 没有任何拦截，且每条 watch 有独立的 `pending`/`delivered`（F10），不会互相吞事件。
- 未决部分：两个目录同时就绪时，目标是收到**两条消息**（现状）还是**合并成一条**？合并会带来「一条里怎么标注多个文件」的格式问题，也会改变现有消息契约（单文件 + `{reason}`）。→ **待主人裁定**（默认按现状保留两条，合并属新功能）。

### 3.2 目标会话已不存在（失效 id）

结论：**运行侧不改（继续 warn + 不投递），配置侧必须让失效可见。**

- 运行侧：`index.js:82-88` 的 warn 已写清了「get 返 undefined、roots 里也没有」，不需要动。
- 配置侧两种口径：
  - A：保存时**拒绝**写入（用 `validate` 抛错，F6）——严格，但用户可能想把配置先存好、稍后再开会话；
  - B：保存时**允许**，但行内标「失效」并在顶部给一条汇总提示——宽松，但要求配置面能定期刷新存在性。
  - → **待主人裁定**（A 更稳，B 更顺手；两者对 `applies` 的要求不同）。

### 3.3 会话改名后是否跟随

结论：**存 id、显示标题 ⇒ 自动跟随改名，这是本需求的默认；「按标题锁定」不是默认行为。**

- 机制：配置里存 id（F8 用它解析），界面上每次渲染时用当前列表把 id 换成 `displayTitle`（F2）。会话改名后，标题自动变，指向不变。
- 反方向的风险：如果用户是靠「名字」认目标的（例如两个目录分别对应「写作」与「审稿」两个会话），改名后他会看到一行陌生标题——需要一句「标题仅供辨认，指向由 id 决定」的说明。
- 若产品想要「名字锁死」语义（标题变了就提示确认），要额外存标题快照。→ **待主人裁定**（是否提供该模式）。

### 3.4 搜索无结果时是否允许手填

结论：**这是本需求里最容易自相矛盾的一条——允许手填会把「手填不可行」的初衷带回来，但不允许又会在会话尚未创建的场景卡死。**

- 支持的场景：用户知道某个会话会在稍后创建/稍后打开，现在就想先把 watch 配好。
- 反对的场景：手填错一个字符，就是 §1 的静默失败；且手填绕过了「只有列表里存在的会话才能选」的保护。
- 折中选项：允许手填，但保存前必须通过存在性校验（同 §3.2 的 A 口径），或手填值在行内强制标「未校验」。
- → **待主人裁定**（枚举：完全不允许 / 允许但校验 / 允许且不校验）。

### 3.5 可选择的范围

结论：**以 `roots()` 的顶层会话为准，不与子代理会话混排。** 依据 F1：`roots()` 的语义是「无 owner 的顶层 agent」，而插件投递对象是会话；`list()` 含子代理，混进来会让用户选到不该收消息的对象。
- 是否需要「子代理会话也可选」→ 属实现层确认（若产品确实要按 agent 投递，需要单独一轮设计）。

### 3.6 `cwd` 的展示与隐私

结论：**展示 `cwd` 有必要（同名会话的唯一区分位），但它是本地绝对路径，属用户隐私面。**
- 选项：显示完整路径 / 只显示末两级目录 / 悬停显示完整路径。→ 与 §3.2 的严格程度一并裁（不单列计数）。

## 4. 取舍

**结论：client 端要引入构建链（React + 打包）几乎不可避免；「零依赖」应只对 core 成立，client 需豁免；core 与 client 是单包双入口还是拆两包，必须先定，因为它决定依赖计数与发布口径。**

### 4.1 client 要不要引入构建链

结论：**要。** 理由三条：

1. 现有产物是纯 ESM、无任何构建（`package.json` 无 `dependencies`/`devDependencies`，`exports` 直指 `./index.js`）。而弹层需要：键盘焦点管理、列表虚拟化（会话多时）、受控输入 + 防抖取消请求——手写无构建版不是不能做，是维护成本会吃掉「零依赖」带来的信誉。
2. Host 的客户端界面本身就是组件化运行时（客户端侧有 settings 镜像与命名空间 scope 绑定，F4），卡片与宿主复用同一渲染环境，用与宿主一致的组件写法最省事。
3. 一旦有 JSX/TS，就需要 `devDependencies` 与产物目录（`dist/`），这会改变 `npm pack` 的内容与 README 的「dependency-free」表述（`README.md:5`）。

代价：发布物里出现构建产物 → 需要在 README 里写清「源码在 `src/`，发布物含 `dist/`」。

### 4.2 零依赖约束是否对 client 豁免

结论：**建议豁免，但这是口径变更，需要点头。**
- core（`index.js`，Host 侧文件监控与投递）保持零依赖：它现在的价值就是「装进 profile 不用装任何东西」。
- client 允许构建期 `devDependencies` + 渲染库作为 `peerDependency`（由宿主提供实例，避免双 React）。
- 风险：README 现状把「dependency-free」当第一句话卖点（`README.md:5`），豁免后必须改成「core 零依赖」。→ **待主人裁定**。

### 4.3 core 与 client 是否分开计数

结论：**先定发布形态，再定计数；两种形态各有代价。**

| 形态 | 做法 | 好处 | 代价 |
|---|---|---|---|
| 单包双入口 | `exports` 增加 `./client`（或宿主约定的卡片入口），`package.json` 同时含 core 与 client 依赖 | 发布一条线、版本天然一致、配对简单（同 namespace） | core 使用者会看到 client 的 peer 依赖；「零依赖」只能写成「core 零依赖」 |
| 拆两包 | `dsh-handoff-relay` + `dsh-handoff-relay-client` | 依赖边界干净；core 仍可宣称零依赖 | 两条发布线、版本要手动对齐、配对可能出现「版本错配」 |
| → **待主人裁定**（若选单包，需同时确认 §4.2 的口径改法） | | | |

### 4.4 命名空间与卡片配对

结论：**namespace 用 kebab-case（`dsh-settings/lib/types/index.d.ts:20` 的约束），建议 `file-watch`；卡片必须注册同名 namespace 才会被自动配对（F4）。**
- 与包名 `dsh-handoff-relay` 的对应关系（是否必须严格等于包短名）→ 实现层待确认。
- `applies` 的取值会直接显示在配置面上（F6），所以 §4.5 的选择会影响用户看到「保存后需重启」的提示。

### 4.5 保存后的生效时机

结论：**`live` 体验最好但要求插件重新订阅 watch；`restart` 最省事但用户要重启宿主。**
- `live` 的实现代价：`apply` 现在只在启动时读一次配置并 `startWatch` 一次（`index.js:154-187`），要 live 就得在配置提交后按 watch 增删/重订，且要处理「正在投递中」的竞态。
- `restart` 的代价：用户改完要重启，而这正是本需求想消灭的「手填 → 重启 → 再手填」循环的一部分。
- → **待主人裁定**（建议 live，但允许先以 restart 交付、后补 live）。

### 4.6 一个「零成本」的中间态（供参考，不计入裁定项）

只做「只读展示」不做「选择器」：配置里仍是手填，但配置卡片把 id 实时翻成 `displayTitle` + 有效/失效徽标。这能在不动写入路径的前提下先解决「看不见」的问题，适合作为第一阶段。是否分两期做 = 与 §4.5 一并裁。

**11-13 补充**：这条中间态不成立——只要界面上出现卡片，就已经是 client 侧（React 组件），「只读展示」并不比「选择器」更便宜。零成本的一期只有「不做界面、只记日志」。

### 4.7 明确不做（二期，不留待议）

| 不做 | 一句理由 | 替代做法 |
|---|---|---|
| **多播**：一个 watch 投多个目标 | 唤醒 N 个会话 = 让 N 个 agent 同时独立开跑（我们刚踩过并发改同一仓库互相覆盖的坑）；插件不认识群、也不知道谁该串谁，做进去等于把编排责任塞进投递层 | 同一目录配多条 watch：`dir` 相同、`targetSessionId` 不同、各带 `done`；哪条失效可单独看见 |
| 「一个被唤醒带动全群」 | 那是被唤醒的 bot 在群里 @ 别人的事，属 agent 层 | 由被唤醒方自行 @ 下一个 |
| `enabled` / `mode` 开关 | 四态已能表达全部意图（省略 / text / regex / null） | — |

|---|---|---|---|
