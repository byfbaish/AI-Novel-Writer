# 重复投递缺陷 · 处置决定（11-13 07:00）

## 现象与已核事实（developer 只读）
- `index.js:204` 每个 watch 一个内存 `Set`，`dispose()` 清空，从不落盘 ⇒ 热重载/重启必重放。
- `index.js:246` 与 `:293` 共用同一 key `${relName}|${sig}` ⇒ 一次载入内 stable 与 DONE 不会双记。
- `index.js:312` `filename == null` 时走 `listFiles()` 把目录全量投一遍 ⇒ 「首次即重复」的来源。
- 今晚载入三次（04:53 / 05:46 热重载、06:20:26 重启），与三次通知次数吻合。

## 决定：落盘去重表，不采用「载入即标记已见」

选 A（落盘）而非 B（载入时把存量标记为已见），理由：
- B 会让**宿主停机期间落盘的产物永远不补发**——静默丢失比重复唤醒更贵，而重复唤醒只是噪音，agent 侧能判断。
- A 的代价是一个状态文件 + 裁剪逻辑，边界仍在「记住投过什么」，不引入队列、不引入状态机。

## 形态（明早派卡，今晚不动代码）
- 状态文件放 profile 目录（watch 目录之外，避免自我触发）：`~/.dsh/profiles/desktop/dsh-handoff-relay-state.json`
- key：`dir|relName|mtime|size`（四元组，避免同名文件被改写后误判已投）
- 上限：保留最近 500 条，超出按时间淘汰
- 损坏/不可解析：整表丢弃 + `warn`，不影响投递
- 写入失败：只 `warn`，本次投递照常
- 只在投递成功后记录；解析不到目标不记（保持现状）

## 明早执行顺序（防验收自污染）
1. 改 7 条 `targetSessionId`
2. 等这一次热重载的重放跑完
3. 清空 watch 目录里的存量文件
4. 只放 **一个** 探针
5. 判据：目标会话收到至少一条、文案含绝对路径；条数单独记录，不作失败判定

## 追加裁定（07:00，回答产品经理规格三问）

产品经理 指出的漏洞成立：同 dir 被两条 watch 使用时，target 不进 key 会让第二条永不投。但**不能加 `watchId` 字段**（配置面冗余，且数组下标增删会漂移）。

改法：状态文件从「key 集合」改成「**文件指纹 → 已投目标集合**」的映射。

- 指纹 key：`dir|relName|mtime|size`（不含目标）
- value：已投达的目标标识数组；目标标识 = `targetSessionId` 原样，或 `title:<targetTitle>`
- 判重：同一指纹 + 同一目标已存在 ⇒ 跳过；同一指纹 + 新目标 ⇒ 照投
- 效果：同 dir 多 watch 各自独立；重启后若 id 未变不重放；id 变了属于「目标变了」，重投一次可接受

其余三问：
1. 位置：profile 根目录 `dsh-handoff-relay-state.json`（不进 `state/` 子目录，少一层）
2. 裁剪：不单独定时，每次成功投递后随写入顺带裁剪，上限 500 个指纹，超出淘汰最旧的
3. 原子写：采纳（临时文件 + rename），崩溃不留半截 JSON
