# AI writer · Roadmap 文档骨架与写作规范

版本：v1.0
日期：2026-11-20
维护人：项目总负责人 · AI writer项目组（2026-11-20 落盘并接任维护；原作者 WorkBuddy）
变更要点：首版——定三级骨架五件套、级数可加深可提前停的判据、逐层判定口径与人类拍板清单。

适用范围：AI writer 平台（工程化写小说）的规划留档与交接。**本文只规定怎么留档、怎么判「达标没有」，不规定做什么功能。**某模块是否已存在、某条命令是否已实装，一律以仓库与台账为据，本文不臆断；拿不准就写 `待填`，并在变更表那一行记一句「哪几处待填」，不靠记忆补。

## 1 roadmap 文档骨架（L0 域 → L1 模块 → L2 卡/动作）

三级职责一句话说清：

- **L0 域**：一条完整能力线，能独立对外描述（例：导出与回灌）。
- **L1 模块**：域内可独立交付、可独立验收的一块（例：导出）。
- **L2 卡/动作**：一次能做完、做完能判的一件事（例：字段白名单校验）。

### 1.1 五件套（字段名固定，不许改名、不许加第六个字段）

| 字段 | 写什么 | 不合格的样子 |
|---|---|---|
| `目标` | 一句话，≤40 字，**动词开头**，说清「做完之后什么变了」 | 名词短语堆叠；一句话里塞两个以上动作；写手段不写结果 |
| `完成判据` | 可机检（命令／脚本／字段）或可对照文件（**具体路径 + 哪一段／哪一行**） | 用形容词代替判据；只写「跑通了」；写了命令但没写期望输出 |
| `前置依赖` | 依赖哪些条目的 ID，逗号分隔；**无则写 `无`** | 写人名、写「等 X 有空」、留空、写「看情况」 |
| `状态` | `未开始` / `进行中` / `达标` / `阻塞`，四选一 | 自造第五个词；一行里写两个状态；用程度词代替状态 |
| `ID` | 见 §1.4 的格式，全局唯一、**永不复用** | 复用已归档条目的 ID；同层级重号；层级少一段 |

两条补充：

1. **状态行可以带尾巴**：`- 状态：达标｜证据：<路径#行号 或 命令原文>`。`｜证据：…` 属于 `状态` 字段的一部分，不算第六个字段——但状态一改，尾巴必须同时改，不许只改字。
2. **依赖只写条目，不写关系**：父子挂接由标题层级表达，不进 `前置依赖`；`前置依赖` 只写「必须先完成的条目」。

### 1.2 三级模板（照抄即用，空的地方就是要填的地方）

**L0 模板**

```markdown
### L0-<域简写> <域名>

- 目标：<动词开头，≤40 字>
- 完成判据：<命令 + 期望输出 / 文件路径 + 段落>
- 前置依赖：<ID 列表 或 无>
- 状态：未开始
- ID：L0-<域简写>
```

**L1 模板**

```markdown
#### L1-<域>-<两位序号> <模块名>

- 目标：<动词开头，≤40 字>
- 完成判据：<命令 + 期望输出 / 文件路径 + 段落>
- 前置依赖：<ID 列表 或 无>
- 状态：未开始
- ID：L1-<域>-<两位序号>
```

**L2 模板**

```markdown
##### L2-<域>-<两位序号>-<两位序号> <卡名>

- 目标：<动词开头，≤40 字>
- 完成判据：<命令 + 期望输出 / 文件路径 + 段落>
- 前置依赖：<L1 / L2 的 ID，或 无>
- 状态：未开始
- ID：L2-<域>-<两位序号>-<两位序号>
```

**挂接总表模板**（放在文首，给人一眼看全局；明细仍按标题层级展开）

```markdown
| ID | 层级 | 名称 | 状态 | 前置依赖 |
|---|---|---|---|---|
| L0-<域> | L0 | <域名> | 未开始 | 无 |
| L1-<域>-01 | L1 | <模块名> | 未开始 | 无 |
| L2-<域>-01-01 | L2 | <卡名> | 未开始 | L1-<域>-01 |
```

### 1.3 三级之间的挂接规则

1. **层级只由标题级别表达**：L0 用 `###`，L1 用 `####`，L2 用 `#####`；不许跳级——L2 直接出现在 L0 下面即算错，读者无法判断它属于哪个模块。
2. **不许悬空**：任何 L2 上方必须能找到所属 L1；任何 L1 上方必须能找到所属 L0。悬空条目一律算未填完，不参与状态统计。
3. **父级 `达标` 的必要条件**：其下所有子级状态均为 `达标`。这条是必要条件，**不是充分条件**。
4. **父级达标不由子级自动推导**，由人裁定：
   - L1 的 `达标` 由该域 owner 在验收记录上签字后写入（签字至少要留下「哪份记录、第几行」）。
   - L0 的 `达标` 由项目总负责人裁定。
   - 裁定人与依据写进变更表那一行，不写在别处。
5. **状态不是脚本回填的字段**：任何状态的改动都要在同一行补 `｜证据：…`；没有证据的状态改动，下一手有权把它打回原状态。

### 1.4 ID 规则

| 层级 | 格式 | 例子 |
|---|---|---|
| L0 | `L0-<域简写>` | `L0-EXP` |
| L1 | `L1-<域>-<两位序号>` | `L1-EXP-01` |
| L2 | `L2-<域>-<两位序号>-<两位序号>` | `L2-EXP-01-02` |
| 加深层 | 序号继续往后接（见 §1.5） | `L3-EXP-01-02-01` |

- 域简写用 2–6 个大写字母或数字，全文档唯一。
- **永不复用**：条目要下线时整条移出正文、进文末归档区；它的 ID 不再分配给任何新条目，理由是新条目顶着旧号，历史记录里同一号会出现两种含义。
- 序号不要求连续，但同一父级下不得重号；补号只能往后接，不能插空改已有号。

## 1.5 级数不固定：可加深、可提前停（口径 2026-11-20 修正）

### 1.5.1 默认三级，但它既不是上限也不是下限

三级只是起步形状。同一份 roadmap 里，这一支可以拆到 L4，那一支可以停在 L2——**深浅由「能不能派活、能不能判」决定，不由整齐好看决定**。一份文档里出现 L2、L3、L4 混排是正常形态，不是格式错误。

### 1.5.2 可以加深：满足任一条件就往下拆

当某条 L2 出现下面任一情况，允许拆 L3、L4……：

1. 说不出这张卡的**输入／动作／产出物**三样，或说出来是三件不相干的事；
2. 判据要拆成两段以上才能核（一条命令判不完，得先造数据再比对）；
3. 派下去必被追问「到底改哪里」——说明动作还没落到文件或命令粒度。

**拆到哪停**：拆到同时满足三句——**一次能做**（单个执行人在一个时间盒内做得完）、**做完能判**（判据可核）、**不需要再问人**（条目里没有留给别人的决策）。三句缺一，继续拆。

规则一致性：

- L3 及以下**同样带五件套**，字段名一字不改；
- ID **顺延**：`L3-<域>-<序号>-<序号>-<序号>`，每深一层多一段序号；
- 加深**不放宽**状态枚举，**不新增**字段。

### 1.5.3 可以提前停：但必须写明为什么够

允许某支停在 L2 不再往下。条件是：在该条目 `完成判据` 下面紧跟一行

```
不可再拆，原因：<具体原因>
```

这行 `原因` 必须回答「为什么这一层已经能派活、也能判」——即写清输入、产出物、判定人三者都不缺。**禁止**写「太细了没必要」「已经够清楚了」这类等于没说的理由。

示例（示例，假数据）：

```
不可再拆，原因：产出物固定为一份 JSON 报告，判定人按 chapters 数组长度与退出码比对即可，动作只有一条命令，无需再拆。
```

判读：这一行说得清「产出物是什么、谁判、拿什么判、动作几步」，所以允许停。反过来，只写「没必要再拆」的条目，一律视为未写完，不得进 Goal。

### 1.5.4 「这一层够了」的四条判据（可逐条打勾）

1. **能写成一张卡**：输入（读什么、给什么）、动作（改哪个文件的哪一块、跑哪条命令）、产出物（新文件／字段／命令输出）三项都写得出来。
2. **有可核产物**：文件路径 + 段落、命令 + 期望输出、字段 + 期望值，至少占一样，且别人能自己重跑一遍复现。
3. **验收人拿到它，不追问就能判**：判「达标／不达标」不需要再问「跑几遍」「错在哪算错」「谁说了算」。
4. **做完不需要再找人拍板**：条目内没有「等谁定」的悬空项；有悬空项说明该拆出前置依赖，或该升级成人类拍板项（见 §5）。

四条全中才算够。缺一条又坚持不拆的，必须按 §1.5.3 写明为什么缺的那条不影响判定。

**正例（示例，假数据）**

```
##### L2-EXP-01-02 导出结果落盘

- 目标：把一次导出结果写成固定字段的 JSON 文件
- 完成判据：node scripts/export/run.mjs --probe tmp/export-probe.json 退出码 0，且 tmp/export-probe.json 含 chapters 数组、长度等于输入章节数
- 前置依赖：L1-EXP-01
- 状态：未开始
- ID：L2-EXP-01-02
```

四问自检：输入＝一次导出结果；动作＝跑一条命令；产出＝固定字段 JSON；判定人只看退出码与数组长度——不问人就能判。

**反例（示例，假数据）**

```
##### L2-EXP-02-01 提升导出稳定性

- 目标：提升导出稳定性
- 完成判据：多次导出不再出错
- 前置依赖：无
- 状态：进行中
- ID：L2-EXP-02-01
```

四问全不过：动作是「提升」，指不到任何文件；判据没说跑几次、什么算错；没有输入与产出物；判定人必须追问「跑几遍」「哪一步出错算错」。

### 1.5.5 Goal 只锚在 L2（必要时下沉 L3）

Goal 的颗粒度就是「一张能派下去、能验收的卡」，所以：

- Goal 只能挂在 **L2**；某支加深后，Goal 允许下沉到 **L3**；
- 再往下的 L4 及更深层，只作为 L3 的内部拆解，不直接设 Goal。

由此得出一条硬话，原句照写进任何派活单：

> **「L2 不合格则 Goal 无法设置」**

理由很实操：L2 还是口号，Goal 的 acceptance 就只能跟着写成口号，之后每一次推进都在拿口号对账，等于没有对账。

### 1.5.6 加深与提前停都不动的三样

无论一支拆到多深、或停在哪一层，下面三样不变：

1. 字段五件套（`目标`／`完成判据`／`前置依赖`／`状态`／`ID`）；
2. 状态四选一（`未开始`／`进行中`／`达标`／`阻塞`）；
3. ID 格式只往后接序号，不改已有段的含义。

这三样一改，各级条目之间就没法互相对账，前面所有「可判」都会退化成各说各话。

## 2 写作规范：怎么写到「可判」

五条硬规则，写的时候逐条过：

- **R1 目标**：动词开头，≤40 字，只写「做完之后什么变了」，不写怎么做、不写为什么值得做。
- **R2 判据**：每条必须落到三者之一——「一条命令 + 期望输出」「一个文件 + 段落／行号」「一个字段 + 期望值」。
- **R3 一条判据只判一件事**：出现「且」「或」「等」就把它拆成两条。
- **R4 依赖**：只写 ID。人、会议、口头承诺都不算依赖；没有就写 `无`，不留空。
- **R5 状态**：四选一；每次改状态，同一行补 `｜证据：<路径#行号 或 命令原文>`。

### 2.1 正例一（L1 级，示例）

```
#### L1-EXP-01 导出

- 目标：把选中的章节导成固定字段的 JSON 报告
- 完成判据：pnpm tsx scripts/export/run.mjs --out tmp/export.json 退出码 0，且 tmp/export.json 中 chapters[].id 去重后的条数与输入一致
- 前置依赖：无
- 状态：进行中
- ID：L1-EXP-01
```

好在哪：判据是一条命令加两个可读值（退出码、去重后条数），谁来跑结果都一样；`前置依赖` 写 `无` 而不是留空，读者不用猜。

### 2.2 正例二（L2 级，示例）

```
##### L2-EXP-01-01 字段白名单校验

- 目标：导出前拦下字段缺失的章节
- 完成判据：pnpm tsx scripts/export/check.mjs --fixture tmp/fixtures/missing-title.json 退出码 1，stderr 含 missing_field=title
- 前置依赖：L1-EXP-01
- 状态：未开始
- ID：L2-EXP-01-01
```

好在哪：把「拦得住」翻译成了「退出码 1 + stderr 里那个字段名」，故意用成功态也会被拒绝（退出码 0 即不达标），判据自带反向验证。

### 2.3 反例一（L2 级，示例）——为什么判不了：判据不可执行

```
##### L2-EXP-01-02 优化导出性能

- 目标：优化导出性能，让导出更快
- 完成判据：导出速度明显变快
- 前置依赖：L1-EXP-01
- 状态：进行中
- ID：L2-EXP-01-02
```

判不了的原因：「明显变快」没有基线数值、没有测量命令、没有阈值，两个人对同一份输出可以给出相反结论；目标里的「优化」是手段，不是产出物，做完也说不清什么变了。改法方向：写成「在 100 章样本上 `--probe` 的 wall time ≤ 基线 × 0.6，基线数值与测量命令都写进判据」。

### 2.4 反例二（L1 级，示例）——为什么判不了：状态含糊 + 缺判据

```
#### L1-DRAFT 正文生成

- 目标：把正文生成做得更好
- 完成判据：生成质量达标，人读不出 AI 味
- 前置依赖：无
- 状态：进行中（基本完成）
- ID：L1-DRAFT
```

判不了的原因，三条：①「质量达标」「人读不出」没有样本、没有判定人、没有比对方法，属于把形容词当判据；②状态写成「进行中（基本完成）」，括号里等于另说了一个第五状态，读的人无法判断还剩多少；③ID 少一段序号（`L1-<域>-<序号>`），下面的 L2 无法挂接，也无法定位。

## 3 版本与交接纪律

### 3.1 文件头三行固定

```
版本：<v主.次>
日期：<YYYY-MM-DD>
变更要点：<一句话，说清这次改了什么>
```

- 三行不许省、不许调序、不许合并成一行。
- 主号变化只发生在骨架或字段改动（会影响所有人对账口径的情形）；其余改版只进次号。
- `变更要点` 一句话，写改了哪块、改成什么；不写「若干优化」。

### 3.2 文末变更表

表头固定四项，每次改版必须补一行：

| 版本 | 日期 | 改了什么 | 谁改的 |
|---|---|---|---|

- 缺行的改版视为无效——下一手无法判断哪一版是真。
- `谁改的` 写执行身份（人／Agent 名），不写「团队」。
- 一句话写完改动；改动涉及多处时，逐条列 ID，不写「多处微调」。

### 3.3 交接时必须附两段

**第一段：当前状态快照**（可直接照抄的骨架）

```
当前状态快照（<YYYY-MM-DD>）
达标：<ID 列表，或 无>
进行中：<ID + 做到哪一步>
阻塞：<ID + 阻塞在谁 / 卡在什么事>
未开始：<条数>
```

**第二段：下一步**（只写一件事）

```
下一步（第一件事）
做：<ID>
命令/文件：<可直接复制的一行命令，或 一处文件路径 + 段落>
完成后判：<该条目的完成判据原文>
```

规矩：`下一步` 只能有一件事；写不到命令级或文件级，说明还没到能交接的状态，先补条目再交接。

- 状态：阻塞｜阻塞在数据组：tmp/fixture.db 目前是只读副本，缺一份可写样本，申请见 tmp/notes/block-01.md

##### L2-EXP-02-02 字段级 diff 报告（示例）

- 目标：输出逐字段差异清单供人工抽查
- 完成判据：`node scripts/export/verify.mjs --diff tmp/rt.json` 输出 JSON，`diff[].field` 覆盖 `chapters` 与 `characters` 两个集合；无差异时输出空数组
- 前置依赖：L2-EXP-02-01
- 状态：未开始
- ID：L2-EXP-02-02

**这一层层是怎么判上去的（4 行）**

1. `L2-EXP-01-01`、`L2-EXP-01-02` 两条状态为 `达标`，证据行都能打开对应日志 → `L1-EXP-01` 满足「子级全达标」这一必要条件，再由导出域 owner 在验收记录上签字，才准改成 `达标`。
2. `L2-EXP-02-01` 是 `阻塞`（缺可写样本）→ 父级 `L1-EXP-02` 不可能 `达标`，只能记 `阻塞`，阻塞点写在状态行里，不散落在群消息。
3. `L2-EXP-02-02` 状态 `未开始` → 再次确认 `L1-EXP-02` 不达标，且 `L2-EXP-02-02` 自身不改判据、不抢跑。
4. `L0-EXP` 要 `达标`，须 `L1-EXP-01` 与 `L1-EXP-02` 都 `达标`；当前后者阻塞，所以 `L0-EXP` 停在 `进行中`，由项目总负责人裁定，不由脚本回填。

## 5 哪些位置必须由人类拍板

| # | 拍板点 | 为什么机器判不了 | 不拍板会怎样 |
|---|---|---|---|
| 1 | 优先级排序：先做哪个 L1 | 判据只判「做完没有」，判不了「哪个更值」；两条都达标时谁先谁后是取舍，不是事实 | 两条并行开工，人被摊薄，两条同时停在 `进行中` |
| 2 | 是否砍功能：砍掉某条 L2 | 砍功能等于把已写好的判据作废，涉及范围与对外预期，机器没有这个授权来源 | 条目长期 `阻塞` 挂着，规划表退化成许愿池 |
| 3 | 上线／验收口径的最终认定 | 脚本能跑出绿，但「这个绿算不算能上线」含着风险承受度，不是数据能回答的 | 判定人与执行人对同一份输出各说各话，反复复跑 |
| 4 | 跨域取舍：改 A 域还是迁就 B 域 | 跨域冲突时两边判据同时成立，谁让谁是组织取舍，技术侧给不出答案 | 两边各改一半，接口对不上，最后返工在合并时爆发 |
| 5 | 对外承诺：时间、范围、能力边界 | 承诺是组织决定，不落在任何判据字段里，也没有可核产物 | 文档里没写、对外已说，交接时才发现两边口径不一致 |
| 6 | 状态从 `阻塞` 转出 | 阻塞点常在人、资源、第三方，解除条件不在仓库里，机器读不到 | 阻塞条目被人随手改成 `进行中`，阻塞原因丢失，下一个人重踩 |
| 7 | 父级 `达标` 的签字（L1／L0） | 子级全达标只是必要条件；「这个模块算不算完了」要人认账，缺口也要人认领 | 模块被标达标，实际缺口无人负责，越往上越虚 |
| 8 | 版本主号变化（改骨架／改字段） | 改字段等于改所有人的对账口径，影响面要靠人评估，机器算不出谁会被打乱 | 各人手上一份不同骨架，ID 对不上账，历史记录作废 |
