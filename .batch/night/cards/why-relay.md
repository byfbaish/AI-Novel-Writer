# 卡：写一篇「为什么叫 relay」随想（草稿，仓外）

## 背景

今晚出现一个真实场景，值得留在仓库里：同一个 agent 有两个会话窗口（群聊一个、私聊一个），共读同一份外部记忆文件。其中一侧看到另一侧写进记忆的内容，以为「自己被夺舍了」，反过来问「发生了什么」。另一侧则收到「文件 X 已就绪，请继续」的通知，但按文件名在本地找不到文件，于是判断「可能是探针在反复触发，要不要帮你查来源」。

这不是模型幻觉，两次都归因清楚：

- 「夺舍」：两个会话共读一份记忆文件，一侧看到另一侧写的内容，但看不到对方的存在 ⇒ 上下文里出现无法解释的自我变化。
- 「找不到文件」：当时的通知只给文件名、不给路径，且文件已被清理 ⇒ 收件方只能在自己 cwd 里找。

要给仓库补一篇随想，记录这件事和它引出的设计判断。**本卡只写文档，不改任何代码与配置。**

## 要做的事（新建一个文件）

新建 `docs/why-relay.md`，中文，800–1200 字，四节：

1. **一个被误认为「夺舍」的瞬间**——把上面那个场景按读者能懂的方式讲清楚：同一个 agent、两个会话、一份共享记忆文件；一侧看到另一侧写的内容。重点写「为什么会误判」，不写「AI 有灵魂」。
2. **我们怎么修的**——三条：通知文案带上被投递文件的绝对路径（收件方按路径读，不靠猜）；会话寻址支持按标题包含匹配（id 在宿主新建会话时会变，标题更稳定）；解析不到就跳过并告警，绝不按 `cwd` 猜（乱发比不发更麻烦）。
3. **多播：想到了，但先不做**——记录这个想法本身：一个事件同时唤醒多个会话，像神经突触；也记录为什么暂缓：同一目录投多个目标已经可以用多条 watch 表达，而「唤醒 N 个会话」等于把编排责任塞进投递层，那是 agent 的事，不是投递层的事。
4. **这个插件的边界**——只做一件事：文件稳定 + 标记 → 投一条消息给指定会话。不读内容、不做状态机、不跑命令、不编排。

## 禁忌（脱敏，逐条执行）

- 不得出现任何内部路径（`C:\`、`.dsh`、`.batch`）、Bot 名、卡号、项目名、真人称呼
- 不得出现「这张卡」「负责人」「主人」这类内部流程词；读者是外部开发者
- 不写公司/团队背景叙事，只写通用问题：文件何时算写完、写完通知谁、通知里该带什么
- 不写「我们内网」「我们的多 Bot 团队」这类描述
- 不夸大：不写「AI 有自我意识」「涌现出智能」这类结论，只写机制与误判原因
