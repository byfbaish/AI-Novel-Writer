## 1. 背景

### 1.1 缺陷本体

relay 设置卡的「目标会话」选择器，候选来源是**历史会话快照**、按标题子串过滤。四个缺口同时存在：

- 没有存活判别：已结束的会话照样列出来；
- 没有身份去重：同一个 Bot 在同一个群里被反复重启刷出来的多条会话，标题完全相同（如多次出现「大肥鱼 · AI writer项目组」），用户只能靠肉眼猜；
- 没有状态标识：候选里看不出哪条活的；
- 选了失效目标不报错：保存静默通过，投递时才失败，且只有一行 WARN。

### 1.2 后果（第二级已发生）

- 选错的直接后果是**静默失败**：信投不出去，界面上一个字都没有。
- 真实受害现场：`watches` 首行指向的会话在 11-14 02:14 后无写入，relay 自 11-14 22:47 起持续报 `agent-not-found`，**两封唤醒信卡在 `scripts\dsh\wakeup-inbox` 未投出**（`dsh-wake-20261114-1005-6263.md`、`dsh-wake-20261114-1800-5718.md`）。

### 1.3 叠加机制（只修选择器治不了）

**重启 DSH 会让会话 id 整批刷新**，Bot 侧新建会话也会变。因此任何写死会话 id 的绑定跨重启都是定时炸弹：今天在界面上选对了，重启后照样死。**只做「只列存活会话」是治症状。**

### 1.4 锚点结论（已实测，需求按此写）

- `state.json` 的 `bots` 键 = **Bot id，跨重启不变**（8 个实测全在）；
- 会变的是 `rooms/<群>/sessions` 里的值（Bot 在该群的分身会话）：重启后 7 个未变、产品经理那条变过两次。

⇒ **锚点 = Bot id + 群（room）**；投递时现场解析该 Bot 在该群的当前分身会话。**不再存会话 id。**

### 1.5 拓扑纠正（写进文档与图，别沿用旧说法）

`bridge\to-group` 绑的不是总负责人，而是**大管家在群里的分身**（已从总负责人的群分身改到大管家的群分身）。原因：绑总负责人等于自己跟自己对话，再由分身传达大管家意志。**总负责人只负责群里的事，不承担「向群里发话」这条链。**

按现有配置，7 条 watch 落点分两类：信箱唤醒（`wakeup-inbox` 及其 `workbuddy`/`doubao` 子目录、`signals\workbuddy`、`signals\doubao`）与桥接（`bridge\to-owner`、`bridge\to-group`）。

## 2. 目标

一句话：**让「目标」从易变的会话 id 变成稳定的身份（Bot + 群），并让任何一次投递失败都不可能静默。**

分两阶段，**各自可独立验收**，阶段一不依赖阶段二：

- **阶段一（根治）**：换锚点 + 存量绑定迁移 + 迁移失败显式报错 + 投递现场解析（解析不到即显式失败留痕）。
- **阶段二（界面与早失败）**：候选按身份呈现、同名去重、状态标识、保存即校验、投递失败回传界面。

阶段一完成后：重启不再让绑定失效。阶段二完成后：人不会选错、错误不会晚到投递才暴露。

## 3. 功能描述

### 3.1 绑定语义（阶段一）

- 每条绑定的目标由「哪个 Bot + 哪个群」唯一确定，不再包含会话 id。
- **一个 Bot 在一个群里只有一条身份**：同一 Bot、同一群的两条绑定，视为**两个不同的投递任务**（各自的目录、完成规则独立），不许合并、不许去重。现有配置里 workbuddy 与 doubao 各有两个目录指向同一目标，迁移后必须仍是 4 行、不是 2 行。
- 目标可以是「Bot 在该群的分身会话」；**私聊/无群归属的会话本期不作为目标**（见 §6 Q1）。

### 3.2 存量迁移（阶段一）

- 迁移在**升级后首次加载配置时执行一次**，产出新锚点并落盘；重复加载不得重复迁移、不得改坏已迁移的条目。
- 迁移按**行**为单位，逐行判定，只有两种结果：迁移成功 / 迁移失败。
- **迁移失败必须显式列出**：哪一行（该行目录 + 原目标名 + 失败原因），不许静默丢弃、不许静默改成空目标、不许整份配置回滚后只留一句日志。
- 失败的行**保留原样但停止投递**，并在配置里带一个「失效待人工处理」标记——目的是重启后不再反复报同一个错，同时人还能看见它。
- 迁移不得触碰目录、完成规则等与目标无关的字段。
- **同一旧目标被多行引用时，各行各自迁移**（不合并、不共享一条结果）。

### 3.3 投递解析流程（阶段一）

一次投递按下列顺序判定，**每一步失败都要有可读原因，且失败原因能落成文字被人看到**：

1. 目标 Bot 是否存在 → 不存在：显式失败（原因：Bot 不存在/已删除）。
2. 该 Bot 是否在该群里 → 不在：显式失败（原因：Bot 不在该群）。
3. 该 Bot 在该群是否有当前分身会话 → 没有：显式失败（原因：分身会话不存在；**不自动代开分身**，见 §6 Q2）。
4. 该分身会话是否已结束 → 已结束：显式失败（原因：目标会话已结束）；**此时不许改用同 Bot 的其它会话兜底**，也不许自行改绑，只报错。
5. 以上全通过：投递。

解析**每次投递现场做**，不缓存会话 id 到磁盘。

### 3.4 存活判据（阶段一、二共用，易错点）

**存活 ≠ 最近有写入。** 一个 140 小时没说话但会话仍在进行中的，是活的；有结束时间的才是死的。**禁止按「最近写入时间」过滤或排序来决定候选。**

### 3.5 候选呈现与早失败（阶段二）

- 候选按**身份**（Bot + 群）列出，同一身份只出现一次，不因重启刷出多份。
- 每个候选必须可区分：至少能看出「是哪个 Bot」「在哪个群」「是否仍存活」。存活状态**只由 §3.4 判定**。
- **界面上不得再要求输入会话 id**（保留 P22b U4 的既有口径）。
- **保存即校验**：保存时逐行校验目标能否解析；解析不到即**拒绝该行写入**并列出「第几行 + 原因」，其余行照常保存。不得保存成功、留到投递时静默失败。
- **投递失败必须回传界面**：设置卡里有一处可见位置显示最近的投递失败（时间、目标身份、失败原因），不能只写日志。至少保留最近 20 条。

### 3.6 两封存量唤醒信

作废，不重投。两封都是 11-14 的定时检查点，对应结项均已走过，重投只会让 Bot 白跑一轮、白烧一次钱。处理口径：**过期条目作废并留痕**（留在原地或改名归档都行，但不许悄悄删除，见 §6 Q4）。

## 4. 验收判据

证据形态只认：命令输出原文、文件/行、截图、仓库提交 SHA、实机操作记录。QA 照着逐条判。

### 阶段一

- **S1-1 落点在仓库**：源码仓存在对应提交，`git show --stat <sha>` 可见改动文件；profile 下的插件文件与仓库该版本一致（用包版本号 + 安装记录证明，`git diff` 对 node_modules 无意义）。仅节点目录有改动、仓库无提交 ⇒ 不通过。
- **S1-2 锚点不再含会话 id**：迁移后的配置里，每条绑定的目标只由 Bot 身份 + 群确定，全文不出现任何 `session-…` 形式的会话 id 参与投递（诊断性保留的旧值必须标为不参与投递，并在判词里指名该位置）。
- **S1-3 迁移正确**：拿现网 7 条存量配置跑一次升级，结果 7 行逐行给出「成功/失败」；成功行能解析到正确的 Bot + 群；`workbuddy`/`doubao` 各两行的情形迁移后仍是 4 行（证明没按锚点合并）。
- **S1-4 迁移失败显式化**：构造一条目标指向不存在会话的绑定，升级后必须出现在失败清单里（可见的位置 + 原因文字）；**该行不得消失、不得变成空目标**。清单里出现一条即算命中，出现零条即不通过。
- **S1-5 迁移幂等**：连续加载/重启两次，第二次不再产生新的迁移动作，配置内容与第一次结束时逐字节一致（贴两次的文件哈希）。
- **S1-6 重启后仍能投**（本卡核心）：绑定建立后**重启宿主一次**，往该目录投一封信，必须投出。重启窗口由总负责人安排、QA 在场；执行方不得自行重启。重启前后各投一封，两封都成功才算过。
- **S1-7 分身不存在/已结束不静默**：把目标 Bot 从该群移出（或令其分身结束），投一封：不得投出，且必须留下可读的失败原因（S1 阶段不要求界面回传，但要求留痕可查，判词里指名痕迹位置）。
- **S1-8 不兜底**：目标分身结束后，relay 不得改用该 Bot 的其它会话投递，也不得自动改绑。检查配置与投递记录，出现自动改绑即不通过。
- **S1-9 过期信留痕**：两封 11-14 的唤醒信不再处于「待投递」状态，且原文件或其归档件仍在磁盘上可找到（贴路径与字节数），不得重投（唤醒日志里无这两封的投递记录）。
- **S1-10 无关字段未变**：迁移前后，每行的目录、完成规则逐条比对一致（贴前后对照）。
- **S1-11 回归**：既有测试套件结果一个不许变（贴前后末行读数）；`pnpm check:fast` 全绿（若源码仓无该脚本，用仓库既有等价闸门并注明）。

### 阶段二

- **S2-1 候选按身份**：设置卡里选目标，同一 Bot 在同一群只出现一次；重启后再开，条数不变（截图：重启前后各一张，条数相同）。
- **S2-2 同名可区分**：构造两个同名 Bot（或同名不同群）的候选，界面上能区分（截图，并说明靠哪几个信息区分）。
- **S2-3 存活判据不放宽**：造一个「140 小时无写入但仍在进行中」的会话，它必须出现在候选里且标为存活（截图）；同时造一个已结束的会话，它必须标为已结束或不出现在可选列表里。
- **S2-4 保存即校验**：手工把某行目标改成解析不到的值，点保存：该行不写入并给出「第几行 + 原因」，其它行照常保存（截图 + 保存后的配置原文）。
- **S2-5 投递失败回传**：构造一次必然失败的投递，设置卡里必须出现一条可见回执（时间、目标、原因），且至少保留最近 20 条（截图 + 条数）。
- **S2-6 无会话 id 输入**：界面上「会话 id」字样 0 命中（截图或渲染输出原文）。
- **S2-7 崩溃不允许**：保存失败、解析失败、渲染异常各走一次，插件不得抛异常导致设置卡白屏（截图 + 宿主日志无未捕获异常）。

## 6. 开放问题（待主人拍板，每条带推荐值）

1. **私聊/无群归属会话能否作投递目标？** 推荐：本期不支持，迁移时列为失败并保留行。理由：锚点是 Bot + 群，私聊无群可锚，硬做等于再造一套锚点。
2. **Bot 在该群尚无分身会话时，是否自动代开一个？** 推荐：不自动，显式报错。理由：代开会在群里产生一条无声会话，属于越权副作用。
3. **迁移失败的行是否自动停投并标失效？** 推荐：是，停投 + 标失效 + 保留行。理由：不停投就每次重启刷同一批错；删行则人永久失去线索。
4. **两封过期信怎么留痕？** 推荐：原地改名加 `.expired` 后缀，不删不动内容。理由：可追溯，且不会被下一次投递误读。
5. **投递失败回执是否显示「最近活跃时间」？** 推荐：显示，但仅作信息，不参与任何过滤或排序。理由：人不该被迫用活跃度猜死活，但知道它多久没说话是有用的。
6. **阶段二是否要显示「上次投递成功时间」？** 推荐：要，只读信息，不做告警。理由：静默失败的可观测性主要靠这一条。
7. **发布流程由谁触发？** 推荐：由总负责人确认窗口后触发，QA 在场，执行方不得自行发布/重启。
