## 为什么先证不做

原计划 P29 = 「dir 校验 + 行状态徽标 + 选择目录按钮」。复核时发现一个前提没证：**渲染层（`client.js`）没有 `fs`**，所以「这个路径能不能读」不可能在 client 本地判。校验只能落在 host 侧（schema 校验）或新增回传通道（可能破坏「写回只走 configForms」的边界）。

在这一点没证清之前派码卡，等于让执行方去做一件物理上做不到的事——与 P22b 那张 B0 的错误同类。

## 四问

1. `Config` 校验失败时，UI 如何呈现：整卡一条错误，还是能定位到字段/行？能否阻止保存？
2. `plugins.row.config` 除 `form.state`/`form.mutate` 外，有没有只读的校验结果 / `warnings` / `errors` 通道？
3. 渲染层有无已暴露的 stat/access 一类服务？（没有就明说没有）
4. 若 1–3 都无解：是否存在现成机制让 host 把「目录可读性」写到 client 能读的地方？还是必须新增服务？

## 裁定预案（先写死，避免事后摇摆）

- 若 1 成立（能按字段呈现错误且能阻保存）⇒ P29 走「host 侧 schema 校验 + 行内错误」，不做徽标。
- 若 2 成立（有只读校验通道）⇒ 可做徽标。
- 若都无解 ⇒ P29 降级为「填了就填了，只在 relay.log 留 not-found」，并把界面上的「校验」说法全部删掉，不在 README 承诺。
- 「必须新增服务」一律判不做（超出本期边界）。
