# P52 · GitHub Projects 是否适合我们的长线规划（只查资料，不许试用）

分类：B 类（只写 staging，无仓库提交）｜执行方：产品经理｜估时：25 分钟
产物：`.batch\night\staging\github-projects-eval.md`，末行必须 `<!-- DONE -->`

## 0. 红线（违反即作废重做）

**只准查资料，不准试用。** 不许创建 Project、不许改仓库设置、不许动任何 issue/PR、不许在我们仓库里点任何按钮。你只读文档与公开页面，写一份评估。
理由：主人原话是「先找资料，而不是直接去尝试它的用法」。我们要的是「它能不能装下我们的阶段门禁」，不是一次演示。

## 1. 背景：我们要装进去的是什么

主人 11-16 的诊断：**项目缺一个全局视野**，所以不清楚「在哪个阶段该 Input 什么资料、Output 什么资料」，收尾时该按哪张清单结项。要评估的是 GitHub Projects 能否承担这层「长线规划 + 阶段门禁 + 结项清单」。

必须覆盖的六件事（评估时逐条作答）：

1. **阶段**：能不能表达「需求确认 → 方案设计 → 开发 → 验收 → 结项」这种有序阶段，而不是只有一列看板？
2. **输入/输出清单**：一个阶段要求「进这个阶段前必须有哪些件、出这个阶段必须交出哪些件」，能不能挂在阶段上、并且**能被检查**（而不是只写在描述里没人看）？
3. **门禁**：某件没交齐时，能不能阻止进入下一阶段？（自动化规则能做到什么程度、做不到什么）
4. **结项清单**：一个任务/一个迭代结束时，能不能要求逐项勾选、留痕？
5. **跨仓**：我们有两处仓库（`AI-Novel-Writer`、`dsh-handoff-relay`），能不能在一个视图里统一看？
6. **机器可读**：能否用 API/GraphQL 读出来，让我们自己的脚本核对「阶段与清单是否齐」？（我们已有大量 `.batch/night/` 文件式台账，能不能对接）

## 2. 要查清的事实（逐条给来源）

- 实体模型：Project / Item / 字段（Field）类型 / 视图（Table、Board、Roadmap）/ 子项（sub-issues 或 hierarchy）/ 迭代（iteration）。
- 内置自动化（built-in workflows）能做什么、触发条件有哪些；**明确写出做不到的**（例如依赖关系、关键路径、工时、基线快照——有就写有，没有就写没有）。
- 与 Issue / PR 的联动方式：加进 Project 是「引用」还是「复制」；Issue 关闭后 item 如何表现。
- 模板：Project templates 的机制与能否自定义模板（我们要的是可复用的「阶段+清单」骨架）。
- 权限：组织级 / 用户级 Project、私有仓库、可见性、谁能改字段。
- 额度与限制：免费/付费档位、item 数量上限、API 速率。
- 跨仓库：一个 Project 能否装多个仓库的 issue；Roadmap 视图的时间维度怎么来（字段还是 issue 的 milestone）。

## 3. 输出格式

一节一个主题，每个结论后面跟 `来源：<URL>`；引用文档原句时用引号并 ≤40 字，不要整段抄。
最后一节固定写**「匹配度结论」**：六件事逐条给 `能 / 部分能 / 不能 + 一句为什么`，再加一段「如果不能用，缺的那层该由什么补（只写方向，不设计实现）」。

**不要写推荐方案的技术实现、不要写脚本、不要写我们的仓库该怎么改。** 这份产物只回答「它装不装得下」。
拿不到的事实写 `unknown` 加一句为什么，不许猜。
