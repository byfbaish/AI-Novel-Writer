# 提示词缓存命中率评估 —— 是否立项

> 起因：2026-10-12 观察 DeepSeek 后台，本工程缓存命中率约 8%，远低于 WorkBuddy 的 99%。
> 结论先行：**分三档处理，不要合并成一个"缓存优化"立项。**

| 事项 | 判断 | 工作量 |
|---|---|---|
| ① 缓存命中观测（记录 hit/miss tokens） | **立做** —— 零风险，是后续一切决策的前提 | 约半天 |
| ② 提示词前缀分层重排 | **立项，但定性为"架构 / 技术债清理"**，不是成本优化 | 2–3 天 |
| ③ 以"省 API 费"为由立项 | **不立项** —— 实测年省约 ¥35，ROI 不成立 | — |

---

## 一、数据事实

### 本工程（2026-10-12）

| 项 | 值 |
|---|---|
| 输入 · 命中缓存 | 12,544 |
| 输入 · 未命中缓存 | 145,531 |
| 输出 | 121,735 |
| 合计 | 279,810 |
| **输入命中率** | **7.9%**（12,544 / 158,075） |
| **输出占总量** | **43.5%** |

### 对照：WorkBuddy（2026-10-11）

| 项 | 值 |
|---|---|
| 输入 · 命中缓存 | 338,129,664 |
| 输入 · 未命中缓存 | 1,976,418 |
| 输出 | 988,077 |
| **输入命中率** | **99.4%** |
| **输出占总量** | **0.29%** |

### ⚠️ 两者不可直接比较

命中率差异**大部分不是优化水平差异，而是工作模式差异**：

- **WorkBuddy 是 agent 多轮循环**：每一轮把此前全部历史重新发一遍，第 N 轮天然命中前 N−1 轮的内容。99% 是这种模式的**自然结果**，不是刻意设计。
- **本工程是一次性独立任务**：每次生成都是一个全新拼装的提示词。

输出占比的反差同样说明问题：WorkBuddy 输出只占 0.29%（输入主导），本工程输出占 43.5%（生成主导）。**缓存只作用于输入侧，而本工程的成本主体是输出。**

## 二、DeepSeek 缓存机制（已核实）

来源：DeepSeek 官方 API 文档与近期第三方实测。

1. **自动开启，无需任何配置**——没有 `cache_control`、没有开关、没有额外请求参数。
2. **从第 0 个 token 起精确前缀匹配**。中间部分匹配**不触发**命中；前面任意位置变化，其后全部失效。
3. **64 token 为存储单元**，不足 64 token 的内容不缓存。实践中可靠命中通常需要前缀 ≥ 1024 token。
4. **响应返回命中明细**：`usage.prompt_cache_hit_tokens` / `usage.prompt_cache_miss_tokens`。
5. **命中价约为未命中价的 1/50 ~ 1/10**（随模型与时段浮动）。
6. **命中还能降低首 token 延迟**（实测 1,800 token 前缀：1.43s → 0.90s）。
7. 缓存按账户隔离；空闲后自动清理（数小时至数天，视负载）。

## 三、根因：结构性反模式（代码证据）

### 3.1 请求结构

`src/services/workflows/commands/base-command.ts:470-473`

```ts
messages: [
  { role: 'system', content: systemPrompt },   // composePromptSystemRole()，短
  { role: 'user',   content: prompt },         // builder.build()，长
],
```

### 3.2 实际提示词布局

以 `src/services/builtin-prompt-templates.ts:1038` 的 `next_chapter_draft` 为例：

```
你正在连载写作最新章节。                              ← 静态，约 12 字
【剧情记忆库与前置断点上下文】
- [全局剧情进展]：{{global_summary}}                  ← 第 4 行即出现变量
- [角色状态监控]：{{character_states}}
- [近期三章简要]：{{short_summary}}
★【上一章已完成的结尾状态】：{{previous_ending}}
...
【网文连载更新核心法则】...                            ← 静态规则，但已排在动态内容之后
```

而 `architecture`（故事架构）与 `novel_config`（小说配置）这两个**项目内永不变化**的大块，被拼在 `systemSuffix` 里——`prompt-builder.ts:56` 是 `result + '\n\n' + suffix`，即**整段的最末尾**。

### 3.3 稳定性与位置的错配

同一项目内，各段的实际稳定性与当前所在位置：

| 部件 | 稳定性 | 当前位置 | 应处位置 |
|---|---|---|---|
| `architecture` 故事架构 | **项目内恒定** | systemSuffix **末尾** | 最前 |
| `novel_config` 小说配置 | **项目内恒定** | systemSuffix **末尾** | 最前 |
| `global_guidance` 全局写作要求 | 项目内稳定 | content 中段 | 前部 |
| `writing_style` 文风 | 项目内稳定 | content 末尾 | 前部 |
| `reference_works` 参考作品 | 项目内稳定 | content 最末 | 前部 |
| 静态规则（连载法则、AI 味反制等） | **全局恒定** | content 中段 | 最前 |
| `global_summary` 章节要点时间线 | **逐章累积增长** | content **第 4 行** | 最后 |
| `character_states` 角色状态 | 逐章变化 | content 第 5 行 | 最后 |
| `previous_ending` 上章结尾 | 逐章变化 | content 中段 | 最后 |
| `chapter_info` 本章蓝图 | 每章不同 | content 中段 | 最后 |

**结论：位置几乎完全颠倒——最稳定的排最后，最不稳定且逐章累积增长的排在开头。**

于是公共前缀只剩「system 角色定位 + 首句」，约 **80 token**，之后立刻断裂。这解释了 7.9% 的命中率，也解释了为什么回落到「连一个 64 token 缓存块都凑不满」的量级。

## 四、成本测算

按 DeepSeek V4-Flash 现行价（命中 $0.0028/M、未命中 $0.14/M、输出 $0.28/M）：

| 场景 | 未命中 | 命中 | 输出 | 合计/天 |
|---|---|---|---|---|
| 当前（命中 8%） | $0.0204 | $0.00004 | $0.0341 | **≈ $0.054** |
| 优化后（命中 70%） | $0.0066 | $0.00031 | $0.0341 | **≈ $0.041** |

**日省 ≈ $0.013，月省 ≈ $0.40，年省 ≈ $4.9（约 ¥35）。**

关键原因：**输出占 43.5% 且输出永不缓存**，输入侧再怎么优化也动不了这块大盘。

延迟侧同理：单次正文生成等待以十秒至分钟计，prefill 优化大约能省 1–4% 的端到端时间。有意义，但不是痛点。

## 五、建议

### ① 缓存命中观测 —— 立做（P1，约半天）

**当前状态：工程内部对缓存完全不可见。**
- `src/shared/ipc-channels.ts:807-811` 的 `TokenUsage` 只有 `promptTokens / completionTokens / totalTokens`；
- `electron/llm/openai-provider.ts:288` 与 `:300` 解析 usage 时，DeepSeek 返回的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` **被直接丢弃**。

改动点：
1. `TokenUsage` 增加两个可选字段（保持向后兼容）；
2. `openai-provider.ts` 两处解析补齐（含流式的 `onUsageEvidence`）；
3. 落到 `generation_attempts` 的 usage 回执；提示词追踪文件里也带一份；
4. 面板 / 日志可见。

价值：把"猜"变成"可度量"，并且**顺带验证本评估的根因推断**——若观测显示 hit_tokens 长期在 0~200 徘徊，即证明前缀确实在极短处断裂。

### ② 提示词前缀分层重排 —— 立项，但定性为架构改善（P2，2–3 天）

按 token 挥发性重新排序，**内容一个字不改，只改顺序**：

```
L0  全局恒定：语言、角色定位、输出格式、AI 味反制、连载法则
L1  项目恒定：故事架构 + 小说配置 + 文风 + 参考作品 + global_guidance
L2  累积上下文：章节要点时间线、角色状态、近期三章摘要、上章结尾
L3  本次任务：本章蓝图、后续预告、作者微操指导
```

L0 与 L1 在同一项目内**字节一致**，构成数 k token 的稳定前缀，跨章节、跨步骤都能命中。

**必须同步处理的连带项（这才是 2–3 天的主要成本）：**
- `VELA_HOME/prompts/` 下有约 20 个全局自定义覆盖模板，其中不少会遮蔽内置模板（优先级 project > global > builtin）。重排内置后，这些覆盖仍按旧顺序渲染，**必须一并迁移**，否则优化只对未覆盖的模板生效。
- 模板的 `systemSuffix` 机制目前把 suffix 拼在最末尾，若要前置需重新定义其语义位置。
- 已有测试锁定部分模板结构，需同步调整。

**立项理由（诚实版）：**
- ✅ prompt 结构变成"稳定块 + 变化块"，本身就更易维护、更易调试；
- ✅ 为将来换模型铺路（Claude 需显式 `cache_control` 断点、Gemini 按 token-hour 计费，前缀分层是前置条件）；
- ✅ 命中率提升是**附带收益**，同时在写长篇 / 多项目 / 多人使用时放大；
- ❌ **不是"省 API 费"**——年省 ¥35，任何人力投入都不划算。

### ③ 跨步骤共享前缀 —— 先观测再定（P3）

架构五步（前提 / 角色 / 世界观 / 弧光 / 大纲）理论上可共用同一个 L0+L1 前缀，从而连续命中。但是否值得，取决于实际使用模式（是否连续跑多步、是否频繁重生成），**在没有 ① 的观测数据前不立项**。

## 六、附：不要被对比误导

WorkBuddy 的 99.4% 容易被读成"别人优化得好，我们差"。实际是**两种工作模式**：

| | WorkBuddy | 本工程 |
|---|---|---|
| 交互模式 | agent 多轮循环 | 一次性独立任务 |
| 输入 / 输出比 | 344 : 1 | 1.3 : 1 |
| 命中来源 | 天然复用上一轮历史 | 需主动设计稳定前缀 |

**该做的不是"追平 99%"，而是消除本工程确实存在的结构性反模式**（稳定内容排在变化内容之后）。即便消除，本工程的命中率乐观估计也在 60–75% 区间，因为输出占比决定了它的成本结构与对话型应用根本不同。
