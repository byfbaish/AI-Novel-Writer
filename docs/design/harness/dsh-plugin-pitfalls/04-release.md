# 04 · 投递链与发版

> 状态：已实施（2026-11-14）
> 日期：2026-11-14
> 上级索引：[README.md](README.md) · 对应事故：插件停用后「交付了没人触发」、0.4.0 坏 tag

## K17 · 交付落盘了，下游零反应

- **现象**：交付文件与 `.done` 信号都在，下游 Bot 没被唤醒；源目录里的信号还留在原处。
- **根因**：投递是**插件搬运事件**，插件停用/崩溃即整条链消失；文件不会自己走进 `delivered/`，也不会自己唤人。
- **解法**：判「是否触发」同时看**源目录**与 `<profile>/dsh-handoff-relay/delivered/<dirKey>/`；插件不可用期间由联络人按固定节奏人工查盘。恢复后 watch 目录须清空、只放一个探针，别把存量重放一遍。

## K18 · 用 mtime 核对投递 / 用「有没有 WARN」判成败

- **现象**：探针投出后时间戳对不上，被判成没投；或者看到 `WARN` 就以为出了问题。
- **根因**：投递会移动/重写文件，`mtime` 已变；成功投递的 `relay.log` 正常只有 **1 行 INFO**，出现 WARN 反而说明走了失败/跳过分支。
- **解法**：只认**字节数与 MD5**；判成功看「1 行 INFO + delivered 内有该文件」，判失败看 WARN 的原文。

## K19 · 改了插件名，重启后插件不加载

- **现象**：代码改了、`package.json` 名也改了，重启后宿主里根本没有这个插件。
- **根因**：加载靠四处/五处**共同指向同一个名字**：仓库 `package.json` 的 `name`、`profiles/desktop/node_modules` 下的目录（联结）、`profiles/desktop/package.json` 的依赖项与 bundles、`cordis.patch.yml` 的 `id`（和 `name`）、两份 README 互链。改一处，剩下几处就指向一个不存在的名字。
- **解法**：四处（五处）**同批改完再重启**；没改完之前不要改目录名。改完用 `cordis.patch.yml` 的 `id` 反查是否对得上实体目录。

## K20 · tag 指向的提交本身跑不起来

- **现象**：`v0.4.0` 的 tag 在远端、版本号也报了，但这个提交装上就崩；npm 上却没有这版。
- **根因**：打 tag / push 与 `npm publish` 是两条独立的动作，可能只做了前一半；tag 一旦推上公开仓库就被别人当可信锚点。
- **解法**：发版前核三件 —— tarball 内容 == tag 指向提交、`HEAD == tag`、`git status --porcelain` 为空；坏版本**不回滚不删**（留作审计锚点），发新版本号并在发布说明首行写「<旧版本> 指向不可用提交，请装 <新版本>」。npm `publish` 返回 202 后 `latest` 约 2 分钟才更新，复验要等 ≥90 秒，属常态。
