# 03 · 测试与取证

> 状态：已实施（2026-11-14）
> 日期：2026-11-14
> 上级索引：[README.md](README.md) · 对应事故：P13 冒烟测试反证、P14 时序用例 stub、issue 提交通道的取证（K22）

## K13 · 冒烟测试空转：单测全绿，同一输入仍崩

- **现象**：新增用例全 PASS，但把原崩溃提交拉起来跑同一场景，照样 `exit 1`。
- **根因**：用例只测「我改的那个函数被调用 / 返回了值」，没有把**原崩溃形态**重建出来；绿是绿在别处。
- **解法**：`git archive <坏提交>` 解到临时目录 + 在它上面跑新用例，必须**复现**原来的 `exit 1` 和报错原文；再拿修复版跑同样的用例。复现不了 = 用例没拦住这个坑。

## K14 · 手写 stub 模拟 cordis ≠ 验证真实 provide 顺序

- **现象**：用例断言「回调恰好调用一次、服务对象非空」，报告写成「先到/后到都已验证」。
- **根因**：stub 只复刻「服务已就绪时调 cb」，真实 cordis 的 provide 顺序、同 fiber 内的异常升级路径都不在模拟范围内。
- **解法**：这类判据在报告里单列「真机项」，并给一个**取信点**（如启动日志里那行 `设置卡 schema 基线=… resolved=…`）；真机项不算已验证，验收须由人/真机给结论。

## K15 · 临时目录清理写在用例内部 `finally`

- **现象**：`%TEMP%` 里累积 `relay-p13-*` 目录，越跑越多。
- **根因**：清理写在**各个用例**的 `finally` 里，某条用例在前面抛错时，后续用例的 `finally` 根本没机会执行；不是「漏写清理」，是清理位置错了。
- **解法**：收尾搬进统一的顶层 `finally` / 每次运行前先清空自己的前缀目录；验收核对 `%TEMP%` 残留数量必须为 0。

## K16 · 拿别人转述的行号当已验证

- **现象**：报告引用的 `index.js:668`、`:974` 在当前 HEAD 上是别的内容，复核时被当成「引用造假」。
- **根因**：提交会位移行号；转述一次再漂一次。行号是「某次快照的坐标」，不是稳定标识。
- **解法**：引用以**符号名 + 原文片段**为主、行号作辅并注明快照 SHA；复核按当前 HEAD 重新取一次，别直接沿用。

## K22 · 一条 `git` 命令失败就判「仓库通道不通」

- **现象**：`git ls-remote` / `git push` 报 `Connection was reset`，结论直接写成「网络不通，推不了」，实际 SSH 认证是通的。
- **根因**：全局 `url."https://github.com/".insteadOf` 会把 `git@github.com:` 改写成 https，于是 HTTPS 被墙时**连 SSH 地址也走 https**；失败的是传输方式，不是通道本身。
- **解法**：先分层再下结论 —— `git config --get-regexp 'url\..*'` 查改写规则；用 `GIT_CONFIG_GLOBAL=<空配置>` + 指定系统 ssh 复测 `git ls-remote git@github.com:<owner>/<repo>.git`。认证回声（`Hi <user>! You've successfully authenticated`）拿到就说明「协议 / 认证 / 目标」里只有传输层要换，别把一个失败命令写成「没通道」。

## K23 · 闷头扒宿主源码，不知道社区早有现成实现

- **现象**：为一个「会话列表 + 搜索」功能连扒两晚 asar，最后发现社区插件早已解决，症状原文都能搜到（如「面板拿不到会话」）。
- **根因**：默认「宿主内部机制没人碰过」，跳过检索直接读 bundle；扒源码成本最高，且容易拿旧运行时（隔离 profile 的旧 CLI）当新宿主结论。
- **解法**：先搜症状原文与机制关键词（`pending (waiting for service:`、`cannot get property ... without inject`、`web boot: ... did not activate`）看 npm / GitHub / 讨论区，再进同类插件源码对照；宿主自带能力优先复用（会话检索直接用 `@deepseek-ai/dsh-session-query` 的 FTS5），别自己造索引。

## K24 · 同一份交付文件被唤醒两次（stable 与 DONE 各投一次）

- **现象**：一份报告只写了一次，群里却收到两条「文件已就绪」；`delivered\` 下同名文件只有一份、字节与 mtime 都没变。
- **根因**：watch 的「稳定」与「完成标记」是两条触发条件，一个文件先满足 stable、再命中 `done`，于是各投一次；投递层按文件名不按内容去重。
- **解法**：验收时先比 `delivered\` 内的**份数 + 字节 + MD5**，三样一致就是同一次交付被推了两遍，不重复登记、不重复派验；信号文件固定写卡面指定的 `signals\<执行方>\`，不放根目录；内容级去重（路径 + mtime + sha256）记为待做，改前不动投递代码。
