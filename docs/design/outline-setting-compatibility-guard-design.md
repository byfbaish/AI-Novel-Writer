### 1.3 弧光层：本例**没有**同类问题

`project_core.plot_structure_plan`（3,903 字，弧光）实测：

- 出现的空间名：`梅林坳 / 老陈记 / 云创大厦 / 人才服务中心 / 夜航便利店 / 康宁医院 / 白鹭湾` —— **与世界观命名逐字一致，无自造地点**；
- **不含任何时钟点**（正则 `(凌晨|早上|上午|中午|下午|晚上|深夜)?[零一二三四五六七八九十两0-9]{1,3}[点时]` 命中为 0）。

### 1.4 生成粒度（决定校验该挂在哪）

大纲是**按章生成**的：本批 `chapterRange = {from:1, to:5}`，共 **5 次** LLM 调用，purpose 依次为 `plot-outline:chapter:1:normal` … `chapter:5:normal`；任务文本收窄为「**本次只写第 1 章**……每章大纲正文目标约 150 字」。

⇒ 校验可以**逐章紧跟生成**，定位精确到章，且不需要额外一次全量调用。

## 2. 关键判定

1. **这是「约束未被执行」型缺陷，不是「信息缺失」型。** 规则在 prompt 里（§1.2），模型仍违反。
2. **因此"再加一次 LLM 事后审查"不是最优解** —— 那是让一个模型去查另一个模型有没有遵守它自己已经看过的规则；且 LLM 审查自身也会漏（同一项目的审稿在**同一份材料**上就把「第一句谎话」的序数断言判成了 pass，见 `consistency-check-ordinal-claim-guard-design.md` §1）。
3. **更高杠杆的是把"埋在 6,185 字散文第 4 节里的规则"变成显式、可判定的硬约束** —— 这与 `keyEvents` 结构化的思路同源：*示例即形态，位置即权重*。
4. **与上一轮的机制补强是同一失效模式的两面。** 上轮已在内置 `consistency_check` 写入判据「作者材料里的序数 / 全称断言必须在正文独立复核，不得采信断言本身」。本设计是把这条判据**从审稿层前移到生成层**，并把适用范围从「序数 / 全称」扩到**一切可判定的具体约束**（时段、准入、数值区间、命名闭集）。

## 3. 三档方案

### A. 提示词层：把「空间准入规则」提为独立硬约束小节（成本 0，建议先做）

世界观模板**已经**要求【空间结构】按固定形状书写（`builtin-prompt-templates.ts:589-593`）：

> 用「空间名：一句话定位 + 关键规则」的格式列出；命名要固定、唯一，后续情节与弧光结构将用同一名字引用它。

**这份形状已经在产出里了，只是没被下游利用。** 做法：

- 在大纲 / 章节蓝图的入参侧，从 `worldbuilding` 中抽出【空间结构】段，生成一张短清单
  「**\【空间约束（硬）】** 老陈记早餐摊：07:00–09:00 营业；康宁医院六楼：探视 15:00–19:00；云创大厦：刷闸机，被裁后门禁失效……」，
  作为**独立小节**与世界观全文并列注入。
- 同时在大纲 / 蓝图模板的「要求」里各加一条自检：
  > 本章安排在某个空间发生的事件，必须满足该空间【空间约束】里的时段与准入条件；**不得因为剧情方便而忽略已声明的限制**。

**为什么先做这条**：同一条规则，藏在 6,185 字散文的第 4 节 vs 以 20 字清单独立成节，模型遵守率的差距远大于"事后多审一次"。

**纪律**：抽取失败必须 **fail-open**（回退为现状、不中止生成），且模板改动须同步**内置 zh / 内置 en / 作者全局覆盖版**三处（红线 3）。

**强化版 A⁺**（本轮建议一并做，§6.2）：`world_building` 模板再加一条 —— 凡涉及时段 / 准入的「关键规则」，须写成**明确可判定的形式**（如 `07:00–09:00`），禁用「早上」「白天」这类模糊词。**这不是为了让框架去解析，而是为了让设定自身可判定** —— 无论如何，规则都得先写清楚，才谈得上遵守。

### B. 确定性静态预检（零 LLM 成本；复用现成通路）

> ⚠️ **本节方案在作者 Q4 质疑后已拆分修订** —— 「解析关键规则里的时段并做区间推断」属于**框架不该管的语义推断**（§6.1），**不做**；只保留「键对键」的结构半。以 **§6.2** 为准。

**现成通路已经存在**：`src/shared/consistency-preflight.ts` —— 已有先例「角色死亡终态 vs 蓝图仍排其出场」（`findBlueprintContinuityRisks`），产出 `ConsistencyFinding`，再由 `mergeConsistencyFindingsIntoReview` 并入审稿 items。本方案只是**新增一条窄规则**（通路与 UI 见 §4）。

**窄规则建议：「空间 × 时段」相容性**

1. 从 `worldbuilding`【空间结构】抽出 `(空间名, 关键规则)` 对，并解析其中的时段（如 `7:00—9:00`、`15:00—19:00`）；
2. 在大纲 / 蓝图文本中定位该空间名的出现位置，取**同句 ±1 句**的窗口；
3. 窗口内若出现可解析的钟点，且落在该空间**所有**已声明时段之外 ⇒ 报 warning（附空间名、时段、命中钟点、原句）。

**必须遵守的三条纪律**（否则它会变成噪声源，比不做更糟）：

- ① 钟点解析失败 ⇒ **静默跳过**（宁漏勿误）；
- ② 只有「空间名」与「钟点」出现在同一小段（按 `。；` 切句后 ±1 句）才判定 —— 本例「下午两点」与「老陈记」分处两句，窗口必须 ≥1 句才抓得到；
- ③ 产出是 **evidence**，不是写入禁令（沿用 preflight 既有语义）。

**成本**：中文钟点归一化（十余个模式）+ 区间比较，约 100–150 行 + 测试。**能直接抓出本例。**

**触发时机（关键选择）**：现成的 preflight 有**两处**落点 —— ① 生成**前**的 `ChapterCreationDialog` / `BatchChapterCreationDialog`（有 finding 就 `return` 停下，见 §4）；② 正文**审稿**时（`review-revision-context.ts:156`，那时正文已定稿，返工最贵）。本方案要加的是**第三处**：**大纲 / 蓝图每章产出后立刻预检**（§1.4 证明逐章生成，落点天然存在），把问题挡在正文之前。三种时机的差异与处理形态见 §4.1 / §5。

### C. LLM 一致性校验步骤（成本 = 每次架构生成 +1~2 次调用；**不建议先做**）

在弧光 / 大纲生成后追加一次「对照上游设定审查」，可复用 `consistency_check` 的 findings 形状。

**不建议先做的理由**：A / B 解决的是"根本不检查 + 规则不可见"，C 解决的是"漏检"；且 C 自身会漏（§2.2）。若 A + B 上线后仍有漏网，再考虑 C，且应放在大纲生成后**一次性覆盖**，不逐章。

## 4. 现成基础设施（**B 不是新建通路**）

作者问「生成后立即预检当然最好，但是修改时机呢？」—— 答案的一半已经在代码里：

**预检的「检出 → 停下 → 作者处理」闭环已经存在**，只是目前只跑一条规则（角色死亡终态）：

| 环节 | 现状落点 | 行为 |
|---|---|---|
| 预检计算 | `src/services/consistency-preflight.ts:11` `readConsistencyPreflight()` | 拉历史投影 + 豁免，逐蓝图跑规则 |
| **停在生成前** | `ChapterCreationDialog.tsx:331-353` | `preflight.findings.length > 0` ⇒ **`return`，不继续**，把决定权交回作者 |
| 批量版 | `BatchChapterCreationDialog.tsx:459` | 同上，`ConsistencyPreflightPanel` |
| 作者处理 UI | `ConsistencyPreflightPanel.tsx` | 逐条 finding 展示 + 填理由**豁免** + 撤销豁免 |
| 豁免落库 | `db:consistency-exemption-save` / `-revoke` → `ConsistencyExemptionRepository` | `{stableFactKey, reason, revoked}` |
| 另一处（事后） | `electron/services/review-revision-context.ts:156` + `review-generation-report.ts:138` | 并入审稿 items 一起呈现 |

⇒ **新增规则 ≠ 新增流程**：`ConsistencyFinding` / `ConsistencyExemption` / 面板 / 落库全部可复用。

### 4.1 但两种「时机」不是同一个东西

| 时机 | 已有？ | 作者在场？ | 适合形态 |
|---|---|---|---|
| **生成前**（对话框预检） | ✅ 已有 | 在（正要点"生成"） | **硬停**：有 finding 就 `return`，当场改或豁免 |
| **生成后**（产出即检） | ❌ 无 | **不在**（批量架构生成，一次跑 5 章） | **不卡流程**，结果携带 findings；在**进入下一层前**设关卡 |

R2 要的是第二种，而它**不能照搬第一种的"当场卡住"** —— 批量生成时作者不在场，硬停只会产生半截产物。

## 5. Q3：检出之后的「修改时机」

**先讲一个本例特有的硬事实**：本例冲突是**源头对源头**的（世界观声明 `7:00—9:00` vs 大纲写「下午两点」），**不是**「新章 vs 前章」。⇒ **任何"重写第 1 章"的动作都治不了**：世界观那条规则还在，模型下次要么再违反、要么"圆回来"（写成"老陈记今天下午临时开门"）。**唯一根治 = 改一处源头。**

因此「修改时机」应分三种处理，按**冲突源位置**定，而不是按检出时机定：

| 处理 | 形态 | 评价 |
|---|---|---|
| **① 只报不改**（作者手改） | findings 随生成结果呈现，作者去编辑器改 | ✅ **推荐**。零副作用、零越权，与 preflight 既有语义（evidence 非禁令）一致 |
| **② 同轮回炉**（带冲突清单自动重生成一次） | 把 findings 塞回 prompt 再调一次该章 | ❌ **不建议**。成本翻倍、结果不可预期；模型倾向"圆回来"而非改对；本例还必须回改上游，回炉无效 |
| **③ 关卡阻断**（进入下一层前必须处理） | 大纲→蓝图、蓝图→正文 两个关卡处，未处理的 finding 要求"改"或"显式豁免" | ✅ **推荐**，且**复用现成豁免机制**（`ConsistencyExemption`：填 reason 即豁免，可撤销） |

**「修改时机」的具体答案**：

1. **检出时机**：大纲 / 蓝图**每章产出后立即**（§1.4 逐章生成，落点天然存在）。
2. **不打断生成**（避免半截产物），findings 挂在产出上。
3. **关卡**：作者要推进到下一层（写蓝图 / 写正文）时，若该章有未处理 finding ⇒ 复用 `ConsistencyPreflightPanel`，二选一：**去改** 或 **填理由豁免**。
4. **改哪里由「冲突源」决定**：finding 需带上"冲突源层级"（世界观 / 前章定稿 / 本章内部）。本例应标 **`源=世界观`** 并给出定位提示，否则作者会误以为改第 1 章就够了 —— **改了也没用**。
5. **绝不自动改**（沿用项目红线：不自动执行副作用）。

## 6. Q4：这算「设定问题」，框架该不该管？

**作者的直觉方向对，但界线要画准。** 关键证据：**框架自己早就为这个点立过契约。**

`world_building` 内置模板 `builtin-prompt-templates.ts:589-593` 原文：

> 用「**空间名：一句话定位 + 关键规则**」的格式列出；命名要固定、唯一，**后续情节与弧光结构将用同一名字引用它**。

要求 6：

> 第 4 维度的空间名一旦确定，就是**后续引用的唯一键**；不要为同一地点使用多个别名。

⇒ 框架**已经声明**：空间名是**跨层引用的稳定键**、且**带关键规则**。它与「角色名」「稳定事实（`stableFactKey`）」同级。

**先例**：`findBlueprintContinuityRisks` 现有那条规则（角色死亡终态 vs 蓝图仍排其出场）本质就是「**设定声明 vs 蓝图使用**」的一致性 —— 同一类事，只是主体是角色而不是空间。

### 6.1 界线（这条分界线与 AGL 被否的理由一致）

| | 归属 | 判据 |
|---|---|---|
| ✅ **框架该管** | **结构对结构**的一致性 | 键是否存在、键是否唯一、同一键的**同一属性**是否被赋了两个不同值 |
| ❌ **框架不该管** | **自然语言的含义** | 从「7:00—9:00 营业」推出「下午两点不该去买早饭」 |

**按这条线重审 §3 的方案 B**：B 现在的形态（正则解析钟点 + 区间比较）**正是"自然语言含义推断"，确实越界了** —— **作者的质疑成立**。而且它同时是**启发式**（抓钟点靠模式匹配），误报漏报都不可控 —— 误报会让作者对 warning 疲劳（上一轮审稿的教训正在于此）。

### 6.2 修正后的方案

**B 拆分两半**：

- **B-结构半**（不越界，可做）：只做**键对键**校验 —— 章节里引用的空间名是否等于世界观声明的**唯一键**（抓别名 / 自造地点）。不需要任何语义解析。
- **B-语义半**（越界，**不做**）：从自由文本关键规则里解析时段并做区间推断。

**「语义半」的正确归宿有两条，都不在框架的解析器里**：

- **A⁺（提示词层强化，成本 0，推荐本轮做）**：既然 `world_building` 模板已经要求写「关键规则」，**再加一条要求**：凡涉及时段 / 准入的关键规则，须写成**明确可判定的形式**（如 `07:00–09:00`），禁用「早上」「白天」这类模糊词；并在大纲 / 蓝图模板「要求」里加自检（§3 A 的方案）。**纯提示词、零解析、不越界。**
- **B′（结构化，中工程，**建议登记为 `keyEvents` 阶段 2/3 的同伴项**）**：让世界观第 4 维**额外产出一个结构化伴随字段**（如 `spaceRules: [{name, keyRule, timeWindow?}]`），框架只做**结构对结构**的比对。彻底不越界、判定确定 —— 但这是"把自由文本设定结构化"，**与 `keyEvents` 结构化是同一件事的不同面**（参见 `blueprint-key-events-structuring-design.md`），应合并规划，不宜零散开两次。

## 附：可复用判据（沉淀）

> **① 断言不是证据（承上轮）**：当上游材料对被生成 / 被审文本作出「可判定的具体约束」（序数、全称、时段、准入条件、数值区间、命名闭集）时，必须独立复核该约束是否被满足 —— 既不得采信材料里的断言本身，也不得以「材料里确实这么写了」代替「产出确实满足了」。

> **② 约束"在不在"与"会不会被执行"是两件事**：前者用 `ioCalls[].messages[].content` 取证（§1.2），后者只能靠显式化（A / A⁺）+ 可判定校验。

> **③ 框架的边界（本轮新增，回答 Q4）**：
> **框架该管「结构与结构之间的一致性」** —— 键是否存在、是否唯一、同一键的同一属性是否被赋了两个不同值；
> **框架不该管「自然语言的含义」** —— 从「7:00—9:00 营业」推出「下午两点不该去买早饭」。
> 判「某个校验能不能进框架」的**试金石**：**它需要框架"读懂设定"吗？** 需要 ⇒ 越界，应改为"让设定自己写清楚（提示词）"或"把设定结构化（B′）"，而不是让框架上解析器。
> （与 `global-guidance-scope-lint-design.md` 被否的理由同源 —— 作者原话「这是使用上的问题，框架就不兜底了」。区别在于：**框架自己已声明为"唯一键 + 关键规则"的东西，校验其引用一致性不算越界，是补上自己立的契约**。）
