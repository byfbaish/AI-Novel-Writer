## 0.0 ★ 必须先纠正：全局与项目**不是叠加，是覆盖**（决定整个方案形态）

作者的需求里有一个关键假设：

> 「比如说全局设置已经有了 AAAAA，本项目设置是 AAAB，那么经过 AI 优化之后，
> 要让用户得到一个优化前 AAAB 和优化后 B 的 diff，并且告诉他实际效果将是 **AAAAAB**」

**这个「AAAAAB」的前提不成立。** 我核实了代码，证据链完整：

1. `prompt-catalog.ts:239-251`（`peek`）与 `:125-146`（`resolve`）的解析顺序是**短路返回**：
   ```ts
   const project = this.projectPromptsFor(projectSession)?.get(localized)
   if (project) return { template: project, source: 'project' }   // ← 命中即返回，不再往下
   const global = this.globalPrompts.get(localized)
   if (global) return { template: global, source: 'global' }      // ← 只有项目没有时才用全局
   const builtin = this.builtins.get(key)
   ```
2. `prompt-templates.ts:33` 的注释也写明了：「三级优先级：**当前 session 项目级 > 全局级 > 内置**」。
3. `prompt-catalog.test.ts:95-103` 有既有测试固化这个语义：项目级存在时，
   `resolve` 返回 `{ template: { content: 'project prompt' }, source: 'project' }` —— **全局那份被完全丢弃**。

→ **实际效果不是 `AAAAA + B`，而是 `B`。** 全局那份 `AAAAA` **一个字都不会进 prompt**。

### 这个纠正对方案的三点影响

| # | 影响 |
|---|---|
| **1** | **「实际效果将是 AAAAAB」这句话本身就是当前的 bug 级误解**，用户按此理解会严重误判自己的配置。→ UI **必须**显示"当前生效的完整文本"，而不是让用户心算。 |
| **2** | 作者设想的 diff（`AAAB` → `B`）**语义要改**：不是"项目里去掉与全局重复的部分"，而是**「项目决定是否接管」**。 |
| **3** | 「建议优化后的结果存为项目级，或者将实际效果存为全局级」——这个建议**有意义**，但理由和作者想的不同（见 §3.3）。 |

> ⚠️ **这一条如果不纠正，P4 会做出一个"帮用户合并两份本该覆盖的配置"的功能，
> 反而把用户的全局设置静默吞掉。**

## 0.1 作者真实痛点：**重复**，而且只有一处会重复

作者说：

> 「可能最需要优化的应该是用户级 Prompt 设定，而这个 Prompt 设定又分全局和项目，
> **这是最容易重复的**；至于大纲蓝图什么的，我觉得会重复的应该是比较少的。」

**前半句对，后半句也对，但"重复"的机制和作者设想的不同。** 我核实了真实结构：

### 会重复的唯一来源：`taskGuidance` 与 `systemRole` 被用户**在两级各写一遍**

- 全局可以存一份 `taskGuidance`（「补充创作指导」）；
- 项目可以存一份 `taskGuidance`；
- **但两者不叠加** → 用户若在项目里又写一遍，**全局那份直接失效**。

→ 所以真实存在的"重复"**不是**「两份配置同时进 prompt 导致重复」（那不会发生），
而是 **「用户在两处写了相近内容，导致语义重复 + 全局那份被浪费」**。

### 而 `content`（模板正文）根本不由用户控制

`PromptSettings.tsx:440` 的注释写得很清楚：

> 「用户层只追加创作指导；内置任务与输出合同保持隐藏且不可改。」

界面上用户只能编辑两个字段（`PromptSettings.tsx:421-465`）：
- **创作角色定位**（`systemRole`）
- **补充创作指导**（`taskGuidance`）

→ **P4 的靶子因此收窄为这两个字段**（加上跨 key 的重复，见 §1.2）。
这**大大降低了 P4 的规模** —— 不需要碰模板正文，不需要碰输出合同。

### 关于「大纲蓝图重复少」：作者判断正确，但有例外

`synopsis` / `chapter_blueprint` 等模板的 `taskGuidance` 同样是两级可编辑的，
所以**结构上同样存在重复可能**，只是作者实际没在两处写而已。
→ 设计上**不排除**它们（统一按同一套机制处理），但**优先做 `assistant_writing_identity`
与 `next_chapter_draft` 这两个高频项**。

## 2. 方案设计

### 2.1 核心原则：**AI 只提建议，作者点确认才落盘**（P4 硬性要求）

backlog `:192-195`（P4 段）明确：

> 「流程必须是 **AI 建议 → 人工确认 → 替换配置** 三段式。
> **不得**让 AI 直接改配置 —— 作者必须逐条确认。」

→ 与 ADR 0020 一致。**AI 绝不直接写 `~/.vela/prompts/`。**

### 2.2 单模板 AI 优化按钮（作者需求的主体）

在每个展开的模板编辑区加一个 **「AI 优化」** 按钮。点击后：

```
输入：当前生效的完整文本（systemRole + taskGuidance）
      + 全局那份（若与当前生效的不同）
      + 内置默认（作为"写作规范基线"）
       ↓
AI 产出：优化后的 systemRole / taskGuidance（一份，不是两份）
       ↓
展示：diff（优化前 vs 优化后）+ 变化说明
       ↓
作者确认 → 选"保存到全局"或"保存到项目" → 走既有 saveCustomPrompt 路径
```

### 2.3 ★「实际效果预览」——这是本方案最有价值的一块（对应 §0.0 的纠正）

因为**项目覆盖全局**，作者必须能直接看到"**现在实际发给模型的是什么**"，
而不是自己脑补叠加。所以界面要有一个**「当前实际生效」**折叠区：

```
当前实际生效（来自：项目）
────────────────────────
【创作角色定位】
你是一位经验丰富……

【补充创作指导】
{{mode_instruction}}
理解项目架构、人物、情节……

⚠️ 全局配置存在，但被本项目覆盖，未生效。
    [查看全局那份]  [删除项目覆盖，改用全局]
```

**这一块单独就解决了 §0.0 的误解**——比 AI 优化按钮更重要。
**建议 P4 的第一件事就是做它**（不需要 AI，纯展示，零风险）。

### 2.4 需求里的 "diff"：正确形态

作者要「优化前 AAAB 和优化后 B 的 diff」。
按 §0.0 的纠正，正确的 diff 有两层：

| 层 | 比什么 | 作用 |
|---|---|---|
| **D1 · 优化前 vs 优化后** | 当前生效文本 → AI 优化后文本 | 让作者看清 AI 改了什么（**必须**） |
| **D2 · 全局 vs 项目** | 两份现存配置的差异 | 让作者知道"项目这份是怎么覆盖全局的"（**P4 的重复问题就在这**） |

**D2 是发现"重复"的地方**：若 D2 显示两份高度相似，
那就是作者说的"最容易重复"的场景 → AI 可以提示「本项目配置与全局配置高度重叠，
建议删除项目覆盖改用全局」或「建议把合并后的结果存为全局」。

### 2.5 作者建议的两种落盘方式（§0.0 影响 3 的展开）

作者说：*「建议优化后的结果存为项目级，或者将实际效果存为全局级」*。
这个建议**是合理的**，但需要给出**明确的判断规则**，否则用户会选错：

| 情况 | 建议存哪 | 理由 |
|---|---|---|
| 优化只针对**这本书**（如本书特有的文风） | **项目级** | 不污染其他小说 |
| 优化是**通用改进**（如"通过行动体现冲突"） | **全局级** | 所有小说受益 |
| **项目配置与全局高度重复** | **删项目覆盖**，让全局生效 | 消除重复（这是 P4 的核心收益） |
| 项目仅想**微调**全局 | 提示：当前是**覆盖**，微调会丢全局内容 → 建议**合并后存全局** | 避免静默丢失 |

→ **AI 优化结果面板要给出"建议存哪"的推荐**（可解释），但**最终由作者点**。

### 2.6 「不用这个功能就堆叠」——这条要澄清

作者说：*「那用户也可以不使用这个功能，那就堆叠呗。」*

**当前架构下不存在"堆叠"这个状态** —— 不合并就是**覆盖**（§0.0）。
所以这句话要么理解为"用户不点优化按钮，就维持现状（覆盖）"，
要么理解为"希望增加一个真正的堆叠模式"。

→ **需要作者确认**（见 §6 决策 3）。若真要堆叠，那是一个**新的层级语义**，
会动 `prompt-catalog.ts` 的解析（**风险较高，且与 P3 的头/尾分层有交互**），**建议单独立项，不塞进 P4**。

### 2.7 显著位置的推荐提示（作者最后一条需求）

> 「在功能显著的地方标注出建议使用 AI 优化 Prompt 设置」

建议落点：
- **设置侧边栏「提示词模板」项**：有可优化内容时加一个角标/圆点
  （参照 P2 已有的 `autoPromptBlueprintCharacterSync` 角标模式）。
- **模板列表每一项**：当检测到"全局与项目重复"时，该项显示一个可点击的提示条。
- **设置面板顶部**：「提示」说明区（`PromptSettings.tsx:159-168`）追加一行推荐语。

## 3. 风险与边界

### 3.1 ADR 0020
作者原文是权威约束。AI 优化只能**改措辞/组织**，**不得削弱或删除作者要求**
（backlog `:230-231`：*「不得吞掉作者原意；整合只能合并表述，不能削弱或删除要求」*）。

→ **落地为验收**：优化前后必须能证明"作者要求的条目数不减少"（§5.2）。

### 3.2 不得改 `content` / `systemSuffix`
用户层只管 `systemRole` + `taskGuidance`（`PromptSettings.tsx:440`）。
`systemSuffix` 由内置模板提供且**不受用户自定义影响**（`render-prompt.ts:56-63`）。
→ **P4 绝不碰它们。**

### 3.3 中英双语独立
覆盖按 `writingLanguage` 分文件（`prompt-catalog.ts:434`）。
→ AI 优化也必须按当前编辑语言走，**不得跨语言复用结果**。

### 3.4 覆盖语义不得被 P4 改变
P4 **只做"建议 + 确认 + 保存"**，**不改** `resolve` 的优先级。
（若作者要"堆叠"，那单独立项，见 §2.6。）

### 3.5 与 P3 的交互
P3 的头（`globalGuidance` / `writingStyle` / `coreOutline`）**不是** prompt 模板，
两者**不重叠**（已核实：`globalGuidance` 是 `novel_config` 的字段，
见 `propose-novel-config.tool.ts:9/83` 与 `builtin-prompt-templates.ts:322`，
与 `PromptSettings` 里编辑的 `systemRole`/`taskGuidance` 是**两套东西**）。

但 P3 §0.3 已指出：**P4 改配置会让 P3 的 `headHash` 失效** → 这正是 P4 先做的理由。

⚠️ **一个易混点（记下来避免后续搞错）**：P4 的"配置整合"实际有**两个战场**：
1. **Prompt 模板层**（本稿主体）：`systemRole` / `taskGuidance` 的全局↔项目重复。
2. **小说配置层**：`novel_config` 里 `coreOutline` ↔ `premise` ↔ `globalGuidance` 的语义重叠
   （backlog `:204-206` 举的例子）。
   **作者本次明确指的是第 1 个**（"最需要优化的应该是用户级 Prompt 设定……这是最容易重复的"）。
   **第 2 个正是 P3 §0.3 说"交给 P4"的那部分** → **属于 P4 的后续范围，本稿不含**，
   但它与 P3 有次序依赖，需在 P4 收尾时一并处理。

## 4. 实施阶段

### Phase 0 · 「当前实际生效」展示（**零 AI、零风险、建议先做**）
- 展开区加"当前实际生效"折叠块（§2.3），显示生效来源 + 全文 + 被覆盖提示。
- **收益**：立刻解决 §0.0 的误解（用户不再以为自己看到的是叠加结果）。
- **验收**：项目级存在时，显示 `source: 'project'` 且明确标注"全局未生效"。

### Phase 1 · 重复检测（**零 AI、只读**）
- 对每个模板比较全局 vs 项目的 `systemRole` / `taskGuidance`，计算相似度。
- 超过阈值 → 列表项显示提示条（§2.7）。
- **注意**：这一层的"相似度"**可以先用确定性手段**（P1 的指纹 + 简单 token 重合度），
  **不必上 AI** —— 真正的重复往往是逐字级的（用户复制粘贴改几个字）。
- **验收**：构造"全局 = 项目 + 改 3 个字"的用例，必须检出。

### Phase 2 · AI 优化按钮（**需要 AI，作者确认后落盘**）
- 按钮 + AI 调用 + diff 展示（D1/D2）+ "建议存哪"推荐 + 确认落盘。
- **验收**：见 §5.2。

### Phase 3 · 显著位置推荐（§2.7）

> **Phase 0 / 1 不需要 AI，也不改任何数据** —— 可以**先单独交付**，
> 立刻解决作者最关心的"重复"与"误解"两个问题。

## 5. 验收

### 5.1 通用
1. **AI 不落盘**：点击 AI 优化**不产生任何写操作**（断言磁盘/存储未变）。
2. **确认才落盘**：只有作者点"保存到全局/项目"才写（复用既有路径）。
3. **覆盖语义不变**：`prompt-catalog` 的优先级测试**全部保持通过**（§3.4）。
4. **双语隔离**：中文优化结果不得出现在英文文件里（§3.3）。
5. **回归**：`npx vitest run <相关文件>` 全绿 → `tsc --noEmit` EXIT=0 →
   全量失败集与基线（18 个 ABI `NODE_MODULE_VERSION 145 vs 127`）逐条 diff 一致。

### 5.2 AI 优化的专项验收（ADR 0020）
1. **不削弱**：优化前后，作者的**要求条目数不减少**（可断言条数）。
2. **不吞并**：不得把两条独立要求合并成一条含糊表述（需人工抽检 + 用例）。
3. **可回滚**：优化结果未保存前，原配置**完全不变**；保存后可用"恢复默认"退回（`handleReset:320-352`）。
4. **可对比**：diff 必须展示**优化前全文**与**优化后全文**（不能只给摘要）。

### 5.3 展示的验收（§0.0 纠正）
1. 项目级存在时，界面**必须**出现"全局未生效"的明确提示。
2. "当前实际生效"显示的文本，**逐字节等于** `getPromptTemplate(...)` 的返回值。

## 7. 工作量

| Phase | 是否用 AI | 风险 | 规模 |
|---|---|---|---|
| Phase 0 · 实际生效展示 | 否 | **极低** | 小 |
| Phase 1 · 重复检测 | 否 | **低** | 小–中 |
| Phase 2 · AI 优化按钮 | 是 | 中（ADR 0020） | 中 |

**不必碰**：`prompt-catalog.ts` 的解析逻辑、`builtin-prompt-templates.ts` 的 `content`/`systemSuffix`、
`render-prompt.ts`、`chapter-materials.ts`、`generate-draft.command.ts`。
