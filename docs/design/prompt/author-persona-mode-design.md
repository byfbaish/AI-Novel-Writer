# 作者人格（Author Persona）：以性格驱动的生成模式 · 设计提案

> 状态：待裁定（2026-10-28）· 提案：本稿只出方案与分叉，未编码
> 日期：2026-10-28 · 分支 `exp/resource-ledger`
>
> 缘起：作者实测发现——同一套六选一（隐 / 迂 / 借 / 刚 / 演 / 换），用现有 system prompt 时模型倾向于选保守项；
> 换成"作者人物卡"之后，模型在大纲阶段第一章就选了「刚」。作者称之为**以性格驱动的 AI 文本生成模式**，并观察到 AI 味下降。
>
> 这份提案要回答三件事：**为什么现在装不下、该加什么、加了以后怎么不失控。**

## 1. 先把现象归因（这一步不能跳）

同样的六选一，改一处输入就改变了决策倾向，说明**模型读到的那句话在"决策层"而不在"表达层"**。
现在的四个槽，语义各不相同：

| 槽 | 模板原文 | 管什么 | 能不能改决策 |
|---|---|---|---|
| `writing_style`（文风） | "文风描述（可选）" | 表达方式 | **不能**——模板里有明文边界 |
| `global_guidance`（全局写作要求） | 生成自 `generate_global_config` | 跨书稳定的硬规则 | **能** |
| `user_guidance`（作者指导） | "**作者本章微操指导**（可选）" | 单章微操 | 能，但只作用于当前章 |
| `reference_works`（参考作品） | "只借鉴调性与节奏，不是必须兑现的作者事实" | 调性 | 弱 |

`writing_style` 槽后面紧跟这一段（正文模板里出现三次，逐字相同）：

> 【文风适用边界】
> - 文风**仅用于选择表达方式，不是新增事实或事件要求**；无需逐条强行兑现。
> - 作者明确事实与指导、实际前文、本章关键因果和本章篇幅优先。

**这段是明文降权。** 任何写进文风槽的"作者人设"，读到这里都被降格成"语气偏好"。
所以"用现有 system prompt 六选一偏保守"不是模型的问题——是它被告知**这个槽不产生决策**。

反过来，"作者人物卡"当时一定落在了别的槽（或别的位置）。三条候选路径，用一次 trace 就能判定：

| 候选 | 怎么验证 | 判据 |
|---|---|---|
| 写进了 `global_guidance` | 看 trace 里【全局写作要求】段 | 人物卡原文出现在该段 |
| 写进了项目"核心设定 / 开头" | 看 trace 里 `novel_config` | 出现在 JSON 的某个字段 |
| 作为新模板/新槽整段注入 | 看 trace 的 system 全文 | 有一段既不在上面任何槽里 |

**没验证之前，不能假定"人物卡有效"。** 因为那次对比同时改了多处，与六选一改版混在一起，
归因风险和 2026-10-28 记的那条一样（网页端对比无法归因到单一变量）。

## 2. 缺的是哪一层：四个概念必须分开

现在的体系里，作者的控制手段是三档，缺了中间那一档：

| 层 | 回答的问题 | 稳定性 | 现状态 |
|---|---|---|---|
| **文风** | 怎么说话（句子、节奏、用词） | 跨书 | ✅ 有槽 `writing_style`（但被降权） |
| **作者人格** | **怎么判断、敢不敢、先想什么** | 跨书，可换 | ❌ **缺** |
| **全局写作要求** | 这本书必须兑现什么 | 单本 | ✅ 有槽 `global_guidance` |
| **本章微操** | 这一章要什么 | 单章 | ✅ 有槽 `user_guidance` |

**"作者人格"回答的不是"怎么写"，是"这个人会怎么选"。**

一个具体例子，同一段大纲材料：

- 文风写"冷峻、短句、少修辞" → 他会**用更少的字**做同一个决定。
- 人格写"不信制度、宁可先动手再补手续" → 他会**做另一个决定**（选「刚」而不是「隐」）。

现有三档全都答不了第二个问题。这就是六选一偏保守的真实原因：**模型没有"这个作者是谁"的信息，只能按最安全的模板默认值选。**

## 3. 为什么这件事会降低 AI 味（机制解释）

AI 味的常见成因之一是**决策分布过于居中**：每一处该做选择的地方，模型都选了"最不容易出错"的那项。
读起来就"没有作者"，因为真人作者的标志恰恰是**有偏好的偏科**。

人格卡的作用不是"给文风加形容词"，而是**给模型一个稳定的偏置**。它会带来三个副作用，都是正向的：

1. **同质选择消失**：同一批章节不再全是「隐」。
2. **前后一致**：第 3 章和第 30 章的选择倾向同源，读者能感到"这是同一个人写的"。
3. **可解释**：某个决定看着怪，但能追到人格卡上某一条——这是可控的怪，不是跑偏。

## 4. 数据模型

**关键约束：作者人格卡与故事角色卡必须是两张表，不能混。**
故事角色卡有 `role/gender/age/appearance/relationships`，作者人格卡有 `决策倾向/底线/忌讳`。
混表的直接后果是角色提议面板会把作者人格当成"配角"塞进角色图谱。

建议字段（都可判定，不写抽象词）：

```ts
interface AuthorPersona {
  id: string
  name: string                 // 「较真的账房」「不肯低头的赌徒」
  oneLine: string              // 一句话：这个人怎么看这个世界
  decisionBias: PersonaBias[]  // ★ 核心：六选一的偏好，不是全部，是"更常选哪几个"
  neverDoes: string[]          // 底线：绝不做的动作（如"绝不当众示弱"）
  alwaysFirst: string[]        // 第一反应：遇事先干什么（如"先算清代价再开口"）
  voiceNotes: string           // 只写与决策相关的语言习惯，不写修辞
  fitGenres: string[]          // 适用题材；空 = 通用
  excludedBy: string[]         // 与哪类人格互斥（防止抽卡抽到两张打架的）
}
```

`decisionBias` 建议直接引用六选一的枚举，而不是自由文本：

```ts
interface PersonaBias {
  choice: '隐' | '迂' | '借' | '刚' | '演' | '换'
  weight: 'high' | 'normal' | 'rare'   // 更常选 / 一般 / 极少
  when: string                          // 什么条件下会这么选（一句）
}
```

这一条是可判定性的来源：**"高权重项"必须在生成结果里出现得更多**，否则卡片是装饰。

## 5. 三处入口

按实际使用频率排：

| 位置 | 做什么 | 为什么放这 |
|---|---|---|
| **设置 → 作者人格库** | 增删改查、导入导出、抽卡、收藏 | 跨项目复用，属于用户级资产（可进 `.vela-pack`） |
| **项目配置 → 本书使用的人格** | 选一张 / 不选 / 临时覆写 | 同一作者写不同题材会换人格（写玄幻用"赌徒"，写历史用"考据癖"） |
| **提示词设置 → 人格片段预览** | 看这张卡注入后长什么样，可手动改 | 与现有提示词编辑习惯一致 |

入口设计有一个取舍要你定（见 §9 分叉一）：人格是**用户级资产**还是**项目级配置**。
前者可跨书复用、能进设置包；后者能跟着项目一起导出。两者也可以同时支持（用户级定义 + 项目级引用）。

## 6. 抽卡（生成候补人格）

用户提到"利用我们的模型接口抽卡，喜欢的保存下来"。这条路可行，且实现成本低于预期——
现有的结构化生成链（角色提议、世界观五维）已经具备"一次出 N 个候选 + 用户勾选"的完整形态，可复用。

抽卡输入建议只用三样，不要更多：

1. **题材 + 平台**（决定这个人要面对什么样的世界）
2. **一句话故事前提**（决定他会为什么而战）
3. **数量**（3–5 张）

输出必须走结构化契约（JSON schema），原因很实际：**自由文本的卡片没法做 §4 里那个"高权重项必须更常出现"的校验**。
抽卡的用处是"给我几个我没想到的性格"，不是"给我一段好文案"。

一条反模式要提前写进规格：**不要让人格卡写"文笔优美""语言有张力"这类词。**
那属于文风槽，写进人格卡会被当成决策依据，产生噪声。

## 7. 注入与优先级

这是整份提案里最要紧的一节。人格卡**必须不受文风边界降权**，否则加了等于没加。

建议的优先级链（从高到低）：

```
作者明确事实与本章指导  >  结构事实（大纲/蓝图/前文）  >  全局写作要求  >  作者人格  >  文风
```

两条配套约束：

1. **人格只决定"在可选路径中选哪条"，不决定"有哪些路径"。** 路径由大纲给。这条防止人格卡越权改剧情。
2. **人格不得覆盖全局写作要求的硬指标。** 人格说"他不爱数数"，但全局要求写"灵石块数必须写准"——后者赢。
   这与现有 `prompt-clause-admission.md` 的三问一致：**限定词够不够**。

落点建议（三选一，见 §9 分叉二）：
- 新增独立槽 `author_persona`，插在 system 段、全局写作要求之后；
- 复用 `global_guidance`，把"人格"写成其中一段（改动最小，但会和自动生成的全局要求打架）；
- 作为 `writing_style` 的前置块，但**必须显式声明不受【文风适用边界】约束**（改动小，语义最脏）。

## 8. 可判定的验收

这份提案如果落地，必须能回答"有没有用"，否则又是一轮感觉对感觉。三条都可机检或可对比：

| # | 验收项 | 怎么测 |
|---|---|---|
| 1 | 人格卡真的改变了决策分布 | 同项目、同章、同材料，跑 3 次不带人格 / 3 次带人格，统计六选一分布。**高权重项占比应显著上升** |
| 2 | 没有越权 | 检查生成结果有没有出现"人格卡里没写、大纲里也没有"的新事件（应有 0 处） |
| 3 | 不是靠禁用项起作用 | 把 `neverDoes` 清空重跑一遍。若效果不变，说明起作用的是 `decisionBias`；若塌了，说明人格卡本质是"负面清单"，那要改权重设计 |

第 3 条是关键——它区分"性格驱动"和"禁令驱动"。两者的效果看起来一样，但**禁令驱动会越写越僵**（和现在"不许清零"那条一样的毛病）。

## 9. 三个分叉，需要你裁定

**分叉一：人格卡的归属。**
（a）用户级资产，跨书复用，可进 `.vela-pack`；（b）项目级配置，跟项目一起走；
（c）两者都支持：用户级定义 + 项目级引用（最灵活，但要处理"引用被删"的悬空）。

**分叉二：注入位置。**
（a）新增独立槽 `author_persona`（最干净，要动模板变量清单与中英两份）；
（b）复用 `global_guidance`（最省事，但与自动生成的全局要求争夺同一段）；
（c）挂在文风前并声明不受降权（语义最脏，但改动最小）。

**分叉三：先验证还是先实现。**
现在的困境是——作者只观察到一个现象，但**还没确认是哪个槽起的作用**。
（a）先用现有槽手写一张人格卡跑一轮，拿到 §8 的第 1 项读数，再决定要不要建库；
（b）直接按提案建最小版本（一张卡 + 一个槽 + 一个入口），用实现去验证。

我倾向 (a)：这条读数很便宜（不用改代码），而它能决定后面全部设计——如果发现真正起作用的是"负面清单"，
那整个 `decisionBias` 的权重模型都要重写。

## 10. 明确不做的

- **不做"人格卡自动优化"**（跑几轮自己调权重）。那会让作者的意图被系统反向塑造。
- **不做人格卡与文风的自动绑定**（选人格就自动换文风）。两件事分开，才可能"同一个人格写两种调子"。
- **不把人格卡塞进架构链的每一层。** 只进"做选择"的那几层（大纲 / 卷单元 / 正文），
  不进"抽取事实"的那几层（角色图谱 / 世界观）——后者要求客观，掺人格会污染设定。
