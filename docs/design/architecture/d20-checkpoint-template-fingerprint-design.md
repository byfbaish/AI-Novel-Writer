## 0. 一句话结论

**指纹是 4 元的（源事实 / 步骤指导 / 批次范围 / 生成模板），报错只认 1 元（源事实），而且是断言式的认。**

判定处拿到的信息只有一个布尔值「不等」——组合哈希是单向的，**比对的那一刻已经不可能知道是哪一项变了**。文案却写了「项目源事实自上次生成后已变化」，`:3135` 还补了一句「（故事前提/角色/世界观/总章数等）」，把读者的视线钉在恰恰没变的字段上。

作者原话即本条的验收标准：

> 「模板变化不应该影响到原事实变更，这完全是错误的说法。开发者倒是可以调查到真实原因，但对于使用者来说，抠破脑袋都找不到这个真实的原因，只会以为自己的写作材料变化了，但其实根本没有变化。」

**修法不是改文案，是让判定侧有归因能力**（§4）——文案只是这个能力的出口。

## 2. 关键更正：实际只有两项会漂移

这一节是**复核推翻我原稿的一处实质错误**，它直接决定修法规模（§4）。

### 2.1 原稿的说法（错）

原稿写「4 项里任一项变化」，并给了 `['guidance']` / `['range']` 两支报文。**这两支是不可达分支。**

### 2.2 为什么 ②③ 恒等

两处判定都是**拿检查点自己存的 ②③ 去重算检查点自己的哈希**：

| 判定点 | ② 从哪来 | ③ 从哪来 |
|---|---|---|
| 续写 `:3127-3133` | `effectiveStepGuidance = partial.synopsis_step_guidance`（`:3126`） | `partial.synopsis_range` → `from/to`（`:3116-3117`） |
| 续批 `:3234-3240` | `checkpointStepGuidance = partial.synopsis_step_guidance`（`:3233`） | `partial.synopsis_range`（`:3237`） |

写入侧写进去的也是同一批值（`:3752`/`:3915`/`:4104` 的 guidance，`:3730`/`:3912`/`:4100` 的 range）。**于是 ②③ 在比对时必然相等**——除非有人手改 `partial_arch.json`。

⇒ **能漂的只有 ① 源事实 和 ④ 模板。** 而且这个结论有个副产品：**只要 12 个源事实字段没变，指纹不等就只能是模板**（D17 复验的推理因此成立，不依赖那两个具体哈希）。

## 4. 修法

### 4.1 只存两个短哈希：源事实 + 模板

**为什么不是 4 项分项**（原稿方案，复核推翻）：②③ 恒等（§2.2），存它们只会换来两个永不可达的报错分支。

**为什么也不能只存 1 个模板哈希**（复核建议的进一步收紧）：裁定 A 要求「模板变化 ⇒ 放行」，但**只存模板哈希无法证明源事实没同时变**——源事实真的变了却照样放行，正是这套指纹存在要防的事故。所以还要一份「源事实单独哈希」。

```ts
// 与 synopsisInputsFingerprint 并列；combined 必须与现函数返回值逐字相等
export function synopsisInputFingerprintParts(
  expected, stepGuidance, range, template,
): { source: string; template: string; combined: string }
```

- `source` = `synopsisFactsFingerprint([JSON.stringify(sourceInputs)])`，`sourceInputs` 就是 `:1130-1143` 那 11 个字段（**字段集合只能有一份**，不能复制字面量）
- `template` = `synopsisFactsFingerprint([JSON.stringify(template)])`
- `combined` = 照旧 4 段拼（`:1144-1149`）
- **实现方式**：让现函数变成 `return synopsisInputFingerprintParts(...).combined`，签名与返回值都不动（`plot-outline-batch.command.test.ts:72` 复用，那份测试明令"不得复写算法"）

⚠️ **最高回归风险点**：**`combined` 必须用原始 4 段拼哈希，不能写成 `synopsisFactsFingerprint([source, template])` 之类**。后者会让**全部存量检查点一次失效**——正是 §7.1 要避免的故障。

### 4.2 两个名单必须同步加字段（原稿漏了，会打坏回滚）

| 名单 | 位置 | 不加会怎样 |
|---|---|---|
| `SYNOPSIS_CHECKPOINT_FIELDS` | `architecture.command.ts:192-204`，驱动 `sameSynopsisCheckpoint`（`:206-213`）/ `restoreSynopsisCheckpoint`（`:215-224`） | **DB commit 失败或 cancel 时** `rollbackSynopsisCheckpoint`（`:3994-3998`）会把 `synopsis_facts_fingerprint` 恢复成旧值，而新字段留在**新值**上 ⇒ 下次续批 combined 不等、`source`/`template` 全等 ⇒ **归因分支没有这一支**，只能报"未知" |
| `SYNOPSIS_CHECKPOINT_KEYS` | `src/services/workflows/synopsis-unit-launch.ts:179-193`，驱动 `resetSynopsisCheckpoint` 与 `arch-step-checkpoint.ts` 的**级联清空** | 重置检查点 / 清空前提或世界观后，新字段变 orphan 残留 |

### 4.3 三处写入点（标签按复核更正）

| 位置 | 归属 | 用哪一份值 |
|---|---|---|
| `:3750` | **完成落盘** | **`completedFingerprint`（`:3645` 用回填后的实际范围算的）**，不是 `:3273` 的请求期值 |
| `:3916` | **逐章导航落盘**（`executeChapterOutline` `:3851` → `saveNavigation` `:3908`） | `:3907` 的 `factsFingerprint` |
| `:4102` | **中断落盘**（`persistInterruptedSynopsis` `:4081`） | 同函数内的 `factsFingerprint` |

> `:3750` 那条是原稿漏掉的第二个坑：`synopsis-unit-batch.command.test.ts:223-252` 就是在防"请求期范围 vs 实际范围"混用。用错了会让单元批第二批被判成范围漂移。

### 4.4 判定与报文（按 `drift` 出）

判定侧（`:3133` 续写 / `:3240` 续批）先比 `combined`，不等时再比两项分项：

| 分项结果 | 报文 | 拦不拦 |
|---|---|---|
| `source` 变 | **现文案一字不改**——这时候它是对的 | 拦 |
| `source` 未变、`template` 变 | 「大纲**生成模板**自上次生成后已变化（源事实、步骤指导、批次范围均未变）。已写的 N 章大纲仍然有效；后续章节会按**新模板**的格式生成。」 | **放行**（裁定 A） |
| 两项都变 | 「源事实与生成模板均有变化：…」 | 拦（源事实变了） |
| 都不变但 combined 不等 | 「输入指纹不匹配，但源事实与模板均未变化（检查点可能被外部修改过）。请从第 1 章重新生成。」 | 拦，且**不说谎** |
| 旧检查点（无新字段） | 「这个检查点写于旧版本，无法核对输入是否变化；已按继续处理。如果发现新生成的大纲与当前设定不符，请手动重来。」 | **放行**（裁定 2，§8.1）+ 必须显示这条提示 |

### 4.5 顺带要改的 4 处复述（§3.1）

`ArchitectureConfirmDialog.tsx:792` 是用户可见的那一处，**且它预告的是 `source` 变这一支**——改写后应说「这样生成会提示源事实已变化」，不再逐字引用报文全文（引用全文的文案一定会再次过期）。另外三处注释同步。

### 4.6 提案（**已裁：做，作 D20b 单开一张卡，排在 D20 本体之后**）：模板段从「整对象」收窄到「影响渲染的字段」

作者 2026-11-05 21:24 追问「粒度可以再精细一点吗？世界观相关联的都是有独立的 Prompt 吧」。分两条轴答。

#### 轴 A：按 prompt 分 —— **今天已经是分开的，没有油水**

世界观链有 **3 份独立 prompt**：`world_building`（生成）/ `world_building_self_review`（自审）/ `world_building_resource_extract`（资源抽取）。但**只有 `world_building` 那一份进指纹**：

| prompt key | 调用点 | 进指纹吗 |
|---|---|---|
| `world_building` | `:2286` 生成 · `:2449` 候选保存后重算 | ✅ 进 |
| `world_building_self_review` | `:2620` | ❌ 不进。它随生成一起跑，findings 引用世界观原文，失效靠**正文被清空时级联清**（`arch-step-checkpoint.ts:38-42`） |
| `world_building_resource_extract` | `:2707` | ❌ 不进。同上（候选的 `quote`/`anchorQuote` 是落库依据，正文没了就命中不了） |

⇒ 「换一份别的 prompt 会误伤世界观候选」这个问题今天不存在。这条轴不用动。

#### 轴 B：按字段分 —— **这里才是真油水，而且今天是两个方向的错**

一份 `PromptTemplate`（`builtin-prompt-templates.ts:20-46`）有 10 个字段，但**模型实际看到的只由 3 段决定**：

| 字段 | 影响渲染吗 | 依据 |
|---|---|---|
| `content` | ✅ 主正文 | `render-prompt.ts:54-57` |
| `taskGuidance` | ✅ 作者补充指导，会拼进 prompt | `render-prompt.ts:32-46` · `prompt-builder.ts:82-107` |
| `systemRole` | ✅ system message | `builtin-prompt-templates.ts:189-203` |
| `systemSuffix` | ⚠️ **渲染时始终取内置那份**，覆盖版上的不算 | `render-prompt.ts:62-65` 明写「始终从内置模板获取，不受用户自定义影响」 |
| `name` / `description` | ❌ 只给人看 | 设置页显示用 |
| `variables` | ❌ 是「变量名 → 说明」字典；渲染用的是**调用方传进去的真值** | `render-prompt.ts:55` 遍历的是参数 `variables`，不是 `template.variables` |
| `requiredContextVariables` | ⚠️ 影响 builder 是否追加缺失上下文（半渲染） | `prompt-builder.ts` |
| `builtinRevision` | ❌ **纯记账**：记录"这份覆盖基于哪个内置版本" | `prompt-builtin-revision.ts:1-19`；它自己的摘要算法明确排除 `key`/`writingLanguage`/`systemSuffix`/`builtinRevision`（`:25`），却**包含** `name`/`description`/`variables` |
| `key` / `writingLanguage` | ❌ 身份与语言标记 | — |

**于是今天有两个方向的错：**

| 错的方向 | 具体 | 后果 |
|---|---|---|
| **该排除的没排除（过度失效）** | `name` / `description` / `variables` 说明串 / `builtinRevision` 全在 `JSON.stringify(template)` 里 | 见下面的触发路径：改一句「用途说明」或只是**点一次保存**，旧检查点就续不上，还被告知"你的写作材料变了" |
| **该追踪的漏了（漏判）** | 保存覆盖时 `delete template.systemSuffix`（`PromptSettings.tsx:373`/`:395`）⇒ 覆盖版 `systemSuffix` 为 `undefined` ⇒ 内置输出合同更新时，**有覆盖的项目指纹不变**（`builtinRevision` 又刻意排除了 `systemSuffix`），但渲染结果变了 | 输出合同悄悄换了，没有任何提示 |

**这些记账字段到底什么时候真会变（两种生效路径不同，必须分开说）**：

| 项目状态 | 模板从哪来 | 记账字段什么时候变 |
|---|---|---|
| **无覆盖**（走内置） | `getBuiltinPromptTemplate(key, language)`（`prompt-templates.ts:72-73`） | **跟着 app 版本变**。升级后内置的 `name`/`description`/`variables` 说明哪怕只改了一个字，指纹就变 ⇒ 旧检查点失效 |
| **有覆盖**（全局或项目） | 覆盖文件（`resolved.template`） | **保存那一刻重新冻结**：落盘的是「当前内置模板 + 作者改过的 `systemRole`/`taskGuidance`」，`builtinRevision` 也刷新成当时的内置摘要（`prompt-builtin-revision.ts:1-19`）。⇒ **作者进设置页什么都没改、只是点了一次「保存自定义」，若内置自上次保存后变过，指纹就变** |

> 一段必须写准的话：**收窄救不了 D17 那个具体案例。** 覆盖版是把当时的**内置正文整份冻结**，所以覆盖 vs 内置的 `content` 本来就不同——该失效。收窄消灭的是**另一类**假警报：`content`/`taskGuidance`/`systemRole` 一个字都没变，只有记账字段变了。

也就是说：**今天的「整对象哈希」既不精细也不完整**——它把记账字段当成了事实，又把一整段输出合同按覆盖状态漏掉了。

#### 提案内容

```ts
// 模板签名 = 真正影响模型输入的 3 段 + 内置输出合同（显式取内置，不读 template.systemSuffix）
function promptRenderSignature(template: PromptTemplate, language: WritingLanguage): string {
  return hash([
    template.content,
    template.taskGuidance ?? '',
    template.systemRole ?? '',
    getBuiltinPromptTemplate(template.key, language)?.systemSuffix ?? '',
  ])
}
```

判定改为「源事实哈希 + 这个签名」，`combined` 退回为**纯兼容字段**（继续写，供旧版本读；判定不再看它）。

#### 代价与前置

| 项 | 说明 |
|---|---|
| **前置：裁定 2 必须已落** | 收窄后新检查点的模板哈希与旧的**必然不同** ⇒ 存量检查点会一次性全失效。裁定 2（旧检查点放行）正好兜住，所以**裁定 2 不只是"旧项目省事"，它是本提案能不能做的前提** |
| 反向风险 | 将来若有人把影响渲染的东西挪进被排除字段（例如给 `variables` 塞默认值），签名就漏了。要一条测试钉住「签名覆盖全部渲染输入」：改 `content`/`taskGuidance`/`systemRole`/内置 `systemSuffix` 任一项，签名必须变 |
