## 0. 一句话结论

**方向正确、证据充分，但参数与粒度两处都不能照抄。**

正确的一半是：**章数预算不该由模型算**——模板第 0 步让它做三层长除法，并要求「逐项相加的算式 + 差额」，而代码注释里已经记着实测翻车（自报 845、实际 880）。这一层必须搬到本地。

不正确的一半是：那套「35:45:20 / 25:50:25 / 每章 40-45-15 三场景 / 第 140 章至暗」的参数**是当场编的**，两处算术自相矛盾，且其中两条与项目已有的硬约束**直接冲突**（见 §2.3、§2.4）。

本稿的结论是：**合并立项成立，但合并的是「平台画像这张参数表」，不是「一套机制」。**
一张画像 → 两个消费者：**结构预算器**（弧光生成前，算章数）+ **文风风格层**（正文每轮，P9 已定）。两者时序、通道、刚性都不同，做成一个模块必然职责错位。

## 1. 现状：为什么现在必然是均分

不是模型选错了比例，是**没有比例可依**。三条证据：

| # | 事实 | 位置 |
|---|---|---|
| 1 | 模板只规定**绝对区间**（大弧 80–150 / 中弧 20–40 / 小弧 5–15 章）与「Σ 与总章数差 ±10%」 | `builtin-prompt-templates.ts:697-699`、`:682-684` |
| 2 | 模板让**模型自己**算大弧数 `= N÷100`、中弧数 `= 大弧章数÷25`、小弧数 `= 中弧章数÷10` | `builtin-prompt-templates.ts:675-677` |
| 3 | 唯一的闭合要求是 **Σ = 总章数**；在没有任何位置性约束时，**能凑齐 Σ 的唯一配比就是均分** | 本文 §2.1 |

第 2 条是最要命的：它把一个需要**长除法 + 逐层取整 + 层间闭合**的算术题交给模型，然后又在模板里写「若算错请重算」。实测它确实算错（`arc-position.ts:22` 注释：自报 880 vs 845）。

**所以本立项的第一性理由是"把不可靠的算术从模型手里拿走"，而不是"让比例更好看"。** 这一点比原讨论里"模型数学很差"的表述更精确，也更能指导实施顺序。

## 2. 对本轮参考讨论的裁定

（作者提供的第三方方案，逐条核对。✅ 可用 / ⚠️ 需改 / ❌ 不可用）

### 2.1 ✅「算与写分离」——成立，且项目已在做

`arc-position.ts` 就是"算"：它解析弧光三层 → 累积求和 → 按全书章数等比折算 → 把「所在大弧/中弧 + 区间 + 后续中弧清单」注入。模型只负责填肉。这个架构不用重新论证，只需要**把"算"的起点从模型挪到代码**。

### 2.2 ✅「给结构体数据而非宏观散文」——成立，且已有先例

P11-1 的 `keyEvents.attacks` 就是这个形态：代码生成语义合同 → 模型在合同内发挥。**不新增模板变量**（判据 ⑪：改变量值优于加模板变量；红线 16：加 `requiredContextVariables` 会穿透作者覆盖版）。

### 2.3 ❌ 参数字符串是现编的，且算术自相矛盾

| 讨论里的说法 | 核对 |
|---|---|
| 「40 万字 ÷ 2500 字 = 160 章」 | ✅ 对 |
| 「大弧1 占比 35% ⇒ 50 章」 | ❌ **160 × 35% = 56**，不是 50 |
| 「第一幕高潮落第 50 章」 | ✅ 50/160 = 31.25%，与 30% 的锚点相符 |
| 「全书中点落第 80 章」 | ✅ 80/160 = 50%，符合节拍表 |
| 「至暗时刻落第 140 章」 | ❌ **140/160 = 87.5%**。经典节拍 All is Lost ≈ 75%（≈120 章），140 章已是高潮收束段。前两个锚点都对、只有第三个错 ⇒ 这是**凑数**而非计算 |
| 「番茄 35:45:20」配注「开局推进极快」 | ❌ **自相矛盾**：占比高 = 铺垫长 = 开局慢。若真要"开局极快"，第一幕应**更短**（≤30%），不是更长 |
| 「番茄中弧 45:55」/「起点 40:60→35:65」 | ⚠️ 与作者原始锚点 `40:60` 不符，且**未给依据**。作者已认可的 30:45:25 / 40:60 才是本项目的默认锚点，第三方无权改写 |

**裁定**：参数一律回退到**作者已给的锚点**（大弧 30:45:25、中弧 40:60、小弧差 ≤2 倍、场景 40-45-15）。平台差异**只做方向性描述**（番茄：单章更短、中段更长、钩子更密；起点：单章更长、允许铺垫），**具体数值留空待实测校准**，不由本稿填。

> 这不是过度谨慎。本项目已有过一次教训：凭空写进 prompt 的硬指标没有判定权（P8），凭空取的默认值会静默污染通用项目（P9 §3.3 的 `platform` 缺省必须是 `general`）。**编数字比不写数字更危险。**

### 2.4 ❌ 「每章场景配比 40% / 45% / 15%」——与既有契约打架，且制造均质化

作者给的 40-45-15 是**场景类型在整体/小弧内**的经验分布，不是"每章必须三个场景各占多少"。若逐章硬套：

- 2500 字 ⇒ 1000 / 1125 / 375 字的三个场景，**每章结构雷同**。这比"章数均分"更严重的均质化——均分只是长度一样，这个连**内部形状**都一样；
- 与 `keyEvents`（2–5 条有序事件 + `estimatedUnits`）语义冲突：字数配额已经由 `estimatedUnits` 承载，再加一层百分比属于双源真相；
- 作者在文风调优里的原话是「从零生成要同时做六个决策 ⇒ 只能选最安全 ⇒ 机械」。每章强制三场景是同一个病的加强版。

**裁定**：场景类型配比**不进章级约束**。若要做，形态是给 `keyEvents` 每条加**类型标注**（信息/冲突/转折），由体检器统计一章/一段的类型分布并报偏离——**报告，不卡**。

### 2.5 ❌ 「节拍点标记器是最牛的」——代码只能定位置，定不了内容

「代码自动算出情绪转折点」是夸大：代码算的是**章号位置**，转折点写什么仍然是模型生成。把它当成引擎最亮的部分，等于把"占位"当成了"生成"。

更实际的风险：**把"第 80 章必须大反转"钉死，会生产"为位置造情节"**——如果第 79 章的素材撑不起那个反转，模型只能硬插一个。这与当前"剧情提前兑现"是**同一个病的镜像**（一个提前透支，一个为凑点强行植入）。

**裁定**：节拍点只做**体检参照**（"你当前写到 45%，但第一幕高潮的锚点在第 48 章，你还差 3 章没起势"），不做生成期硬约束。位置信息进注入块，措辞是**参照**不是**命令**。

### 2.6 ❌ 「Priority 0 最高优先级」/「写几个 Python 脚本」/「仪表盘 UI」

| 说法 | 裁定 |
|---|---|
| 抬到 P0 | 与作者裁定冲突（"仅次于当前任务优先级"）。**不抬** |
| 另写 Python/Node 脚本 | 项目是 Electron + TS，已有 `arc-position.ts` / `auditArcDensity` / 结构位折算。正确做法是**扩展纯函数**，不是另起脚本（另起脚本还会造成第二套折算实现，正是 `arc-position.ts:315` 注释里警告的"两份实现必然漂移"） |
| 做仪表盘（左选题材、右拉树状图） | 属新 UI，成本远高于收益。本立项的**全部产出可以只有"算完写进注入块"**，UI 是 P9 S4 的下拉框，不是树状图 |
| 「别的作者靠经验，你用工业化代码算结构」「稳如老狗」 | 吹捧，对决策零价值。"结构正确而节奏难看"的书满地都是，比例精确不等于好看 |

## 3. 那条讨论没看到的三个结构性风险（本稿的主要增量）

### 3.1 ⚠️ 硬预算会夺走模型对本卷容量的判断权

当前链路是「模型自报章数 → 代码折算」。改成「代码给定章数 → 模型照抄」后，一个新的失配就出现了：**故事容量 ≠ 给定配额**。

- 配额 45 章，故事只要 30 章 ⇒ 注水；
- 配额 45 章，故事需要 60 章 ⇒ 挤压、越界、提前兑现。

而 A2 早已对此有裁决（`prompt-assembly-backlog.md` 第 22 行）：

> **规划不是契约** —— 允许 Σ 与全书章数相差 ±10%；必须逐项写出加法式并声明差额，**但不得为凑齐总数而增删章节**（作者反对「以目标为导向的凑数」）。

**所以本引擎的正确形态不是"算死硬塞"，而是"算目标 → 模型可偏离但必须声明 → 代码复核并报差额"。** 这是 A2 裁决的直接推论，不是新偏好。

由此得到一条内部区分：

| 谁算的 | Σ 是否必须闭合 |
|---|---|
| 模型自报（现状） | ✗ 允许 ±10%，但必须声明差额 |
| **代码算（本引擎）** | ✓ **必须严格闭合** —— 代码没有"规划弹性"这个理由，算不齐就是 bug |

### 3.2 ⚠️ 配额 × 骨料 = 新的注水通道（判据 AY 的延伸）

判据 AY 说的是「每下一层必须严格多于上一层」。但配额是**先定死**的，骨料是**模型生成的**。两者一旦不匹配，模型唯一的选择就是把少量事件**拉长**——这是"信息量不足"的另一种表现，且**现有体检器抓不到**（`auditArcDensity` 只看材料够不够，不看配额有没有超）。

~~建议新增一条体检（`M / N < 0.5` ⇒ 报「配额超出骨料承载」）~~

> **[已失效 2026-10-18，见 [`synopsis-expansion-design.md`](synopsis-expansion-design.md) §1]** —— 作者裁定「小弧章数是必须的，撑不起不是配额问题」（陈佩斯吃面：一个动作、一个场景、零时间跨度撑 25 分钟）。`M / N` 比值**不能**用作注水判据：8 章 / 6 段同一天的动作可以完全合法，压章数治不了它。**这条体检撤销。**

**2026-10-18 实测证据（结论仍然有效，归因已改）**：作者第一个小弧「刚醒的第一句」8 章 / 6 段事件，**第 1 章就把 6 段全部写完了**，第 2–8 章写的是下一个小弧的素材（覆盖行仍写小弧 1，INV-1/2/3 全绿）。同时这 10 章的大纲正文只有 **200–290 字/章**，目标是 600。

~~判据 **BF**：大纲字数显著低于目标 = 骨料不足的直接症状~~

> **[改归因 2026-10-18]**：字数探针**保留**（连续 ≥3 章 < `target × 0.6` 即报，纯字数统计、可回放历史库），但结论改为「**这一章没有被赋予一个可能失败的目标**」，不是"料不够"。见 [`synopsis-expansion-design.md`](synopsis-expansion-design.md) §4.6。

⇒ 真正的失配不在"章数 vs 事件数"，而在「**弧光给的是结果陈述，大纲要的是可争夺的处境**」。这是**形状**问题，不是**数量**问题。

### 3.3 ❗ 比例与绝对区间在 150 章规模下**数学上不兼容**

这是本稿最重要的技术发现，也是作者原始 §4 第 5 问的确切答案。

按 150 章、作者锚点 30:45:25 + 40:60 算：

| 大弧 | 章数 | 中弧 40:60 | 是否违反「中弧 20–40 章」 |
|---|---|---|---|
| 大弧1 | 45 | 18 + 27 | ❌ **18 < 20，违反** |
| 大弧2 | 67 | 26.8 + 40.2 → 27 + 40 | ✅ 恰好顶到上限 40 |
| 大弧3 | 38 | 15.2 + 22.8 → 15 + 23 | ❌ **15 < 20，违反** |

⇒ **「每大弧固定 2 个中弧」这条现有约束在 30:45:25 + 40:60 下必然失效。** 三条出路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A** | 放宽中弧下限 20 → 16 | 一个数字，最小改动 |
| **B** | 大弧1/大弧3 改 3 个中弧（45 = 15+15+15，38 ≈ 13+13+12） | 中弧数不再固定 2，比例体系要重述 |
| **C** | 只约束**相对比例**，绝对区间降级为"体检参照"不再卡模型 | 与 §2.6「只报告」策略一致，最省事 |

**建议 C**：绝对区间本就是经验值，让它和比例**争夺同一批数字**只会两头不到位。区间降为参照后，比例规则是唯一的硬数字，冲突消失。

## 4. 设计：一张画像，两个消费者

```
                  ┌──────────────────────────────┐
                  │  PlatformProfile（平台画像）  │  ← 唯一参数源，P9 G1/G2
                  │  单章字数 / 退回线 / 结构占比 │
                  │  / 文风 KPI                  │
                  └───────────┬──────────────────┘
                    ┌─────────┴─────────┐
                    ▼                   ▼
        ┌───────────────────┐   ┌──────────────────┐
        │ 结构预算器         │   │ 文风风格层        │
        │ arcBudget.ts      │   │ P9 Skill + KPI    │
        │ 时机：弧光生成前   │   │ 时机：正文每轮     │
        │ 输出：整数章号区间 │   │ 输出：提示          │
        │ 刚性：硬闭合       │   │ 刚性：软阈值        │
        └───────────────────┘   └──────────────────┘
```

**为什么必须拆开而不是一个大模块**：

| 维度 | 结构预算器 | 文风风格层 |
|---|---|---|
| 时机 | 弧光生成**前**（一次性） | 正文每一轮（每章） |
| 输出 | 整数章号，不能有 45.5 | 比例阈值，20% 告警即可 |
| 通道 | 弧光模板 + `arc-position` 注入块 | 写作 Skill（每轮注入、不被豁免，P9 §1） |
| 失败后果 | 全书区间错位（结构性） | 单章偏味（局部） |

合并成一个模块，结果一定是"算骨架的东西去管对话占比"。

### 4.1 画像字段草案（只定结构，数值待定）

```ts
// src/shared/platform-profile.ts（新增，纯数据 + 纯函数，无 IO）
export interface PlatformProfile {
  id: 'fanqie' | 'qidian' | 'jinjiang' | 'literary' | 'general'
  /** 单章字数基准；缺省不假设平台 */
  wordsPerChapter: number | null
  /** P9 §3.4 的三个魔数（0.7 / 1.3 / 0.85），平台化 */
  draftUnits: { aimLow: number; upperBound: number; lowerBound: number } | null
  /** 结构占比；null = 不约束（退回「区间 + Σ」的现状） */
  arcShare: {
    /** 大弧层占比，长度即大弧数。TODO-待作者定 */
    major: number[] | null
    /** 中弧前幕 : 后幕。TODO-待作者定（作者锚点 40:60） */
    mid: [number, number] | null
    /** 小弧最大/最小比上限。作者锚点 2 */
    minorMaxRatio: number | null
  }
  /** 文风 KPI（P9 §3.5，只提示不阻断） */
  styleKpi: {
    dialogueRatioMin: number | null
    paragraphRange: [number, number] | null
    hookEveryWords: number | null
    simileMax: number | null
  } | null
}
```

**缺省一律 `null`，不做任何平台默认**（P9 §3.3 的教训：默认取番茄会静默污染通用项目）。`null` 时引擎**完全不介入**，行为与今天一致——这是本次改动的安全底线。

### 4.2 预算器算法（纯函数，无 IO）

```ts
export interface ArcBudgetNode {
  kind: 'major' | 'mid' | 'minor'
  index: number
  start: number   // 1-based，含
  end: number     // 含
}
export function computeArcBudget(input: {
  totalChapters: number
  profile: PlatformProfile
  /** 模型自报的结构（可选）：给了就按它的层级数量分配，没给就按 N÷100 等推导 */
  shape?: { majors: number[]; midsPerMajor: number[][]; minorsPerMid: number[][][] }
}): { nodes: ArcBudgetNode[]; closed: true } | { error: string }
```

三条硬规则：

1. **逐层闭合，不逐层独立取整**。每个父节点的子节点之和**必须等于**父节点章数（用**最大余数法**分配余数，不是各自四舍五入）。原讨论里 `35% × 45%` 的乘法必然产生 15.75 这类小数，四舍五入后两侧不互补——这是它方案里最会静默出错的地方。
2. **只输出整数区间**，不输出"约"。下游 `arc-position.ts` 的 `scaledBoundaries` 可以退役为「解析模型自报结构」的兼容路径。
3. **闭合失败必须报错，不得兜底**。兜底（比如把余数塞给最后一章）会让错误看起来像成功——这是本项目反复踩过的坑（判据 AQ：`split` 静默丢数据）。

### 4.3 注入形态：改「变量值」，不加「变量」

| 动作 | 是否做 | 依据 |
|---|---|---|
| 新增 `requiredContextVariables` | ❌ **不做** | 红线 16：会穿透作者覆盖版，且覆盖版未引用时被追加到正文末尾 |
| 新增事件总线字段 / 语义合同字段 | ✅ 可做 | 判据 AO：代码生成的合同优先级 ≥ 模板 `systemSuffix` > `content` |
| 改弧光模板第 0 步正文（"不要自己算，复核系统给的"） | ✅ 做，**但先查覆盖版** | 红线 3：`project > global > builtin`，改前必查作者真实覆盖目录 |
| 改 `arc-position` 注入块的区间措辞（"约第 A–B 章" → "第 A–B 章（预算锁定，不得增删）"） | ✅ 做 | 同一块，改变量值 |

⚠️ 模板第 0 步的三条公式（`N÷100`、`÷25`、`÷10`）是**模型侧算术的唯一来源**。改成"系统已给定"后，**必须同时删掉那三条公式与示例算式**，否则模型会拿两套数字打架（红线 12：示例即形态）。

### 4.4 与 P9 的合并方式

| 项 | 归属 | 说明 |
|---|---|---|
| `platform` 一等概念（小说配置下拉 / `.vela-pack` manifest） | **P9** | 已设计，S4 |
| 平台文风 Skill | **P9** | S1，零代码 |
| 平台 KPI 后置校验 | **P9** | S3 |
| **画像里的结构占比字段** | **本引擎** | 新增字段，挂到同一张画像上 |
| **章数预算器** | **本引擎** | 新增纯函数 |
| **配额 vs 骨料体检（§3.2）** | **本引擎** | 扩展 `auditArcDensity` |
| 仪表盘 UI | **都不做** | 本立项不产出 UI |

**结论**：P9 修"怎么说"（文风），本引擎修"说多少"（篇幅）。共用画像，不共用机制。**两者都依赖 S4 的平台下拉**，但都可以先于 S4 落地（用 `general` + 显式传参验证）。
