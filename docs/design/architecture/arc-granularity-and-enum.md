## 1. ★ 步骤粒度：一步出整段 vs 分节 —— 举例 + 稳定性 + 够不够用

### 1.1 先把三个概念分清（作者问的其实混了两件事）

作者问"一步出整段 vs 分节"，但"分节"在**两个不同层面上**都成立，必须先拆开：

| 概念 | 含义 | 是否改变管线 |
|---|---|---|
| **A. 一步出整段**（单次 LLM 调用产出完整弧文本） | 1 个 DB 步骤 = 1 次调用 | ✅ 最省 |
| **B. Prompt 内分节**（同一次调用里，要求 AI 按"先判型→再列弧→再写推进"的顺序写） | 仍是 1 次调用，只是**输出结构**被规定 | ❌ 零管线改动 |
| **C. 拆成多个 DB 步骤**（骨架步骤 → 事件链步骤 → 章级拆分步骤，各自 checkpoint/UI 卡片） | N 个 DB 步骤 = N 次调用 | ⚠️ 管线 ×N |

**→ 作者真正要区分的是 A 和 C。B 是 A 的内部质量手段，不是 A 的替代品。**

我们此前的建议（`arc-prompt-assessment.md §3.2`）= **A + B**：一步出整段，但 Prompt 内部分节。**拒绝 C。**

### 1.2 同一段弧，两种产出形态对照（实例：无声公寓，约 30 章）

**形态 ①：A 单步、不分节（"一步出整段"的最粗形态）**

AI 一次调用直接吐出：

```markdown
## 大弧 2：无声公寓（约 16–45 章）
沈舟因为在大弧 1 发现规则异常，主动追查，被引入无声公寓。
公寓里他先遇到隔壁邻居的信息博弈，又验证了"三长两短的敲门"这条规则，
最后与管理员正面冲突破局，揭开了第四十七条规则的真相。
```

**问题**：它**混在一段散文里**，AI 没被判型、没被要求写"为什么接在大弧 1 之后"。
"因为没有大弧 1 的异常，这一弧不可能发生"这句话**可能被写、也可能被漏** ——
漏了就没有推进链，而**推进链正是这一层的全部价值**（`arc-nesting-design.md §0.0`）。

**形态 ②：A + B 单步、Prompt 内分节（我们的建议）**

同一次调用，但 Prompt 规定输出格式：

```markdown
### 大弧 2：无声公寓（约 16–45 章）
- 类型：A 因果驱动型
- 因果：因为大弧 1 末尾沈舟发现"规则异常"，所以他主动追查并被引入无声公寓
  —— 没有大弧 1 的异常，这一弧不可能发生
- 时序：紧接大弧 1 的当夜，沈舟尚未从异常中恢复
- 目标：完成首个副本、确认规则体系
- 转折：第四十七条规则的真相
  - 支线：隔壁的人（约 6 章）
  - 支线：三长两短的敲门（约 8 章）
  - 主线：破局（约 16 章）
```

**→ 差别不在"写得好不好"，而在**结构性字段是否被强制产出**（`类型/因果/时序`）。
→ 形态 ② 还**天然可被 preflight 正则解析**（`arc-prompt-assessment.md §6.3`），形态 ① 不能。**

**形态 ③：C 三步拆分（报告主张、我们拒绝的）**

```
步骤 2a「弧骨架」 → 产出：只有 ## 大弧N + 一句话标题
步骤 2b「事件链」 → 消费 2a 输出，产出：每个弧的事件链
步骤 2c「章级拆分」 → 消费 2b，产出：每弧拆到章
```

**→ 每个步骤都要：独立 checkpoint、独立指纹、独立 UI 卡片、独立失败恢复分支。**
**→ 这是把 `architecture.command.ts` 里 `executeChapterOutline` 那套（`while cursor ≠ complete` + `saveNavigation`）复制三遍。**
**→ 收益（"骨架立稳"）用 B 的 Prompt 内分节就能拿到 ~90%（`arc-prompt-assessment.md §6.2-H`）。**

### 1.3 稳定性对比（作者问的"稳定性怎么样"）

| 维度 | 形态 ① A（不分节） | 形态 ② A+B（内分节） | 形态 ③ C（拆步） |
|---|---|---|---|
| **一致性单元** | 1 次调用 = 1 个整体（**无跨步漂移**） | 1 次调用 = 1 个整体（**无跨步漂移**） | N 次调用，**每步都可能漂移** |
| **"因果行"是否必然产出** | ❌ 可能漏（散文形式，模型可自由省略） | ✅ 强约束（格式在 Prompt 里写死） | ✅ 强约束（但由后一步补，可能与前一步语义不一致） |
| **断点续写** | 一次生成完，无需续写 | 同 ① | 每步可断点，但**步骤间状态一致性要靠 checkpoint 保证** |
| **长文本截断风险** | ⚠️ 弧多时可能被输出上限截断 | ⚠️ 同 ① | ✅ 每步短，截断风险低 |
| **管线改动** | 零 | **零**（只改 Prompt 文本） | 3×（3 套 checkpoint/指纹/UI） |
| **回归测试面** | 无 | 无 | **大**（新增 2 个步骤 = 新失败分支） |

**→ 结论：形态 ② 在"结构性产出 vs 成本"上是最优点。**
**形态 ③ 唯一真正超出的能力是"抗截断"，而这个能力本项目 `executeChapterOutline` 已有 —— 属于"需要时再启用"，不是"设计时就必须拆"。**

### 1.4 "能不能满足需求" —— 分三种情况

| 场景 | 形态 ②（A+B）够不够 | 说明 |
|---|---|---|
| **短篇 / 单弧**（1–2 个弧） | ✅ 完全够 | 输出短，无截断风险，一次成型最优 |
| **中篇 / 10 个以内弧** | ✅ 够 | 每个弧 6 行，10 弧 ≈ 60 行，单次调用轻松容纳 |
| **长篇 / 30+ 个弧** | ⚠️ **可能要退化到"分批"** | 此时不是"拆步"，而是**复用 `executeChapterOutline` 的分批模式**（按幕/按卷分批续写） |

**★ 关键判断：即使长篇需要分批，也**不是拆成"骨架/事件链/章级"三类步骤**，
而是**按同一套格式、沿"弧列表"水平切批**（第 1–10 弧一批、11–20 弧一批）——
这跟大纲按章节分批是**同一种机制**，管线复用，不新增步骤类型。**

**→ 所以对作者的问题回答是：**
> **一步出整段（A）+ Prompt 内分节（B）能满足需求，从短篇到长篇都够。
> 只在"弧数极多导致单次输出超限"时才需要分批，而那是复用现有分批机制，不是拆步。
> "分节"我们采纳，但采纳的是"Prompt 内分节"（B），不是"拆成多个 DB 步骤"（C）。**

## 2. ★ 弧与 `plotStructure` 枚举的关系（作者提出：写一个替换枚举效果的新表现形式）

### 2.1 先回答作者的判断：**"plotStructure 不就是静态的弧么？"**

**✅ 这个判断成立**，而且有代码依据（`stage-structure-layer.md §1`）：

| 作者之问 | 核实结果 |
|---|---|
| plotStructure 是静态的弧？ | ✅ 是。`getPlotStructureGuide` 用枚举值现算出**一段固定的、硬编码的**阶段划分文本 |
| 写短篇还行？ | ✅ 是。短篇 1–2 弧时，三幕/起承转合这种固定模板**足够用** |
| 主要是兜底，没有合适的选择入口？ | ✅ 是。UI 只有一个 `<NativeSelect>`（`NovelConfigEditor.tsx:273`），6 个选项，没有"自定义" |
| 弧机制可编辑，能替代枚举？ | ✅ **技术上完全可行** —— 因为 `:2281` 已经是一个三元消费点 |

**→ 所以作者说的"写一个替换原有枚举类效果的新表现形式"= 把枚举从"唯一来源"降级为"默认值"，
让可编辑的弧文本成为**主来源**。这与 `stage-structure-layer.md §2.3` 的"自定义优先、枚举兜底"**完全一致**。

### 2.2 枚举当前的"锁定面"（替换前必须知道它锁在哪）

我先摊开枚举被消费的**全部位置**，再判断"替换"要付多大代价：

| # | 位置 | 用途 | 若"替换枚举"会怎样 |
|---|---|---|---|
| 1 | `architecture-workflow.ts:279-355` `getPlotStructureGuide` | 枚举 → 硬编码文本 | 保留（作兜底默认值） |
| 2 | `architecture.command.ts:2281` `.withPlotStructureGuide(...)` | **唯一消费点** | ✅ 改一行三元即可（自定义优先） |
| 3 | `architecture.command.ts:607-614` `PLOT_STRUCTURES` Set | 输入校验白名单 | 保留（校验的是枚举本身，不影响弧文本） |
| 4 | `architecture.command.ts:410-430` 指纹 `sourceInputs.plotStructure` | "改了就失效" | 保留 + 追加弧文本（`stage-structure-layer.md §1.4`） |
| 5 | `NovelConfigEditor.tsx:273` `<NativeSelect>` | 作者选择入口 | ⚠️ **这里才是"入口不够用"的真正痛点** |
| 6 | `novel-config-localization.ts:33-63` `PLOT_STRUCTURE_LABELS` | 枚举→中英标签（**注意 UTF-8 的 `三幕式`/`three_act` 双键**） | 保留 |
| 7 | `builtin-prompt-templates.ts:578` `{{plot_structure_guide}}` 占位符 | 注入点 | 不变（已抽象，不认枚举） |
| 8 | `propose-novel-config.tool.ts:13`、`prompt-language.ts:193` | AI 工具/语言的枚举引用 | 保留 |

**→ 关键发现：枚举的"锁定面"虽多，但**全部是"保留即可"** ——
除了 #5（UI 入口），**没有任何一处必须"删除枚举"。**
**→ 所以正确动作不是"替换枚举"，而是"让枚举退位为默认值"。**

### 2.3 三种可能方案对比（作者要的"新表现形式"是哪种）

| 方案 | 做法 | 成本 | 风险 | 评价 |
|---|---|---|---|---|
| **① 保留枚举 + 弧文本优先**（我们建议） | `:2281` 改三元：`弧文本?.trim() \|\| getPlotStructureGuide(枚举)` | **1 行** | 极低 | ✅ **推荐** |
| **② 枚举改成"快捷填充"**（作者"新表现形式"的字面理解） | UI 下拉框保留，但选枚举时**把枚举文本填充进可编辑弧框**，作者可在其上改 | 1 个 UI 交互 + 1 个填充函数 | 低 | ✅ **与 ① 正交，可叠加** |
| **③ 删除枚举，只留自由文本** | 移除 `PLOT_STRUCTURES`/`NativeSelect`/`PLOT_STRUCTURE_LABELS` | 8 处改动 + 迁移旧项目 | ⚠️ 中高 | ❌ **不推荐** |

**★ 为什么否决 ③（删枚举）：**
1. **兜底价值真实存在**：新用户、不熟悉的作者、短篇 —— 需要一个"我不知道怎么规划，给我个默认"的入口。删了就是"逼用户从零写弧"。
2. **向下兼容**：已建项目里 `plotStructure` 有值，删掉字段要么迁移、要么留死数据。
3. **零收益**：保留它**不阻碍**任何"新表现形式" —— 弧文本一样能是主来源。

**★ 推荐组合 = ① + ②：**
- **①** 保证弧文本是**运行时主来源**（`:2281` 三元，1 行）；
- **②** 让枚举变成**编辑器里的"模板按钮"**（点一下把三幕文本填进弧框，作者继续改）——
  这正是作者说的"**替换原有枚举类效果的新表现形式**"：**枚举不再是"最终结果"，而是"起手模板"。**

### 2.4 UI 形态建议（回答"没有合适的选择入口"）

作者抱怨的是：现在只有 6 个死选项，没有"自定义"入口。

**建议的入口形态（落在 `WorldBuildingEditor` 的第 5 项卡片里）：**

```
┌─ 阶段结构（第 5 个架构文件）─────────────────────┐
│  [ 编辑全文 ][ 重新生成 ]                        │
│  ┌───────────────────────────────────────────┐  │
│  │（可编辑的弧文本 Markdown，占满卡片）        │  │
│  │                                           │  │
│  └───────────────────────────────────────────┘  │
│  💡 起手模板：[三幕] [起承转合] [英雄之旅] [多线] │ ← 点一下填充
│     （= 原枚举，降级为"填充按钮"，不再直接生效）   │
```

**→ "枚举"从一个**最终结果**（选中即生效）变成**起手模板**（填充后由作者改）。
**→ 弧文本才是被消费的东西（`:2281` 三元），枚举只提供"一键生成初稿"。**

**★ 这正好回应作者的"没有合适的选择入口"：**
- 之前：**入口缺失**（只有 6 个死选项）
- 之后：**入口 = 自由编辑 + 一键填充**（既有自定义，又有兜底）

### 2.5 一句话结论

> **"plotStructure 是静态的弧"判断成立，但它不该被"替换"，该被"降级"。
> 弧文本成为主来源（`architecture.command.ts:2281` 一行三元），
> 枚举降级为 UI 里的"起手模板按钮" —— 这就是作者要的"新表现形式"，且向下兼容、零迁移。**
>
> **★ 唯一红线：不要删除枚举。** 它是短篇/新手/旧项目的兜底，删除的收益为零、风险为负。

## 4. 更新后的落地次序（覆盖 `00-OVERVIEW.md §2`）
