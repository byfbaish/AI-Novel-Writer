## 2. ★ 实测反例：为什么"机读行 + 纯算术"这条路在本项目已经失败过一次

作者 Q1 的直觉有硬证据支持，而且**比资源更通用**——失败的是**空间机读行**，一个本来与题材无关的格式：

| 世界观的机读行（原文） | 解析结果 | 原因 |
|---|---|---|
| `青阳山·杂役处｜hours=06:00-06:30` | ✅ | — |
| `外门广场｜hours=08:00-17:00` | ✅ | — |
| `执法殿·审讯室｜hours=14:00-16:00` | ✅ | — |
| `藏书阁·外楼｜hours=09:00-12:00` | ✅ | — |
| `试炼峰·聚气台｜hours=当日00:00-24:00` | ❌ **静默失效** | `CLOCK` 只认 `[01]\d\|2[0-3]`，`24:00` 越界 |
| `百草园·禁地方块｜hours=每月01日08:00-03日18:00` | ❌ **静默失效** | 带"每月N日"复合语义，解析器只认纯区间 |
| `青冥海·边缘岛屿｜hours=每月15日00:00-00:10` | ❌ **静默失效** | 同上 |
| `废弃矿洞·地下三层｜entry=…` | ⭕ | 无 `hours=`，按设计不可判 |

**8 条里 4 条判不了，而这 4 条恰好最重要的三个（百草园、青冥海、试炼峰）全是"周期性窗口"** —— 也就是剧情真正会撞的东西。

> **判据 CN：机读格式的失败是静默的。** 解析不了的机读行不会报错，它只是变成"没有可判定形式"→ fail-open → 界面显示"未发现冲突"。
> **⇒ 任何"让世界按我们的格式写"的方案，都会把"内容漂移"转成"校验静默失效"。后者更危险，因为看不出来。**

这也解释了另一件事：`consistency-preflight.ts` 的空间核对在本项目**从未产出过一条 finding**（ch1–ch6 的 `structured_refs` 全部合法，而 4 条不可判的行正好覆盖了后续剧情要用的空间）。

## 4. Q2 答复：本书实证下缺的维度（按价值排，不列清单）

### 4.1 第一位：故事日历（day ordinal）—— 全书没有"今天是初几"

**证据**：ch1 签到（`timeRef=06:00-06:30`）、ch2 同一天、ch3 买药（同一天）、ch4「明早卯时到园子门口领签」「清到初八」、ch5「天没亮」。**六章里没有一处写出今天几号/初几。**

而挂在这个轴上的规则有 **6 条**：

| 规则（原文出处） | 无日序的后果 |
|---|---|
| 签到 06:00–06:30（第 4 维） | 只能判"在不在窗口"，判不了"漏签了几次/扣多少" |
| 百草园「每月初一开园，初三傍黑关」（ch3） | 判不了"明天去清草"是否在开园前 |
| 「开园前三天，外园那片草要清出来」（ch3/ch4） | **「初八夜里收工」这条 error 的根因** |
| 试炼峰「当月 25 日前登记报名」（第 4 维） | 判不了还有几天 |
| 「初一十五，我得往上送」（ch4 王德发） | 判不了下一次是哪天 |
| 赵无妄「每七日巡一次」（ch5 大纲） | 判不了下次巡 |

**⇒ 日序不是"七槽之一"，它是主轴**：药剩几副 ÷ 三天 = 剩余天数；百日倒计时 = t0 + 100 − today。**没有 t0，所有倒计时都是形容词。**

### 4.2 第二位：口径（period / 结算单位）—— 30 倍 bug 的死因

「每日劳作十二时辰换取十枚」 vs 「杂役处月例十枚」 vs 「一副六枚」 vs 「三天一副」。
**同一个"枚"，四种周期：日 / 月 / 副 / 三天。** 世界从没声明"十枚是按什么周期结算的"。

> **判据 CK（沿用）：相对量与金额必须带分母/周期**，未声明即"不可判定"，校验器**不得补猜**。
> 这一类**完全世界无关**：月薪/日薪/每单/每股/每副，现代都市与异世界货币一样适用。

### 4.3 第三位：知情边界（谁告诉了谁）

| 传播链（库内原文） | 现在没有任何登记 |
|---|---|
| ch3 小郑 → 顾长风「赵无妄的人昨天来问过你」 | — |
| ch4 小郑「把买药的事报上来了」→ 王德发 | — |
| ch4 王德发「命老赵誊药铺近三月流水」 | — |
| ch6 王德发「报上来你还欠着月例钱」→ 赵无妄 | — |

**本书特别吃这条**：主角是重生者 + 金手指是掠夺记忆，「他知道什么」与「他该知道什么」就是核心张力。**这个槽现在是真空。**

## 6. Q4 答复：方向对，但有四个前提

### 6.1 前提一：状态必须带证据与来源章，不能是"模型总结"

本项目已有两套可用机制：`finalized_continuity_facts`（statement → 原文 evidence 匹配）与 `characters.cs_provenance`（字段级 `kind/draftId/finalizationId/chapterNumber`）。
**新状态一律带 `source` + `evidence`，否则它会变成第三个事实源。**

### 6.2 前提二：不能让模型自评对错

审稿输出里只能有"事实 + 原文 + 冲突源层级"，**不能有"应改为 X"**（判据 CJ）。否则就是把现在"每章一条、无处落笔"放大成"每章一条错处方"。

### 6.3 前提三：先并存，后替换 —— 不要一步换掉散文

散文设定承担**质感/口吻/意象**（本书文风要求里"少比喻少通感"是刻意收的，不是没有）。直接换成字段会掉文风。
**顺序**：状态快照**新增**一块 → 验证漂移下降 → 再谈按需检索（外部稿 S3 依赖投影机制 `far-term-section-collapse`，那是第二步）。

### 6.4 前提四：没有权威值，写回就是"错误的固化"

外部稿说"没有写回，快照就是死数据"。要补一句更狠的：

### 9.4 W1 实现记录：判据版合同，不是复用写作版

原预案是「把 `generate-draft.command.ts` 的内联模板抽成共享函数（禁止复制，否则两份必然漂移）」。落地时改成了另一条路，理由是**同一句话在两个角色里语法不同**：

| 生成侧措辞（义务） | 审稿侧必须写成（判据） |
|---|---|
| 事件「必须通过具体行动及其实际后果发生」 | 「只认本章已发生的具体行动及其实际后果；计划、承诺、签字认责、否定翻转都不等于结果已发生」 |
| 「不得把已撤回、取消或被取代的计划追溯写成已执行」 | 「不得**要求**正文把已撤回的计划追溯写成已执行」 |
| 「普通无代价情节无需增加代价」 | 「不得因本章没给事件附加代价、没更换时点或场景而判为矛盾」 |

逐字照搬的风险不是「两份漂移」，而是**制造错误义务**：审稿模型会把写作义务读成对自己的要求，甚至按合同去改写而非判定。

**防漂移改用可执行手段**：生成侧条款标题（`【…】`，共 9 条）必须在 `review-execution-contract.ts` 的对照表里表态（进 / 不进 / 改写）。`review-execution-contract.test.ts` 直接读生成侧源码抓标题，**新增条款而审稿侧没表态，测试即红**。抓取面覆盖两个文件（`generate-draft.command.ts` 的 `chapterExecutionContractText` 与 `chapter-time-continuity.ts` 的 `chapterTimeContinuity`）—— 后者证明过一件事：条款被拆到独立模块时，抓取面不跟过去，测试会一直绿着却什么都没查。

对照表结论：**6 条进、2 条由专门模块覆盖（远期设定 → `reviewFarTermSettingRule`；时间承接 → `【时间一致性检查】` + `reviewTimeContinuity`）、1 条改写**（操作边界 → 「核对范围」，续写/压缩语义对审稿不存在）。

**落点**：`src/shared/review-execution-contract.ts`（新增，zh/en）＋ `review-chapter.command.ts` ordinary 分支一处调用。
**刻意不进 recheck 分支**：那一轮只裁决既有 finding 是否 resolved，两套判据并存会互相干扰（已有测试守住 `not.toContain`）。
**体积守卫**：zh < 1100 字、en < 2800 字符 —— 审稿 prompt 已有大量裁决规则，口径膨胀会稀释注意力。

**验证**：新增 7 个单测（含条款覆盖契约与体积上限）；`review-revision-runtime` 46 例（含 zh/en 两个语种、recheck 反向断言）、`review-revision-context` 30 例、`character-state-lines` 10 例、`generate-draft.command` 全绿（合计 303 例）；`tsc --noEmit` 零错、`eslint` 零警告。

## 12. W2 方案：日序与口径怎么落（待作者定两件事后动 schema）

### 12.1 先说清矛盾：历法刻意不可解析，日序却要能做算术

§11.1 定的是「历法维**不要机读行**」——因为解析失败会转成校验静默失效（第 4 维 8 条机读行里 4 条解析不出来，界面照样显示「未发现冲突」）。
但 W2 要的 `storyDay` 必须能做整数运算（药剩几副 ÷ 3 = 剩余天数；百日倒计时 = t0 + 100 − today）。**这两条直接冲突。**

解法不是把历法改成机读，而是**换一个产出者**：

| 谁 | 做什么 | 为什么是它 |
|---|---|---|
| 历法维（人读） | 只描述纪年、月长、时辰、周期事件、t0 | 世界的形状由世界定，工程不约束格式 |
| 定稿后处理（模型） | 读历法 + 读本章，输出**一个整数**：本章距 t0 的天数，外加书中写法 | 模型本来就懂「二月廿三 → 第 3 日」这种换算；工程不解析文本，只接收结果 |
| 校验（纯算术） | 单调不减 / 相邻差与章内明示间隔一致 / 倒计时类字段可反算 | 模型算错可以被算术抓到 |

★ 与 AC5 的差别必须写清：AC5 的问题不是"模型填错"，而是**解析失败后静默当作没问题**。所以 W2 的铁律是 —— **取不到日序就必须显式降级**（状态里标「本日序缺失」，而不是填 0 或跳过校验）。

### 12.2 存储：加两列，不新建表

`summary_snapshots` 已有 `chapter_number / chapter_notes / continuity_facts`，日序天然是"每章一张快照"的属性：

| 列 | 类型 | 含义 |
|---|---|---|
| `story_day_offset` | INTEGER NULL | 本章距 t0 的天数（t0 = 0）。NULL = 未取到，**不等于 0** |
| `story_day_label` | TEXT NULL | 书中写法（如「二月廿七」），只用于展示与审稿比对 |

**为什么不新建表**：日序与章节笔记是同一份产物的两面，分开存会出现"笔记有、日序无"的孤儿行；而且 `summary_snapshots` 的读写路径已经接好（`listFinalizedContinuityBefore` 等），新建表要把这些路径全改一遍，收益为零。

### 14.2 三条不变量

1. **NULL ≠ 0**。0 是「开篇当日」这个合法值，缺失用「没有这个键 / NULL」表示；解析失败绝不填 0（AC5 的死法就是让「没算出来」和「第 0 日」同形）。
2. **缺失要看得见**。UI 明确提示「已记为未知，不按章号推算」；审稿块写「（缺失——不得按章号臆测）」。
3. **倒退即失败**。日序是算术锚，倒退通常意味着模型把闪回当成了本章主时间；不夹紧、不静默修正，直接拒绝并给出两章数值。

### 14.7 判据 CU：基线冻结 —— 新列只能走 M 迁移，不能改 `CREATE TABLE`

判据：**`baseline-schema.ts` 是已签署的 S01 基线的物化，它的列集 = 签名契约的 356 项；要加列就新建 M 迁移步骤（含 `from/to/owner` 槽位、幂等 apply、`verify`），并同步 `CURRENT_DESKTOP_SCHEMA_VERSION` / `LATEST_SCHEMA_VERSION` / `MIGRATION_IDS`。** 本次落地 M10（v10→v11），lane 测试见 `m10-installed-lane.test.ts`。

### 14.8 判据 CV：状态机的前置断言不能被「为下游准备数据」的副作用先行破坏

老库离线的整条导入流程里，`adoptCopiedLegacyCards` 无条件调了一次 `refreshCharacterIdentityProjection(db)`。这个函数会把 `character_roster_meta.migration_state` 直接写成 `'ready'`，而紧接着的 `adoptLegacyCards` 要求它仍是 `'legacy_cards_preserved'` —— 用自己的副作用废掉了下一步的前置条件，13 例必挂 `LEGACY_ROSTER_CARDS_REQUIRED`。

修法不是放宽断言，而是**只在真正需要刷新时刷新**（`if (readySource)`：源名单已 ready 才需要重建投影；旧卡待采纳的分支由 `adoptLegacyCards` 自己在内部刷）。

判据：**任何「为了让下游能用」的准备工作，都要先确认它不会改写下游的前置判据字段。** 一个函数如果既改数据又改状态枚举，它就不能无条件地插在状态机中间。

### 14.9 判据 CW：读新列也要能读旧库

`listFinalizedContinuityBefore` 一度直接 `SELECT summary_snapshots.story_day_offset`。基线冻结后，任何**尚未升到 M10** 的库（包括停在版本 0 的测试库、只读探测路径）都会 `no such column` 整条查询失败。

修法：读侧先查 `PRAGMA table_info`，缺列时把两列选成 `NULL`。语义正好对得上判据 CS —— **缺列 = 日序未知**，而不是报错，也不是第 0 日。

配套改了一处测试夹具的口径：`generation-source-binding` 的 fixture 刻意停在裸基线（它靠「没有身份表」来跳过冻结校验），所以不能给它补跑全量迁移（那会让 `sourceStatus` 从 `current` 变 `legacy`，属于另一个测试的职责）。

### 14.5 顺带修掉的上轮遗漏

英文 `world_building` 模板仍是**四维**旧版（缺第 5 维时间历法，`日序` 相关 0 命中）—— 上轮只同步了中文。后果：英文项目永远生成不出日序，W2 在 `en-US` 下直接失效。本次补齐第 5 维与「五维结构必须齐备」的验收句，并给中英第 2 维都加上「数额必须同句写明结算周期」。

### 15.3 为什么不采用「无卡就报警」

朴素做法是「`continuity_facts` 里的实体系不到卡 ⇒ 报一条 warning」。**本条否决**，理由是它正好踩中判据 CL：

- `facts.entities` 同时含**人物、物件、地点**（`summary-repository.ts` 的注释明写这一点）。无卡实体绝大多数是物件；
- 而「作者判过是功能性角色」与「作者漏了建卡」在数据上**同形**，除非读 `character_cast_decisions`；
- 读它之后，剩下的真缺口只有「正文点名、蓝图未列、也从未登记」这一类（现存一例：老张头）。

所以这一条留给**人工一次性裁决**，不做成每次生成都刷的 warning：作者在待确认批次里对 老张头 选
`create`（补卡）或 `functional`（登记），两条路都会让它出队。

### 15.4 已存在的悬挂批次怎么处理

`cpb:377b20aa43…` 里的 `小郑` 项属于已登记名字，但**已落库的批次不会自动回缩** ——
`read()` 只在 revision 变化时重解析。作者只需对这一批做一次决定（`老张头` 是唯一真选项），
或在界面上取消该批次；之后再定稿不会再有 `小郑` 的项。

## 16. W3：审稿状态差分（v3 报告）· 2026-10-22

> **状态**：**第一单元已落地**（契约 + 五个下游 + 提示词契约，§16.1–§16.7）；**第二单元已落地**（定稿期交叉 + 判据 DA，§16.8）。

### 16.1 与预案的分歧：差分落不进 `finalized_continuity_facts`

§9.2 把 W3 写成「审稿输出 `stateDelta` → 落 `finalized_continuity_facts` → 写回 `cs_*`」。实测中间那段走不通：

| 链路 | 要求 | 审稿期是否有 |
|---|---|---|
| `finalized_continuity_facts` 写入 | `evidence` 在**已定稿**正文里精确定位；整条绑定 `FinalizedSourceIdentity`（`draftId` + `finalizationId` + `contentHash`） | ❌ 审稿发生在定稿之前 |
| `PendingFinalizedCharacterStateCandidate` | `source: FinalizedSourceIdentity` | ❌ 同上 |

审稿期的 `reviews` 只绑定 `draft_id + version + status`，此刻既没有 finalization 回执，也没有不可变正文哈希。硬塞只能造假锚点 —— 而假锚点会被下游当成证据，这比不写回更糟（§6.4 的同一条理）。

⇒ **差分落在审稿报告体（v3）**，定稿期再消费。好处是引文锚点在同一次调用的**同一份 `source_content`** 里天然成立，不多花一次模型调用。

### 16.2 形状：一条观测，不是一个判断

```
{ characterName, field, observed, quote }
```

| 字段 | 约束 | 为什么 |
|---|---|---|
| `characterName` | 正文里出现的名字，原样照抄 | 对齐 `characterId` 是定稿期的事；在审稿期猜 ID 会把重名问题固化 |
| `field` | 必须是 `CHARACTER_STATE_TEXT_FIELDS` 之一（6 个） | 与 `cs_*` 一一对应，否则定稿期无处回写，差分就是死数据 |
| `observed` | 正文写出的**新值**，**不得抄档案旧值** | 抄了就变成「正文与档案一致」的假信号，而它会被当成「本章确认了旧值」消费 |
| `quote` | 必须能唯一定位 | 定位不了 / 能定位到两处的引文是**错证据**，会把 A 段的行为记到 B 段头上 |

**不做的事**：审稿不裁决「谁对」。裁决需要权威值 + 时效性，那两样在定稿期才有。审稿只记观测。

上限 12 条；同一人物同一字段只留一条（报告体是 append-only 的事实记录，不允许自带矛盾）。

### 16.3 判据 CY：审稿期的产出不得伪造定稿身份的锚点

> 任何要求 `FinalizedSourceIdentity` 的表，在审稿期都不能写 —— 哪怕「先写进去以后再补锚点」看起来更省事。
> 一个定位不到、或定位到别处的锚点，下游无法与「真的是在这一段」区分。

这条同时解释了为什么 §9.2 的原始表述必须改：不是工程上做不到，是做到了就是错的。

### 16.4 判据 CZ：附加产出的失败只能丢自己，必须计数

审稿的**主产物是 items**（作者逐条采纳/驳回），`stateDelta` 是附加观测。

- `quote` 定位失败 ⇒ **丢弃该条**，报告仍有效；`stateDelta` 的**形状**非法（字段越界、超限、重复）⇒ 整份报告无效（那是模型没按契约产出，该重试）。
- 丢弃必须**计数**（`diagnostics.stateDeltaDropped` 出参），否则「模型引文质量变差」永远不可见 —— 判据 CL 的老坑。
- 反过来若让一条坏锚点作废整次审稿，等于用附加功能的失败惩罚主产物。

### 16.7 v2 与 v3 在无差分时重建出同样的字节

### 16.8 第二单元：定稿期交叉（已落地 2026-10-22）

`stateDelta` 在第一单元里只被存下来、没有消费者 —— 这正是 W0 批判过的形态（「不是没有状态，是两条链都不读」）。第二单元给了它第一个消费者：

- **落点**：`SummaryRepository.commitFinalizedCharacterStates`，在 `decideDerivedPatch` 返回 `apply-derived` **之后**再加一道「审稿侧是否反对」。反对 ⇒ 不写库，改产出一条 `reason: 'review-conflict'` 的待裁决候选。
- **判据 DA：冲突判定必须用 span 重叠，不能靠字符串比较。**
  `observed` 与定稿抽取值都是自然语言，字符串不等不等于矛盾（「北塔」与「北塔三层」说的是同一件事）。只有当**两边指的是同一段原文**时，取值不同才是真冲突 —— 那是「同一句话被读出两个结果」的机械证据。
  若按字符串比，要么几乎全冲突（作者每章处理一堆待裁决 ⇒ 判据 CX 的队列爆炸），要么几乎不冲突（等于没做）。

**判定是三档，不是两档**（`src/shared/review-state-conflict.ts`）：

| 档 | 条件 | 动作 |
|---|---|---|
| `agree` | 两值归一化后相等 | 写回（无论位置） |
| `finalization-wins` | 不重叠，且审稿引文在定稿引文**之前** | 写回 —— 同一章内的正常时序推进（早上 6 枚、傍晚 4 枚） |
| `conflict` | span 重叠却值不等，**或**审稿引文在定稿引文**之后** | 降级待裁决 |

第三档的后半句是容易被漏掉的一半：定稿读的是前文、正文更靠后处已经写了新值，说明定稿**漏读了后文**。只判重叠会让这种情况静默写回一个过期值。

**值的归一化只抹写法差异**（NFKC / 空白 / 句读引号括号），**不猜同义**：`六枚` 与 `6枚`、`余量：6枚` 与 `6枚` 都会被判冲突。这是有意的 —— 「看起来差不多」正是 AC5 静默失效的来源，归一化一旦聪明到能猜同义，它就会把 `6枚` 和 `16枚` 也猜成一样。多问作者一次，远小于把一个错值当作者审定值写进 `cs_*`。

**三种「拿不到可信证据」都不交叉，但都不等于「审稿没意见」**（`readReviewStateDeltaForDraft` 返回状态而不是有无）：

| 状态 | 含义 | 处置 |
|---|---|---|
| `absent` | 这一稿没审过 | 不交叉 |
| `legacy` | 审过，但报告是 v1/v2（无差分字段） | 不交叉 |
| `unreadable` | 有报告体，但解析不了 | 不交叉 |

**取哪一份报告不是口味问题**：`reviews` 里混着**复核报告**（`commitRecheck` 那条链，body 是 `findingId` / `targetId` 形状、没有 `stateDelta`、也不该有）。按 `id DESC LIMIT 1` 取最新 ⇒ 凡走过修订的章节都读到复核报告 ⇒ `unreadable` ⇒ 交叉一次都不触发。**一个永远不生效的判据比没有判据更坏**，所以改成倒序扫到「最新一份带差分的审稿报告」，有界 20 条。

#### 判据 DB：闸门粒度必须与判据粒度一致（作者裁定 ②，2026-10-22）

合并修订是**原地写回同一 draft**（`merged_to_draft_id === base_draft_id`，`commitMergedRevision` 有断言），所以审稿时冻结的 `source_content` 与定稿正文**必然不等**。第一版拿「整篇正文哈希相等」当闸门，写在路径中间，结果是：**真实主链路（生成→审稿→采纳→修订→合并→定稿）上一章都不触发**。

这跟前面踩的坑是同一个形状 —— 判据的有效条件被一个更粗的前置闸门整体否决了。所以闸门下沉到**逐条引文**：

| 定位结局（`origin`） | 含义 | 动作 |
|---|---|---|
| `finalized` | 在**定稿正文**里唯一定位到 | 照判（三档见上） |
| `revised-away` | 只在**审稿那一版**正文里定位到 | **静默跳过** —— 那是正常修订，不是坏证据 |
| `unlocatable` | 两版都定位不到/不唯一 | 降级待裁决（判据 CS） |

把后两者混成一个 `span: null` 会二选一地错：要么把正常修订全变成待裁决（作者每章被问一堆已经改好的事），要么把坏报告当沉默吃掉（AC5 的静默失效）。所以 `locateReviewStateObservations` 多接一个 `previousContent`，把「整篇变了但这一句还在」与「整篇没变但这一句找不到」分开。

**代价（都已付）**：`FinalizedCharacterStateCandidate.reason` 加一档 `review-conflict`；候选新增 `reviewObserved` / `reviewQuote` 两个可选字段（便携投影的键白名单同步放行 —— 判据 CT）；`PendingFinalizedCharacterStateCandidate` 面板显示「审稿读到 + 原句 + 需要你裁决」。

**已知边界（不是 bug，是 W4 的地盘）**：审稿里的名字靠 `displayNameSnapshot` + `aliases` 映射到卡，对不上或对上多位都不猜；名字与卡的归位表是 W4。以及：审稿说过、而定稿后处理**根本没提**的字段不会产生任何东西 —— 那是「补写」而不是「防止写错」，属于下一步。

### 16.9 随之而来的审稿面板调整（2026-10-22，作者提出）

复核 review 时被两件事干扰，都是**信息密度**问题，与判据无关：

- **报告区太窄**：`max-w-2xl`（672px）→ `max-w-4xl`（896px）。指摘多是长句 + 原文引用，672px 下换行太碎。

## 18. W4：归位表与六槽（2026-10-22 起 · 进行中）

§9.2 只把 W4 写成一句「六槽/孤儿设定归位表（外部稿 S0）+ 设计意图栏」。这一节把它拆开，并记下**为什么不按外部稿的顺序做**。

### 18.1 拆成两半，顺序不能反

| 子项 | 内容 | 是否动 schema | 前置 |
|---|---|---|---|
| **W4a** | **归位表**：把「系统已经说出口的名字」对账到落点（有卡 / 多卡 / 作者判锚点 / 孤儿） | ❌ 不动 | W3（已完成：`stateDelta` 才有 `characterName` 的出处） |
| **W4b** | 六槽补齐 + 设计意图栏 | ⏸ **后置** | W4a 的真实数据 |

**为什么不先做六槽**（§9.2 已有一句，这里展开）：六槽里三槽已有宿主（`cs_location` / `cs_power_level` / `cs_key_items` + `cs_provenance`），再定一遍不产生新能力；而真正卡住的日序与口径（W2）各占一句话。**先落 schema 会把「现在能写的」和「新加的槽」混成两套真相** —— 判据 CU 的教训（初版把两列写进冻结基线，老库导入直接失败）在同一处又踩一次的概率很高。

### 18.2 W4a 的核心判断：不从正文抽名字

中文人名没有形态学标记，「他走进药铺」与「王德发走进药铺」在字符层面同构。用规则或词表去抽，**抽错一次就制造一批假孤儿**，而假孤儿直接变成作者要一条条处理的待办 —— 判据 CX 要防的就是这个形态。

所以归位表只对账**已经被模型点名过的名字**。这些名字本身就是证据，缺的只是落点。三条来源：

| 来源 | 出处 | 说明 |
|---|---|---|
| `review-state-delta` | 审稿报告 v3 `stateDelta[].characterName` | W3 的产出，天然带字段与章节 |
| `finalized-proposal` | 定稿后处理的角色状态候选 | 与 W3 交叉共用同一批名字 |
| `blueprint` | 蓝图/章节大纲的人物清单 | 计划角色：正文还没出现也要能提前归位 |

### 18.3 W4a 的四档状态

`src/shared/cast-ledger.ts`（纯函数，11 例）：`buildCastLedger(characters, anchors, mentions)`。

| 状态 | 判定 | 为什么单独一档 |
|---|---|---|
| `carded` | 恰好命中一张**未退休**卡 | 可写 |
| `ambiguous` | 命中多张卡 | 这不是「已归位」，是「归不了位」。动作是作者指定哪一张，**与建卡不是同一件事** |
| `anchored` | `character_cast_decisions` 里有 `register` | 作者的有意决定（小郑 = 功能性角色），**不是待办** |
| `orphan` | 提到过、无卡、未判定 | 唯一的真待办 |

两条容易做反的细节：

- **别名必须等价于显示名**。作者给一张卡加过旧名，说明两个字符串是同一个人；不做映射就会把改过名的卡报成孤儿，作者照着建第二张卡 —— 那才是真造出重名。
- **退休卡不是落点**。`retired=1` 是「建卡→补全→退休」的正常产物；算成落点会让状态显示「无需处理」，等到写回时才发现卡不能写。
- **有卡优先于 anchored**：先建的卡比后补的判定更具体，不能被后者的状态盖掉。

### 18.4 归位表刻意不持久化

它是「当前状态」，不是「历史记录」。存一份下来，作者建完卡它还在，就变成**永远无法应用的项**（判据 CX 的老坑）。每次从三处输入现算，解决掉就自动消失。

### 18.5 裁定结果（2026-10-22 作者定）

| # | 议题 | 裁定 | 后果 |
|---|---|---|---|
| 1 | **归位表在哪看** | **① → 改为 B：并入 W5 只读视图** | 归位表**没有独立界面**；W4a 的接线出口就是 W5 ⇒ **W5 从「不排期」变成 W4a 的唯一出口**，两者顺序被裁定绑在一起 |
| 2 | **「建卡」走哪条链** | **A：复用「角色提案 → 采纳 → 建卡」**（作者注明：要保障系统稳固健壮性） | 不新增写路径。归位表里的 `orphan` 只负责「指路」，落库仍由提案链的 `approve` 完成 |

**②A 有一个必须补的缺口（实现事实，不是偏好）**：`character-proposals.stage(source)` 现有五个入口 ——
`generation`（architecture / planning-material + 运行句柄 + 产物）· `directory` · `import` · `finalized-generation` · `legacy-roster-generation` ——
**每一个都要求上游产物**，而归位表的 `orphan` 只有名字（可能带章节号）。所以「复用提案链」不能直接接，必须先补一个入口。两条都合规：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A1** | `CharacterProposalSource` 加一档 `{ kind: 'cast-ledger', names }`，后续仍走 `stage → approve` | **写路径仍唯一**，只是给 stage 多一个合法的产物来源。推荐 |
| A2 | 把孤儿名字喂给「AI 生成角色卡」工作流，再走提案 | 完全不动提案链，但每建一张卡多一次模型调用，且 AI 会顺手补满字段（作者只想要「有个落点」时是负担） |

**为什么不能「从归位表直接建卡」**（即被否掉的 ②B）：`characters` 表的写入带着 `character_identity_meta.revision`、
`character_identity_origins`（原始行快照 + 哈希）、`character_identity_approvals`（payload 哈希 + 收据）三件套，
它不是一个 `INSERT` 而是一笔**可校验的交易**。绕过它建卡，等于让「作者手工建的卡」和「系统建的卡」在审计上分叉 ——
正是 ②A 要防的那件事。

**A1 与 A2 不是二选一，是三段流水线**（作者 2026-10-22 追问「A1 补的卡内容全吗」—— 问得对，不全）：

| 段 | 做什么 | 现状 |
|---|---|---|
| **① 起骨架** | 归位表的 `orphan` 名字 → 提案项。**必然只有 `name`** | 要新写（A1） |
| **② 补全** | 拿名字补 `appearance` / `background` / `personality` / `abilities` … | **能力现成**：`prompt-language.ts` 的 `detailSystem`（「只为指定的冻结角色身份补全紧凑资料」）+ `detailContract`（每字段**必须非空**，未知也要写「未知/待补充」）。但入口绑在角色架构流程里（`architecture.command.ts` 的 manifest → detail 两段），**输入是架构材料，不能只喂名字** |
| **③ 落库** | 走提案链 `approve` | 现成 |

`characters` 的写入只校验 `name` 非空（`character-roster-repository.ts` 的 `validateFields` + name 检查），
所以**只有名字的卡技术上能落库** —— 这正是必须警惕的地方：它是一张空壳卡，而 §4.4 里那个
`retired=1` 的空壳「刘三」就是这么来的。**归位表不该生产空壳卡**，所以 ① 之后必须串 ②。

②要落地只需要一件事：把 `detailSystem` 段从架构流程里**取出来单独调**，输入成「最小 manifest（slotId + name）」。
`detailTask` 的输入形态（`manifest` + `slotIds` + `validatedPrefix`）本来就支持这个用法，缺的只是调用点。

W4b（六槽 + 设计意图栏）等 W4a 接线后拿真实数据再定，**不提前落 schema**。

### 18.5.1 实施裁决（2026-10-22，与设计稿 A1 的差异）

A1 写的是 `{ kind:'cast-ledger', names }` —— **只有名字就 stage**。实现改成 **先生成、后 stage**：

```
source = { kind:'cast-ledger', names, handle:{projectId,epoch,rootActionId,runId}, artifacts:[{artifactId,revision,textHash}] }
```

三条理由都是代码事实：

1. `character-proposal-service.ts` 的 `readEnvelope` 每次重算 `sourceProof` 并深比较，`proposalBatchId` 又由 `JSON.stringify([projectId, source])` 决定 ⇒ **改 source 就是改批次 id**，旧批次永远 `pending`（判据 CX：不产生永远无法应用的项）。
2. 提案项只能由 proof 派生（同一文件 :203-223 的 items 构造），只带名字的 proof 无法产出可批准字段。
3. 先 stage 再补全 ⇒ 库里存在过「只带名字的可批准批次」⇒ 一旦有人在这窗口点通过，就是 §4.4 那种空壳卡。**先生成后 stage 让它结构上不可能存在。**

因此「三段流水线」在实现里的形状是：**② 补全（生成 + proof）→ ① 骨架（stage 时 items 由 proof 派生）→ ③ approve**。写路径仍然只有 `approve → commitCharacterIdentities`，没有新增。

另外两条落地细节：

- 归位表命令 `src/services/workflows/commands/cast-ledger-completion.command.ts` 在 stage 前**重查一次 `db:character-get-all`**：名字在这期间已被建卡就整批报「名单已变化，请刷新世界状态后重试」，不做静默剔除（避免部分覆盖）。
- detail 产物里的 `currentState` **故意不投影**进新卡（`CharacterStaticFields` 无此字段，`decodeCharacterDetails` 也把它压成 `updatedAtChapter=0`）⇒ 新卡状态是「未观测」，不是伪造的第 0 章状态（判据 CS）。

### 18.6 因此的排期变化

原计划 W4 → W5 并列，现在变成 **W4a 纯函数（✅）→ W5 视图（✅，含归位表接线）→ W4b（schema，未动）**。
理由不是顺序偏好：归位表不落地任何界面，它的价值只在「被看见」，而看见的地方就是 W5。

## 19. 一人多身份与角色卡别名（2026-10-22 评估 · 未开工）

作者提出的意象：主角叶凡因剧情需要经常改头换面、甚至造出另一个身份（如「张三」）。问：现有系统下建第二张卡、在人物关系里写「二者实为一人」，这种关联性**够强吗**。

### 19.1 结论先说

**弱。弱到几乎等于「作者自己记得」。**

那句「实为一人」是一句**写进数据库的注释**：结构上有源、有目标、有审批、有快照，看着很硬；但 `relation` 是自由文本，全库**没有任何一处代码按它的内容做判断**。系统不会因此让两张卡共享状态、共享道具、互相认名字，也不会在归位或交叉判定时把它们并成一个人。

### 19.2 现在只有两条通道，能力都很窄

| 通道 | 结构 | 机器读它做什么 | 缺什么 |
|---|---|---|---|
| **`character_aliases`**（别名） | 有 `valid_from` / `valid_through` 窗口 | **真读**：① 进定稿提示词（`finalizedCharacterPromptCards` 带 `aliases`）② W3 交叉的名字映射 ③ W4a 归位表把别名当等价 | **没有手工入口**：写入点只有两处 —— M02 迁移把旧 `characters.name` 记一条，提案链 `create` / `rename` 时插一条（改名才产生）。`src/**/*.tsx` 里搜不到 `aliases`，UI 上**无处添加** |
| **`character_relationships`**（人物关系） | `source_character_id` → `target_character_id` + `relation` 自由文本 + 审批 + 双方显示名快照 | **只有渲染**：正文生成提示词里变成 `relationship: 张三 (实为同一人)` 一行字 | 无任何语义解析。没有人按 `relation` 做合并、写回、归位 |

两句话概括：
- **别名有机器语义，但没有入口**（它的语义还是「曾用名」，不是「另有一身份正在使用」）。
- **关系有入口，但没有机器语义**（且它是唯一一条能进正文提示词的通道）。

### 19.3 若按「两卡 + 关系写实为一人」，系统会怎么错

四条都是代码事实，不是设想：

1. **状态分裂，永不汇合。** `cs_*` 六列挂在 `characters` 表的**行**上（`baseline-schema.ts` 第 75 行建表、第 92 行 `cs_key_items`），按 `character_id` 存。叶凡的灵石余量与伤势记在卡 A，「张三」记在卡 B —— 系统里从此有两个人的账，作者得自己心算「其实一共 6 枚」。
2. **W3 交叉会静默写到错卡，而且不报冲突。** 审稿说「张三 灵石 6 枚」⇒ 名字映射命中卡 B ⇒ 写卡 B；定稿说「叶凡 灵石 4 枚」⇒ 写卡 A。**两边都成功**，没有任何机制发现这是同一个人被写了两次。判据 DA 的三档在这里完全失效 —— 因为它比的是「同一张卡同一字段」的两个观测，跨卡根本不会进比较。
3. **W4a 归位表会把「张三」判成 `carded` 并静默通过。** 它确实命中了卡 B。四档状态里没有一档叫「这可能是别人」——**这是归位表的固有盲区**，不是 bug：它只对账名字到落点的映射，不知道也不该猜身份重合。
4. **最糟的一条：提示词按一人写、数据按两人存。** 关系渲染进了正文提示词（`generate-draft.command.ts` 第 2086 行），所以模型读到「张三与叶凡实为一人」，会按一个人写；但结算层（状态写回 / 归位 / 交叉）不认识这句话，按两个人算。**分裂发生在模型与系统之间，而且两边都不报错。**

### 19.4 三档，代价递增

| 档 | 做法 | 解决什么 | 不解决什么 | 动 schema |
|---|---|---|---|---|
| **L0** | 现状：两卡 + 关系写「实为一人」 | 人看得懂 | 以上四条全中 | — |
| **L1** | **一张卡 + 别名**（给别名补一个作者可写入口） | 状态不分裂、交叉不写错卡、归位表直接判 `carded` | 卡上只有一份 `appearance` / `background` ⇒「张三」的易容后外形与编造履历**无处安放**，只能挤进 `notes`；且与提示词第 6 条（「不要为同一对象使用多个别名」）直接冲突，要为「作者显式登记的身份」开口子 | ❌ 不动表，但要加写路径 + 提示词开口 |
| **L2** | **一人多身份**：卡 = 人，身份 = {名字, 外观, 对外身份, 谁知道真相}；状态仍记在人身上 | 上面全部，加上「两个身份各有外观」与**「外人只认识张三」这个悬念本身** | —— | ✅ 新表 + 改归位/交叉的名字解析 |

### 19.5 判断与建议

**L0 现在就够用，但只在你不需要系统算账时够用。** 如果叶凡与「张三」的灵石、伤势、地点你愿意在脑子里分开记，L0 不是错的选择 —— 关系那句话至少能让**模型**不写串。

**L1 是性价比最高的一档 —— 但作者 2026-10-22 已判定「L1 肯定不够用」，理由见 §19.7。**
它仍有一个硬前提现在不成立：别名没有入口。 这是最小的一片真缺口 —— 补一个「给这张卡加一个名字」的动作（仍然走提案链的 `approve`，写路径唯一），L1 立刻可用。它顺便修掉一个既存问题：现在作者改了名，旧名只在 `valid_through` 里留一条，**正文若回头写旧名会归不到卡**。

**L2 才是那个意象的真正落点，但它不是"补字段"，是新概念。** 关键差别不在"能不能有两个名字"，而在**「外人只认识张三」本身是剧情资产**：系统若认定两者是一人，就可能在任何面向读者的位置把真相漏出去（比如角色卡面板、关系图、待裁决候选的显示名）。所以 L2 的核心表不是 `character_identities`，而是**「谁知道」这一维**——那是信息可见性，不是状态。

### 19.6 待作者定

| # | 议题 | 说明 |
|---|---|---|
| 1 | **先做 L1 还是直接 L2** | L1 是「同一人两个名字」，L2 是「同一人两个身份」。若你的用法主要是**临时化名**（躲人、递话、留假名），L1 够；若是**长期假身份**（有独立履历、独立社会关系、别人真的不知道），L1 会把设定挤成 `notes` 里的一段话，不如直接 L2 |
| 2 | **若 L1：别名入口放在哪** | ① 角色卡编辑面板加一个名字列表 ② 复用提案链的改名动作（把别名当"改名但旧名仍有效"） |
| 3 | **若 L2：可见性维度的粒度** | ① 全局「知道/不知道」两档 ② 按角色分别记「谁知道」 ③ 按势力/阵营 |

**本轮未改任何代码**：这是新概念的取舍，不是补一个字段能定的。归位表的 `ambiguous` 一档恰好是 L1/L2 落地后会高频出现的形态 —— 它现在只报「命中多张卡」，不报「这两张可能是同一人」。

### 19.7 三种形态，两个正交维度（作者 2026-10-22 给出·取代原「L1 够不够」的问题）

| 形态 | 作者 | **读者** | 角色 | 生命期 | 系统真正缺的能力 |
|---|---|---|---|---|---|
| **(a) 反派双底** | 知 | **揭示章前不知**（连读者一起瞒） | 本人知，他人不知 | 全书 | **时间维**：揭示章 + 禁止提前写穿 |
| **(b) 主角伪装**（躲暂时无解的矛盾） | 知 | **全程知** | 本人知，他人不知 | 长线 | **认知维**：谁认识哪个身份 |
| **(c) 临时伪装**（扮龙套打探） | 知 | 全程知 | 本人知，他人不知 | 数章 | **寿命**：随章失效 |

三者的差别**不在「真假」，在两个互不替代的维度上**：

- **读者知情与否** —— (a) 否，(b)(c) 是。这一维决定「要不要给模型上禁止写穿的约束」。
- **身份寿命** —— (a)(b) 长，(c) 短。这一维决定「值不值得建长期结构」。

**为什么一张卡 + 别名（L1）一定不够**：L1 只能表达「两个名字是同一个人」，不能表达「这两个名字**各自是什么样的人**」。而 (a) 的明面正道身份与真实 BOSS 身份，**外观、修为、说话方式、社会关系全两套**。一张卡只有一份 `appearance` / `background`，无论写哪套，另一套就是错的。挤进 `notes` 更糟 —— `notes` 同样逐章进提示词（`generate-draft.command.ts:2081`），两套描述会同时注入，模型只能混着写。

### 19.8 (a) 那种「连读者都瞒」，靠的是什么

**不能靠「不告诉模型」。** 模型不知道 A = B 时，会把两个身份写成两个不相干的人：动机不接、行为逻辑割裂、埋的线收不回来。读者复盘时看到的不是伏笔，是破绽。

**正确姿态是「告诉 + 划定期界」**。库里已有同形先例，而且两种姿态都出现过：

| 链 | 机制 | 姿态 |
|---|---|---|
| 正文链 | `architecture-projection.ts` 把远期整节替换成一行声明 | **不给**（省 token） |

(a) 要的是后者那套措辞，作用在**人物层**而不是世界观层。所以 (a) 的产物不是「藏起来的事实」，而是

### 19.9 对三档的修正结论

作者说 L1 不够用 —— 成立。但 L1 并非没有位置：

| 档 | 对应形态 | 判断 |
|---|---|---|
| **L1**（一卡多别名） | **(c) 临时伪装** | **正好够，而且现在就能表达**：别名窗口 `valid_from` / `valid_through` 本来就是「这个称呼在第几章到第几章有效」。缺的只是作者可写入口。**但这不该叫 L1 的全部价值** —— 它解决的是「短命称呼」，不是「另一重身份」 |
| **L2a**（身份分面 + 揭示章） | **(a) 反派双底** | 必须做，且**是 L2 的第一优先**：它没有 (b) 的替代路径（不解决就只能二选一地错，见 §19.3 第 4 条） |
| **L2b**（per-observer 认知） | **(b) 主角伪装** | 第二优先。难点不在隐瞒（读者已知），在**一致性**：正文里必须始终按「他人只认识假身份」写 |

**(a) 与 (b) 的共同地基是「身份分面」，差别只在多不多一维「揭示章」**。所以合理顺序是：
先做身份分面（一张卡 N 个身份，各自外观与对外身份；状态仍记在人身上）→ (a) 加揭示章 → (b) 加观察者。
**先做 (b) 的观察者维度会错**：没有身份分面，「谁知道」没有可指的对象。
