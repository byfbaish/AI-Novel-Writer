## 0. 四问

| 问 | 答 |
|---|---|
| **行业里叫什么** | **power system**（也作 magic system / 能力体系；网文侧叫「金手指」，英文侧对「逐级变强」用 **progression / progression fantasy**）。限制的三分法出自 **Sanderson's Second Law**（Brandon Sanderson，2012）：**limitations > powers**，且限制分 **hard limit / weakness / cost** 三类；**Third Law**（2013）要求「先扩展已有设定，再新增设定」。第一定律（2007）：「读者能理解的能力，解决冲突才可信」。本稿全部术语用这五个：power system · hard limit · weakness · cost · progression stage，不造新词。 |
| **谁消费它的产出** | **写第 N 章之前的正文链**，且今天确实缺这一口。已核代码事实：`golden_finger` **从不进正文请求** —— 全仓只有 `architecture.command.ts`（架构规划）调 `withGoldenFinger`；正文请求的 `{{architecture}}` 由 `generate-draft.command.ts:2050-2076` 拼成，只含 **前提 + 世界观 + 情节大纲**，没有金手指。所以模型写第 N 章时，对「主角这条能力的代价条款」**一个字都看不到**。<br>今天的替代通道只有两条，都漏：(a) `characters.abilities`（只注入**本章出场角色**的卡，`generate-draft.command.ts:2171`）；(b) 【本书规则】从世界观第 1 维抽 ≤3 条（`worldbuilding-rules.ts`，每维上限 3 条、按模态词表筛）。实测这三本书的【本书规则】各**抽满 8 条上限**，第 1 维只剩 3 个名额 —— 修仙本的第 2 条「因果反噬判定标准」被挤掉，都市本（两版）的「真信即豁免」「载体盲区」全部被挤掉。<br>**因此不是只多一块面板**：多出来的东西是「一条带章号的、能在 640 字内被读到、且能说『本章还不能用』的限制句」。<br>反证：修仙本第 1 章审稿实测报出一条 `剧情合理性` finding ——「世界观与金手指机制规定须『击杀仇敌后提取功法记忆』方可推演。但刘三此后『从地上爬起来……才出去』证明其未死……**破坏金手指限制逻辑**」。审稿能查（它拿到整篇世界观），正文链不能防（它拿不到）。 |
| **失败形态在行业分类里属哪一类** | 人物塑造 · **forgotten abilities / skill fluctuations**（能力被遗忘、强弱漂移）—— 不是数值矛盾，所以不用账本。上一条 finding 就是它的变体：**触发条件被写软**（「必须击杀」变成「拧一下脚踝就触发」）。同一类的第二种表现已在数据里：主角 `abilities` 只有 **35 字**，而六个配角是 **139–245 字**（`characters`，修仙本），主角的能力是全书**最薄**的一条文本。 |
| **已有产品/论文做过什么** | story bible 类工具（Scrivener / NovelCrafter / Sudowrite 一类）与写作课都把 magic system 记成**一段自由文本**；这正是本仓现状（`golden_finger` 一段 223–406 字、`characters.abilities` 一人一段）。把「硬限制 / 弱点 / 代价」拆成**可注入短语**并带**阶段**，通常是游戏设计里的做法，不是写作工具的做法。<br>**我们的差异是需求差异，不是功能差异**：长篇网文的金手指要被同一个模型在几百章里反复使用，因此需要的不是「更全的设定库」，而是「每次落笔前 640 字内读到的那三条约束」。<br>⚠️ **本轮未做外部产品实测**（本期取样只覆盖本机项目库与本仓代码），上段对同类产品的描述属公开资料层面的常识，不作为验收依据。 |

**两种典型崩法（本仓数据里都出现过）**

- **触发条件漂移**：设定写「击杀仇敌后方可掠夺」，正文写成「拧一下脚踝就掠夺」——审稿抓到了，正文链没拦住。
- **代价消失**：世界观第 1 维用整节写「雷劫难度随杀伐非线性上升 / 因果反噬」，而**已写的 4 章正文里「雷劫」0 次、「反噬」0 次、「代价」0 次**（`drafts` ⋈ `contents`，10,063 字）。样本只有 4 章、剧情还没到渡劫，**不能据此断定流水线丢了代价**；但能确定一件事：代价条款今天**没有任何一条通道**能保证被写到。

## 2. 建议的字段形状

### 2.1 与计划 §1.3 的偏离（先摊开）

| 项 | 计划 §1.3 | 本稿建议 | 为什么 |
|---|---|---|---|
| `evidence` 的语义 | 与物品/知情同形（章号 + 逐字引文） | **保留逐字引文，新增 `evidence_scope`** 标明出处域 | 三本书的能力出处 **100% 是设定文本**（`golden_finger` / 世界观第 N 维），**0% 是章号**（F5）。没有出处域，UI 只能把「世界观第 1 维那句话」渲染成「来源第 3 章」—— 那是**伪造章号**（判据 DN 同型），比不写更糟 |
| 登记主体 | 隐含「一条 = 一种能力」 | **明确：只登「本书级规则能力」，不登角色技能** | 角色技能已经在 `characters.abilities` 里，且**已随角色卡进正文**（`:2171`），再登一份就是第二套账（W6）。见 §4 |
| `name` | `UNIQUE` | 保留，但**面板必须能一键从金手指原文取名字** | 三本书里只有 1 本有现成名字（「噬魂推演录」）；1 本有引号短语（「每日一次的现实编辑权」）；1 本**完全没有**（都市本 B）。`name` 是唯一必填项，卡在这里作者就进不去 |
| 其余 9 列 | — | **不改** | 三列的取样支撑见下 |

### 2.2 DDL 草案

```sql
CREATE TABLE power_abilities (
  ability_id     TEXT PRIMARY KEY,
  name           TEXT NOT NULL UNIQUE,
  form           TEXT,            -- 形态短语（系统/宝物/导师/功法/天赋/知识/规则，或混合描述）。无 CHECK。
  hard_limit     TEXT,            -- 硬限制：永远做不到什么 / 触发的必要前提
```

### 2.3 逐字段判定（每行必须二选一：取样支撑 / 落不住的理由）

| 列 | 判定 | 取样支撑 或 落不住的理由 |
|---|---|---|
| `ability_id` | **落得住** | 与既有三格同形（`key_items.item_id` / `cadence_id` / `knowledge_id`）。无争议 |
| `name` | **落得住（需改口径）** | 支撑：修仙本「金手指名称：噬魂推演录」。落不住的部分：都市本 B 的 `golden_finger` **通篇没有名字**，只有机制；都市本 A 只有「每日一次的现实编辑权」这个引号短语。⇒ 列保留，**但必须提供「从金手指原文取首句/取引号短语作为名字」的入口**，否则 2/3 的书第一步就卡住 |
| `form` | **落得住** | 见 §2.4 的逐条归类：三本书的**每一条**都跨类（修仙本金手指 = 规则 + 功法 + 天赋寄生；玄真子 = 功法 + 知识 + 宝物权限；都市本 B 的记事本 = 宝物 + 规则）。**不设 CHECK** 的决定被数据支持：定枚举等于替作者切一个切不开的东西 |
| `hard_limit` | **落得住（3/3）** | 修仙本：「必须击杀仇敌后方可掠夺」「每日只能承受一次超越境界的灵力注入」「此限制无法通过任何丹药修复」；都市本 A：「被动触发+不可控+不可撤销」「仅限第一句」「不可说能力本身，否则当天失效」；都市本 B：「三条铁律永不解除」「写下来、发出去、梦话都不算」。⇒ 这个字段**不是空气**，每本书都写满了，只是写在自由文本里 |
| `weakness` | **落得住（3/3），且是三类限制里最好填的** | 修仙本：洞 1-4 的「体系漏洞」+ 配角卡里的「死破绽」「最致命的破绽」；都市本 A：「真信即豁免」「判定依赖信念……最大的缝」；都市本 B：「现实打架的三条件」= 敌人当面揭穿即可。<br>⚠️ 与开工前的预判相反：**这不是最容易落不住的字段，而是最容易落住的**。原因是网文作者写金手指时几乎必然要写「怎么破」，否则爽点没有张力。措辞上是「漏洞 / 破绽 / 缝 / 打架条件」，不是「弱点」——**UI 提示语必须用作者的话，不能用术语** |

| `stage_note` | **落得住** | 修仙本「开局 / 中期 / 后期」三段；都市本 B「从『用废话拖住第一句』到『以最小代价说谎』再到『主动制造细节矛盾』」；配角卡「锻体境初期」「炼气大圆满」。⇒ 阶段的**名字**有，阶段的**章号**没有 |

## 3. 三个「为什么不」

### 3.1 为什么不叫 `abilities`

`characters.abilities` 是**真实存在的列名**（`pragma_table_info('characters')` 三库一致），装的是「这个人会什么」的一段 35–245 字自由文本，而且**已经随角色卡进正文**（`generate-draft.command.ts:2171`）。若新表也叫 `abilities`：

- 两个同名不同义的东西会在代码搜索、迁移 verify、便携字段白名单里互相冒充；
- 作者会以为「我已经在角色卡里填过能力了」，从而不去登记本书级规则 —— 而这恰恰是今天**唯一没有通道**的那一半；
- 更糟的是数据层：`characters.abilities` 是**静态档案**，`cs_*` 是**当前状态**，新表是**本书规则**。三者主语不同（人 / 人此刻 / 书），同名会把「谁的能力」这件事永久搅浑。

`power_abilities` 里的 `power` 是行业词（power system），`abilities` 保留复数是因为一行 = 一种能力规则（不是一个人）。

### 3.2 为什么 `form` 不设 CHECK

数据直接回答：**18 个实例里有 3 个横跨两到三类**（§2.4），且混合不是作者偷懒 —— 修仙本的金手指「噬魂推演录」名字像宝物（「录」）、机制像规则（天道信号）、载体是天赋（寄生神魂）。行业资料也明确「类别界限并不分明，常是几种特性的混合体」。

定 CHECK 的后果是可预测的：作者为了存下去，会挑一个「最不冲突」的类别，于是数据里 `form` 与真实机制脱节，而 `form` 一旦进入注入文本，模型就会按那个错类别写（把规则型宝物写成「掏出法宝」）。**词表只作 `datalist` 提示，词表外照样保存、原样渲染**，这一条要写成测试（词表外值 `SELECT` 回来必须一字不差）。

### 3.3 为什么不记次数 / 冷却 / 积分

四个理由，从硬到软：

1. **ADR-0022**：派生数值不进上下文，模型会拿它当既定事实写进正文，而那个数字从来没有作者确认过。
2. **数据里没有这个位数**：三本书的 `golden_finger` 与第 1 维里能算成「次数」的只有「一天一次」「每日只能承受一次」这类**规则本身**（属 `hard_limit` 的原文），没有「已用 3 次 / 还剩 2 次」的账。`resources` 表有 `resource_movements` 逐章累加，能力没有对应物，硬造就要再造一张变动表。
3. **它和「账本」是两回事**：资源有余额是因为「灵石会花掉」；能力不是消耗品，「今天还能不能用」由 `hard_limit` 的原文决定（比如「每日只能承受一次」），**不需要我们替作者数**。
4. **一旦记了就必须对账**：记次数就要判「这一章用了几次」，这是从定稿正文里抽事实 —— 而本期明确不做自动抽取（模型说的不算数）。

> **若作者认为必须有**：写成「提议，待作者裁定」，不进 M17 表：`usage_ledger(ability_id, chapter_number, count, evidence)`，按 `resource_movements` 同形另立一期。**本期不建**。

## 4. 与相邻格的划界

一句话：**有归属与转手 = 物品；有硬限制/弱点/代价 = 能力；有数量增减 = 资源。** 同时成立就分别登记，**不做跨表外键、不做「主登记」**。

| 边界 | 判据 | 真实例子（三库） | 怎么登记 |
|---|---|---|---|
| 能力 ↔ 物品 | 有没有**归属**（谁拿着 / 能不能被夺走） | 修仙本「**执法铜牌**」：`key_items` 一行（在玄真子手里、可被夺）；`power_abilities` 一行（`form`=宝物，`hard_limit`=「持牌方可调用，牌失则禁制不可用」） | **两行，各说各的**。物品行回答「牌在谁手里」，能力行回答「有牌能做什么」 |
| 能力 ↔ 资源 | 有没有**数量增减** | 修仙本 `resources` 7 行（下品灵石 / 聚气丹 / 九转回魂草 / 活气散 …，各有 `unit` + `period` + `resource_movements` 逐章累加）；金手指不产灵石 | 能力不记数量；金手指如果「产资源」，那是资源格的事，能力行只写规则 |
| 能力 ↔ 角色卡 | 有没有**角色归属** | 玄真子的「最致命的破绽」已在 `characters.abilities` 且已进正文；金手指「噬魂推演录」在全库**没有任何角色列**装它 | **有角色归属 ⇒ 留角色卡**（`characters.abilities` 已经是它的家，再登一份就是第二套账）；**无角色归属、属本书规则 ⇒ 登本表** |
| 能力 ↔ 知情 | 是否「谁知道」 | 「林恪能凭语气识破撒谎」是**能力**（他会不会），不是**知情**（他知道哪件事） | 能力登本表；「谁在第几章知道了金手指存在」登 `knowledge_states` |
| **「小绿瓶」型**（计划里的典型） | 同时是物品 + 能力载体 | 取样中的同型实物：都市本 B 的**记事本**（`cs_key_items` 有它、「写下来的不算数」是能力） | **物品一行 + 能力一行**，`name` 可同名，两表各自独立。**不合并**：合并后「记事本丢了」这件事在能力行里没有位置（能力还在，载体没了），而「载体没了能力还在不在」正是作者要写的那场戏 |

**一个刻意的空缺**：本表**没有 `character_id`**。三本书里 `characters.abilities` 已经覆盖角色技能（7/8、8/9、12/12 填满），而主角金手指在 `characters` 里**没有任何槽位**（F2：`cs_power_level` 全空、无 `cs_abilities`）。这个不对称本身就是划界的依据，不是遗漏。

## 5. 注入口径

```
【能力（本书的能力规则：能做什么、要付什么、什么情况下会被破）】
以下是作者登记的能力规则；未登记的用法不在本节范围内，不得据此推定无限制。
- 噬魂推演录（规则·功法·天赋混合；作者登记，未标章号）：硬限制——必须击杀仇敌后方可掠夺功法记忆，每日只能承受一次超越境界的灵力注入；代价——每次吞噬向天道发送一次坐标，雷劫难度随之上升；弱点——蚀毒未清时强注灵力即经脉爆裂
- 每日一次的现实编辑权（规则；作者登记，未标章号）：硬限制——一天只有第一句、不可撤销、不可预知；代价——成真素材从最近的记忆里挪用；弱点——当面指出这句话是假且尚未落地时，现实会打架
```

> 两行都是 `undated`（真实数据里没有一位作者标过章号）。`active` 分支只是把括号换成「自第 N 章起」，**本期样例里不出现具体章号**，以免看起来像编的。

- **位置**：`【知情】` 之后、`【本书规则】` 之前（顺序 facts → items → cadences → knowledge → **abilities** → rules，`prewrite-consultation.ts:174-182`）。理由：能力是「能做什么」，规则是「什么不许做」，约束条款收尾最不易被忽略。
- **上限**：**5 条 / 640 字**；装不下**整条丢弃**，不截半行（截断的限制句会变成一条更宽松的规则，比不写更危险）。
- **三态**：`active`（`stage_chapter ≤ 本章`）注入，行首标「自第 N 章起」；`ahead`（`stage_chapter > 本章`）**一律不注入**（剧透）；`undated`（`stage_chapter IS NULL`）**注入**，标「作者登记，未标章号」——**绝不写「第 0 章」或「当前章」**（判据 DN 同型）。
- **缺字段怎么渲染**：`hard_limit` / `weakness` / `cost_note` 哪一段为空就**整段省略**，**不写「未登记」**。理由：注入文本里的「限制未登记」会被模型读成「**没有**限制」，比不写更糟；缺失提示只放在登记页（黄条），与制度槽 `note` 不进提示词同一原则。**这是对判据 DN 的一处刻意例外，理由如上，测试要钉住「空字段不产生任何字节」。**
- **排序**：`active` 与 `undated` **混排，统一按 `name` 码元序**（不用 `localeCompare`）。不按「强度」排（需要派生数值）、不按「出场角色」排（本表没有 `character_id`）、不按「解锁先后」排（`undated` 无章号可比）。5 条以内，顺序不承载语义；固定码元序的好处是可测、且不随数据抖动。
- **空数组 ⇒ 整节不出现**，材料块逐字节不变（四条旧哈希 + `{cadences}` + `{knowledge}` 一字未改，本期只新增 `{abilities}` 一条独立哈希）。

- **`stage_chapter` 的真实数据是空的**：三本书都没有章号级解锁。这一列在可预见的项目里会长期为空，`ahead` 的期界过滤是「为将来准备的开关」。期 4b 不得宣称「解决了剧透」，只能说「提供了出口」。
- **`evidence_scope` 是本稿唯一的形状新增**：若作者驳回，退路是「`evidence` 存带前缀的字符串（`金手指：…`）」——但那等于把结构塞进自由文本，渲染层要猜，**不推荐**。
- **`cost_note` 与 `resources.cost_note` 同名不同义**：后者在 `m11-resource-ledger.ts:29` 是「这种资源换进来要花什么」，前者是「用一次这个能力要付什么」，且 `resources.cost_note` 在修仙本 7 行里**全空**（作者从没用过）。建议：**不改名**（改了与计划 §1.3 冲突），但在迁移注释与登记页面板里逐字写明两者不同义。
- **`characters.abilities` 的质量不可控**：26/29 条是 `generated`（模型生成后采纳），主角那条最薄（35 字）。本表不接管它，也**不能**替它兜底；「主角能力写得比配角薄」这个现象值得单独一期（属角色卡质量，不属能力槽）。
- **本轮未做外部产品实测**（四问第 4 条已声明），差异论证只有「需求差异」这一层，没有功能对比表。
- **未验证真实注入效果**：本期没有跑生成、没有做 A/B。第 6 节是否真的降低「触发条件漂移」，要等期 4b 的 G4 与之后的实机观察。

## 8. 不做（防下一轮发明）

- ❌ **角色技能登记**：`characters.abilities` 是它的家，已进正文；本表只登「本书级规则能力」（§4）。
- ❌ **次数 / 冷却 / 积分 / 强度等级 / 技能树**：ADR-0022；要做得另立 `usage_ledger`，本期不建（§3.3）。
- ❌ **自动抽取**：不从 `golden_finger` 或定稿正文里猜「硬限制是什么」。模型的复述不算作者事实（与制度锚、「谁在第几章知道了什么」同一原则）。
- ❌ **`form` 的 CHECK 约束 / 把混合体拆成多行**：混合是真实形态（18 个实例里 3 个跨类），拆行会让「这条能力到底怎么用」断成两半。
- ❌ **给 `power_abilities` 加 `character_id`**：加了就与角色卡变成两份账，且三本书里没有任何「能力 ↔ 角色」的登记需求证据。
- ❌ **`undated` 折算成「第 1 章」或「当前章」**：判据 DN 同型。未标章号就是未标。
- ❌ **在本表存金手指原文全文**：那是 `golden_finger` 的位置，本表只存**摘出来的那一句** + 引文出处；存全文就是第二套账。
- ❌ **用本表替换【本书规则】**：两者不得互相引用或互斥；能力槽回答「能用什么」，规则槽回答「什么不许做」。
- ❌ **把 `stage_note` 当「当前境界」使用**：它是**作者的阶段描述**（开局/中期/后期），不是「主角现在第几层」；「现在到哪了」属于 `cs_*` 当前状态，本期不碰。
