# 弧光的「逐节点展开」验证方案（exp/arc-tree-v2）

> 2026-10-18。作者裁定：**弧光层级的承载方式和一次性生成方式太重了，该有的职责信息没有，不该有的一堆**，
> 需要 fork 分支做技术验证。本文是**待评审的方案**，不含代码改动。
> 分支：`exp/arc-tree-v2`（从 `dev_byf` fork）。

## 1. 要验证的假设

一次性生成的毛病不是"重"，是**逼模型在同一个上下文里同时做 27 个决定**
（3 大弧 × 3 中弧 × 3 小弧）。上下文里同时有 27 个待决，模型只会**套格式**——
于是出来的东西格式整齐、一个都不错，但一个都不好看。

逐节点展开的本质是**把决策拆开**：每次只做一个决定，模型才有可能在这个决定上用力。

**验证目标**：同一份总纲，拆开生成的中弧，是否明显比一次性生成的中弧"有料"
（每条都能读出一个具体处境，而不是一句可以互换的套话）。

## 2. 范围：只做两层，小弧先不拆

| 层 | 本轮 | 理由 |
|---|---|---|
| 总纲 + 大弧 | 一次生成（含个数） | 全局只有一份，拆不开也不需要拆 |
| 中弧 | **逐个大弧展开**（每次只展开一个父节点） | 这是要验证的机制 |
| 小弧 | **不生成** | 少一层，承载立刻轻一半；中弧可直接承载必发事件 |

为什么敢砍掉小弧：`arc-node.ts` 的中弧本来就带结构位 ID（`M1-1`）与「转折」，
大纲的「覆盖：」对账不依赖小弧存在。小弧只是**更细的声明单位**，不是必需品。
若中弧承载不住，再把它加回来——加回来比一开始就带着容易。

## 3. 两轮提示词草案

### 3.1 第一轮：总纲 + 大弧（一次成型）

```
【全书问题】<一句话，能判是/否>
【全书时间跨度】<故事世界里的总时长>
【弧光个数】大弧 N 个（按总章数算；这一行之后不许再出现任何章数、字数）
【这个故事真正在赌什么】<一句话：他想要什么、挡住他的是什么、输了他失去什么>

## 大弧一：<名称>
- 从 <入口状态> 到 <落点状态>
- 这一段必须改变的是：<一件具体的事>
- 中弧个数：N（只写个数，不写标题）
```

规则（每条都对着一处真实翻车）：

1. **不写章数、字数、Σ、差额**（P18 已定：篇幅只用来算个数）。
2. **不写中弧内容**，只写个数 —— 越级写细节会让逐节点展开没有意义。
3. **不规定功能顺序**（入卷钩子 / 初次冲突 / 转折 / 扩张 / 低谷 / 卷末爆点）。
   每卷同一形状 = 全书 n 卷一个节奏（判据 BX）。功能由内容自己长出来。
4. **不设敌人分层**（小怪→精英→干部→卷BOSS→阶段BOSS→最终BOSS）。
   这是升级流的模型；都市 / 脑洞 / 轻喜剧没有 BOSS，照写会硬造一个出来（判据 BS/BR）。
5. 写"从哪到哪"时，只需**可达**，不需要必然（判据 CD）。写不出入口的那段 = 没有路，删掉或挪位。

### 3.2 第二轮：展开某一个大弧（每次只展开一个）

输入 = 总纲 + **该大弧全文** + 兄弟大弧的名字与一句话（不传其余内容）。

```
父节点（唯一展开对象）：
<粘贴该大弧全文>

为它写出 N 个中弧。每个中弧一行一字段，形如：

## 中弧 1：<名称>
- 从 <入口状态> 到 <落点状态>：<这一段结束时，世界和他各自变成了什么样>
- 必发：<一到两件必须发生的事>（写"什么变了"，不写"他用了什么招"）
- 赌注：<这一段没走通，他失去什么——具体、补不回来、挂在全书问题或本大弧的"必须改变"上>
- 入口：从上一段留下的哪个状态出发、靠什么走过去（写第一段时省略）

约束：
1. 不许写章数；不许开新的大弧剧情；不许解决全书问题。
2. 相邻两个中弧之间必须说得出**至少一种到达方式**；写不出的，不是"缺因果"，是**没有路**。
3. 中弧的落点不许越出本大弧的入口与落点之间。
4. **必发事件写"处境"不写"流程"**：如果两条事件能在同一天、同一个地点、面对同一个人做完，
   它们是一个场景，合并成一条。
5. 每一条必发事件问一句：走完它，他还能回到上一条的处境吗？能回到 ⇒ 这一步没有分量。
6. 不许"他知道了 / 他意识到 / 他确认了"作为唯一的结果——认知推进可以在一个场景里完成，
   处境推进不能。每条至少要有一处"世界变了"（谁掌握了什么 / 什么被拿走了 / 哪条路封了）。
```

## 4. 编排方案（建议 A）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（建议）** | 复用 `plot_structure` 这一个 key，跑 **1 + N 次**：第一轮出总纲与大弧，之后每个大弧跑一次展开；结果**拼接**成一份 markdown 写入 `plotStructurePlan` | 零 DB / 零契约改动；现有 `parseArcStructure` 直接认（`## 大弧` / `### 中弧` 就是它认的形状） |
| B | 新增 prompt key（如 `plot_structure_children`） | 要同步登记 `ARCHITECTURE_STEP_OPERATIONS`、`ARCHITECTURE_PRIOR_STEPS`、`agent-generation.ts` 的 `expectedOperations`（`generation-owner-contract.ts:34-40` 明写漏一个就抛 `GENERATION_PLANNING_INTENT_CHANGED`），成本高 |

方案 A 的两个技术点：

- **轮次区分**：给模板加一个**非必填**变量 `{{arc_pass}}`（`'outline'` / `'expand'`），
  由 builder 填；不进 `requiredContextVariables`（红线 16：进 required 会穿透作者覆盖版）。
  或者更省：两段文本都放进 `systemSuffix`，用 `{{step_guidance}}` 之外的第二个可选变量切换。
  **这点要先验证渲染层对"未声明的可选变量"是否原样保留**，否则会漏字面 `{{arc_pass}}`。
- **父节点上下文**：拼进 `arc_parent` 变量（同一份大弧原文），不塞进 `step_guidance`
  （`step_guidance` 是作者指导的位置，混用会让作者看到的指导变样）。

## 5. 回退

- 任一展开轮失败 / 解析不出中弧 ⇒ **退回现有的一次性生成**（现 prompt 原样保留为 fallback）。
- 拼接后 `parseArcStructure` 返回 null ⇒ 同样回退，并记一条 log（不静默）。

## 6. 验收（人眼，两条）

同一份总纲、同一个模型，旧版与新版各跑一次，只比两件事：

1. **中弧有没有料**：逐条读"必发"，能不能各自读出一个**不同的处境**？
   读起来可以互换（把三个中弧的必发事件打乱重配也不违和）⇒ 失败。
2. **大纲还能不能摊开**：新版弧光喂给现有大纲，第一章是否仍然一口吃完整段？
   若吃掉，问题不在弧光粒度，在大纲层的章级局面（那就别再改弧光了）。

## 7. 本轮明确不动

- DB schema（`sub_genre` 列早已存在，本轮只用不改）
- `arc-node.ts` 的结构位解析与「覆盖：」对账
- 大纲 ⑤⑥⑦（章级局面 / 章数给定 / 四来源三禁止）
- 三型 A/B/C 的**名字**（在方案 A 里它们根本没出现，等于事实上下线；是否删除留给验收后决定）

## 8. 已裁定的取舍（作者 2026-10-18「按建议来」）

| 事项 | 裁定 |
|---|---|
| 先验哪两层 | 大弧一次 + 中弧逐个展开，小弧不拆 |
| 功能固定六格 | 删（每卷同一形状） |
| 敌人分层 BOSS | 删 |
| 字数 / 章数 | 只做边界，不进节点内容 |
| "每个中弧只揭一层谜底" | 泛化成"只推进一层认知或一层局势" |
| 伏笔配额（消耗≤2 / 新埋≥1） | 删配额，只登记埋/收了哪条 |
| "每个胜利必须带出新问题" | 改成"每次解决要么付代价、要么引出新麻烦"（否则全书 no-and） |
