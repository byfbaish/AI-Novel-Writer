## 0. 一句话结论

**作者担心的两件事（撑爆上下文 / 越写越慢）是同一个原因：每个批次都把整段已完成大纲塞进 prompt，成本 O(已写章数)。**

按作者自己的两个规模算：

- **短篇**：40 万字 ÷ 2500 = 160 章，大纲 300 字/章 ⇒ **4.8 万字**；
- **长篇**：200 万字 ÷ 3000 = 666 章，大纲 300 字/章 ⇒ **20 万字**（作者原话「超过 20 万字」）。

20 万字大纲本身就是 **133k–200k tokens**，比 128k 上下文还大——**整段塞入在长篇上必然爆**，而且不是"最后才会爆"，是**写不到一半就爆**（§3 给断点）。

⇒ 修法不是加额度，是**投影**：把「已完成大纲前缀」从「全量」改成「**本卷全文 + 上一卷快照 + 最近 K 章**」。投影后输入**恒定 ≈ 2.6 万字**，与书写到第几章、第几卷都无关。**下游蓝图步骤早就是这么做的**（`projectSynopsisForBlueprint` 三段切分），只是大纲步骤自己没做。

⇒ 其中「上一卷快照」是本稿唯一新增的模型调用，形态与 **agent 压缩上下文 / 拍快照**同构：只记**要交给下一卷的**重要事件与物品，**生命周期终止于下一卷**（作者 2026-10-19 裁定，见 §5.4）。

⇒ 连带结论：一旦投影落地，E4 原设计的 `cap`（容量上界）**从"全局约束"降级为"本单元还剩几章"**，不再是全书级概念。真正该做的事变成了「大纲前缀投影 + 等待时间可见」。

⇒ 另外两件事也一并落在这里：**结构按卷冻结**（与定稿同机制、作者触发、当前卷永不冻，§8.1），以及**长卷单元的阅读体验**（默认折叠可全量展开 / 卷-单元只读树 / 滚动条 / 切 Tab 保留进度，§7A）。

## 1. 三个预算，别混成一个

作者这两轮说了三个不同的数，它们**不是一回事**，混起来就会得出错误的结论：

| 预算 | 单位 | 从哪来 | 谁消费 |
|---|---|---|---|
| **正文预算** | 全书章数 × 单章字数 | 小说配置页：`totalChapters` / `wordsPerChapter`（`ipc-channels.ts:658-659`） | 弧光模板 `{{number_of_chapters}}`、区间折算 `scaledBoundaries` |
| **大纲预算** | 大纲总字数 = 章数 × 大纲字/章 | 规划弹窗「大纲每章目标字数」`outlineTargetUnits`（`config.json`，当前 **300**） | `planningTargetInstruction('outline', …)`（`plot-outline-contract.ts:24-30`） |
| **上下文预算** | 单次请求能塞多少字 | 模型能力 + 代码里的字符/字节闸门 | **本文要解决的就是它** |

> ⚠️ **「1–5 万字」是"一整本书的大纲"的规模，不是每卷、也不是每单元。** 上一版稿子把它读成「每卷 1–5 万字」并据此推「应切 8–37 卷」，是错的，已删。作者本轮的算法（章数 × 300 字）才是唯一口径。

## 2. 实测：真实项目现在是什么样

项目 `如果我的能力是每天第一句谎言都会成真`（只读拷贝 `project_core` 统计）：

| 量 | 实测 | 说明 |
|---|---|---|
| `total_chapters` / `words_per_chapter` | **150 / 2500** | 37.5 万字 |
| 大纲每章目标（`outlineTargetUnits`） | **300** | 与作者本轮口径一致 |
| **实际大纲** | **591 字/章**（10 章，511–746） | 其中结构行 **122 字**（覆盖 4 + 选择 55 + 收尾 63），正文 **469 字** |
| 已写大纲 | 5,919 字 | `synopsis_covered_to = 10` |
| 固定材料（前提+角色+世界观+全局要求） | **11,348 字** | 每批整段注入 |
| 弧光结构 | 13,791 字 / 7 卷 28 单元 | 投影后更小（待测） |

**两个观察，都影响本文**：

1. **实际是目标的 1.6–2.0 倍**（正文 469 vs 300；含结构行 591 vs 300）。大纲不会"刚好 300 字"，所以下面所有外推都按 **300（作者口径）** 与 **591（实测）** 两个数分别给。
2. **结构行只占 122 字/章（21%）**，其中「收尾：」是**唯一**能跨章传递未决项的信号——投影要保住的正是它。

## 3. 规模外推：长篇在哪一章爆

换算口径：中文 **1 token ≈ 1–1.5 字**（区间都给），上下文占用按 token 算。

### 3.1 大纲本身的体积

| 规模 | 章数 | 大纲字数（300/章） | 大纲字数（实测 591/章） | 折算 tokens（300 口径） |
|---|---|---|---|---|
| 短篇 40 万字 | 160 | **4.8 万** | 9.5 万 | 32k–48k |
| 当前项目 37.5 万字 | 150 | 4.5 万 | 8.9 万 | 30k–45k |
| 长篇 200 万字 | 666 | **20 万** | 39.4 万 | **133k–200k** |

⇒ 长篇的**大纲全文**已经比 128k 上下文大。**"把大纲整个塞进去"在长篇上不是"可能撑爆"，是"数学上不可能"。**

### 3.2 前缀在什么时候超过可用输入

可用输入 = 上下文 − 预留输出（取 16k tokens）− 固定材料（11.3k 字 ≈ 7.5–11.3k tokens）。

| 上下文 | 可用输入（tokens） | 可用字符 | 按 300 字/章 | 按实测 591 字/章 |
|---|---|---|---|---|
| **128k** | ≈ 101k | 101k–151k | **337–505 章** | **171–256 章** |
| **64k** | ≈ 37k | 37k–55.5k | **123–185 章** | **63–94 章** |

⇒ **长篇 666 章：128k 模型写到 170–500 章之间就写不动；64k 模型 63–94 章就写不动。**
⇒ **短篇 160 章：128k 够用（勉强），64k 在 591 字/章下也会在 63–94 章处卡住。**

> ⚠️ 这里的 128k / 64k 是示意，不是本项目实测能力：`contextWindowTokens` 在能力未知时可以是 `null`（`generation-harness.ts:495`、`main-generation-plan.ts:250`），此时**闸门根本不存在**，失败会表现为**模型静默截断**而不是报错——比硬失败更难发现。真实数字由 E4a 的日志量。

## 4. 等待时间：为什么会"越写越慢"

两个独立原因，**只有一个是本文能治的**：

| 原因 | 机制 | 能不能治 |
|---|---|---|
| **输入变长** | prefill 与输入 token 数近似线性 ⇒ 第 1 章和第 400 章的首字延迟可以差十几倍 | ✅ **投影能治**（输入恒定） |
| **输出变长 / 重试** | 单章写超、触发 `maxContinuations: 3`（`architecture.command.ts:2413`）的自动续写 | ⚠️ 靠字数目标与探针，不靠本文 |

**代码里现在看不到缓存有没有帮上忙**：`electron/llm/openai-provider.ts:139-147` 只解析 `prompt_tokens / completion_tokens / total_tokens`，**没有 `cached_tokens`**；全仓 grep `cache_control` / `cached_tokens` / `prompt_cache` = **0 命中**。

⇒ 两个动作（都便宜）：

1. **解析 `prompt_tokens_details.cached_tokens` 并记进 attempt receipt**——否则"是不是变慢了"永远只能靠体感；
2. **保持 prompt 顺序稳定**。现在 `confirmedPrefix` 追加在 `taskPrompt` 末尾（`architecture.command.ts:2375-2381`），前面的模板/指令/材料逐字不变 ⇒ 天然是「可缓存前缀」。**投影落地后要保住这个性质**：把会变的部分（本批范围、状态块）放在稳定部分**之后**。

> 注意：**缓存只省时间和钱，不省上下文**。20 万字前缀即便全部命中缓存，仍然占 133k–200k tokens 的窗口。这两件事不能互相替代。

## 5. 修法：大纲前缀三层投影

### 5.1 先看下游已有的先例（这不是新机制）

蓝图步骤早就在做同一件事：`projectSynopsisForBlueprint`（`src/shared/synopsis-projection.ts:211-241`）把大纲按与本批的关系切三段——前序**剔除**（已由 `chapter_list` 承载）、本批**原样**、后续**降级为边界声明**。调用点 `directory.command.ts:413-430` 还专门用 `previous.slice(-100)` 计算"实际覆盖"的章号集合，避免误删。

⇒ **下游已经知道不能整段喂，上游大纲步骤自己没做。** 本稿就是把同一个纪律补到上游。

### 5.2 三层大纲记忆

| 层 | 给什么 | 来源 | 体积 |
|---|---|---|---|
| **L1 本批（本单元）** | 完整规格：卷五格 + 本单元四格 + 可声明结构位 | 弧光投影（已有 `withProjectedArcGuide`） | 随弧光投影，恒定 |
| **L2 本卷已写** | **全文**（本卷第 1 章 → 本批前一章） | `confirmedPrefix` 的**本卷切片** | ≤ 本卷章数 × 591；按 20 章/卷 ≈ 1.2 万字 |
| **L3 本卷之前** | **只有上一卷那一份快照**（事件 / 物品 / 债 / 未决项，见 §5.4） | 卷末快照（新增，每卷一次调用） | 硬上限 1,500 字，**恒定** |
| **L4 最近 K 章（K=3）** | 全文 | `confirmedPrefix` 末尾 | ≈ 0.2 万字 |

**投影后前缀 ≈ 固定材料 1.1 万 + 本卷 1.2 万 + 上一卷快照 0.15 万 + 最近 3 章 0.2 万 ≈ 2.65 万字（17k–26k tokens），与全书写到第几章、第几卷都无关。**

关键点：**弧光给方向，快照给「手上还剩什么」**。弧光的卷五格（卷叙事任务 / 进入与离开状态 / 结账）说明这一卷要完成什么；但它说不出「哪份记录落在谁名下」「哪扇门被封了」——那是已写内容里的事实，必须抽出来交接（§5.4）。

### 5.3 三条硬规则

1. **只改喂给模型的材料，不改落库正文**。数据库里的大纲仍是完整 20 万字（`project_core.synopsis` 是 TEXT，存得下），下游蓝图/正文/审稿都读全文。**投影只发生在 prompt 装配处**。
2. **解析不可靠时整体退回全量**（沿用 `synopsis-projection.ts:216-217` 的纪律：宁可多留，也不猜着丢作者事实）。
3. **L2 的边界必须由检查点给，不能由章号反推**——这与 E3 的「显式单元游标」是同一条约束（见 §7）。

### 5.4 卷末快照（= agent 的 compaction / snapshot）

**这是本稿唯一新增的模型调用，也是 L3 的来源。** 作者 2026-10-19 已确认方向：「类似 agent 压缩上下文 / 拍快照」，并给了三条硬约束。

> **先澄清两个词（作者 2026-10-19 追问）**：本文里的「冻结」和「快照」**不是一件事**，它们只是发生在同一个时点（一卷末 = 下一卷开头）：
>
> | 词 | 对象 | 动作 | 谁触发 |
> |---|---|---|---|
> | **快照** | **大纲内容**（已写出来的东西） | 压缩成一份交接单，喂给下一卷 | 系统自动，每卷末一次 |
> | **冻结** | **弧光结构**（卷/单元怎么切、`plotStructure` 枚举） | 原则上不再改；改则二次确认（事实层存在时拒绝） | 作者手动改时触发 |
>
> 一句话：**快照是「把这一卷的经验打包 + 留一个能回去的地方」，冻结是「暂时不许再动方向」。**
>
> ⚠️ **快照有两个身份**：① 喂给下一卷的交接单（`handoff`，≤1,500 字）；② 解冻回滚的锚点（`anchor`，含当时弧光全文，**永不进 prompt**）。见 §8.1.4。

#### 5.4.1 触发与产出

| 项 | 定义 |
|---|---|
| 触发 | 本卷最后一个单元写完（`unitIndex === midCount`），**且本卷大纲已落库** |
| 输入 | 本卷大纲全文 + 本卷五格（卷叙事任务 / 进入与离开状态 / 换的阻力 / 结账 / 时间密度） |
| 输出 | **快照 JSON**（见 5.4.2），落库；**不写进大纲正文** |
| 体积 | 硬上限 **1,500 字/卷**（约 1–1.5k tokens） |
| 失败姿态 | **不可用则退回「弧光里那一卷的离开状态」**（不阻断续写）；快照可被作者审阅、手改、重生成 |

#### 5.4.2 只记「要交给下一卷的」，且只在下一卷有效

作者原话：「只能是重要的事件、重要的物品，因为这些信息是要交给下一卷使用的。而生命周期终止于下一卷的冻结时间，即使有东西或者事件，比如说主线横跨数个卷章，但那个信息也是由当时要开卷的上一卷传递下来的，与数个卷之前的卷章不存在直接联系。」

⇒ **快照是「交接单」，不是「编年史」。** 字段设计必须体现这个生命周期：

```ts
interface VolumeHandoff {
  volume: number
  /** 本卷结束时世界与他各自的状态（一句话各一条） */
  worldState: string
  heroState: string
  /** 重要事件：下一卷必须承接的那几件（≤5 条），每条一行 */
  events: string[]
  /** 重要物品/凭证：现在在谁手上、什么代价换的（≤5 条） */
  items: string[]
  /** 未结清的债：下一卷必须还的（≤3 条） */
  debts: string[]
  /** 本卷末的未决项（来自最后一章「收尾：」行） */
  openThread: string
}
```

**三条写入纪律（直接来自作者的裁定）**：

1. **只写下一卷要用的**。写不出来的就留空——**留空是合法的**，不许为了填满而编。
2. **不写「已经结束的事」**。一卷内已经了结的支线、已经用完的道具、已经退场的人，**不进快照**。
3. **跨卷主线由「链」传递，不靠「全量累积」**：第 5 卷拿到的跨卷信息，来自第 4 卷的快照；第 4 卷的来自第 3 卷。**第 5 卷不读第 3 卷的快照**。

> 第 3 条是本设计的关键简化：它把「跨卷一致性」从 **O(卷数²) 的全量累积** 压成 **O(1) 的链式传递**，同时保住了「主线横跨数卷」的表达能力——因为每一环都只负责把「我这一卷改变了什么」交给下一环。

#### 5.4.3 注入形态：只注入上一卷那一份

```
【上一卷交接（卷 N−1）】
- 世界：…
- 他：…
- 必须承接的事件：…（≤5 条）
- 现在在谁手上的东西：…（≤5 条）
- 未结清的债：…（≤3 条）
- 未决项：…
```

**注入的是「上一卷那一份」，不是「所有卷的快照」**。所以这一段的体积恒定（≈1.5k 字），不随卷数增长——与 §5.2 的「输入恒定」是同一个目标。

#### 5.4.4 与「弧光本身就在控方向」的关系

作者 2026-10-19：「以前就是担心这个问题，所以才加了这一层来控制脉络。实际上现在的卷单元层级就是在控制方向。」

⇒ **快照不承担「控方向」的职责，那是弧光（卷/单元两级）已经在做的。** 快照只承担一件弧光做不到的事：**把「已经写出来的、弧光里没有的具体物」交接下去**——哪扇门被封了、哪份记录落在谁名下、谁现在知道了他什么。

| 层 | 控什么 | 谁提供 |
|---|---|---|
| 卷 / 单元两级结构 | **方向**（这一卷要完成什么、换什么阻力、失去什么） | 弧光（已存在） |
| 单元四格 | **这一段的对峙局面与逼法换代** | 弧光（已存在） |
| 卷末快照 | **已落地的具体物**（人 / 物 / 债 / 未决项） | **本稿新增**（每卷一次调用） |
| 本卷大纲全文 | **本卷内的连续性** | 投影的 L2（已存在） |

> 换句话说：**弧光管"往哪走"，快照管"手上还剩什么"。** 两者不重叠，所以快照不需要写方向性内容（那会与弧光形成第二事实源）。

## 6. 对 E3 / E4 的连带影响

### 6.1 `cap` 降级：不再是全书级概念

投影前：`cap` 随进度单调收紧，最终归零，看起来像个全局约束。
投影后：输入恒定 ⇒ 容量不再随进度恶化 ⇒ **`cap` 退化为「本单元还剩几章」**，由结构给出（卷内剩余章数），与上下文无关。

⇒ **E4 不需要"容量上界"这个新概念**。需要的只有一个：`maxChapters`（本单元的结构上界），供主进程冻结根预算（§7.1）。

### 6.2 状态块：保留但换触发量

E2 已证明「收紧/展开」两个方向有效（刚性组 −53%，稀薄组 +37%；限定：n=5、单模型 9b、温度 0.9，倍数不可当常数——上位稿 §2.5 注）。

| 信号 | 算法 | 动作 |
|---|---|---|
| 本卷已写 vs 本卷结构上界 | `本卷已写 ÷ 本卷章数上界` | 接近上界 ⇒ 注入「收紧」（原措辞不变） |
| 全书进度 | `covered_to ÷ totalChapters` | 只陈述，不下命令 |

**删除**：`Z`、`plannedUsed`、±10% 三档、卷计划额度。`planProgress`（`arc-position.ts:570-610`）降级为卷内统计（`actualUsed` / `midCount` / `bookProgress`）。

## 7. E3 的前置修订

### 7.1 「不给 `to`」在主进程层与检查点层都不自洽

| 位置 | 依赖 `to` 做什么 | 不给会怎样 |
|---|---|---|
| `electron/services/main-generation-plan.ts:139-145` | 根预算 `= priorSteps + 2 × (to − from + 1)`，再经 `scaledRootBudget` | 请求数无上界 |
| `src/shared/plot-outline-contract.ts:100-103` | `to − from + 1 ≤ maxPhysicalRequests` | 契约不成立 |
| `electron/services/main-generation-owner.ts:1376-1381` | 续批 range 必须 `isDeepStrictEqual` | 检查点无法描述「这一批到哪」 |
| `electron/services/agent-generation.ts:336-338` | agent 子 run 的 `{from,to}` 必须 deep-equal | 同上 |
| **`architecture.command.ts:703-708`** | **强制 `Number.isSafeInteger(range.to)`** 且 `coveredTo === range.to` | **检查点自己就不接受「没有 to」** |
| **`architecture.command.ts:618`** | 指纹里是 `range.from:range.to` | 实际 to ≠ 请求 to ⇒ 检查点/续批全失效 |

⇒ 正确形态：**批次声明 `{ from, unitIndex, maxChapters }`，主进程按 `maxChapters` 冻结预算，生成后解析回填真实 `to`，再把 `{from, to}` 写进检查点**。不是"永远没有 to"，是"**请求时没有、落库时才有**"。

**回填必须有越界规则**：实际章数 > `maxChapters` 时根预算已冻结 ⇒ 中途 `ROOT_BUDGET_EXHAUSTED`。建议生成后校验 `to ≤ from + maxChapters − 1`，超出则报「本单元超长，请回弧光拆分」并**保留已生成部分**。

### 7.2 单元游标必须带卷序号

`{ 卷序号, 单元序号, 本卷已写章数 }` 三元组。缺卷序号则卷末计数无法重置；缺「本卷已写」则 L2 切片的边界无处可取（§5.2）。

## 7A. 阅读体验：长卷单元的显示问题（作者 2026-10-19 提出）

作者原话：「卷纲这东西可能会非常长，到了后期要通览的话，也很困难。那么结合现在的冻结机制，可能还要实现**分卷显示**的问题。而且由此引出在体验中遇到的其他问题，比如**文章太长没有滚动条**，**切换 Tab 再返回时无法保留离开时的浏览进度**。」

这三条是**同一个根因**：弧光/大纲是「一整篇长文本」，而 UI 把它当成「一个普通文本文件」在渲染。

### 7A.1 分卷显示（与冻结机制天然配套）

§8.1.2 已经把冻结做成**按卷**，那么显示也应当按卷：

| 能力 | 做法 | 依赖 |
|---|---|---|
| 卷级目录 | 解析 `## 卷N：` / `### 单元N：` 生成侧边目录，点击跳转 | `parseArcStructure` 已有（`arc-position.ts:325`） |
| **默认折叠**（作者 2026-10-19：「默认当然是折叠状态了」） | 打开时只展开**当前卷**，其余卷折叠成一行（卷名 + 单元数 + 冻结标记） | 冻结状态（§8.1.2） |
| **一键全量展开**（作者：「但是要允许人家全量展开」） | 工具栏一个「全部展开 / 全部折叠」开关；**记住作者的选择**（存 tab 或项目级偏好） | 无 |
| 冻结卷只读 | 已冻卷的编辑区 `readOnly`，与冻结语义一致 | 冻结标记 |

### 7A.1b 树形显示：卷 → 单元（作者 2026-10-19 提出，评估如下）

作者原话：「我之前的一个意向好像也可以一起并进来，就是以**树的形式在卷下显示单元**。你评估一下吧。」

**结论：可以做，但必须做成「同一份文本的第二个视图」，不是新的事实源。**

#### 可行性（都是现成的）

| 需要什么 | 现状 | 证据 |
|---|---|---|
| 解析出「卷 → 单元」两级树 | ✅ 已有 | `parseArcStructure` → `ParsedArcStructure.majors[].mids[]`（`arc-position.ts:325-400`） |
| 每个单元的可读标签 | ✅ 已有「叙事任务 / 逼法」字段 | `ArcMid.fields`（`arc-position.ts:97-109`） |

| 节点 → 文本位置 | ❌ **缺** | `parseArcStructure` 只返回结构化数据，**不带行号**；`ArcMajor/ArcMid` 上没有 offset |

⇒ **唯一的真实工作量是「节点 → 文本位置」**：点树节点要能滚到对应段落。`parseArcStructure` 目前用 `plan.split(/\r?\n/u)` 逐行遍历（`:334`），**行号是天然就有的**，只是没往返回结构里放。

#### 设计（三层，都是视图）

```
卷 / 单元结构                     [全部展开] [折叠]

│   └─ …（折叠时只显示前 3 个 + 「还有 9 个」）
├─ 卷二（8 单元 · 已冻结）
└─ 卷三（6 单元 · 正在写）  ← 默认展开这一卷
```

| 项 | 做法 |
|---|---|
| **树的落点**（作者 2026-10-19：「可以用可折叠抽屉，但是这个抽屉要能选择性的把它固定住。如果人家真的是宽屏呢？那我固定以后就变成了左树右文」） | **抽屉 + 可固定（pin）**：默认抽屉收起；点「固定」后变成常驻侧栏 = 左树右文；**记住 pin 状态**（项目级偏好） |
| 点节点 | 编辑器滚动到对应段落并选中标题行 |
| 单元徽标 | 交手类型 + 档位（来自 `PRESSURE_TAG`），让「相邻两个单元同类」一眼可见——这正好是 `ARC_SAME_HAND_TYPE` 体检的可视化 |
| 编辑 | **树只读**，编辑仍然在右侧文本里做 |
| 折叠 | 树节点折叠 + 文本折叠**共享同一个折叠状态**（否则两处不一致） |
| 窄屏 | pin 后正文被压到 <600px 时，**自动退回抽屉**并提示（或允许作者强行 pin） |

#### 为什么「树只读」是硬规则

1. **避免第二事实源**：树一旦可编辑，就出现「文本是一份、树是另一份」，必须双向同步，而 markdown 里的自由格式（多行小弧、各种别名）不可能无损往返；
2. **作者已经习惯改文本**：`ArchFileViewer` 就是编辑器（`CodeMirrorEditor`），树是导航；
3. **与 §7A.1 的折叠共享状态**，树和文本永远一致。

|---|---|
| 工作量 | 中：解析加行号（小）+ 树组件（中）+ 双向滚动同步（中） |
| 风险 | **低**：纯视图，不碰存储、不碰生成链路 |
| 前置 | 需要把 `parseArcStructure` 的 `PressureTag` 暴露出去（现在是私有函数，`arc-position.ts:1005`） |

### 7A.1c 情节大纲的三层树：卷 → 单元 → **章**（作者 2026-10-19 追加，已实施）

|---|---|

⇒ **切 Tab 回来必然回到顶部**，因为编辑器实例整个重建了。

**修法**（作者 2026-10-19 提了合并方案，并把实例数定为 4：「实例只留最近 3 个，其他的存 scrollTop 当墓碑」→ 后改「暂时定 4 个吧，如果真的有需求了再改就是」）：

| # | 做法 | 成本 | 效果 | 代价 |
|---|---|---|---|---|
| 1 | 只存 `scrollTop` | 小 | 位置恢复 | 光标、撤销历史、折叠状态全丢 |
| 2 | 全保留实例 | 中 | 全部恢复 | N 个 EditorView 常驻内存 |
| **3** | **混合：LRU 保留最近 **4** 个实例，其余存 `scrollTop` 墓碑** | 中 | 最近切换的 4 个 tab 体验完整；更早的至少回原位 | 实现要管 LRU + 生命周期，比 1 复杂 |

**评估：方案 3 可行，但有一个坑要先解决。**

#### 为什么是 4 个（作者给的用例）

作者原话：「最常利用这个功能的，反倒是**审稿以后要对照审稿建议和原文来看**，每次一切，浏览进度就没了，这个才是最破坏体验的。」

这个场景的 tab 集合正好是 4 个：

| # | tab | 为什么要保留进度 |
|---|---|---|
| 1 | 正文草稿（`chapter`） | 读原文 |
| 2 | 审稿报告（`review-report`） | 读建议 |
| 3 | 修稿 diff / 修订（`diff`） | 对照改动 |
| 4 | 上一章或下一章（`chapter`） | 跨章核对 |

⇒ **4 个不是拍的数，是「审稿对照」这个最高频场景的完整工作集。**

> ⚠️ 顺带记一个现有约束：`review-report` 类型的 tab **每次打开都会强制更新内容**（`editor-store.ts:291-296`），所以它天然是"同一个 tab 反复重载"——**实例保留对它尤其重要**，否则每次打开都重建。

| 项 | 结论 |
|---|---|
| 可行性 | ✅ 技术上没问题：`useEditorStore` 已经是集中式 tab 状态（`editor-store.ts:111-121`），加一个 `recentTabIds: string[]`（LRU，长度 3）+ 每 tab 的 `scrollTop` 即可 |
| 隐藏方式 | ⚠️ **不能用 `display:none`**：CodeMirror 在 `display:none` 容器里量不到高度，恢复时会错位、滚动位置丢失。要用 `visibility:hidden` + `position:absolute` + 保持尺寸，或 `content-visibility:hidden`（需实测） |
| 卸载时机 | 被 LRU 淘汰时**主动 destroy**，否则「墓碑」和「实例」两套状态会同时存在 |
| 墓碑要存什么 | `scrollTop` 必存；**建议连光标位置一起存**（`view.state.selection`），成本几乎为零，体验差别明显 |
| 内存 | 4 个 EditorView ≈ 可以接受（一个 2 万字文档的 CodeMirror 实例量级是 MB 级） |

**建议的落地顺序**：先做「墓碑」（方案 1 的核心，独立可交付）→ 再加 LRU 4 个实例（方案 3）。这样第一步就有收益，第二步是增量。

> ⚠️ **审稿对照场景有个额外要求**：`review-report` tab 每次打开会强制重载内容（`editor-store.ts:291-296`），所以「墓碑」对它不够——重载会重置滚动位置。**这个 tab 必须走实例保留路径**，或者重载时保留 `scrollTop`。

> ⚠️ 一个额外发现：**架构文件 tab 的内容是 `plot_structure_plan` 整段**（最长实测 13,791 字），而正文 tab 可能几万字。3 个实例的内存上限由**最大的那个 tab** 决定，不是平均值。

### 8.1 结构冻结 = 定稿机制（作者 2026-10-19 第五轮裁定）

#### 8.1.2 冻结是**按卷**的，不是整本（作者 2026-10-19 第六轮裁定）

作者原话：「冻结的顺序是**第一卷、第二卷、第三卷**，除了**正在展开的那一卷**，自然是之前的都冻结。你把当前卷冻结了，那我中间有剧情修改，岂不是都动不了了？」

⇒ **冻结粒度 = 卷**，不是整本弧光。这是本条裁定里最关键的修正：

| 卷 | 状态 | 作者能做什么 |
|---|---|---|
| 卷一、卷二、卷三（已写完的） | 🔴 **冻结** | 只能解冻回滚（见 §8.1.3） |
| **卷四（正在展开的）** | 🟢 **永远不冻结** | 随便改——这一卷的单元/逼法/结账都还在长 |
| 卷五及以后（未展开的） | 🟡 **可调** | 可以改，改了不影响已写内容 |

**关键**：**当前卷永远不冻**。冻结只发生在「这一卷写完了、进入下一卷」这个时点——由作者点，系统不代劳。

**顺带统一措辞**（作者 2026-10-19）：「以后要统一措辞，都使用**卷单元**来描述结构。」⇒ 本文后续一律用「卷 / 单元」，不再混用「大弧 / 中弧」「卷纲 / 卷」；旧项目存量文本不动（`arc-position.ts:203-205` 已定：只读存量不做文本迁移）。

#### 8.1.3 回滚粒度：**只回滚上一卷**（作者 2026-10-19 第六轮裁定）

作者原话：「考虑到工程难度，**暂时只实现回滚上一卷**。而且回滚这个功能，实际上跟定稿回滚是有联动的……我卷纲都要重新生成，你定的稿子有啥用？因此回滚这个机制是要**把定稿和卷纲并项**的。可以单独立项，优先级往后放。」

⇒ **本稿不做回滚，回滚单独立项**。这里只记录它的边界，供那个立项参考：

| 项 | 裁定 |
|---|---|
| 回滚粒度 | **只能回滚上一卷**（不做到任意卷、不做到任意章） |
| 回滚对象 | **卷单元结构 + 情节大纲 + 章节蓝图 + 正文定稿，四者并项** |
| 为什么并项 | 卷单元结构作废了，那一卷的定稿正文也就没有依据了——「我卷纲都要重新生成，你定的稿子有啥用？」 |
| 优先级 | **往后放**，单独立项 |

**关于「定稿不可撤销」的重新定性**（作者 2026-10-19）：「当前的定稿不可撤销，在我的理解里，是**功能还不完善**的一种表现。」

| 场景 | 是否破坏已成事实 | 应否允许 |
|---|---|---|
| 已定稿 5 章，删第 1 章 | ✅ **破坏**（后面的章都建立在第 1 章之上） | ❌ 禁止（今天的 `FINALIZED_DRAFT_DELETE_REQUIRED` 拦得对） |
| **回滚最近一章** | ❌ 不破坏（后面没有东西依赖它） | ✅ 应当允许 |
| **连续回滚到某个节点**（如上一卷末） | ❌ 不破坏（节点之后的内容整体作废，没有孤儿） | ✅ 应当允许 |
| 跨冻结删除中间某一章 | ✅ **严重破坏** | ❌ 禁止 |

⇒ 判据是「**删掉之后会不会留下孤儿依赖**」：**从尾部连续回滚不产生孤儿，从中间挖洞才产生孤儿**。今天的实现把两者一律禁止了，是功能不完善，不是设计意图。

> ⚠️ 这条对本文的直接影响：**结构冻结的"解冻"不是本稿范围**。本稿只做「冻结标记 + 按卷冻结」，解冻/回滚留给那个独立立项。

**回滚要动哪几层**（留给独立立项的备忘，`anchor` 里那三个数就是为此存的）：

| 层 | 回滚动作 | 现状可逆性 |
|---|---|---|
| 卷单元结构 | `plot_structure_plan` ← `anchor.arcPlan`（hash 校验） | ✅ 纯文本，可直接覆盖 |
| 情节大纲 | `synopsis` 截到 `anchor.coveredTo`；检查点 `synopsis_covered_to` 同步 | ⚠️ 截掉的正文可进回收站 |

| **正文定稿** | 需**连续从尾部撤销**（不允许中间挖洞） | ❌ 今天完全不可逆，要新立项才做 |

#### 8.1.4 快照的第二个身份：回滚锚点

作者原话：「你说的对，快照当然是作品的一部分。我在上面还提到回滚的可能性，**你没有快照，你到时候怎么回滚？**」

⇒ **快照不是"顺手存的一份摘要"，它是回滚唯一的锚点。** 所以 §5.4 的 `VolumeHandoff` 要扩成两个部分：

```ts
interface VolumeSnapshot {
  volume: number
  /** ① 交接单：喂给下一卷（体积受限，见 §5.4.2） */
  handoff: VolumeHandoff
  /** ② 锚点：回滚所需的最小事实（不在 prompt 里出现，只用于恢复） */
  anchor: {
    /** 冻结那一刻的弧光全文（含 hash，用于校验） */
    arcPlan: string
    arcPlanHash: string
    /** 本卷末已写到第几章大纲 */
    coveredTo: number
    /** 本卷末已写到第几章蓝图（没有则为 0） */
    blueprintCoveredTo: number
    /** 本卷末已定稿到第几章正文（没有则为 0） */
    finalizedTo: number
  }
}
```

**两部分的纪律完全不同**：

| 部分 | 进 prompt？ | 体积 | 可被模型改写？ |
|---|---|---|---|
| `handoff` | ✅ 只进**下一卷** | ≤1,500 字 | ✅ 可（模型生成） |
| `anchor` | ❌ **永不进 prompt** | 弧光全文（约 1.4 万字） | ❌ 不可（代码写入，纯事实） |

> ⚠️ `anchor.arcPlan` 存弧光全文是有意的：**回滚要能恢复"当时的弧光长什么样"**，否则回滚完结构还是新的，等于没回滚。它只在解冻/回滚时读取，不参与任何生成。

## 11. 验收

1. **前缀恒定**：同一本书在第 10 / 100 / 400 / 600 章四个位置，投影后的 prompt 总字符数**落在 ±20% 内**（不随进度增长）。
2. **落库不变**：投影启用后，`project_core.synopsis` 仍是完整大纲，字数与投影前一致。
3. **失败退回**：构造一份解析不可靠的大纲（无章标题 / 章号乱序）⇒ 投影整体退回全量，不报错、不丢内容。
4. **连续性能验**：同一单元内逐章生成，第 N 章仍能正确承接第 N-1 章「收尾：」行（人工抽检 3 组）。
5. **长篇可达**：模拟 666 章规模的已写前缀，投影后单次请求输入 < 40k 字符。
6. **等待可见**：`cached_tokens` 与首字延迟出现在 attempt receipt 里。
7. **超写可见**：把某几章写超 1.5 倍 ⇒ `OUTLINE_OVERSHOOT` 出现且不阻断。
8. **快照链式注入**：第 5 卷的 prompt 里**只出现第 4 卷那一份快照**，不出现第 1–3 卷的任何快照（防止 O(卷数) 累积）。
9. **快照不编**：构造一卷「什么都没发生」的大纲 ⇒ 快照允许大部分字段为空，**不得**为填满而生成新事实（人工审阅 3 组）。
10. **不自动冻结**：生成 12 章大纲 + 18 章蓝图 + 6 章正文，全程**不出现任何拦截**，只出现「本卷写完，可冻结」的提示；
11. **按卷冻结**：冻结卷一后，**卷二（当前卷）仍可随意修改**，只有卷一对应段落被拦；
12. **当前卷永不冻**：连续冻卷一、卷二，进入卷三时卷三仍可改——冻结按钮只出现在「本卷已写完」时；

11. 不在清除全部时留下悬空引用（弧光必须一起清，§8.1.7）；
12. 不把快照放进 `partial_arch.json`（回滚锚点必须随作品走，§8.1.5）；
13. **本稿不做回滚、不做定稿撤销**——单独立项，优先级往后（§10.1）；
14. 不做「任意章回滚」（存储量级完全不同，作者已定只做上一卷）。
