# 故事节拍库与分层换拍（`story-beats`）

> 状态：✅ 已实施（2026-10-28）· 分支 `exp/resource-ledger`

> 缘起：作者 2026-10-28 提出「剧情节拍要按篇幅嵌套，不能全书一套」——
> 内置的节拍（三幕等）是前人总结的拍子，问题不在拍子本身，在**它被用在整本书上**；
> 几百万字的长篇不该固定用一套，应在合适的篇幅内嵌套搭配多种；
> 对所有单元都用同一套，读者后期会觉得"怎么全一个套路"，**而这是机器测不出来的感觉**。
> 同轮作者定：**拍子用枚举**（能数得出来的东西），**全书那一层也一起改**。
> 分支 `exp/resource-ledger`。

---

## 1. 病因在代码里是多少：82 章

旧 `getPlotStructureGuide`（`architecture-workflow.ts`）六套节拍，原文一律是
「**严格按以下结构组织大纲**」+ 按百分比切章。代进 150 章：

| 幕 | 区间 | 章数 | 这一整段被赋予的职责 |
|---|---|---|---|
| 第一幕 建置 | 1–30 | 30 | "建置" |
| **第二幕 对抗与发展** | **31–112** | **82** | **"对抗与发展"** |
| 第三幕 高潮与结局 | 113–150 | 38 | "高潮与结局" |

**82 章共用一句话的职责。** 中段没有任何分段依据，模型只能靠同构循环填
（再打一场、再赢一次、再来个更狠的）。读者读到的"拖沓"和"全都一个套路"是同一件事。

项目自己的设计稿早已写过同一判断（`arc-nesting-design.md:40`）：
*"这是三段并列的区间，不是三段有推进关系的阶段。"*

**所以节拍本身没错，错的是它被装在了全书这一层。**
本书 7 卷 × 21 章 ≈ 5.3 万字／卷 —— 那正好是一部中篇／一部电影的量，
**三幕在这一层才是它的原生尺寸**。

另有一处结构缺口：`plot_structure`（卷纲）模板的变量里**没有全书拍子**
（`premise / character_dynamics / world_building / genre / number_of_chapters /
word_number / global_guidance / step_guidance / reference_works / rhythm_profile`）。
即卷 / 单元层此前**看不到全书用的是哪一套**，只能自由发挥。

## 2. 资料核实的四条

| # | 结论 | 出处要点 |
|---|---|---|
| 1 | **七点结构是明确设计成跨尺度的** | Dan Wells：*"A single point may take a chapter or a paragraph"*；七个位置只规定职责，**不规定页码**；且是唯一**从结局倒推**的结构 |
| 2 | **八序列就是"不同尺度各一套"的行业标准做法** | 一部长片 = 8 部 10–15 分钟短片，各有自己的戏剧问题；"宏观张力由微观张力承担"；序列**嵌套**在三幕里（每幕 2 个） |
| 3 | **起承转合明确说网文会叠着用** | "a web serial ... kishotenketsu stacks. There's one set of four for the whole story, one for each arc, and one for each chapter"；且「三幕管外部情节，起承转合管关系线，两者可共存」；`转` 是**重新框定**，不需要反派 |
| 4 | ⚠️ **但同一层不许叠两套** | 六模型对比：*"choose one and only one. Layering Save the Cat's beats over the Hero's Journey over three acts produces a spreadsheet, not a book."* |

**第 4 条是这次改动的闸门**：纵向套用（不同尺度各一套）成立，横向叠层（同一层叠多套）不成立。
没有它，"换拍"会退化成"把六套全叠上去"，比原来更机械。

中文侧印证（作者的判断就是行业共识）：
- **"剧情注水"的标准定义**就是 *"同样的套路换了张脸又来一遍：打败一个敌人→获得奖励→遇到更强的敌人"*。
- 《龙族》学术分析（中国作家网 2025-10）：**副本单元增殖反向侵蚀主线** ⇒
  *"重复的屠龙任务与冗余支线替代矛盾升级的**质变**，导致叙事动力衰竭"*；
  称「**半部杰作现象**」＝情节时间被强行拉长、艺术叙事时间提前终止。
  这是"单元同质化"在 400 万字尺度上的实证案例。

## 3. 设计

### 3.1 唯一事实源

`src/shared/story-beats.ts` 是节拍库的**唯一一份**。它被四处消费：

| 消费方 | 用它做什么 |
|---|---|
| `architecture-workflow.getPlotStructureGuide` | 全书层引导（拍序 + 跨度判定 + 可选表） |
| `builtin-prompt-templates.ts` / `prompt-language.ts` | 卷纲正文里的【可用拍子】表与【五条规则】 |
| `arc-position.ts` | 体检时把中文名归一成 key |
| `ipc-channels` / `novel-config-localization` / `propose-novel-config` / `architecture.command` / `import-inference-contract` | 配置枚举（原先 8 处各写一份） |

原先 `plotStructure` 这个枚举在**八处**各写了一遍字面量；本次全部改为引用
`STORY_BEAT_KEYS` / `storyBeatEnumDoc()`。
这符合项目已有的红线（「章标题只有一份解析」同理），也是本次唯一的顺带重构。

### 3.2 十套拍子与原生跨度

跨度按单章 2500–3000 字估。**这一列决定了每套拍子能装在哪一层**。

| 名字 | 引擎（靠什么产生意义） | 原生跨度（章） |
|---|---|---|
| 三幕 | 冲突升级：两个拐点把一段生活劈成三段 | 6–30 |
| 节拍表 | 节拍的位置本身就是意义（十五拍按比例钉死） | 8–30 |
| 七点 | 从结局倒推；只定职责不定页码 | 3–80 |
| 英雄之旅 | 单一主角的完整变形 | 20–150 |
| 八序列 | 每个序列自带一个戏剧问题 | 12–40 |
| 故事圈 | 角色内在的改变，八步可循环 | 2–40 |
| 起承转合 | 重新框定：`转` 引入新角度，**不需要反派** | 1–10 |
| 三二一递进 | 情绪递进：小爽三次、中爽两次、大爽一次 | 3–8 |
| 多线 | 线间交汇 | 20+（不设上限） |
| 自由 | 不预设拍序（必须写明为什么上面九套都不合适） | 不限 |

**层与拍子的对应**（本书 150 章为例）：

| 层 | 体量 | 可用拍子 |
|---|---|---|
| 全书 | 150 章 | **只定两端**（起点状态 / 终点状态）；不切百分比 |
| 卷 | 21 章 | 三幕、七点、八序列、故事圈、多线 |
| 单元 | 5 章 | 起承转合、故事圈、三二一递进、七点 |

### 3.3 五条规则（全部可机检）

1. **每一层只准一套** —— 防叠层（第 2 节第 4 条）。
2. **相邻两个单元不许同拍。**
3. **同一卷内，同一套拍子不许用两次。**
4. **相邻两卷不许同拍。**
5. **拍子必须匹配篇幅** —— 算出这一段折算多少章，再选跨度覆盖它的那几套。

规则 2–5 由 `arc-position.ts` 的 `auditBeatVariety()` 检查，四个新码：
`ARC_SAME_BEAT` / `ARC_BEAT_REPEAT` / `ARC_BEAT_OVERSPAN` / `ARC_BEAT_UNKNOWN`。

**拍子体检排在「没有逼法标注就整体跳过」之前** —— 两套标注互相独立，
一个单元可能只写了其中一套；跟着逼法的早退一起跳过，"全卷同拍"最该报的情况反而会静默。

### 3.4 只查下限，不承诺质量

作者说这类节奏问题"机器测不出来，它是一种感觉"。准确地说：

- **测不出来的**：好不好看。**全都不同 ≠ 一定好看。**
- **能测的只有下限**：连续几段用同一副骨架 ⇒ **一定腻**。这是**必要条件，不是充分条件**。

所以这四条诊断是**下限告警**，职责是排除最坏情况，不保证质量。
若要把"篇幅越长越明显"变成读数，还有一条便宜的算法（未实现）：
**节拍序列的信息熵随卷序号的曲线** —— 曲线往下掉，就是那个感觉在成形。

## 5. 边界（本轮刻意不做）

- **卷 / 单元用哪套拍子，仍由模型在表内自选**，不按功能查表。
  上一轮讨论过的「功能 → 情绪 → 拍子」三层查表更精确，但它需要先有单元功能的枚举，属于下一刀。
- **金手指的 A/B 两类、材料槽第五类「兑现」、爽点独立标注**等前几轮结论均未落。
- **`爽点：` 塞在 `（交手…；档…）` 括号内会污染 `PRESSURE_TAG`**，导致"档位原地踏步"检测失效；
  本次未动，但新字段一律独立括号。下次动 suffix 时一并修。
- 作者在**网页端**手改的六选一（`隐/迂/借/刚/演/换`）与阶梯逼法**没有落在任何文件里**。
  那次对比同时变了选择行、阶梯逼法、爽点字段等多处 ⇒ "效果比现在好"目前**无法归因**到具体哪一处。
  因此本轮只动拍子一个变量，选择行保持四选一。

## 6.1 拍子格改形（2026-10-28 晚，实机被截断后）

**实测故障**：首版要求"这一套的几拍分别落在哪些动作上（一拍一句话）"。7 卷 + 26 单元各写一段，
节拍表那套有 15 拍 ⇒ 单是这一格就三四千字，卷纲生成**整份被请求长度限制截断**（作者实机读数）。

**行业对照**（查证）：beat sheet 的正规形态是**每拍一行、整张一页**（ScreenWeaver：1 page / 15 rows，
读者是作者自己；Prescene：每拍 1–2 句）。写成段落不是加料，是**换了文种**。

**改法**：每层两行，只写名字 + 落位，骨架仍只出在 `story-beats.ts`：
```
拍子：三幕
落位：建置→单元一｜拐点一→单元二｜对抗→单元三｜收束→单元四
```
- 卷的落位指向**单元**，单元的落位指向**场**（单元内部第几段），**一律不写章号**（章数由平台折算）。
- 允许一拍跨两个单元 / 一个单元承接两拍 —— 拍数与下层数量不必相等，但**顺序必须排得出来**。
- 模板里明写"不要复述每一拍该干什么：骨架只有一份"。

**为什么不在大纲层再设拍子**：beat sheet 往下就**不是 beat 了**，是场景清单
（Prescene 四层：beat sheet / outline / treatment / scene list；中文侧同构：总纲 / 卷纲 / 章纲，
章纲写"每一场谁看到了什么、怎么掂量、说了什么"，明确不写效果词）。
在章纲再挂拍子 = 拍子套拍子，每层都展开骨架，字数必然指数膨胀。

**守卫**：`prompt-language-contract.test.ts` 的 `keeps each beat line to a name plus a landing` ——
断言中英模板含「拍子/Beat + 落位/Landing」，且**不含**旧写法（`一拍一句话` / `one sentence per slot`）。
`arc-position.ts` 的 `BEAT_NAME_CUT` 截到破折号/冒号/括号/竖线，`拍子：三幕` 这种纯名字仍能认出；
`落位` 是独立字段，不进 `BEAT_FIELD`，不会污染拍名解析。
