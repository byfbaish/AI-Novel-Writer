## 0. 结论先行：**有必要，但要**分层分阶段**做，不能一次上五层**

### 一句话判断

**作者的直觉是对的（"感觉不简单"）——它不简单的原因不是"写校验规则难"，
而是**五层里有四层是纯文本、没有可比较的结构**，脚本根本无从下手。**

**→ 但它**值得进后续计划**，因为本项目已经有**两个可复用的校验引擎**，
不需要从零造轮子。关键是**分三段推进**，而不是"一次做一个五层校验器"。

### 三句话结论

| 问题 | 回答 |
|---|---|
| **有没有必要？** | ✅ **有必要**。当前的架构生成是"**只生成、不体检**"——四层之间可能互相矛盾但无人发现，直到写到第 200 章才暴露 |
| **难在哪？** | ⚠️ 四层是**纯文本**（`premise`/`worldbuilding`/`characters_arch`/`synopsis`），**没有实体表可引用**、没有 ID 可比对。蓝图有 JSON 所以能查，架构没有 |
| **怎么落地？** | ★ **三段走**：S1 层内结构校验（现在可做）→ S2 层间引用完整性（需先给架构加"最小锚点"）→ S3 弧加入后的四层+弧校验（依赖第五层落地） |

## 1. ★ 本项目已有的两个"校验引擎"（这是"值得做"的根本理由）

作者的记忆是准确的 —— 本项目**确实有一致性检查**，而且不止一套：

| 引擎 | 位置 | 校验类型 | 现状 |
|---|---|---|---|
| **① 确定性结构校验器** | `blueprint-semantic-contract.ts`（313 行） | 字段/引用完整性 | ✅ **成熟**，13 种诊断码 |
| **② 确定性连续性预检** | `consistency-preflight.ts`（135 行） | 定稿事实 vs 蓝图 | ✅ 但**只有 1 条规则** |
| **③ AI 语义连续性检查** | `builtin-writing-skills.ts:231` `continuity-check` | 自由文本语义 | ✅ 已有（AI 驱动） |
| **④ 事实抽取 + 证据链** | `finalized-continuity-facts.ts` | 事实→原文溯源 | ✅ 成熟 |

### 1.1 引擎① 的能力（这正是"架构校验"需要的模式）

`blueprint-semantic-contract.ts` 已经实现了**跨字段引用完整性校验**：

```ts
// 关系端点必须出现在同一项的 characters 中
if (!characterSet.has(from) || !characterSet.has(to)) {
  throw new StructuredContractDiagnostic('relationship_endpoint_not_in_characters', ...)
}
// 角色候选名必须逐字复制 characters 中的一项
if (!characterSet.has(name)) {
  throw new StructuredContractDiagnostic('invalid_value', `${candidatePath}.name`)
}
```

**→ 这套"**A 引用的东西必须在 B 里真实存在**"的校验范式，正是架构五层最需要的。**
**→ 关键差别：蓝图有 JSON（`characters: string[]`），所以能查；架构五层是纯文本，所以不能查。**

### 1.2 引擎② 的成熟度（可扩展，但被"只有 1 条规则"限制）

`consistency-preflight.ts:97` 只有一条规则：

```ts
if (fact.category !== 'character-state') return []
```

它已经实现了**完整的配套**：`stableFactKey`（稳定去重键）、`ConsistencyExemption`（作者豁免）、
`mergeConsistencyFindingsIntoReview`（并入审校报告）。

**→ 引擎②的"骨架"是好的：证据 + 豁免 + 严重级。缺的只是**规则集**。**

## 2. ★ 五层的**可校验性分层盘点**（诚实版的"能查什么/查不了什么"）

这是本评估最核心的一节。**"五层一致性"听上去是一个概念，实际是五种难度的叠加。**

> ⚠️ **术语澄清（重要）**：项目里并存两套层编号，本文用**作者的"五层架构"**（L0–L4 + 弧），
> 与 `seven-layer-skeleton-assessment.md` 的**七层骨架模型**（L0 内核 → L1 世界 → L2 人物 →
> L3 叙事弧 → L4 事件单元 → L5 章节 → L6 场景）**不是同一套**。
> 换算：本文 L0=七层 L0；本文 L1=七层 L1；本文 L2=七层 L2；
> 本文 **L3 情节大纲 ≈ 七层 L4–L5**；本文 **L4 蓝图 = 七层 L5/L6 的产物**；
> 本文 **L5 阶段结构 = 七层 L3**。**引用时请以文内表格的"字段"列为准，不要跨文档比层号。**

| 层 | 字段 | 载体 | **层内可查** | **层间可查** | 难度 |
|---|---|---|---|---|---|
| **L0 故事内核** | `premise` | 散文 | ❌ 无结构 | ❌ 无法比对 | **不可确定性校验** |
| **L1 世界框架** | `worldbuilding` | 散文 | ❌ 无结构 | ⚠️ 需"空间/规则锚点" | 高 |
| **L2 人物体系** | `characters_arch` | 散文 | ⚠️ 有角色名单（半结构） | ✅ **可查**（名字是实体） | 中 |
| **L2.5 角色卡** | `characters` 表 | ✅ 结构化 | ✅ **已成熟** | ✅ 可查 | 低 |
| **L3 情节大纲** | `synopsis` | 纯文本 `## 第N章` | ⚠️ 章节号可查 | ⚠️ 实体提及无结构 | 高 |
| **L4 章节蓝图** | `blueprints` 表 | ✅ JSON | ✅ **已成熟** | ✅ 已可查 | 低 |
| **L5 阶段结构（新）** | 弧文本（未落地） | Markdown | ⚠️ 见 `arc-prompt-assessment.md §6.3` | ⚠️ 同上 | 中（约定格式后可查） |

**→ 关键结论：**
**"五层一致性校验"真正**难**的部分是 L0/L1/L3（散文），
而**容易**的部分（L2.5 角色卡、L4 蓝图）**我们已经做完了**。**

**→ 所以这个需求本质上是："把校验能力从**结构化层**上移到**散文层**" —— 这才是"不简单"的根源。**

## 3. ★ 可以做的**三种校验**（从易到难，价值密度递减）

### 类型 A：**层内结构校验**（易，现在可做）

**定义**：单层自己是否形态完整、无内部矛盾。

| 检查项 | 状态 | 落点 |
|---|---|---|
| 大纲章节号连续/无重复/覆盖完整 | ✅ **已有**（`validPlotOutlineEntry` + `derivePlotOutlineCursor`） | 无需新增 |
| 蓝图字段/引用完整性 | ✅ **已有**（`blueprint-semantic-contract.ts`） | 无需新增 |
| **大纲是否覆盖了 `total_chapters` 全部** | ⚠️ 部分（`renderPlotOutlineSynopsis` 有 `coveredTo`） | 小补 |
| **角色卡与 `characters_arch` 名单是否一致** | ❌ 无 | ★ **可做，中等价值** |

**→ 类型 A 里唯一真缺口：`characters_arch`（人物群像散文）与 `characters` 表（角色卡）
的双向一致 —— 散文里写了但没建卡、或建了卡但散文里没有。**

### 类型 B：**层间引用完整性**（中，需先补"最小锚点"）

**定义**：下层提到的东西，必须在上层真实存在过。**这是价值最高的一类。**

| 检查项 | 前置条件 | 难度 |
|---|---|---|
| 大纲里出现的**角色名**，是否都在 `characters` 表里 | 需从大纲提取人名 | ★★ 中（有别名/简称问题） |
| 大纲里出现的**地点/空间名**，是否都在 `worldbuilding` 里 | 需从散文提取空间名 | ★★★ 高 |
| 大纲里出现的**规则**，是否在 `worldbuilding` 的规则列表里 | 需世界规则半结构化 | ★★★ 高 |
| 蓝图里的 `characters[]` 是否都在角色表里 | ✅ **已有素材** | ★ 低 |
| 蓝图引用的伏笔是否在 `narrative_thread_plans` 里 | ✅ 表现成 | ★★ 中 |

**→ 类型 B 的核心矛盾：**
**"角色名"是最容易抽的（中文人名有相对明确的形态），但**自然语言指代**是杀手** ——
"他""那位老人""白衣人"这类**没有名字的指代**，任何正则都抽不准。**

**→ 所以类型 B 必须接受"**只查具名实体、放过指代**"的降级，否则会做成一个假阳性泛滥的噪音器。**

### 类型 C：**跨层语义一致性**（难，只能 AI 驱动）

**定义**：下层的**语义**是否与上层冲突（不只是名字对不上，而是"说法矛盾"）。

| 检查项 | 例子 | 手段 |
|---|---|---|
| 大纲的**能力设定**是否超出内核给的"金手指"边界 | "金手指是预知 3 秒" → 大纲却写"预知三天" | AI |
| 大纲的**世界规则**是否违反世界观设定 | 世界观"无魔法" → 大纲写"魔法阵" | AI |
| 大纲的**动机链**是否与人物体系矛盾 | 人物"重情" → 大纲写"为利益出卖挚友且无铺垫" | AI |

**→ 类型 C 无法形式化**，只能走"把两层文本一起喂给 AI，让它找矛盾"。
**→ 但本项目**已有这个模式**：`continuity-check` skill（`builtin-writing-skills.ts:231`）就是这么干的。**

**★ 类型 C 的正确形态：**不是"新写一个校验器"，
而是**把现有的 `continuity-check` skill 从"章级"扩到"架构级"**（给它一个"审架构"的入口）。

## 4. ★ 为什么"不简单"（作者直觉的技术解释）

**三层原因，层层叠加：**

### 4.1 载体不对称（最根本）

| | 蓝图（能查） | 架构四层（不能查） |
|---|---|---|
| 载体 | JSON | 散文 / Markdown |
| 角色引用 | `characters: string[]` | 散落在大纲正文里 |
| 引用方式 | 逐字复制 | 自由指代（"他""白衣人"） |
| 可否正则 | ✅ | ❌ |

**→ "五层校验"里有四层没有可比对的结构。** 这就是难度的全部来源。

### 4.2 没有"唯一 ID"（跨层无法对齐）

蓝图能用"角色名"当键，是因为**名字就是 ID**。
但架构四层里，"沈舟"在 `characters_arch`、`premise`、`synopsis` 里可能叫**沈舟 / 小沈 / 他**。
**→ 没有 ID 就没有 join 键，跨层比对退化成"模糊字符串匹配"。**

### 4.3 ★ 校验时机未定（最容易踩的坑）

**校验放在"架构生成完成时"还是"章节写作时"？**
- 放**生成完成时**：此时大纲才刚生成，四层都是热的 → 但**作者可能本就要改** → 假阳性劝退。
- 放**写作时**：此时架构已冻结、正文在写 → 但**矛盾可能已传播进正文** → 发现太晚。

**→ 本项目的既有回答是**"两者都有，但都是**证据而非禁令**"**（`consistency-preflight.ts:82`
注释原文：*"Findings are evidence, never a writing prohibition."*）——
**这个哲学必须继承到架构校验上。**

## 5. ★ 分阶段方案（推荐进后续计划）

**原则：不追求"一次做一个五层校验器"，而是"每个阶段独立可交付、独立有价值"。**

### S1：**层内一致性 + 角色卡对齐**（现在可做，成本低）

| 交付 | 内容 |
|---|---|
| **S1.1** | `characters_arch`（散文）与 `characters` 表（角色卡）**双向对齐检查** —— 散文写了没建卡 / 建了卡散文没写 |
| **S1.2** | 大纲**章节覆盖完整性**（是否覆盖 `total_chapters`）纳入现有一致性报告 |
| **S1.3** | 复用引擎②的**豁免 + 证据 + 严重级**框架（不新建 UI） |

**→ 成本：小。价值：中。** 复用引擎①的范式（引用完整性）+ 引擎②的框架。

### S2：**层间引用完整性（具名实体）**（需先定"最小锚点"）

| 交付 | 内容 |
|---|---|
| **S2.1** | ★ **从大纲抽取具名实体**（人名/地名），比对 `characters` 表 + `worldbuilding` |
| **S2.2** | **降级策略**：只查**具名实体**，明确**放过指代**（"他/那位"），并**在报告里声明这个局限** |
| **S2.3** | 高置信度才报（要求名字 ≥2 字 + 出现 ≥2 次），**压假阳性** |

**→ 成本：中。价值：高（这是"跨层校验"的实质）。风险：假阳性。**
**→ 必须先在 `architecture-consistency-design` 里定"锚点"：谁算具名实体、如何抽。**

### S3：**弧加入后的四层+弧校验**（依赖第五层落地）

| 交付 | 内容 |
|---|---|
| **S3.1** | 弧文本的**引用完整性**（承接 `arc-prompt-assessment.md §6.3` 的"Markdown 约定格式"） |
| **S3.2** | "弧声明的因果引用是否指向真实存在的前弧" |
| **S3.3** | "弧声明回收的伏笔是否真在 `narrative_thread_plans` 里" |
| **S3.4** | 弧与大纲的**覆盖一致性**（大纲是否落在弧声明的阶段内 —— **仅作提示，不校验**，守 §5.1 边界） |

**→ 成本：中。价值：高，但**必须等第五层落地**。这就是 S3 排在最后的原因。**

### S4（可选）：**AI 语义审计入口**（低优先）

**把现有 `continuity-check` skill 扩成"审架构"** —— 把四层文本一起喂给 AI，让它找语义矛盾。
**→ 不新增确定性代码，只是给已有 skill 一个"架构级"的调用入口。**

## 6. ❌ 明确**不建议**做的

| 不建议 | 理由 |
|---|---|
| **为架构四层建结构化表** | 与作者"整段文本"定性冲突（见 `arc-prompt-assessment.md`）；且违背项目规律（散文层就该是散文） |
| **做"一次校验五层"的大一统校验器** | 四层无结构，必然退化成"糊匹配"，假阳性劝退 |
| **校验结果**阻止**生成/写作** | 违背既有哲学（"Findings are evidence, never a writing prohibition"） |
| **追求 100% 实体覆盖（含指代消解）** | 自然语言指代无法确定性解决，投入产出比极差 |
| **在第五层落地前做"五层"校验** | 第五层还不是数据，做了也是空的 |

## 7. 结论表

| 问题 | 回答 |
|---|---|
| **有必要吗？** | ✅ **有必要**，进后续计划。当前四层"只生成、不体检"是个真实缺口 |
| **难吗？** | ⚠️ **难，但难点明确**：不是规则难写，是**四层纯文本、无 ID、无 join 键** |
| **从零造吗？** | ❌ **不必**。已有引擎①（引用完整性范式）+ 引擎②（证据/豁免框架）+ `continuity-check`（AI 审计） |
| **怎么排？** | **S1 层内对齐（现在）→ S2 层间具名实体（中）→ S3 弧加入（依赖第五层）→ S4 AI 审计入口（可选）** |
| **守什么边界？** | **证据非禁令**（继承 `consistency-preflight` 哲学）；**只查具名、放过指代**；**架构保持散文** |

**★ 一句话：**
**这个需求**值得做**，但它的正确形态不是"一个五层校验器"，
而是"**把已有的校验能力，从结构化层（蓝图/角色卡）向散文层（内核/世界观/大纲）分阶段上移**"。
S1 现在就能做且成本低；S2 是实质；S3 必须等第五层落地。**

## 6. ★ 实机样本：前 30 章大纲 vs 弧光结构（2026-10-11 独立核对）

作者分批生成了 1-5 / 6-15 / 16-25 / 26-30（845 章项目），并明确要求"**暂时不能信任框架自己的校验**"。
以下核对全部基于库内原文与纯算术，不采信任何运行时结论。

### 6.1 弧光结构自身：一处**硬算术错误**（自检第 1 条被违反）

| 大弧 | 章数 |
|---|---|
| 规则初学 / 规则博弈 / 规则立法层 / 执笔人痕迹 / 第四面墙 | 100 / 95 / 95 / 95 / 100 |
| 历史拼凑 / 反制与代价 / 国运初醒 / 破幕与新生 | 95 / 95 / 90 / 115 |
| **Σ 大弧** | **880** |

项目 `total_chapters = 845` → **多出 35 章**。而模型的【篇幅预算】里**写着**
「计算逻辑：Σ(各大弧) = 845」—— **它写了结论，却没有真的相加**。
（其余自检项通过：9 个大弧各含 3–4 个中弧，Σ中弧 = 本大弧章数 9/9 对；
30 个中弧的 Σ小弧 = 本中弧章数 30/30 对。）

→ 已改为**要求逐项写出加法式、禁止只写结论**（见 §6.4）。

★ **但作者对本项的定性是"可接受"**（2026-10-11 原话）：规划不是契约 ——
"规划 800 章，最后多个 100 章，或者说提前完结都是有可能的……这反倒体现了该模型的弹性和适应力"。
真正要避免的是**以目标为导向的凑数**（"写 3000 字 → 只写了 2500 → 灌水到 3000 立刻停"）。
→ 因此约束按作者口径调整为：**必须写出实际和并声明差额；允许 ±10% 弹性；不得为凑齐总数而增删章节**。
`Σ` 精确相等**不再是**硬要求。详见 §6.4。

### 6.2 弧光 ↔ 大纲的**时序错位**（本次最重要的发现）

弧光把 `大弧一【规则初学】` 切成 4 个 25 章的中弧，其中 **中弧 2【工程题拆解】（26–50）**
标注为 **B 目标驱动型**，核心动作是：

- 尝试 1：观察字面歧义 → **利用「访客身份」规避停留限制**
- 尝试 2：查找被抹规则空位 → **铃连续微震指向隐藏出口 → 成功逃生**
- 小弧：规则A4（26–32）/ 弹幕干扰（33–42）/ 旧痕发现（43–50）

## 8. 衍生缺口登记：「有待决 ≠ 可决策」（2026-10-15 实机登记）

> 缘起：实机缺陷 —— 作者删除「老陈」人物卡、撤销其锚点登记后，名字重新出现在
> 「AI 生成角色卡」的待建卡清单里，但该入口**没有任何可确认的批次**，确认步只抛一句
> 「缺少已预览的角色卡候选，未写入角色名单」，作者完全看不出该去哪。

### 8.1 缺口是什么

**候选清单**与**决策账本**是两条链，各自都"对"，但从未对齐：

| 链 | 事实来源 | 生命周期 |
|---|---|---|
| **候选清单** | 蓝图声明的 `newCharacterCandidates`，减去名册 + 已登记锚点人物 | **每次重新派生**（纯内容函数） |
| **决策账本** | `character_identity_proposals` 批次，身份 = `cpb:hash([projectId, {kind:'directory', operationId}])` | **一个 operation 一个批次、批准即冻结** |

于是：**撤销（`revoke`）只打通了清单侧**（名字重新成为待建卡候选），**没有打通决策侧**
（原批次已 `approved`、不可重开；而"每个蓝图提交都会 stage 一个批次"的批次内容是**该操作
声明的候选**，撤销的名字**不在其中**）。

**→ 一般形式：任何"派生清单"都必须同时回答"谁来决策"。清单说"有待决"，
不等于存在一个"可决策"的载体。**

### 8.2 与 AC1–AC4 的关系

这不是新的"跨层语义"问题，它落在 **AC1（层内一致性）** 的边界上，且与 AC2 同源：

- **AC1 的 S1.1** 是「`characters_arch` 散文 ↔ `characters` 表 双向对齐」。
  本缺口是它的**决策侧补全**：不只问"散文写了没建卡"，还要问"清单里的候选**归谁决策**"。
- **AC2（具名实体引用完整性）** 的同一纪律：**只查具名实体**。本缺口天然满足
  （候选名就是具名字符串）。
- 与 **AC3** §6.2 的发现同构：**"名义约束"vs"实际状态"** 的错位 —— 那里是
  "弧光约束大纲目前只是名义上的"，这里是"清单声明待决，但实际无载体"。

### 8.3 建议归属与形态（待定，不预设实现）

| 项 | 建议 |
|---|---|
| **归属** | **AC1 新增交付 S1.4**：**「派生清单 ↔ 决策账本」一致性** |
| **判据（本轮已用测试锁死）** | **「有待决」≠「可决策」** —— 清单必须能指认一个可决策载体；不能时**如实说明**，绝不抛配置错误 |
| **症状侧（已落地）** | 已批准的批次**不可重开**（决策有身份效果）；列表步落**空数组**（"没得确认"）并给出说明；收件箱不把 **0 项批次**当"待处理" |
| **深层侧（未做）** | 「候选复审批次」（内容寻址：`operation + 当前待决候选集`）—— 让撤销 / `keep-unresolved` 的名字**真正能再决策**。**动批次身份与证明，需独立设计小节 + 配套测试** |

### 8.4 同一根因的其他表现

- **`keep-unresolved`**：本项目那 5 个恰好都在名册里、被 `built` 过滤掉了，才没暴露；
  一旦它们不在名册里，症状与老陈**完全相同**。
- **0 项批次**：目录操作声明了空 `newCharacterCandidates` 时，批次仍被 stage（作完成回执的
  证据，不可删），于是「待处理 N」里出现一个**永远无法被决定**的空条目。
