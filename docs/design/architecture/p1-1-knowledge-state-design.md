# P1-1 期 3 · 信息流（谁知道什么 / knowledge state）

> **状态**：✅ 已落地（2026-10-23，M16 · 独立登记页 · 写前查阅第五小节）
> **行业名**：knowledge state / who-knows-what —— story bible 里属于「人物（记忆/知识）」那一格，
> 但它不是角色卡上的自由文本，而是**「角色 × 事实 × 从第几章起知道」的三元关系**。
> **它不做负知识**：只记「谁知道」，不记「谁不知道」，也不做 C1 身份分面。

---

## 0. 四问

| 问 | 答 |
|---|---|
| 行业里叫什么 | knowledge state / information flow。ConStory-Bench 把它归到「人物塑造」下，并称其为**最难靠重读发现**的一类 —— 错误不在句子里，而在场景**假定**的东西里（角色用了没人告诉他的信息） |
| 谁消费产出 | ① 写前查阅（生成第 N 章时告诉模型「这个人此刻知道什么」）② 作者扫表（谁在什么时候该知道了）③ 将来的 findings（未卜先知 / 集体失忆） |
| 失败形态 | 人物连续性 · 知情边界（未卜先知、集体失忆），**不是**数量矛盾，所以不用账本 |
| 已有产品做过什么 | 写作软件普遍只有「角色卡备注」；story bible 也很少把「谁知道」结构化。我们的差异是**需求差异**：长篇里作者自己会记混，模型更会 |

两种典型崩法：

- **未卜先知**：第 5 章的角色说出了第 9 章才揭晓的真相（模型从「后续计划」或全量设定里读到了未来）；
- **集体失忆**：上一章亲眼看见的人，这一章又被蒙在鼓里。

## 1. 形状（M16 `knowledge_states`）

一行 = **「某角色在第 L 章得知了第 C 章定稿里的那条事实」**。

| 列 | 说明 | 可空 |
|---|---|---|
| `knowledge_id` | 主键 | 否 |
| `character_id` | 主语。**表里不存名字**（M02 之后 `characters.name` 不再唯一），显示名读时 JOIN | 否 |
| `fact_chapter` | 这条事实写在哪一章（> 0） | 否 |
| `fact_evidence` | 作者从定稿正文里选的**逐字引文** | 否 |
| `fact_evidence_hash` | 引文的完整 sha256（64 hex），供人工核对引文是否被改过 | 否 |
| `fact_key` | 引用键 `kf:<16 hex>`，由「章号 + 归一化引文」算出 | 否 |
| `learned_chapter` | 从哪一章起知道（`CHECK(learned_chapter >= fact_chapter)`） | 否 |
| `evidence` | **这条知情关系本身**的出处（哪一章写了「他这才知道」） | ✅ 空 = 没记出处 |
| `source` | `author` | 否 |
| `created_at` / `updated_at` | 时间戳 | ✅ |

约束与索引：

- `UNIQUE(character_id, fact_key)` —— 挡**同一角色对同一条事实重复登记**（不是「同角色多条事实」：
  两条不同的引文 = 两个不同的 key，照常允许）。
- `CHECK(fact_chapter > 0)` —— 0 会被读成「序章」。
- `CHECK(learned_chapter >= fact_chapter)` —— 挡「先于事实存在就知道」。
- `idx_knowledge_states_character` / `idx_knowledge_states_learned` —— 面板按人扫、生成链按期界筛。

**`fact_evidence` 与 `evidence` 不是一回事**，这是本表最容易看错的两列：前者是**事实本身**的逐字引文
（引用主体，键由它算出），后者是**这条知情关系**的出处（可空、**不进提示词**）。关系出处不进提示词的理由
与制度槽的 `note` 相同：本节预算 640 字，关系出处会挤掉判定行。

## 2. 引用键：为什么不用 `continuityStableFactKey`

```
fact_key = 'kf:' + sha256(`${fact_chapter}\u001f${normalizeQuote(fact_evidence)}`).slice(0, 16)
normalizeQuote = trim + 连续空白压成一个空格（不做 Unicode 归一）
```

| 问题 | 结论 |
|---|---|
| 为什么不用 `continuityStableFactKey`（`consistency-preflight.ts:73-91`） | 它把模型复述的 `statement` 也算进 key。`statement` 每章重抽都会换措辞 ⇒ 同一件事换个说法 key 就变 ⇒ 作者登记的知情关系立刻全部指向空气 |
| 新键用什么 | 只用两个**不随抽取漂移**的量：「事实所在章 + 逐字引文」 |
| 为什么不拿引文原文当键 | 200 字做索引与 IPC 太重；16 hex 够用，「同章同文」本就该是同一条 |
| 为什么不让 `statement` 参与 | 一旦允许，就等于承认「同一引文两种表述 = 两条事实」，封闭默认立刻失效 |
| 为什么不做 Unicode 归一 | 定位用的是原文切片。归一过的文本与定稿正文对不上，作者按它去正文里搜就搜不到 |
| 事实被重抽 / 改稿怎么办 | key **不重算**（键是引用，不是内容哈希），由 `refState` 判失效 |

**键必须用 `crypto.subtle`**（与 `source-ref.ts:21-24` 的 `hashAuthorText` 同一写法）：共享层严禁
`import 'node:crypto'` —— 渲染层会直接炸。因此 `knowledgeFactKey` / `knowledgeFactEvidenceHash` 是
**async**，仓储、面板、测试都要 await 同一个函数，绝不各写一份算法。

**键由主进程算**：`db:knowledge-upsert` 的入参里**没有** `factKey` / `factEvidenceHash`。让渲染层传 key
就等于让它决定「这条登记指向哪条事实」，改一个字就能把 A 事实的知情关系挂到 B 事实上。

## 3. 失效三态（`refState`）

判定**在主进程仓储里算好再返回**（`db:knowledge-list` 的返回里就带 `refState` 与 `characterName`）。
渲染层与生成链都不自己拼 —— 否则「哪一行才是本章当前的事实」会出现第二套判断。

| 状态 | 条件 | 处理 |
|---|---|---|
| `valid` | 该 `fact_chapter` 有 `sourceStatus === 'current'` 的定稿连续性投影，且 `fact_key` 在其中 | 参与注入 |
| `stale` | 有 current 投影，但 key 不在其中（该章索引在、这条事实已不在：可能被重抽/改稿） | 跳过 + 登记页标红「请重选」 |
| `unverifiable` | **没有** current 投影（缺失 / `stale` / `legacy`）⇒ 读不到，不能断定 | 跳过 + 登记页提示「读不到」 |

判定**复用现有那条「读定稿连续性投影」的路径**（`SummaryRepository.listFinalizedContinuityBefore`，
即 `db:continuity-list-before` 背后那个函数），不新写一份 `summary_snapshots` 查询。
`summary_snapshots.continuity_facts` 是 JSON 列、**无主键、无 supersede 语义**，所以：

- **不自动改键、不自动删行、不自动迁到新事实** —— 自动改等于替作者认定「新的就是旧的那条」；
- 面板只标红 + 给「重选事实」入口，作者重选后才产生新 key 的行。

## 4. 注入口径

```
【知情（谁知道什么）】
以下只列已登记的事实：登记过的事实，未列出的角色视为不知道；未登记的事实一概不判。
- 顾长风：知道（事实出处：第9章「灵根检测结果被人改过」；自第12章得知）
- 小郑：知道（事实出处：第9章「灵根检测结果被人改过」；自第13章得知）
```

- **位置**：`【制度】` 之后、`【本书规则】` 之前（顺序 facts → items → cadences → **knowledge** → rules；
  期 4b 的能力槽插在知情之后）。
- **上限**：6 条 / 640 字，装不下**整条丢弃**（不截半行 —— 截断的引文就不再是引文）。
- **引文截断**：进提示词时超过 60 字加「…」；截断只发生在显示，登记页与库里保留全文。
- **排序**：本章出场角色优先 → `learnedChapter` 降序 → 角色名（码元序，不用 `localeCompare`）。
- **只注入 `refState === 'valid'`**；`evidence`（关系出处）不进提示词。
- **空数组 ⇒ 整节不出现**，材料块逐字节不变（三条旧哈希 + 期 2 的 `{cadences}` 哈希一字未改）。

### 封闭默认只在注入文本里成立

「登记过的事实，未列出的角色视为不知道」是**封闭默认**，但它只对**已登记的事实**成立；
「未登记的事实一概不判」是它的边界。两句必须同时在节首出现：

- 少了前半句 ⇒ 模型不知道「没列出 = 不知道」，会继续按自己的推断写；
- 少了后半句 ⇒ 读者把本节读成「这本书里谁都不知道别的任何事」，比不注入更糟。

测试逐字钉这两句（`src/shared/__tests__/knowledge-state.test.ts`）。

### 期界铁律

`learnedChapter > 本章` 的行**一律不注入**（未来知识 = 剧透）。纯函数不知道本章号，所以这件事由
`generate-draft` 在调用处过滤，并有专门用例（`generate-draft.command.test.ts`）证明未来行没进上下文。

## 5. 界面的两条硬边界

- **角色选择器只列有 `character_id` 的角色**。人粒度是 id，名字不唯一（同名不同人、改名、别名都真实存在）。
  旧数据里只有名字没有 id 的角色**不出现**，面板写明原因 —— **不静默用名字兜底**：那会把两条登记并成一条。
- **事实只能「引用」，不能新写**。候选来自已定稿且投影为 `current` 的各章连续性索引
  （`db:knowledge-fact-candidates`，只读）；也允许手填「章号 + 逐字引文」，但那同样走 `knowledgeFactKey`
  —— 与库里那条事实算出同一个 key 才算指对。面板**不存 `statement`**：一旦允许作者另写一份说法，
  同一件事就有两种措辞，封闭默认立刻失效。

其余交互：保存前不落库；同角色同事实重复**整批不提交**（本地先算 key，不等数据库报 UNIQUE）；删除需两步确认。

## 6. 验收

| 项 | 结果 |
|---|---|
| 登记「顾长风 / 第9章引文 / 自第12章」→ 写第11章 | 该行**不出现**（未来知识不注入） |
| 同上 → 写第12章 | 出现，且本章出场角色排前面 |
| 同一引文换一种 `statement` | 同一个 `fact_key`（引用不随抽取漂移） |
| 定稿改稿后该章索引里没有这条引文 | `stale`：不注入，登记页标红「请重选」；键与行都**没被自动改** |
| 该章没有 current 投影 | `unverifiable`：不注入，登记页提示读不到 |
| 未登记任何知情 | 零字节；三条旧哈希与 `{cadences}` 哈希不变；新增 `{knowledge}` 单独钉一条 |
| 续写轮 | 同一份材料块 ⇒ 同样有 |
| 单元与集成 | M16 lane 6 · 仓储 9 · 纯函数 11 · 面板 9 · prewrite 4 · chapter-materials 1 · parity 1（新增哈希）· 生成链 1 |

## 7. 已知限制

- **多章缺投影时会出现大量 `unverifiable`**：只要某章没走过定稿后处理（或投影被判 `stale`），那一章的
  所有知情登记都无法核对。这是设计（读不到就说读不到），不是缺陷；重新定稿该章即恢复。
- **手填引文与库内引文有一字之差就会 `stale`**：归一化只压空白，不改字。作者最省事的做法是从候选里选。
- **不做负知识**：没法表达「他到现在还不知道师父已死」。要表达只能靠不登记 —— 而不登记的含义是「不判」，
  不是「不知道」。这是本期的边界，负知识要另立项（含「什么时候破功」的消费方）。
- **不做 C1 身份分面**：一人多身份（马甲、易容、化名）目前只能各自登记为不同 `character_id`。
- **不做自动抽取**：「谁在第几章知道了什么」仍由作者登记；模型说的不算数（与制度锚同一原则）。
- **不做 findings**：未卜先知 / 集体失忆的自动检出属 P2-1（`consistency-preflight` 的插入点），本期只提供数据。

## 8. 不做（防下一轮发明）

- ❌ 负知识 / 「谁知道谁不知道」的对称表。
- ❌ C1 身份分面（角色多身份）。
- ❌ 自动改键、自动删行、自动迁移到「看起来像」的新事实。
- ❌ 在表里存一份名字快照（改名后会与角色表各说各话）。
- ❌ 把 `statement` 存进本表（同一事实两种措辞 = 封闭默认失效）。
- ❌ 让关系出处（`evidence`）进提示词（预算下会挤掉判定行）。
- ❌ 世界状态只读区（要动 7 处，与「只读视图」一起另立项）。
