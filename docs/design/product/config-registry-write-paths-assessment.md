# 配置与登记格的写入通道评估（工作量 / 冲突风险 / diff 复用）

> 状态：**待裁定（只评估，未动代码）** · 日期：2026-10-26
> 起因（作者原话）：①「手填管理工作量大不说，还可能造成设定冲突，这个要评估下」②「不是有现成的 diff 面板机制可以利用么，正好我觉得有些输入框看都看不清，这么重要的东西三四行阅读不便不说，修改也麻烦」
> 相邻稿：[`live-verification-checklist.md`](./live-verification-checklist.md)（本轮实机验证）· [`writing-capability-assessment.md`](./writing-capability-assessment.md)（路线裁决）

## 0. 三句结论

1. **同一个「AI 产出配置」动作，工程里有 5 条独立实现，只有 2 条带作者确认面。** 作者质疑「精修、审稿不都有 diff 界面？」——**成立，而且比本稿第一版写的更强**：diff 在**正文侧是成熟设施**，三个生产入口都在用同一个 `ThreeWayMerge`，`diff` 还是一等 tab 类型（§5.1）。所以缺口不是「没有 diff 机制」，是**配置与登记格侧没接线**。
2. **「抽卡变成追加」和「输入框看不清」是同一个缺口的两个症状：缺一个显式的「采纳 / 替换」动作。** diff 面板正好提供这个动作，所以两件事应当一起裁。
3. **手填的真正负担不是建账，是持续维护锚**；而冲突风险里**只有数量类有审计，归属与周期类没有**。

## 1. 现状：五条写入路径，确认面不齐

| # | 路径 | 触发 | 模型看到什么 | 有预览/确认面吗 | 落库语义 |
|---|---|---|---|---|---|
| 1 | **一键配置** | 配置页「AI 填充配置」 | 只给作者灵感 + 章数字数 | ❌ 直接写回表单 | `preserveAuthorText` **追加** |
| 2 | **单项生成** | 各字段右侧「AI 生成」 | 已有配置 + 该字段要求 | ❌ 直接写回表单 | 同上，**追加** |
| 3 | **Agent 提案** | 对话里 `propose_novel_config` | 对话上下文 | ✅ `DomainProposalDiff`（当前/建议）+ `ConfigImpactPreview`（波及面） | 作者批准后写入 |
| 4 | **资源登记候选** | 世界观生成后自动跑 + 面板可重跑 | 世界观全文 | ✅ 候选表逐条勾选，每条附原文引文 | 勾选才落库 |
| 5 | **关键物品 / 制度** | 面板手填 | — | — | 纯手填 |

**读法**：1 与 2 是「模型直接改作者的表单」，3 与 4 是「模型只提议、作者点头」。同一个产品里两种信任模型并存，而**最常用的 1 和 2 恰好是最不受控的那两条**。

> 补充一条易混点：设计稿里的「统一」指的是**运行边界**统一（`plans/novel-quality-modernization/specs/S06A.md:93`：世界观、架构、角色规划、大纲和单字段等入口都经过统一运行边界），不是 prompt 统一，更不是写入语义统一。**路径 1 与路径 2 用的确实是两份不同 prompt**（`generate_global_config` vs `generate_novel_config_field`，后者的字段要求还硬编码在 `generate-field.command.ts:259` 的 `fieldRequirements`），两处措辞已漂移。

### 1.1 对照：正文侧同一件事是怎么做的（作者 2026-10-26 指出，第一版漏了）

| 正文侧入口 | 落点 | 确认面 |
|---|---|---|
| **精修 / 修稿**（`refine`） | `DraftEditor.tsx:1024` | 内联 90vw Dialog「修稿合并」，`ThreeWayMerge` 三栏 |
| **审稿修订**（review revision） | `review-revision-command.ts:212` | 开 `type: 'diff'` **tab**（带 `originalContent` / `content` / `revisionPath`） |

**读法**：正文侧的动作序列是「**AI 产出 → 先并排对比 → 作者逐段采纳 → 才落库**」，而且已经跑了很久——`diff` 是被写进 `EditorTab['type']` 枚举（`editor-store.ts:32`）的一等类型，不是临时弹窗。

⇒ **方案 B 的性质因此改变**：不是「给配置造一个 diff」，而是「**把已经在跑的 `ThreeWayMerge` 接到配置字段上**」。工作量大头不在对比视图（现成），在**落库语义**——现有的三种意图（替换 / 追加 / 放弃）必须先和 `preserveAuthorText` 的追加规则对齐（§5.3）。

## 2. 评估一：手填的工作量到底在哪

### 2.1 两条手填格的性质不同

| 格 | 条目粒度 | 每条要填 | 建账成本 | 维护成本 |
|---|---|---|---|---|
| **关键物品**（M14） | 一件物品 | 名称 / 持有者 / 展示名 / 状态短语 / 出处章 / 引文（6 项，必填 2） | 中（一本书几十件） | **中**：转手、烧毁、丢掉都要改 `statusNote` |
| **制度 / 周期事件**（M15） | 一条周期规则 | 名称 / 判定轴 / 间隔 / **锚（上次真的发生）** / 降级间隔 | 低（一本 2–5 条） | **高**：每发生一次就要更新锚 |

**结论**：制度的建账成本低但维护频率最高——300 章的书，「月例」「送账」这类事件各发生几十次，**每次都要回来改锚**。这是这两格里唯一会随时间线性增长的成本。

### 2.2 现状已有的两个减负设计（不要当缺陷重开）

1. **`unknown` 与 `not_due` 严格分开**（`institution-cadence.ts` 头注释）：锚缺失或本章日序不可知 → 渲染成 `unknown`，**绝不折成「未到」**。所以「忘了更新锚」不会让模型收到错误事实，只会让那一格失效（缺失就说缺失，判据 DN）。
2. **物品出处可以为空**：空章号/引文渲染成「作者登记」，**不伪造章号**。所以建账时不必回头翻章。

⇒ 这两个设计把「漏维护」的后果从「写错」降级为「没帮上」，是正确取向。**问题不在它们，在于没有提醒作者该更新了。**

## 3. 评估二：冲突风险分三类，只有一类有审计

| 类型 | 具体形态 | 现有防护 | 风险 |
|---|---|---|---|
| **数量冲突** | 月例发了三块还是五块、账上有多少灵石 | ✅ 有：资源账本 + 世界观的数值审计（A-1～A-4，日时间量 ≥24h / 相对量缺分母 / 同资源双单位 / 资源名重复） | **低** |
| **归属冲突** | 刀在谁手里、角色改名或删卡后引用还指得着吗 | ⚠️ 半有：`holderCharacter` 刻意存**角色名**而非 ID（理由：不能因为改名去改写历史物品的归属），但**没有引用校验** | **中**：改名/删卡后该行变成悬空引用，注入时仍会写出去 |
| **周期冲突** | 世界观说「月例按月发」，制度格写「每 7 日」 | ❌ 无：两格各自成文，**没有任何交叉校验** | **中低**：不会崩，但会同时给模型两套口径 |
| **语义冲突** | 手填内容与 AI 生成的世界观/五维/资源描述说的是两回事 | ❌ 无 | **中**：正是作者担心的那类 |

**为什么不做全自动抽取填这两格**：P1-1 的设计前提是「作者侧 SSoT —— 模型推断不能直接成为角色/物品事实」（`KeyItemRegistryPanel`、`CadenceRegistryPanel` 头注释都写着「作者侧唯一写入口」）。**这个前提不推翻，就不能自动落库**；能做的只有「自动出候选 + 作者勾选」，与资源登记同一种信任模型。

## 4. 自动化的真实上限：物品能抽，制度的锚抽不出来

资源登记通道（W6a-4）的可复用件是三样：**模板** `world_building_resource_extract` + **生成侧挂载** `attachWorldBuildingResourceCandidates` + **面板候选确认区**。这套模式平移到物品/制度，技术上没有新机制。

但两类条目的可自动化程度差一个量级：

| 要抽什么 | 能不能从世界观抽 | 原因 |
|---|---|---|
| **物品清单**（有哪些关键物品、谁拿着） | ✅ 能 | 世界观第 4 维本来就在写「人名｜定位｜口吻｜关系」这类具名条目 |
| **制度清单**（有哪些周期事件） | ⚠️ 勉强 | 世界观会写「按月发放」，但**间隔与判定轴要猜** |
| **制度的锚**（上次真的发生在哪一章） | ❌ **不能** | 锚的定义是「上一次真的发生」，要从**正文**里识别「这件事发生过了」——这是事件识别，不是抽取。世界观里根本没有这个信息 |

⇒ **所以制度的自动化上限就是「提议有哪些制度 + 建议间隔」，锚仍然只能手工维护。** 如果要做，别承诺「制度全自动」。

## 4.5 底线裁定：制度缺省会不会影响主线（作者第 2 条）

> 作者原话：「制度抽不出来没关系，但是缺省的话不能影响主线，这是底线问题，有则锦上添花」

### 结论

**缺省不会把主线写崩，但会让「周期事件」这一层完全没有约束。** 这是可接受的降级——**前提是作者知道它是空的**。

### 已达成的事实（三条，都查过代码）

| 判定 | 现状 | 证据 |
|---|---|---|
| 会不会阻断生成 | **不会** | `readCadences` 全函数在 `try/catch` 里，失败/空都 `return []`；注释写死纪律「这一格缺了不该让整章生成停摆（与物品、制度、知情同一纪律）」 |
| 空表在提示词里长什么样 | **整节消失**，不留痕迹 | `renderCadenceSection`：`if (lines.length === 0) return ''`，且明确要求「**不要**产出只有标题的空节」（`institution-cadence.ts:276`） |
| 作者看不看得见 | **看得见（日志）** | 章前日志 `Injected pre-writing reference: … ${cadenceCount} cadences …`（`generate-draft.command.ts:1099`），读数会是 `0 cadences` |

同一个纪律覆盖物品 / 知情 / 能力 / 规则四节，不是制度单独的特殊处理（`prewrite-consultation.ts` 五节统一「空串即不出现」）。

### 真正的风险形态（不是"写崩"，是"失控"）

缺省时模型并非束手无策——**世界观原文照样在上下文里**。所以真实后果是：

- 世界观写了「每月初一宗门大比」，制度格却空着 ⇒ 模型**按世界观原文自行安排**，写得通顺但节奏不在作者掌控内；
- 没有任何 `due / overdue / unknown / not_due` 判定 ⇒ 「该发生的没发生」这件事**没人拦**（首稿闸门、审稿连续性核对读的是同一张表，空表两边都空）；
- 三章连着漏掉同一件事，事后要人工比对才能发现。

**注意这不等于需要"防模型"，反而是需要"防作者忘记"**。

### 为什么不建议给模型加「（未登记）」提示

直觉方案是空节也输出一行「（本书尚未登记周期事件）」。**不建议**：

1. **会诱发编造**：模型拿到「未登记」的显式信号，倾向自己补一个合理设定，比"看不见这一格"更危险；
2. **打散哈希基线**：`context-entry-parity` 守的是 `assembleChapterMaterials` 的 sha256 逐字节基线，加一行会让它必红——红是合法的（可同步更新），但**换来的是负收益**；
3. **现有设计已明确反对**：渲染层注释「不要产出只有标题的空节」是刻意的。

### 底线的正确落点：作者侧可见，模型侧零字节

| 层 | 做法 | 成本 |
|---|---|---|
| **面板** | 制度登记格里，`unknown` 条目的角标独立于 `not_due`（已有语义，只需可视）。空表时面板给一句「这一格是空的 ⇒ 本章不会有周期事件约束」 | 低（纯 UI） |
| **章前日志** | 已有 `0 cadences`。可在 `cadenceCount === 0` 时追加一句可读说明（日志不改任何字节） | 极低 |
| **可选启发式** | 世界观全文命中周期词（每月/每逢/每年/每旬/每季）但制度表为空 ⇒ 章前**非阻断**警告 | 低，但**会误报**（世界观用"每月"形容气候就会出现），须标成启发式 |

**判定**：前两条属「低垂果实」，可以并进方案 A（提醒 + 校验）。第三条不做默认行为，作者要才加。

## 5. 评估三：diff 面板能复用多少（作者第 2 条）

### 5.1 现成的三件，能力不同，别混

| 组件 | 粒度 | 交互 | 生产调用点 |
|---|---|---|---|
| `panels/agent/DomainProposalDiff.tsx` | **字段级**：左「当前」右「建议」，纯文本 `whitespace-pre-wrap` | 只读对比 | Agent 提案（`propose_novel_config`） |
| `editor/ThreeWayMerge.tsx` | **段落级**（自研 DP 对齐，支持 1:2 / 1:3 / 2:1 / 3:1 段落拆分合并），三栏：原稿只读 / 中栏可编辑 / 新稿只读 | 逐段采纳 | **三处正文入口**：精修（`DraftEditor.tsx:1024`）、审稿修订（`review-revision-command.ts:212`）、版本历史（`VersionHistory.tsx:141`） |
| `panels/agent/ConfigImpactPreview.tsx` | 波及面：改了这些字段会影响哪些未写蓝图 / 活跃伏笔 / 已定稿章 | 只读提示 | Agent 提案 |

**注意**：
- `DomainProposalDiff` **不是行级 diff**，只是两段文本并排。真 diff 能力在 `ThreeWayMerge`。
- `diff-match-patch` 与 `@uiw/react-codemirror` 都已是现有依赖，不需要新装。
- **`ThreeWayMerge` 的中栏不是 CodeMirror**（自研渲染 + 纯 React），所以它**没有行号、没有页内搜索**——这与 §「长文 tab 字符操作」那条待办同源，但优先级不同（diff 是短时决策场景，正文是长驻场景）。

### 5.2 输入框的问题不在行数

配置页现状：`worldSetting` / `coreOutline` / `protagonistProfile` 各 `rows={4}`，`goldenFinger` 只有 `rows={3}`，最长两个（`globalGuidance` / `writingStyle`）`rows={6}`；组件样式 `resize-y min-h-[60px]`（`ui/Textarea.tsx`）。

这些字段的实际内容是**几百到上千字的结构化设定**。核心问题不是「行数少」，是：
- **没有大纲视图**：几百字挤在滚动框里，找一段要滚；
- **和 AI 生成结果无法并置**：生成后是「旧 + 新」拼在一起（见 §5.3），作者得自己找分界线；
- **改完看不出改了什么**。

所以「加大 rows」只是挠痒。

### 5.3 关键洞察：「抽卡变成追加」正是缺 diff 的结果

两条路径都过 `preserveAuthorText`（`novel-config-expansion.ts:46`）：

```ts
if (!authorText) return generatedText
if (!generatedText || generatedText.includes(authorText)) return generatedText || authorText
return `${authorText}\n\n${generatedText}`   // 有原文 ⇒ 追加
```

这条规则是为「防 AI 抹掉作者输入」而定的（2026-09 审计第 92 条）。但它同时让**「不满意就重抽一次」这个最自然的动作变成「每抽一次长一段」**。

**根因不是追加规则错，而是缺一个显式的「这次我就要替换」的动作。** diff 预览恰好就是这个动作的天然载体：并排给出当前/建议，作者选「采纳替换 / 采纳追加 / 放弃」，三种意图都能表达。**这正是作者第 2 条提议真正解决的东西**——它顺手修掉了第 1 条提到的「越抽越长」。

## 6. 方案对比（供裁定，均未实施）

### 6.1 手填管理（对应作者第 1 条）

| 方案 | 内容 | 代价 | 解决什么 | 不解决什么 |
|---|---|---|---|---|
| **A. 提醒 + 校验**（最小） | ① 物品 `holderCharacter` 找不到同名角色 ⇒ 行内标红（不阻断）② 制度锚超过 2 个间隔未更新 ⇒ 面板角标提示 ③ 制度与世界观「按月/按日」极性不一致 ⇒ 提示 ④ **空表 ⇒ 面板与章前日志明说「本章无周期事件约束」**（§4.5 底线项，模型侧仍零字节） | 低（纯面板 + 一行日志） | 悬空引用、锚漂移、**缺省不可见** | 建账工作量；语义冲突 |
| **B. 复制资源通道** | 世界观生成后自动抽「物品候选 / 制度候选（含建议间隔）」，面板勾选落库，每条附原文引文 | 中（契约 + 模板 + 挂载点 + 候选区，模式已有先例） | 建账工作量（物品基本解决） | **锚仍要手填**（§4 上限） |
| **C. 全自动落库** | 模型抽取直接写表 | — | — | **不做**：推翻 P1-1「作者侧 SSoT」前提 |

**建议**：先 A（本轮实机验证就能顺带看出误报率），B 等实机验证完再定——因为它要多一份模板和一次额外模型调用，而**本轮验证的目的正是先搞清现有链路值不值这个成本**。

### 6.2 编辑体验 + diff（对应作者第 2 条）

| 方案 | 内容 | 语义变更 | 代价 |
|---|---|---|---|
| **A. 全屏编辑抽屉** | 每个长字段加「展开」→ 弹大编辑区，保存回表单。复用 `Dialog` + 现有 `Textarea` | 无 | 低 |
| **B. A + 生成结果走 diff** | 「AI 生成」不再直接写回，改为弹出「当前 / 建议」对比 + 三选（替换 / 追加 / 放弃）；对比视图**直接用现成 `ThreeWayMerge`** | **有**（改变 1、2 两条路径的落库语义） | **中低**（视图现成，§1.1；大头在语义，见下） |
| **C. 换 CodeMirror** | 大字段直接用 `CodeMirrorEditor` | 无 | 高，收益低（配置不是代码，不需要语法层） |

**建议**：A 与 B 一起做才划算——A 解决「看不清」，B 解决「改了什么 / 要不要替换」。**但 B 动写入语义，属结构变更，须作者先裁定。**

**B 的成本拆分（2026-10-26 修正，因作者指出正文侧已有 diff）**：

| 部分 | 成本 | 说明 |
|---|---|---|
| 对比视图 | **几乎为零** | `ThreeWayMerge` 已支持「原稿只读 / 中栏可编辑 / 新稿只读」，配置字段可以直接塞进去 |
| 三种意图的语义 | **中** | `preserveAuthorText` 现在把「有原文」一律判成追加；要支持「替换」必须由**显式动作**传入，不能靠内容判断 |
| 落库与脏标记 | 低 | 配置页已有 `setProjectEditorDirty` / 后台草稿账本 |
| 与单项生成的契约 | 低 | `generate-field.command.ts` 返回建议值即可，不需要新 purpose（**不改生成链**） |
