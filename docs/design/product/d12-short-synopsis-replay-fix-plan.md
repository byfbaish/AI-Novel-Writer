# D12 · 短细纲写错对象 → 正文重演被丢弃：修复方案（草拟）

**三句结论**

1. 真因链的第一、第二环已经在代码里断了：短细纲不再拿上一章全文，只拿「要点 + 结尾 300 字」，判据也改成「每段必须对应本章蓝图的一个事件」（2026-11-04，R6；D:748 · D:80）。但只到单测级，**没有实机复验、没有 A/B**。
2. 真正剩的缺口是**拦截点太晚**（正文生成完、压缩完才判）与**判据没有读数**，不是「少一条禁令」；同类条款在同一请求里已经有三条并存。
3. 因此不建议：① 再加分隔话术（已有且无效）；② 重跑正文（首稿已被账本登记，`composeVisible` 拒绝回退）。建议：③ 把「对象归属」判据前移到短细纲出口，命中就不发正文请求。

**候选 ① 的判断**：不加话术。理由见 §3；它真正剩下的动作是「按 A:242 讨论 300 是否该放到 800–1,000」，而 S:55-58 已把这个数与守卫窗口解耦，改大等于把更长正文送进细纲，与「减载荷」相反。要做也必须先有成对实测（A:244）。

**候选 ② 的判断**：不建议按「带原因重跑正文」做。两个硬障碍：
- 账本不可回退（R:646-655）：首稿已 compose（G:1461），重跑结果只能拼在后面，得到「重演开头 + 新开头」的拼接稿，比原文更糟；要替换只能新开 run，丢掉本次 run 的归属与账。
- 「带原因」在当前红线下的唯一合法写法是给判法，而判法与 T:1315 同义 → 重跑没有新增信息，成功率不可预期（无读数）。
「留稿」这一半已由 D13 裁定 2=A 以**恢复候选**兑现（G:1718-1767、G:1723），候选不进草稿库。

**候选 ③（推荐）**：判据前移，省掉「正文生成完再作废」这一段。命中后不发正文；可选一次「去掉前驱块」的短细纲重跑（需新授权）；仍命中则抛新受控码 + 落候选（候选此时是短细纲，不是正文），作者看到的是「这一章的细纲写成了上一章，正文没有开始」。
