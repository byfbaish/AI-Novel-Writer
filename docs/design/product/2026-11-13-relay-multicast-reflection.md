# 随想：多播是神经突触，但先不做

> 状态：待裁定（2026-11-13）· 日期：2026-11-13
> 分工：对外的「为什么叫 relay」正文由立卡写（产物 `.batch/night/essays/why-relay.md`，四节 800–1200 字、严格脱敏）。**本篇不重复讲故事**，只留三样东西：故事引出的产品判断、一份 README 中英故事版备选、以及需要拍板的三件事。

## 1. 故事引出的三条产品判断

1. **界面上的「一个 Bot」是幻觉。** 多会话宿主里，同一个形象背后是彼此隔离的会话：上下文不共享，只共享文件与记忆；权限也不共享（只有一侧能发 IM）。所以设计里凡出现「通知这个 Bot」，都要先答三问：哪一个会话？它有什么权限？它现在醒着吗？
2. **基础设施会被使用者自己发现。** 我们以为在造一个文件通知器，实际被当成跨会话的通信底座用了：一侧写文件、插件投一句话、另一侧用它的权限去发通知——这条链路没有一条是我们预先设计的。所以接口要窄、语义要死，别塞业务假设。
3. **误报比不投更贵。** 收到看不懂的中继消息时，第一反应该是「停下、问人」，这一次是好事；但如果天天来，它就会学会忽略所有中继消息，那时插件就死了。这也是为什么「完成规则只是加速判据、未命中仍按稳定投递」这条口径不能反过来，以及为什么解析不到会话时就跳过并告警、绝不按 `cwd` 猜。

## 2. 多播：想到了，但位置放错了层

顺着一件事同时唤醒多个会话（神经突触 / 事件总线）想下去，确实有三类玩法：瞬间拉齐相关分身、按文件把活切几份并行、业务规则变了广播给同一 Bot 的所有分身。

**但二期不做**，理由不是「不好」，是职责放错了层：

- 一条规则投 N 个会话 = N 个 agent 同时独立开跑。并发改同一个仓库互相覆盖，这是编排问题不是配置问题。
- 插件不认识群、不知道谁该串谁、也不知道先后。把编排塞进投递层，投递层会长成一个劣质的调度器。
- 「同一目录投多个目标」现在用**多条 watch**（同 `dir`、不同目标、各带完成规则）就能表达，语义清楚，哪条失效也能单看。
- 「一个被唤醒带动全群」的正确位置是**被唤醒的 agent 在群里 @ 别人**，不是插件替它广播。

一句话：**先有总线，再有广播。** 等编排层有了，多播才是加一个循环；现在做，是替编排层做决定。

## 3. README 故事版（备选，中英各一段）

若立卡那份正文走「机制 + 设计判断」路线，README 顶部可以只用更短的一段，解释名字：

> **中文**：这个插件不生产消息，也不决定谁该说话。它只做一件事——当一份产物真的写完了，把信号送到该醒的那个会话。它叫 relay，因为在多会话的宿主里，一个 Bot 在界面是一个形象，底层却是彼此隔离的会话；把这些会话接起来的，是一个谁都不注意、但断了就没人知道发生了什么的环节。

> **English**: This plugin does not produce messages, and it does not decide who should speak. It does one thing: when an artifact is truly finished, it delivers the signal to the session that should wake up. It is called a relay because inside a multi-session host, one agent is a single face on screen but separate, isolated sessions underneath — and the part that connects them is the one nobody notices until it is gone.
