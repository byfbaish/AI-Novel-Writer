## 速查：四个问题的一句话答复

| 你的问题 | 一句话答复 | 详见 |
|---|---|---|
| 我配置的边界在哪 | 三条边界：只能改 23 个模板、只改「正文 + 补充指导」、改的是三级里的一级 | §1 |
| 我的配置是在改善还是反向优化 | 写「口味」是改善；写「数字」多半在与模板硬写的数字打架 | §2、§3 |
| 系统级 prompt 稳不稳 | 不会被你改坏（护栏在），但**不会自动跟着版本升级**（存的是快照） | §4 |
| 没生成平台风格正文，问题在哪 | 按五步归因，先确认那段话有没有进请求，再谈条款够不够狠 | §5 |

## 1. 三条边界

作者通常以为边界只有一条——"哪些模板我能改"。实际有三条，困惑基本都来自把后两条当成第一条。

| # | 边界 | 你实际能做的 | 你做不到的 |
|---|---|---|---|
| 一 | **能改哪些模板** | 23 个 key 可覆盖（`src/services/builtin-prompt-templates.ts:37-61`） | 其余模板是系统模板，设置页里没有编辑入口 |
| 二 | **能改模板的哪一部分** | 模板**正文**、**补充创作指导** | `systemSuffix`（输出格式与判定标准）**永远从内置取**，覆盖改不到（`src/services/prompts/prompt-builder.ts:89`、`:110`） |
| 三 | **改完在哪一级生效** | 内置 / 全局 / 项目 三级任选 | 不能"只对某一章生效" |

### 1.1 第一层：23 个可改模板，其中 6 个不建议改

| 分组 | 数量 | key |
|---|---|---|
| **架构链**（设置页标「架构链」，不建议改） | 6 | `premise`、`character_dynamics`、`world_building`、`plot_structure`、`synopsis`、`chapter_blueprint_chunk` |
| 正文与精修 | 4 | `first_chapter_draft`、`next_chapter_draft`、`refine_chapter`、`refine_from_review` |
| 审稿与笔记 | 3 | `consistency_check`、`generate_chapter_notes`、`update_character_cards` |
| 配置与素材生成 | 6 | `generate_novel_config_field`、`generate_global_config`、`infer_novel_config`、`infer_novel_config_with_vectors`、`infer_single_chapter_blueprint`、`planning_material_character_extraction` |
| 其它 | 4 | `assistant_writing_identity`、`edit_selected_text`、`analyze_writing_style`、`character_background_synthesis` |

架构链那 6 个只是**标注**，不是禁止：每一步的输出都是下一步的输入，并被后续所有章节引用，改一处会沿链级联（`src/services/builtin-prompt-templates.ts:74-81`）。确需定制时，正确做法是在「补充创作指导」里增补要求，而不是删改正文里的输出契约、字段清单与判定标准。

### 1.2 第二层：只能改「半张纸」

一条 prompt 由四块拼成，你能碰的只有前两块：

| 块 | 内容 | 你能改吗 |
|---|---|---|
| 模板正文 | 材料与创作要求（设定池、本章信息、全局写作要求……） | 能 |
| 补充创作指导 | 你在设置页写的额外要求 | 能 |
| `systemSuffix` | **输出格式与判定标准**（JSON 字段清单、字数合格线、结尾法则、AI 味反制清单） | **不能**，永远取内置 |
| 必需上下文 | 内置模板声明"必须在场"的权威变量，你的正文若漏引用会被自动补回 | 不能 |

代码注释写得很直白：「始终从内置模板取 systemSuffix，与 build() 行为对齐（项目覆盖改不到这一段）」（`src/services/prompts/prompt-builder.ts:89`）。

**这不是你没找到入口，是设计上就不给。** 原因很实际：输出格式与判定标准一旦可改，模型就可能被改成不按 JSON 返回、或自行放宽合格线，下游解析直接崩。所以这条边界是护栏，不是遗漏。

### 1.3 第三层：内置 / 全局 / 项目

设置页每个模板卡片上有颜色标签（`src/components/settings/PromptSettings.tsx:35-39`）：

| 标签 | 含义 | 作用范围 |
|---|---|---|
| 内置 | 出厂设定 | 全应用 |
| 全局 | 你保存的全局覆盖 | 全应用所有项目 |
| 项目 | 你保存的项目覆盖 | 仅当前项目，优先级最高 |

优先级：项目 > 全局 > 内置。**同一个模板只生效一级**——项目覆盖存在时，全局那份不会被合并进来（`src/services/prompt-catalog.ts:136-141` 的解析顺序是"命中即返回"）。

但**不同模板可以分别落在不同级**：模板 A 用项目级、模板 B 用全局级是完全正常的，各自独立判断。所以"我在哪一级改的"这个问题，要按模板问，不能按整个应用问。

## 2. 作者级该放什么：口味，不要放数字

### 2.1 写数字，几乎必然与模板硬写的数字冲突

真实例子（本仓库代码里就写着）：

- 你在作者级清单里写：「**2–3 章一个小爽点**」
- 章纲模板正文里硬写：「连续小高潮法则：维持**每 3-5 章**一个小高潮的节奏」（`src/services/builtin-prompt-templates.ts:1042`）

这两句会**同时出现在同一轮 prompt 里**。模型收到两个互相矛盾的节奏数字，最后按哪个走取决于它当次的心情——你观察到的"有时 2 章就爽、有时拖到 6 章"，往往不是模型不稳定，是它每次在两条指令之间二选一。

### 2.2 写口味，不会跟任何条款对着干

| 可以放（口味） | 不要放（可计数的量） |
|---|---|
| 冷一点、少抒情 | 每 2–3 章一个爽点 |
| 对话密、少心理描写 | 每章至少 3 处反转 |
| 少用形容词、句子短 | 打斗不超过 800 字 |
| 女主不哭、不示弱 | 前 5 章必须完成三次打脸 |
| 叙述贴主角视角，不跳反派 | 配角戏份不超过 20% |

口味是对**表达方式**的偏好，任何模板都不会写"必须热烈抒情"，所以它不冲突。数字是对**结构节拍**的规定，而节拍数字模板里已经有了。

### 2.3 判断口诀

> 写进作者级配置的每一句，问自己：**换成另一位作者，他会不会不同意？**
>
> - 会 → 这是口味，可以进。
> - 它是个可计数的量 → 先翻模板正文，看这个数字是不是已经被规定过；规定过就别再写一遍。

## 3. 打架的三种情况

"我的配置是在改善，还是在反向优化"——本质是三种打架。三种的**症状完全不同**，混在一起看就会得出"系统不稳定"的错误结论。

| 类型 | 机制 | 症状 | 系统会提示吗 |
|---|---|---|---|
| (a) 同层重复 | 模板正文与补充指导分别渲染后拼进同一条请求，同一个变量写两处就注入两遍 | 同一条要求被说两遍，效果反而变弱 | 会，但只提示不自动删 |
| (b) 跨层矛盾 | 你写的量级与模板硬写的量级不一致 | 节奏忽快忽慢、时好时坏 | **不会** |
| (c) 覆盖滞留旧版 | 覆盖文件冻结的是保存当时的内置正文，内置升级后不跟进 | 改了没反应、行为像旧版本 | 会，出现「内置已更新」标签 |

### (a) 同层重复

`build()` 的顺序是：先渲染模板正文，再把「补充创作指导」拼在后面，然后是 `systemSuffix`，最后补必需上下文（`src/services/prompts/prompt-builder.ts:98-116`）。所以两处写同一个 `{{变量}}`，等于同一段内容在请求里出现两遍——白占上下文，还让模型收到同一件事的两种措辞。

设置页会这样提示：

> 「补充创作指导」里有 N 个变量（`{{xxx}}`…）是模板正文本身就会渲染的 —— 同一段内容会被注入两遍，既白占上下文、又会稀释指令。建议把这几处 `{{变量}}` 删掉，只保留你真正想额外补充的要求。（`src/components/settings/PromptSettings.tsx:681`）

**它只提示，不自动删。** 因为系统分不清你是"不小心重复"还是"故意强调"。看到这条提示，正确动作是删掉补充指导里的那几处变量，把要求写在纯文字里。

### (b) 跨层矛盾

就是 §2.1 那个例子：作者清单与模板硬写的数字互相打架。系统**不会提示**，因为它无法判断两个数字里哪个才是你的本意。

这类问题只能靠人工对表：把你写过的所有**数字型要求**列出来，逐条去模板正文里搜（设置页展开模板卡片可以看到「当前生效的模板正文」，`src/components/settings/PromptSettings.tsx:588-591`）。

### (c) 覆盖滞留旧版（最隐蔽）

覆盖文件里存的是**保存当时**的内置正文快照，不是一个指向内置的引用。后果：

- 内置模板升级了（修了措辞、补了判定标准）→ 你的覆盖不跟进。
- 你以为在用新版系统 → 实际跑的是几个月前那份正文。
- **代码是新的，行为是旧的。**

识别信号：模板卡片上出现橙色的「内置已更新」标签，悬停提示原文是：

> 内置模板已更新，但当前生效的是覆盖文件（沿用保存当时的旧版内置内容）（`src/components/settings/PromptSettings.tsx:503-506`）

展开卡片后会看到更完整的说明，以及一个按钮：

> **采纳新版正文（保留我的指导）** —— 正文会被替换；「补充创作指导」保留。（`src/components/settings/PromptSettings.tsx:561-571`）

点它就解决：正文换成新版内置，你自己写的补充指导原样保留。若你想连自定义一起清掉，用「恢复默认」。

**三种打架里，(c) 是唯一一种"你觉得系统不稳定、其实是自己的配置太旧"的情况。** 排查任何"改了没反应"之前，先看有没有这个标签。

## 4. 系统级 prompt 稳定吗

拆成两问，答案相反——这是最容易混的一处。

| 问法 | 答复 | 为什么 |
|---|---|---|
| 会不会**被我的配置改坏**？ | **不会** | `systemSuffix` 覆盖不到，是刻意护栏（§1.2） |
| 会不会**跨版本还是最新的**？ | **不会自动** | 覆盖存的是快照不是引用（§3c） |

第一条可以放心：输出格式、字段清单、判定标准、字数合格线都在护栏内，你无论怎么改配置都动不到它们。

第二条是机制性质，不是 bug：如果覆盖存的是引用，那么内置一升级，你精心调过的正文就会被无声替换——那才是真正的"反向优化"。所以系统选择冻结，代价是**需要你自己决定何时采纳新版**。管理手段只有两个：「内置已更新」标签 + 「采纳新版正文（保留我的指导）」按钮。

### 4.1 一条反直觉但重要的事实

正文链最终发给模型的是**两条消息**：`system` 角色 + `user` 角色（`src/services/workflows/commands/generate-draft.command.ts:1370-1371`）。分配是这样的：

| 消息 | 装什么 |
|---|---|
| `system` | 创作角色定位（`systemRole`）+ 代码追加的固定系统合同 |
| `user` | 模板正文 + 补充创作指导 + `systemSuffix` + 必需上下文 |

也就是说：**名为 `systemSuffix` 的「输出格式与判定标准」、以及「不可偏离的作者事实」这类硬约束，实际都拼在 `user` 消息里**（`src/services/prompts/prompt-builder.ts:110-114`；硬约束原文见 `src/services/builtin-prompt-templates.ts:1132`）。

它们靠的是**位置靠后**（同一轮里最后出现）来获得影响力，而不是靠"角色更高"。

结论：**"内容稳定"不等于"影响力稳定"。** 你的补充指导排在这些硬约束**之前**，所以一段又长又啰嗦的补充指导，会把这批判定标准推得更远、稀释得更淡。这也是 §3(a) 反复强调"别重复注入"的底层原因。

## 5. 没生成平台风格正文，问题出在哪

先给最确定的一条：

> **绝大多数"没按风格写"不是文案不够狠，是那段话根本没进请求。**

所以排查顺序是「先确认在场，再确认层级，最后才谈条款强度」。工具是 Prompt 追踪。

### 5.1 怎么开

设置 → 开发者 → 「**Prompt 追踪（输入 / 输出落盘）**」（`src/components/settings/DeveloperSettings.tsx:108`）。

打开后跑一次主链路生成（架构 / 正文 / 精修任选）。开关说明原文：

> 打开后，每次生成会把「组装前的提示词片段（含来源）+ 组装后原文 + 实际发出的请求与模型输出」写到当前项目的 debug/prompt-trace 文件夹，供定位调优。

### 5.2 落在哪

固定写到**当前项目根目录**下 `debug/prompt-trace/`（`src/services/prompts/prompt-trace-writer.ts:32-36`）。每次生成两枚文件：

| 文件 | 用途 |
|---|---|
| `.md` | 给人读：拼装后的完整提示词、片段归因表、实际请求与输出 |
| `.json` | 给脚本处理：同一批数据的结构化版本 |

文件名：`<时间戳>-<业务标签>-<章节段>-<runId 前 8 位>`，缺的段会省略（`src/services/prompts/prompt-trace-writer.ts:377-382`）。

**两点注意**：

1. 追踪只覆盖走提示词装配的链路。个别链路（如结构化批量执行）会有片段快照，但拿不到真实请求面，文件里会写「本次未拿到真实请求面（该链路的请求未回传渲染层）」（`src/services/prompts/prompt-trace-markdown.ts:174`、`:210`）。
2. 落盘失败不影响生成——写文件是旁路，出错只回显状态，不中断任务。

### 5.3 先分清「请求面」是哪一种

`.md` 文件头有一行 `请求面来源`，两种取值含义差别很大：

| 写法 | 可信度 | 说明 |
|---|---|---|
| 实际发出（与模型收到的一致） | 最高 | 逐字就是模型看到的东西，含运行时注入的「补充写作 Skill」等 |
| 按装配结果重建 | 次之 | 由「system 角色」+「组装后正文」拼出骨架，运行时注入的内容不在其中（`src/services/prompts/prompt-trace-markdown.ts:137`、`:169-170`） |

判断"某段话有没有进请求"，**以第一种为准**。第二种只能证明"装配层认为它进去了"。

### 5.4 五步归因表

按顺序走，命中即停——后面的步骤都建立在前面成立的前提上。

| 步 | 看什么 | 命中意味着 |
|---|---|---|
| 0 | 该事实源有没有接到这条链路上（代码层，见 §1 边界） | 没接 → **接线缺失，改文案无用** |
| 1 | `.md` 里「片段来源（可改性归因）」表：有没有你改的那块 | 没有 → 覆盖没被加载（文件没存上 / 存到了另一级 / 链路上没接这个模板） |
| 2 | 同一张表的「生效来源」列：`builtin` / `global` / `project` | 是 `global` 而你改的是项目级 → **改错了层级** |
| 3 | 设置页有无「内置已更新」标签 | 有 → 覆盖滞留旧版（§3c），点「采纳新版正文」 |
| 4 | `### 变量投影（进入请求前已改写）` 的 `before → after 字（省 N，x%）` 与「被边界化的块」 | 被裁 → **上下文预算问题，不是文案问题** |
| 5 | 以上都没有，但模型没照做 | 才轮到条款强度；且先查是不是被覆盖版里的旧条款盖住了 |

### 5.5 片段归因表的六列怎么读

表头固定为 `序号 | 来源 | 名称 | 可改 | 生效来源 | 变量`（`src/services/prompts/prompt-trace-markdown.ts:189-194`）。

| 列 | 取值 | 读法 |
|---|---|---|
| 来源 | `builtin-content` / `override-content` | 模板正文：内置版 / 覆盖版 |
| | `builtin-taskGuidance` / `override-taskGuidance` | 补充创作指导：内置版 / 覆盖版 |
| | `builtin-systemRole` / `override-systemRole` | 角色定位（进 system 消息） |
| | `builtin-systemSuffix` | 输出格式与判定标准，**永远是 builtin** |
| | `required-context` | 系统补回的权威项目设定 |
| | `variable-value` | 变量替换后的值 |
| 可改 | `可改` / `锁定` | `锁定` = 你没有任何入口能改它，别再找 |
| 生效来源 | `builtin` / `global` / `project` | 与设置页颜色标签一一对应（§1.3） |

来源枚举定义在 `src/services/prompts/prompt-trace.ts:30-39`。看到某块是 `override-*` 且 `生效来源` 写着 `project`，说明你改的那一版**确实在跑**——此时再去第 4、5 步找原因，不要回头怀疑配置没生效。

## 6. 常见误判对照表

| 现象 | 容易误判成 | 实际常常是 |
|---|---|---|
| 改了配置没反应 | 系统不稳定 / 提示词不够强 | 覆盖滞留旧版（§3c）——先看「内置已更新」标签 |
| 模型没按平台风格写 | 文案写得不够狠 | 那段根本没进请求（§5 第 0/1 步） |
| 首稿对了、续写跑偏 | 规则没用 | 续写轮不重新渲染模板正文，只带角色定位与规则块（`src/services/prompts/prompt-builder.ts:66-76`、`generate-draft.command.ts:1412`） |
| 同一条要求要写两遍 | 模型理解差 | 正文与补充指导重复注入，互相稀释（§3a） |
| 节奏忽快忽慢 | 模型随机性 | 你在作者级写了数字，与模板硬写的数字打架（§3b） |
| 配置里明明写了，trace 里找不到 | 追踪坏了 | 你改的是项目级，这条链路读的是全局（§5 第 2 步） |
| 追踪文件里段落少了一截 | 模板被删了 | 变量投影把它边界化省掉了（§5 第 4 步） |

```text
   ├─ 设置页有「内置已更新」？ ── 有 ──→ 点「采纳新版正文（保留我的指导）」→ 重跑
   │
   ├─ 开了 Prompt 追踪？ ── 没开 ──→ 设置 → 开发者 → 打开 → 重跑一次
   │
   ├─ .md「片段来源」表里有你改的那块？ ── 没有 ──→ 覆盖没加载（§5 第 1 步）
   │
   ├─ 「生效来源」列是不是你改的那一级？ ── 不是 ──→ 改错了层级（§5 第 2 步）
   │
   ├─ 「变量投影」里看到被裁？ ── 是 ──→ 上下文预算问题，先减冗余再谈措辞
   │
   └─ 以上都过 ──→ 才调条款强度；同时检查是否与模板里的数字/格式打架
```

读法：从上往下走，**每一步都是一个"排除"，不是"猜测"**。走到最后还没解决，才是真正的提示词措辞问题。
