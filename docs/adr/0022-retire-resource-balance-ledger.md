# 账本余额下线：小说不需要会计，只需要口径一致

W6 把「资源」这条线做成了账本：逐章抽取变动、纯函数累加余额、三态（known / unknown / conflict）、中断语义、逐章走势、按章回填。实现本身没有问题，**是目标错了**。

## 为什么错

1. **唯一的消费者是一块展示面板。** `balanceAt` 在代码里只被 `WorldStatePage` 与它的视图模型调用，没有任何生成链路读它。也就是说：为一套算术 + 三态 + 中断 + 走势，付出的成本换回来一个「给人看的数字」。
2. **正文本来就不用精确数字。** 写作时讲「一大笔」「几十枚」「兜里见底」，读者感知的是稀缺与代价，不是余额等式。系统算出的余额一旦与这种模糊表述相遇，只会产出一个作者不认的结论。
3. **崩盘的根因不是「没记账」。** 修真文灵石经济崩盘的通行解释是供给失控与数值膨胀——新矿脉随便开、主角随手得巨款、宗门月例想发多少发多少。这些都不是余额算得准能救的；反过来，账算得再准，也救不了「元婴修士年薪买不起一件法宝」。
4. **如果按原计划走下去，它会主动制造错误。** W7 要把「当前余额 154 枚」注入给模型。模型看到数字就会在正文里写出来，而这个余额可能是 `unknown`、可能被模糊表述低估、可能跨越中断章——等于用**派生数字反向约束一手文本**。因果是反的。

## 决定

**下线入口，保留代码与数据。**

- 定稿后处理不再注册 `resource-ledger` 步骤（`buildFinalizePostProcessSteps` 的 `includeResourceLedger` 默认 `false`）⇒ 不再每章花一次模型调用。
- 世界状态左栏不再列出「资源」（`WORLD_STATE_SECTION_ORDER` 移除 `'resources'`）⇒ 余额、走势、补扫入口全部不可达。
- 资源登记面板保留，但它的含义收窄为**资源词汇表**：名称 / 单位 / 口径 / 换算锚，供生成时统一口径，避免每章重新发明单位与周期。
- `resources` / `resource_movements` 两张表、`resource-ledger.ts` 全套算术、`ResourcesSection` 组件、以及它们的测试**全部保留**。想恢复时：打开 `includeResourceLedger`、把 `'resources'` 加回分类数组即可。

## 那「一致性」交给谁

1. **生成期规则层 A-1~A-4**（`worldbuilding-numeric-audit.ts`）：量纲上限、「几分之一」缺分母、同资源双单位、资源名重复定义。它不需要账本，只需要资源名清单。
2. **审稿第 9 维「计量口径」**：日结/月结双口径、数额与周期不匹配。
3. **资源定义表 + 建议级提示（W6a-7）**：`unit` 填成数字、`period` 不是口径词时提示一次。

这三样的共同点是**判「说得对不对」，不判「账平不平」**——这才是写作需要的那一层。

## Consequences

- 第 2–4 章那类「十二时辰换十枚灵石」「药钱占五分之一」的错误，仍然会被 A-1/A-2 在生成期抓到；这不是账本的功能，是规则层的功能。
- 已抽取的 4 条变动作为历史数据留在库里，不再新增；它们不影响任何生成行为。
- 判据 DI（权威值唯一）仍然成立且更重要：`resources` 成为唯一的口径来源。
- 判据 DJ（中断必须显式）、DK（模型不做算术）在账本下线后暂时没有消费者，**不要删除判据**——它们是以后任何"派生数值"机制的红线。
- 这次退化不是失败，是把一个**想过头**的设计收回原位：资源的价值在「设定一致性」，不在「记账准确性」。
