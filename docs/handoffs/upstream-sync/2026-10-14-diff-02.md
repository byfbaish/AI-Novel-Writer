| **(d) 没写出字的片段不列出 + 恢复项规则** | `src/components/run/run-recovery.ts`（新目录） | **我方无该文件** | ⛔ 不适用 |

**(a) 的根因（重要）**

- `llm_calls.created_at` 的默认值是 SQLite `datetime('now')` → 产出 `YYYY-MM-DD HH:MM:SS`，**UTC 但不带时区标记**；
- `LLMHistoryRepository.getHistory` 直接 `created_at as createdAt` 返回**原样字符串**；
- JS `new Date('2026-08-29 10:00:00')` 对**无时区标记的 date-time** 按**本地时间**解析 ⇒ 东八区**慢 8 小时**；
- 我方 `stats-service.ts:42 callCompletionRange` 早已正确（正则捕获后拼 `T...Z`），但**只用于 `diagnosticWorkflowForCall` 的区间匹配**，没导出到展示层。

**改动**
```ts
/** 调用记录的时刻。SQLite 的 CURRENT_TIMESTAMP 是不带时区的 UTC，直接交给 Date 会被当成本地时间。 */
export function llmCallTime(createdAt: string): Date {
  return new Date(callCompletionRange(createdAt)?.[0] ?? Date.parse(createdAt))
}
```
`BottomPanel.tsx`：「模型调用」历史表时间列改 `llmCallTime(row.createdAt)`。
**不动 `BottomPanel.tsx:207`** —— 那是 `run.createdAt`（`WorkflowRun`），来源是 JS `new Date().toISOString()`（带 `Z`），无此问题。

**(c) 的改动**：`roleLabel(role) => getCharacterRoleLabels(role)` 经 `text(zhCN, enUS)` 输出；空 role 仍走原 fallback。

**(a) 的验证**
- 新增 `stats-service.test.ts` 3 例：SQLite UTC 串按 UTC 解析 / 已带时区的 ISO 不变 / 不可解析值返回 Invalid Date 不抛；
- **负向验证**：把实现改回 `new Date(createdAt)` ⇒ UTC 用例变红，断言差值 `1787997600000 - 1787968800000 = 28,800,000 ms`，**恰为 8 小时** ⇒ 缺陷真实、测试有效。
