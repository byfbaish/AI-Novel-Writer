**原判「精确匹配撞上拼接串」不成立。** 复核依据三条：

1. `:281 / :335 / :336` 三处断言**都没有 `exact: true`**；provider 是 Playwright（`vitest.browser.config.ts`），`getByText(string)` 默认**子串**匹配 —— 拼接串能命中前半句。
2. **硬反例**：`:335 / :336` 断言的正是同一个拼接串（同一元素内两句并列），它们**通过**。若拼接致败，这两条必同红；基线只有 1 条 B16 失败。
3. `:281` 的真实失败路径与拼接无关：该用例 `sourceStatus: 'current'`（`:269`），先过 `CodeMirrorEditor.tsx:714` 的门；随后 `:720-728` 的 `targetStillCurrent` 因 `filePath` 从 `draft/1` 变 `draft/2` 而为 `false`，直接落到 `:730` 的「正文或原目标已变化…」。`:717` 的 `sourceConflictNoticeText` 分支**根本没进入**。

## 四、实机新发现（原卡未覆盖）

**改正文后点「替换」，命中的是「正文或原目标已变化」，不是「来源已变化」。**
也就是说：作者最可能遇到的操作路径（先改动再应用），文案并不指向「来源」，
而 `sourceStatus !== 'current'`（真来源漂移 / 候选丢失）才走「来源已变化」。

两条文案语义不同（前者 = 你的正文/目标变了，后者 = 上游来源变了），当前用户难以区分。
**这条才是本轮真正值得裁的产品议题**，且与 `:281` 的测试失败是同一处分支 ——
原判把它当「测试写法」放过了，等于把产品线索引到了错误的方向（第 2 节已修正）。

另：切文件（`filePath` 从 `draft/1` 变 `draft/2`）也落进同一条 `:730` 文案。
对「作者切换了章节」这个场景说「正文或原目标已变化」是否准确，值得单独判一次。
