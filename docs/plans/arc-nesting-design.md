> 「比如说一个副本跨越了 30 章。但是在这 30 章内，可能还有**小的情节弧**（只有五六章），
> 比如说**小支线、小番外**之类的，你看一下有没有可能设计」。

## 0. 先确认作者的两条定性（都成立）

### 0.1 「弧跟大纲相似度非常高，基本上属于 Prompt 约束」

**✅ 成立，且有代码依据。** 两者的对照：

| | 情节大纲（`synopsis`） | 故事弧（= 第五层） |
|---|---|---|
| 本质 | 一段给 AI 的**结构引导文本** | 一段给 AI 的**结构引导文本** |
| 落点 | `project_core.synopsis` | （原为硬编码）`plot_structure_guide` |
| 消费方式 | 注入 prompt 后由 AI **逐章展开** | 注入 prompt 后**约束**这个展开 |
| 是否结构化 | ❌ 纯文本 | ❌ 纯文本 |
| 是否绑章号 | ✅ 有（它自己就是章） | ❌ 无 |
| 是否管角色 | ❌ | ❌ |

**→ 所以作者说「不需要什么字段不字段的」是对的：弧**不需要任何数据模型**。
**它需要的只是"一段能被编辑、能被注入的文本"，和 `synopsis` 一模一样。**

**★ 这一条推翻了我 `stage-structure-layer.md §2.1` 的字段命名讨论 —— 字段名不重要，
重要的是"它是一段和 synopsis 同级的管理文本"。**

### 0.2 「初始生成时，可以按下表作为参考」

作者给了**单弧篇幅的参考表**（这张表的真正用途见 §2）：

| 单弧章节数 | 对应字数 | 阅读体验 | 适用场景 |
|---|---|---|---|
| 5–8 章 | 1.5–2.4 万 | 太短，刚代入就结束 | 短篇 / 快节奏小事件 |
| 10–15 章 | 3–4.5 万 | 紧凑，适合首弧 | 首副本、开篇建立期 |
| **20–30 章** | **6–9 万** | **饱满，适合中段** | **主副本、核心剧情** |
| 35–50 章 | 10–15 万 | 偏长，容易疲劳 | 大卷 / 多副本合集 |
| **50 章以上** | 15 万+ | **太长，读者会弃** | **不建议单弧超过 50 章** |

**★ 这张表揭示了嵌套的必然性：**
**"不建议单弧超过 50 章" + "一书可能 800 章" ⇒ 一章级不可能只有一层弧。**
如果一个副本 30 章是"一弧"，那么全书 800 章至少 27 个弧 ——
**但作者说 30 章的副本内部还有 5–6 章的小弧 ⇒ 弧是分层的。**

## 1. ★ 新概念梳理：弧的层级（这是本次的核心产出）

### 1.1 三个层级，不是两个

作者提到"大弧和小弧"。**梳理后实际是三个层次**，且有现成的对应物：

| 层级 | 名称 | 篇幅（据作者表） | 本质 | 现有对应物 |
|---|---|---|---|---|
| **L-a** | **总弧 / 全书弧** | = 全书 | 全书的整体阶段划分 | `plot_structure_guide`（三幕/起承转合）—— **就是现在那一层** |
| **L-b** | **大弧 / 副本弧** | 20–50 章 | 一个副本 / 一个大事件 | （新增） |
| **L-c** | **小弧 / 支线弧** | 5–15 章 | 小支线、小番外、副本内的阶段 | （新增） |

**→ 关键洞察：现有的 `plot_structure_guide` 不是"和弧并列的东西"，
它就是这套层级的**最顶层**（L-a）。**

```
【L-a 总弧】三幕 / 起承转合 / 英雄之旅        ← 现有 plot_structure_guide（硬编码）
      │
      ├─【L-b 大弧】副本一「无声公寓」（约 30 章）
      │        ├─【L-c 小弧】支线：隔壁的人（约 6 章）
      │        ├─【L-c 小弧】支线：规则第四条（约 8 章）
      │        └─【L-c 小弧】主线：破局（约 16 章）
      │
      ├─【L-b 大弧】副本二「循环小数走廊」（约 25 章）
      │        └─ …
      │
      └─【L-b 大弧】…
```

### 1.2 层级关系是**"包含"**，不是"并列"

- **大弧包含小弧**；
- **小弧不跨越大弧**（一个小支线不会横跨两个副本）；
- **所有大弧加起来 ≈ 全书**（覆盖总章数）；
- **总弧（三幕）是所有大弧的上位分组**（第一幕可能含 2 个大弧）。

**→ 这条与作者此前"按层级约束"的说法完全一致：
每一层只约束它的直接下层，不跨级。**

### 1.3 ★ 为什么这**恰好证明**了"弧 = Prompt 约束"（作者的定性）

如果弧要绑定章号，那"大弧 30 章、内含 3 个小弧各 6/8/16 章"就必须是**精确的整数分配** ——
**那就必须结构化存储、必须做区间校验、必须处理"小弧总和 ≠ 大弧"的冲突。**

**但作者从来没要求这些。** 作者要的是：
> 「不一定非要明确在多少章到多少章」

**→ 所以在"无章号"的前提下，嵌套只是"文本里的缩进层级"，不是"数据的父子外键"。**

## 2. ★★ 那张参考表的真正用途（本次最重要的设计判断）

作者给的表，**不是"给弧做校验用的"，而是"给 AI 生成时的约束语料"。**

**→ 它的正确落地方式：写进生成"弧结构"那一步的 Prompt 里，作为篇幅建议。**

就像现在 `getPlotStructureGuide` 里已经写着的：

```
【三幕结构】（严格按以下结构组织大纲）
建议章节分配：全书共 800 章
第一幕：建置（约第1章~第160章，占总篇幅约20%）
```

**新的一层只是把"百分比"换成"这张表的经验值"**：

```
【阶段结构】
建议按以下篇幅经验划分（单弧不宜超过 50 章，否则读者疲劳）：
- 首弧：10–15 章（紧凑，用于建立期）
- 主副本：20–30 章（饱满，用于中段核心剧情）
- 大事件：35–50 章（需内部再分小弧，否则节奏拖沓）
- 小支线 / 小番外：5–8 章（穿插在大弧之间或内部）

每个大弧内部，若超过 20 章，应当拆出 1–3 个 5–15 章的小弧（支线/番外/阶段）。
```

**★ 注意这张表的一个隐含结论：它不是"约束"，而是"经验参考"。**
表里说"50 章以上不建议" —— 但作者的 800 章项目显然**总会有超过 50 章的阶段**，
所以它是**"拆弧的提示"**，不是"禁止"。

**→ 落地形态：作为给 AI 的"篇幅经验语料"，让它据此**主动建议在哪拆小弧**。**

## 3. 落地设计：一段带层级的文本（无字段、无表）

### 3.1 存储形态（作者已定：整段文本）

**✅ 作者明确回答：「"调整"是「编辑整段文本」（同 worldbuilding）→ yes」**

→ **所以完全不结构化**。就是一段 Markdown，用**标题层级**表达嵌套：

```markdown
# 阶段结构

## 第一幕：建置（约 1–160 章）

### 大弧 1：出租屋与现实世界（约 1–15 章）
- 目标：建立沈舟的处境、金手指首次触发
- 转折：发现规则的异常

### 大弧 2：无声公寓（约 16–45 章）
- 目标：完成首个副本，确认规则体系
- 转折：第四十七条规则的真相
  - 支线：隔壁的人（约 6 章，沈舟与邻居的信息博弈）
  - 支线：三长两短的敲门（约 8 章，规则验证）
  - 主线：破局（约 16 章，正面冲突）

## 第二幕：对抗（约 161–600 章）
…
```

**→ 嵌套 = Markdown 的 `##` / `###` / `-` 缩进，没有别的机制。**

### 3.2 生成方式

| 环节 | 做法 |
|---|---|
| **生成步骤** | 架构阶段新增一步（同 `worldbuilding`），**输出上述 Markdown** |
| **输入** | `premise` + `charactersArch` + `worldbuilding`（含空间结构）+ `totalChapters` |
| **篇幅约束** | ★ **把作者那张表作为 Prompt 的一部分喂进去**（§2） |
| **`totalChapters`** | **只用于"建议每个弧多少章"，不产生任何强绑定**（弧里的章号是"约 X–Y 章"，是**建议值**） |
| **编辑** | 整段文本编辑（同 worldbuilding） |
| **重新生成** | 可单步重新生成 |

**★ 等价于"给 AI 一张篇幅经验表 + 这本书的设定，让它规划出分层的阶段结构"。**

### 3.3 消费方式（复用管线，仍然是一行）

```ts
.withPlotStructureGuide(
  core.plot_structure_plan?.trim()
  || getPlotStructureGuide(config.plotStructure || 'three_act', sourceExpected.totalChapters, language)
)
```

**→ 与 `stage-structure-layer.md §2.3` 完全一致，嵌套不带来任何额外消费成本。**

## 4. 与既有实体的关系（嵌套视角的重新审视）

| 既有实体 | 在嵌套里的位置 |
|---|---|
| `plot_structure_guide`（三幕等） | = **L-a 总弧**（现在硬编码，显现后成为可编辑文本的最顶层） |
| `synopsis`（情节大纲） | = 各层弧**展开成章**之后的结果（**它自带章号，是"落地"的产物**） |
| `blueprints`（章节蓝图） | = 大纲的进一步落地（逐章） |
| `narrative_thread_plans`（伏笔） | 可关联到**任意层级**的弧（不强制） |
| `characters` | **不参与**（v3 已定：角色归"参与关系"） |

**→ 弧与大纲的分工（这次的精确表述）：**
**弧回答"有哪些阶段、每段的意图是什么"；大纲回答"每段用几章、每章写什么"。**

## 5. 一个必须提醒的**边界**（防止设计失控）

**作者明确说过"弧不绑章号"，但 §3.1 的示例里出现了"约 1–15 章"。这怎么统一？**

**→ 统一方式是：那些章号是"建议/预估"，不是"契约"。**

| 是 | 不是 |
|---|---|
| ✅ 生成时 AI 会给出"约 16–45 章"的建议 | ❌ 不是强制的区间边界 |
| ✅ 大纲展开时可以偏离（写 50 章或 40 章都行） | ❌ 不做"大纲章号是否落在弧区间内"的校验 |
| ✅ 它帮助大纲"知道自己在展开哪一段" | ❌ 不构成对大纲的硬约束 |

**★ 这条边界很重要：一旦给弧加校验，它就从"上游引导"退化成"同层冲突源"——
这正是 v3 撤回章号字段的原因。**

**→ 建议：在生成的 Prompt 里明确写"章号为预估，供参考，大纲可据实际需要调整"。**

## 7. 一句话总结

**作者的两条定性成立：① 弧跟大纲一样，**本质是 Prompt 约束，不需要字段**；
② 弧**是分层的** —— 全书弧（=现有 `plot_structure_guide`）⊃ 大弧（副本，20–50 章）
⊃ 小弧（支线/番外，5–15 章）。**

**嵌套的落地**不需要任何数据模型**：它只是**一段用 Markdown 标题层级表达的文本**，
存储方式与 `worldbuilding` 完全相同（作者已确认"编辑整段文本"）。

**作者给的篇幅参考表的正确用途，是**写进生成 Prompt 的"经验语料"** ——
像现在 `plot_structure_guide` 里写"第一幕占 20%"一样，
新的一层只是把"百分比"换成"单弧 20–30 章、不超过 50 章、超了要拆小弧"，
让 AI 据此**主动规划分层结构**。**

**唯一要守的边界**：弧里的章号是**预估、非契约**，绝不做校验 —— 一旦校验，它就从上游蜕变成冲突源。**
