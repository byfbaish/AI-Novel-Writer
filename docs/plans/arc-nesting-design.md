## 1. 弧的层级（**权重下调为次要**，但仍是必要的结构性约束）

### 1.1 三层结构

| 层级 | 名称 | 篇幅（据作者表） | 本质 | 现有对应物 |
|---|---|---|---|---|
| **L-a** | **总弧 / 全书弧** | = 全书 | 全书的整体阶段划分 | `plot_structure_guide`（三幕/起承转合）—— **就是现在那一层** |
| **L-b** | **大弧 / 副本弧** | 20–50 章 | 一个副本 / 一个大事件 | （新增） |
| **L-c** | **小弧 / 支线弧** | 5–15 章 | 小支线、小番外、副本内的阶段 | （新增） |

```
【L-a 总弧】三幕 / 起承转合 / 英雄之旅        ← 现有 plot_structure_guide（硬编码）
      │
      ├─【L-b 大弧】副本一「无声公寓」（约 30 章）
      │        ├─【L-c 小弧】支线：隔壁的人（约 6 章）
      │        ├─【L-c 小弧】支线：规则第四条（约 8 章）
      │        └─【L-c 小弧】主线：破局（约 16 章）
      │
      ├─【L-b 大弧】副本二「循环小数走廊」（约 25 章）
      └─【L-b 大弧】…
```

### 1.2 两类关系（**这才是重点**）

**弧与弧之间有**两种**关系，必须分别处理：**

| 关系类型 | 说明 | 我的上一稿 | 作者指出的重点 |
|---|---|---|---|
| **纵向：包含** | 大弧 ⊃ 小弧 | ✅ 覆盖了 | 次要 |
| **横向：推进** | **同级弧之间的因果/时序链** | ❌ 几乎没谈 | ⭐⭐ **核心** |

**纵向（包含）**：
- 小弧不跨越大弧；大弧加起来 ≈ 全书。

**横向（推进）★★ 真正要关注的**：
- **同级弧之间不是并列的，是有先后与因果的。**
- 例：`大弧1：发现异常 → 大弧2：因此进入副本 → 大弧3：副本暴露更深规则`
- **每一弧必须能回答"我为什么接在前一弧之后"。**

**→ 这是现有 `plot_structure_guide` 完全没有的能力**（它只分段、不连接）。

### 1.3 ★ 为什么这**恰好证明**了"弧 = Prompt 约束"（作者的定性）

如果弧要绑定章号，那"大弧 30 章、内含 3 个小弧各 6/8/16 章"就必须是**精确的整数分配** ——
**那就必须结构化存储、必须做区间校验、必须处理"小弧总和 ≠ 大弧"的冲突。**

**但作者从来没要求这些。** 作者要的是：
> 「不一定非要明确在多少章到多少章」

**→ 所以在"无章号"的前提下，嵌套只是"文本里的缩进层级"，不是"数据的父子外键"。**

## 2. ★★ 生成 Prompt 里必须写进去的**两样东西**（本次最重要的设计判断）

作者对生成的表述是**一句话两层意思**：

> 「**只描述用多少章来处理**，在弧生成期间**根据下面经验来约束章节数**，
> 但是**真正要关注的是，同级弧是有因果、时序等事件推进逻辑的**」

**→ 拆成两个 Prompt 段落，缺一不可：**

### 2.1 第一样：篇幅经验表（"只描述用多少章来处理"）

作者给的表，**不是"给弧做校验用的"，而是"给 AI 生成时的约束语料"。**
它的正确落地方式：**写进生成"弧结构"那一步的 Prompt 里，作为篇幅建议。**

就像现在 `getPlotStructureGuide` 里已经写着的：

```
【三幕结构】（严格按以下结构组织大纲）
建议章节分配：全书共 800 章
第一幕：建置（约第1章~第160章，占总篇幅约20%）
```

**新的一层只是把"百分比"换成"这张表的经验值"**：

```
【篇幅经验】（用来判断"一个弧该多大、什么时候该拆"）
- 5–8 章：太短，刚代入就结束 —— 只适合快节奏小事件
- 10–15 章：紧凑，适合首弧（开篇建立期）
- 20–30 章：饱满，适合中段主副本 / 核心剧情
- 35–50 章：偏长，容易疲劳 —— 适合大卷，但**必须先拆出内部小弧**
- 50 章以上：太长，读者会弃 —— **不建议任何单弧超过 50 章**

→ 为每个弧给出"预计用多少章"（如"约 20–30 章"）。
→ 若一个弧预估超过 30 章，应当在其内部拆出 1–3 个 5–15 章的小弧。
```

**★ 这张表的语气是"经验参考"，不是"硬约束"：**
表里说"50 章以上不建议"，但长项目**难免有超长的阶段** ——
所以它的作用是**"拆弧的提示器"**，不是"禁止令"，更不是事后校验的区间。

### 2.2 ★★★ 第二样：**同级弧之间的因果/时序推进要求**（"真正要关注的"）

**这是作者反复强调、而现有 `plot_structure_guide` 完全没有的那一半。**
篇幅表只说了"每个弧多大"，**完全没说"弧和弧之间是怎么接上的"**。

**→ 生成 Prompt 里必须显式要求 AI 输出这条链。**

> **★ 补充（2026-10-11，吸取外部报告的 §1）：推进要求**不能是一句话模板**。
> 外部报告《弧生成 Prompt 设计》指出一个我们漏掉的点：**不是所有弧都走因果链**，
> 探索型弧若被强行套上因果，会写出**伪因果**。**
> **→ 所以 §2.2 的写法是"先判型、再套结构"。**

#### 第一步：先判断本弧属于哪种类型

| 类型 | 特征 | 判定信号 | 适合的结构 |
|---|---|---|---|
| **A 因果驱动型** | 事件 A→B→C 环环相扣 | "因为…所以…"能串成链 | **因果链**（每步说明前置事件） |
| **B 目标驱动型** | 主角有目标，反复尝试 | 出现"尝试-失败-再尝试" | **目标-尝试-结果三元组** |
| **C 探索型** | 在空间/人群中并列遭遇 | 事件之间是"又遇到…"而非"因此…" | **探索路径**（节点=发现+状态变化） |

**→ 这份类型学的价值：它让"推进要求"从"必须写因果"降级为"**必须写清推进逻辑**"——
A 型写因果、B 型写"为什么进入下一次"、C 型写"探索的动机与阶段"。**

#### 第二步：按类型输出（全部写成 Markdown 文本行，不用字段）

```
【同级弧的推进关系】（重中之重，必须逐弧交代）
先判断本弧类型（A 因果驱动 / B 目标驱动 / C 探索型），再按对应方式写推进关系：

▸ A 因果驱动型 —— 逐条写因果链：
  因果：因为 <上一弧/前一事件> 的 <具体结果>，所以 <本弧发生的动作>
  时序：本弧起点 = 上一弧结束时的 <具体状态>

▸ B 目标驱动型 —— 写目标与尝试序列：
  目标：<一句话，从 X 到 Y 的完整变化>
  尝试 1：<方法> → 结果 <什么> → 因此进入尝试 2（说明为什么必须再试）
  尝试 2：…（每次尝试都要交代"为什么进入下一次"）

▸ C 探索型 —— 写探索动机与路径：
  动机：<为什么要探索>（这是补偿"无因果"的关键）
  路径：<地点A> → 发现 <X>；<地点B> → 发现 <Y>（节点之间是"接着去…"）

→ ❌ 不要写成"第一弧…第二弧…第三弧…"的平铺罗列。
   ✅ 要写成有推进逻辑的链条：**"我为什么接在前一弧之后？"** 答不出来就是断链。
   ✅ C 型例外：它不要求弧间因果，但**必须交代探索动机**，否则就是流水账。
```

**★ 注意两个层次的推进，报告只说了下面那层，我们要的是上面那层：**

| 推进的层次 | 说明 | 现状 |
|---|---|---|
| **弧内推进**（报告说的） | 这一弧**内部**事件之间的因果/时序 | 报告重点；但弧内细节本就归大纲管 |
| **弧间推进**（作者说的） | **上一弧 → 本弧**为什么这样接 | ★★ **本层核心，报告几乎没谈** |

**→ 报告整篇在讲"弧内事件链"，而作者要的是"弧与弧之间"。**
**两者都要，但**弧间推进是我们的第一优先级**（§0.0）。**

**★ 与 §2.1 的分工：**
- **§2.1 篇幅表** 管的是**"横向铺开多大"**（一个弧多宽）
- **§2.2 推进链** 管的是**"纵向怎么接"**（弧与弧之间的先后与因果）
- **作者的最新纠正正是说：§2.2 才是重点，而我上一稿只写了 §2.1。**

## 3. 落地设计：一段带层级的文本（无字段、无表）

### 3.1 存储形态（作者已定：整段文本）

**✅ 作者明确回答：「"调整"是「编辑整段文本」（同 worldbuilding）→ yes」**

→ **所以完全不结构化**。就是一段 Markdown，用**标题层级**表达嵌套：

```markdown
# 阶段结构

## 第一幕：建置（约 1–160 章）

### 大弧 1：出租屋与现实世界（约 1–15 章）
- 类型：（首弧，无前序）
- 目标：建立沈舟的处境、金手指首次触发
- 转折：发现规则的异常

### 大弧 2：无声公寓（约 16–45 章）
- 类型：A 因果驱动型
- 因果：**因为**大弧 1 末尾沈舟发现"规则异常"，**所以**他主动追查，
  被引入无声公寓 —— 没有大弧 1 的异常，这一弧不可能发生
- 时序：紧接大弧 1 的当夜，沈舟尚未从异常中恢复
- 目标：完成首个副本，确认规则体系
- 转折：第四十七条规则的真相
  - 支线：隔壁的人（约 6 章，沈舟与邻居的信息博弈）
  - 支线：三长两短的敲门（约 8 章，规则验证）
  - 主线：破局（约 16 章，正面冲突）

### 大弧 3：公寓之外的注视（约 46–75 章）
- 类型：A 因果驱动型
- 因果：**因为**大弧 2 破局时暴露了沈舟的存在，**所以**他才被外部势力盯上
- 时序：大弧 2 结束后约一周
- 目标：从"生存"转向"反击"，确认外部势力的性质

### 大弧 4：休整区（约 76–90 章）
- 类型：C 探索型（★ 不套因果，套动机）
- 动机：大弧 3 的高压对抗后，沈舟需要打探情报、补充资源、建立人脉
- 路径：大厅（遇旧榜，得知其他幸存者坐标）→ 匿名提示者（获得警告）
  → 引路人（获得进入下一副本的资格）→ 储物格（发现前人的遗留物）
- 时序：大弧 3 结束后，沈舟主动选择进入中立空间休整

## 第二幕：对抗（约 161–600 章）
…
```

**→ 嵌套 = Markdown 的 `##` / `###` / `-` 缩进，没有别的机制。**
**→ 推进关系 = 每个 `###` 弧下的 `类型 / 因果 / 时序`（或 `类型 / 动机 / 路径`）几行文字，
也没有别的机制。**

**★ 关键：推进关系不是数据，是文本。** 它靠 AI 在生成时写出来、
靠作者在编辑时读得懂 —— **不需要任何字段去存"from_arc/to_arc"**。

**★ 注意大弧 4（C 探索型）的写法**：
它**不写因果**（因为它和前一弧不是因果链），而是**写"动机/路径"** ——
如果强行给它编一句"因为大弧 3…所以休整"，那就是**伪因果**，反而降质。
**→ 这就是 §2.2 类型学的实际效果。**

### 3.2 生成方式

| 环节 | 做法 |
|---|---|
| **生成步骤** | 架构阶段新增一步（同 `worldbuilding`），**输出上述 Markdown** |
| **输入** | `premise` + `charactersArch` + `worldbuilding`（含空间结构）+ `totalChapters` |
| **📌 篇幅约束** | ★ 把作者那张表作为 Prompt 的一部分喂进去（§2.1） |
| **📌 推进约束** | ★★ 显式要求 AI **先判弧类型（A/B/C）、再按对应结构写推进关系**（§2.2）—— **本次新增的硬要求** |
| **📌 Prompt 内分节** | 借鉴外部报告"先立骨架再展开"的顺序感：**在一条 Prompt 内分节**（先判型 → 再列弧 → 再逐弧写推进关系），**不拆成多个 DB 步骤**（理由见 `arc-prompt-assessment.md §3.2`） |
| **`totalChapters`** | **只用于"建议每个弧多少章"，不产生任何强绑定**（弧里的章号是"约 X–Y 章"，是**建议值**） |
| **编辑** | 整段文本编辑（同 worldbuilding） |
| **重新生成** | 可单步重新生成 |

**★ 等价于"给 AI 一张篇幅经验表 + 一条分型推进要求 + 这本书的设定，让它规划出分层的推进结构"。**

**→ 两个约束的**不对称性**要注意：**
- 篇幅（§2.1）是**软约束**，AI 可以偏离（实际写多写少都行）。
- 推进（§2.2）是**硬要求**，AI **必须**对每个同级弧给出理由 —— **写不出来就等于这一层白做**。

### 3.3 消费方式（复用管线，仍然是一行）

  || getPlotStructureGuide(config.plotStructure || 'three_act', sourceExpected.totalChapters, language)

## 4. 与既有实体的关系（嵌套视角的重新审视）

| 既有实体 | 在嵌套里的位置 |
|---|---|
| `plot_structure_guide`（三幕等） | = **L-a 总弧**（现在硬编码，显现后成为可编辑文本的最顶层） |
| `synopsis`（情节大纲） | = 各层弧**展开成章**之后的结果（**它自带章号，是"落地"的产物**） |
| `blueprints`（章节蓝图） | = 大纲的进一步落地（逐章） |
| `narrative_thread_plans`（伏笔） | 可关联到**任意层级**的弧（不强制） |
| `characters` | **不参与**（v3 已定：角色归"参与关系"） |

**→ 弧与大纲的分工（这次的精确表述）：**

| | 回答什么 | 是否管章号 | 是否管因果 |
|---|---|---|---|
| **弧（第五层）** | "有哪些阶段、每段意图是什么"** + "阶段之间怎么接"** | ❌ 只给预估 | ✅ **这是它的核心职责** |
| **情节大纲（`synopsis`）** | "每段用几章、每章写什么" | ✅ 自带章号 | ✅ 但它只管**章与章之间**的承接 |

**★★ 最关键的一条分工（对应 §0.0 的作者纠正）：**
- **章与章的因果**：已有 —— `builtin-prompt-templates.ts:672`（"保持因果链"）、`:709`（"紧密承接上一章"）、`:853`（"从上一章最终状态之后推进"）。
- **弧与弧的因果**：❌ **现在是空白**。`grep 因果|时序|推进|承接` 遍 `architecture-workflow.ts` 无任何命中。

**→ 所以"弧"这个新层的**唯一不可替代的价值**，就是**填上"弧与弧之间的因果/时序"这段空白**。
如果只做"篇幅分层"而不做"推进链"，那这一层就退化成了"更漂亮的三幕模板"，**不值得新建。**

## 5. 一个必须提醒的**边界**（防止设计失控）

### 5.1 章号：预估，绝不校验

**作者明确说过"弧不绑章号"，但 §3.1 的示例里出现了"约 1–15 章"。这怎么统一？**

**→ 统一方式是：那些章号是"建议/预估"，不是"契约"。**

| 是 | 不是 |
|---|---|
| ✅ 生成时 AI 会给出"约 16–45 章"的建议 | ❌ 不是强制的区间边界 |
| ✅ 大纲展开时可以偏离（写 50 章或 40 章都行） | ❌ 不做"大纲章号是否落在弧区间内"的校验 |
| ✅ 它帮助大纲"知道自己在展开哪一段" | ❌ 不构成对大纲的硬约束 |

**★ 这条边界很重要：一旦给弧加校验，它就从"上游引导"退化成"同层冲突源"——
这正是 v3 撤回章号字段的原因。**

**→ 建议：在生成的 Prompt 里明确写"章号为预估，供参考，大纲可据实际需要调整"。**

### 5.2 ★ 但"推进链"不受这条边界约束（关键区别）

**不要误把 5.1 的"不校验"套到 §2.2 的推进链上。两者性质不同：**

| | 章号 | 推进链（因果/时序） |
|---|---|---|
| 性质 | 数值预估 | **语义断言** |
| 是否校验 | ❌ 绝不校验（会变成冲突源） | ❌ 也不做机器校验（无法形式化） |
| 是否**必须存在** | 可省略（"约"字即可） | ✅ **必须存在，缺了就是废层** |
| 检查方式 | 无 | **人**读一遍：每个弧能否回答"我为什么接在前一弧之后" |

**→ 一句话：章号允许"不精确"，推进链不允许"没有"。**
**这是这一层全部设计里唯一不能妥协的地方。**

## 7. 一句话总结

**作者的两条定性都成立：① 弧跟大纲一样，**本质是 Prompt 约束，不需要字段**；
② 弧**是分层的** —— 全书弧（=现有 `plot_structure_guide`）⊃ 大弧（副本，20–50 章）
⊃ 小弧（支线/番外，5–15 章）。**

**★ 但经过作者最后一次纠正，这一层的价值排序被重新校准：**

| 排序 | 内容 | 重量 | 在哪实现 |
|---|---|---|---|
| **1** | **同级弧的因果/时序推进链** | ⭐⭐⭐ **核心** | Prompt（§2.2，硬要求） |
| **2** | 篇幅经验表约束章节数 | ⭐⭐ 重要 | Prompt（§2.1，软约束） |
| **3** | 弧的分型（A 因果 / B 目标 / C 探索） | ⭐⭐ 重要 | Prompt（§2.2，先判型） |
| **4** | 大弧 ⊃ 小弧的嵌套 | ⭐ 次要 | Markdown 缩进 |

**→ 第 1 项是这一层**唯一不可替代**的存在理由：**
现有 `plot_structure_guide` 只把全书切成三段**并列的区间**，从不解释"第二幕为什么必然接在第一幕之后"；
而章与章的因果**已经**由 `builtin-prompt-templates.ts:672/709/853` 兜住了 ——
**弧与弧之间的因果，全项目是空白，只有这一层能补。**

**落地不需要任何数据模型**：只加**一段用 Markdown 标题层级表达的文本**，
存储方式与 `worldbuilding` 完全相同（作者已确认"编辑整段文本"）。
`project_core` 加一列 + 生成步骤 + 一行消费 + UI 一项 ≈ **<20 行代码**。

**唯一要守的边界**：弧里的章号是**预估、非契约**，绝不做校验 —— 一旦校验，它就从上游蜕变成冲突源。
**—— 而这条边界不适用于"推进链"：推进链不是章号契约，它是**必须写出来的语义要求**。**
