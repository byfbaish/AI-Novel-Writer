## 0. 结论先行：**这份报告的价值不在"新发现"，而在给了一把**统一的尺子**

### 一句话判断

**它列的所有具体项，我们前几轮都已经评估过；但它给出了一个**统一的判据**，
把之前散落在五份文档里的结论**串成了一条明确的落地次序**。**

**→ 它的核心判据只有一条：**

> **这个约束能不能靠"上下文推理"得出？**
> **能推理 → prompt 够用（改模板即可，零代码）**

**→ 这条判据我们其实一直在**隐含使用**（"弧是 Prompt 约束""状态要建表"），
但它**第一次把它写成了一句可复用的决策规则**。这是本报告的最大贡献。**

### 但有一处**关键简化失真**（见 §3）

报告把"因果"整体划进"prompt 够用"，**划得太粗** ——
它没有区分**弧间因果**（真空白，要写 Prompt）和**弧内因果**（已有）。
这与我们 `arc-nesting-design.md §4` 的核实结论冲突。**这一点必须纠正。**

## 2. ★ 报告的真贡献：把"能推理 / 不能推理"落成四类，且**与我们既有结论高度吻合**

我把它四类逐一对照我们已有的评估 —— **没有一条与既有结论冲突**：

| 报告分类 | 报告判定的项 | 我们既有文档的结论 | 是否吻合 |
|---|---|---|---|
| **一、prompt 够用** | 弧级因果、弧类型判断、因果/时序分节 | `arc-nesting-design.md §2` 正是这么设计的 | ✅ **一致** |
| **二、接线现有实体** | 弧引用空间/伏笔/角色 | 弧"不跨级管理"、角色归参与关系（v3 定论） | ✅ **一致** |
| **三、需写代码** | 物品 / 场景 / 角色知识 / 空间节点 / 时间线 | `state-tracking-assessment.md` 同判 | ✅ **一致** |
| **四、复用现有** | evidenceExcerpt / readCharacterProfiles / JSON 严格输出 / 纯文本注入 | 同判 | ✅ **一致** |

**→ 三条"给 agent 的关键判断"尤其精准，直接引用：**

> **判断 1：区分"因果"和"状态"。** 因果是推理链，prompt 够用；状态是数据链，必须显式追踪。
> **判断 2：区分"引用现有实体"和"新建状态"。** 引用只需接线；新建才需新表。
> **判断 3：区分"生成时约束"和"生成后验证"。** prompt 约束"生成时知道什么"，约束不了"生成后是否一致"。

**★ 判断 3 是本项目一个**尚未在文档里显式写出**的维度**，值得记下：

| | 生成时约束 | 生成后验证 |
|---|---|---|
| 手段 | Prompt | 代码（preflight / 事实抽取） |
| 能防 | "这一章该知道什么" | "跨章是否漂移" |
| 本项目现状 | ✅ 有多处（时间承接、因果链） | ⚠️ 只有 `consistency-preflight` 1 条规则 |

**→ 这正好解释了 `architecture-consistency-design.md`（AC 系列）的定位：
AC 系列全部属于"生成后验证"这一格，而这一格目前最薄。**

## 3. ❌ 一处**关键失真**：报告把"因果"整体划给 prompt，**划得太粗**

**报告说**：

> 「弧级因果结构」「因果与时序分节」→ **第一类，prompt 够用，零代码**

**→ 这个判断**在我们的语境下不完整**，因为它没区分两个层次（见 `arc-nesting-design.md §2.2`）：**

| 因果的层次 | 报告归类 | 我们的核实 | 结论 |
|---|---|---|---|
| **弧内因果**（一弧内部事件链） | prompt | ✅ 章级因果**已有**（`builtin-prompt-templates.ts:672/709/853`） | ✅ 报告对 |
| **弧间因果**（同级弧之间为什么接） | prompt | ❌ **全项目空白**（`getPlotStructureGuide` 六分支只描述区间） | ⚠️ **报告漏了这层是"要新写 Prompt"** |

**→ 所以"因果一律 prompt 够用"这句话，如果被 agent 当成结论，会导致：
**忽略了"弧间因果"这一条**根本还不存在的 Prompt 约束**。**

**→ 正确表述应该是：**
**"因果"分两层 —— 弧内因果已由章级 Prompt 兜住（零改动）；
弧间因果是**必须新写的 Prompt 段落**（仍是零代码，但不是'保持现状'，而是'新增内容'）。**
这与报告"第一类的落地方式是'改输入源/加进 prompt'"并不矛盾 ——
**只是报告没说清"弧间因果"这一项现在还没有。**

## 5. ★ 报告最有用的产出：一条**落地次序**（我接受，并做微调）

**报告给的次序：**

> 先改 prompt（第一类，零代码）→ 再接线现有实体（第二类，低代码）→ 最后建状态表（第三类，中代码）

**→ 我认为这个次序**基本正确**，但要插一刀：**

| 报告次序 | 我的微调 | 理由 |
|---|---|---|
| 1. 第一类：改 prompt | ✅ 保持 | 弧的自定义化 + 弧间因果 Prompt（零代码，`stage-structure-layer.md` 已备好 <20 行方案） |
| — | **★ 插入 AC1**（架构层内一致性） | `architecture-consistency-design.md S1`：**低成本、现在可做**，报告未覆盖 |
| 2. 第二类：接线现有实体 | ✅ 保持 | 弧引用伏笔/空间（若第五层落地）；**同时做 AC2**（层间引用完整性） |
| 3. 第三类：建状态表 | ⚠️ **收窄** | 只做**报告第三类里的 1 项：角色知识**（挂事实链，不建矩阵）；**物品/空间/时间线均已评估过，各有更轻方案** |

**→ 微调后的落地次序（建议）：**

```
① 弧层落地（Prompt，零代码）      ← stage-structure-layer.md 的 6 步
② AC1 架构层内一致性（低代码）     ← architecture-consistency-design.md §S1

④ AC2 层间引用完整性（中代码）     ← architecture-consistency-design.md §S2
⑤ 物品/场景/空间/时间线：合并为一  ← 均应"与空间结构一起决策"，不零散立项
```

## 6. 与 `state-tracking-assessment.md` 的关系：**增量，非替代**

**必须说清楚：这份报告**不能替代**第一份报告的评估。** 原因是：

| | 第 1 份报告（状态管理分层） | 本报告（因果 vs 状态） |
|---|---|---|
| 视角 | **状态类型的完整清单**（13 类） | **状态类型的落地判据**（4 类） |
| 贡献 | 穷举了"有哪些状态" | 给了"哪类该用哪种手段" |
| 盲点 | 低估了本项目已有机制 | 把"因果"简化为一类 |

**→ 两份报告是**正交**的：一份管"广度"（有哪些），一份管"深度"（怎么做）。**
**→ 合起来才是完整的方法论。本报告应作为 `state-tracking-assessment.md` 的**判据补充**，
而不是另立一份台账。**
