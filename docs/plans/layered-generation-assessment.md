## 2. ★ 实测到的两个精确根因（带行号）

### 根因 A：角色模板**写死了数量上限**（比"没有约束"更糟）

`src/services/builtin-prompt-templates.ts:443`：

```
围绕主角，根据小说篇幅（{{number_of_chapters}}章）设计合理数量的核心角色（短篇3-4人，中长篇4-6人）。
```

→ **"中长篇 4-6 人"是写死的常量**，与 800 章无关。这是"角色少"的直接原因，
也解释了为什么模型输出了接近上限的数量。

**这不是"缺约束"，是"约束本身是错的"** —— 分析把它归因为"没有篇幅约束"，方向对但没找到病灶。

### 根因 B：弧光模板**有单阶段篇幅表，但没有"按总章数推算数量"**

`src/services/builtin-prompt-templates.ts:592-599`（本次新增的篇幅经验）只回答
**"一个阶段该多大"**：

```
- 20–30 章：饱满，适合中段主副本 / 核心剧情
- 50 章以上：太长，读者会弃 —— 不建议任何单一阶段超过 50 章
→ 为每个阶段给出"预计用多少章"（如"约 20–30 章"）。
```

**缺的是**："总 800 章 ÷ 每阶段 25 章 ⇒ **应当输出约 30 个阶段**"这一步推算。

叠加两个诱导因素，模型自然收敛到少数几个顶层阶段：
1. 输出格式示例只给了 `## 阶段一` / `## 阶段二`（`builtin-prompt-templates.ts:603` 起），
   示例形态本身在暗示"两三个阶段"；
2. `systemRole` 强调"每个阶段都能回答我为什么接在前一个之后"（`:546`）——
   因果链天然是短的，进一步压低阶段数。

→ **结论**：分析说"AI 默认按叙事结构分弧"方向正确，但真正可修的是上面这两点
（**补数量推算 + 明确示例不是数量上限**），不是"没有篇幅约束"。

## 3. 五条建议逐条裁决

### 建议 1：角色拆「核心角色 / 弧光角色」+ 同表 `scope` 字段 —— ❌ 不能这样做

- **`scope` 字段与已定边界冲突**：`00-OVERVIEW.md §5` 纪律 #1 明确
  「弧/空间结构**保持纯文本，不建表、不加字段、不做结构化**」（作者定性）。
- **而且这个诉求已有既有通路**：本项目 **P1 已实施**（`5933a50`/`9504097`）——
  蓝图语义契约里模型**已经在标注** `newCharacterCandidates`，蓝图提交后会
  自动提示建卡，候选可编辑、可回溯来源章节。
  → **"弧光角色"天然就是"弧光对应的那些章纲里新增的角色"**，
    由蓝图→角色卡流水线按需产生，**不需要在架构阶段提前分层，也不需要新字段**。
- **采纳其意图，拒绝其手段**：目标（角色随故事展开而增长）成立；
  实现路径 = 强化既有 P1 通路（例如让候选提示带上"所属弧光"），而不是改数据模型。

### 建议 2：弧光拆三层、各自增量生成 —— ❌ 与「不拆步」直接冲突

- 作者已拍板：「**一步出整段 + Prompt 内分节**；拒绝拆成多个 DB 步骤」（`arc-granularity-and-enum.md §1`，
  `00-OVERVIEW.md §5` 纪律 #9）。拆步 = 管线 ×3 + 回归面大增。
- **分层诉求本身已被满足**：`arc-nesting-design.md §3.1` 已定
  「嵌套 = **Markdown 标题层级**（`##` 大弧 / `###` 小弧 / `-` 支线）」，**零额外技术成本**。
- → 采纳"要有层级"，拒绝"用三次生成实现层级"。

### 建议 3：地图拆「世界骨架 / 地图节点」 —— ⚠️ 一半已落地，一半撞边界

- **世界骨架：已落地**。本次（`796528f`）世界观模板已加**第 4 维度【空间结构（地图与区域）】**
  （`builtin-prompt-templates.ts:523`），并同步了 6 处文案。
- **"地图节点随弧光增量生成"：不建议**。理由：
  1. 与纪律 #2「**弱引用靠命名一致**（弧写"空间：X"，名字对上即引用），不用外键」冲突；
  2. 与纪律 #3「弱引用**不做硬校验**」冲突；
  3. 会引入**第三个空间事实源**（世界观第4维 / 弧光的"空间：X" / 新地图节点），
     正是 `state-tracking-assessment.md` 警告的"两套事实打架"。
- → 弧光的"空间：X"与世界观第 4 节**靠同名引用**即可，不需要节点实体。

### 建议 4：篇幅约束写进 Prompt —— ✅ **唯一直接采纳项**（但要改口径）

- 不应再加一张表（弧光模板已有篇幅表，`:592`），而应补**数量推算**：
  由"总章数 ÷ 每阶段章数 ⇒ 期望阶段数"这一步。
- 角色模板同理：把写死的「中长篇 4-6 人」（`:443`）改成**按篇幅推算**。
- **零契约改动、零新字段、不碰任何指纹**（两个模板：`plot_structure` 无指纹；
  `character_dynamics` 需先确认是否参与指纹——见 §6 待办 1）。

### 建议 5：每个弧光生成后更新"当前状态" —— ⚠️ 属既有议题，不新立项

- 这是**状态追踪**范畴（`character_states` / `continuity projection` / S1 角色知识 / S3 时间锚点），
  已在 backlog 有归属，且已有成熟链路（定稿 → 抽事实 → 快照 → 注入）。
- **不应随弧光生成"顺手"做**：它是另一个坐标系（逐章推进），与"弧光是纯文本"张力大。
- → 并入 S1/S3 一起决策，不在本议题内单独立项。
