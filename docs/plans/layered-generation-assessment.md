## 2. ★ 实测到的两个精确根因（带行号）

### 根因 A：角色模板**写死了数量上限**（比"没有约束"更糟）

`src/services/builtin-prompt-templates.ts:443`：

```
围绕主角，根据小说篇幅（{{number_of_chapters}}章）设计合理数量的核心角色（短篇3-4人，中长篇4-6人）。
```

→ **"中长篇 4-6 人"是写死的常量**，与 800 章无关。这是"角色少"的直接原因，
也解释了为什么模型输出了接近上限的数量。

**这不是"缺约束"，是"约束本身是错的"** —— 分析把它归因为"没有篇幅约束"，方向对但没找到病灶。

### 根因 B：弧光模板**有单阶段篇幅表，但没有"按总章数推算数量"**

`src/services/builtin-prompt-templates.ts:592-599`（本次新增的篇幅经验）只回答
**"一个阶段该多大"**：

```
- 20–30 章：饱满，适合中段主副本 / 核心剧情
- 50 章以上：太长，读者会弃 —— 不建议任何单一阶段超过 50 章
→ 为每个阶段给出"预计用多少章"（如"约 20–30 章"）。
```

**缺的是**："总 800 章 ÷ 每阶段 25 章 ⇒ **应当输出约 30 个阶段**"这一步推算。

叠加两个诱导因素，模型自然收敛到少数几个顶层阶段：
1. 输出格式示例只给了 `## 阶段一` / `## 阶段二`（`builtin-prompt-templates.ts:603` 起），
   示例形态本身在暗示"两三个阶段"；
2. `systemRole` 强调"每个阶段都能回答我为什么接在前一个之后"（`:546`）——
   因果链天然是短的，进一步压低阶段数。

→ **结论**：分析说"AI 默认按叙事结构分弧"方向正确，但真正可修的是上面这两点
（**补数量推算 + 明确示例不是数量上限**），不是"没有篇幅约束"。

## 3. 五条建议逐条裁决

### 建议 1：角色拆「核心角色 / 弧光角色」+ 同表 `scope` 字段 —— ❌ 不能这样做

- **`scope` 字段与已定边界冲突**：`00-OVERVIEW.md §5` 纪律 #1 明确
  「弧/空间结构**保持纯文本，不建表、不加字段、不做结构化**」（作者定性）。
- **而且这个诉求已有既有通路**：本项目 **P1 已实施**（`5933a50`/`9504097`）——
  蓝图语义契约里模型**已经在标注** `newCharacterCandidates`，蓝图提交后会
  自动提示建卡，候选可编辑、可回溯来源章节。
  → **"弧光角色"天然就是"弧光对应的那些章纲里新增的角色"**，
    由蓝图→角色卡流水线按需产生，**不需要在架构阶段提前分层，也不需要新字段**。
- **采纳其意图，拒绝其手段**：目标（角色随故事展开而增长）成立；
  实现路径 = 强化既有 P1 通路（例如让候选提示带上"所属弧光"），而不是改数据模型。

### 建议 2：弧光拆三层、各自增量生成 —— ❌ 与「不拆步」直接冲突

- 作者已拍板：「**一步出整段 + Prompt 内分节**；拒绝拆成多个 DB 步骤」（`arc-granularity-and-enum.md §1`，
  `00-OVERVIEW.md §5` 纪律 #9）。拆步 = 管线 ×3 + 回归面大增。
- **分层诉求本身已被满足**：`arc-nesting-design.md §3.1` 已定
  「嵌套 = **Markdown 标题层级**（`##` 大弧 / `###` 小弧 / `-` 支线）」，**零额外技术成本**。
- → 采纳"要有层级"，拒绝"用三次生成实现层级"。

### 建议 3：地图拆「世界骨架 / 地图节点」 —— ⚠️ 一半已落地，一半撞边界

- **世界骨架：已落地**。本次（`796528f`）世界观模板已加**第 4 维度【空间结构（地图与区域）】**
  （`builtin-prompt-templates.ts:523`），并同步了 6 处文案。
- **"地图节点随弧光增量生成"：不建议**。理由：
  1. 与纪律 #2「**弱引用靠命名一致**（弧写"空间：X"，名字对上即引用），不用外键」冲突；
  2. 与纪律 #3「弱引用**不做硬校验**」冲突；
  3. 会引入**第三个空间事实源**（世界观第4维 / 弧光的"空间：X" / 新地图节点），
     正是 `state-tracking-assessment.md` 警告的"两套事实打架"。
- → 弧光的"空间：X"与世界观第 4 节**靠同名引用**即可，不需要节点实体。

### 建议 4：篇幅约束写进 Prompt —— ✅ **唯一直接采纳项**（但要改口径）

- 不应再加一张表（弧光模板已有篇幅表，`:592`），而应补**数量推算**：
  由"总章数 ÷ 每阶段章数 ⇒ 期望阶段数"这一步。
- 角色模板同理：把写死的「中长篇 4-6 人」（`:443`）改成**按篇幅推算**。
- **零契约改动、零新字段、不碰任何指纹**（两个模板：`plot_structure` 无指纹；
  `character_dynamics` 需先确认是否参与指纹——见 §6 待办 1）。

### 建议 5：每个弧光生成后更新"当前状态" —— ⚠️ 属既有议题，不新立项

- 这是**状态追踪**范畴（`character_states` / `continuity projection` / S1 角色知识 / S3 时间锚点），
  已在 backlog 有归属，且已有成熟链路（定稿 → 抽事实 → 快照 → 注入）。
- **不应随弧光生成"顺手"做**：它是另一个坐标系（逐章推进），与"弧光是纯文本"张力大。
- → 并入 S1/S3 一起决策，不在本议题内单独立项。

### 7.0 先修正一条我上一轮说绝对了的话（自我更正）

上一轮我写「分析说『没有篇幅约束』→ 机制说错了一半」。**这个措辞过重，应修正为**：

> **报告说对了"没有数量约束"，我补充了"存在一个错误的固定上限"。两者合起来才是完整解释。**

证据（模板级，非推测）：

| 层 | 报告说"没有约束" | 我的补充 | 合起来 |
|---|---|---|---|
| 角色 | 部分对 | 有约束但**写死**「中长篇 4-6 人」（`:443`） | 有约束=错的约束 |
| 弧光 | **完全对** | 有"单阶段多大"的表（`:592`），但**没有任何"总共多少个"** | **确实没有数量约束** |

→ **在弧光这一层，报告的判断是完全正确的**。我上一轮把两层的结论混在一起说，是我的问题。

### 7.1 为什么只出 3-4 个大弧、且没有子弧（模板级诊断）

逐条对照 `plot_structure` 模板（`builtin-prompt-templates.ts:543-620`）：

| 诱因 | 具体文本 | 后果 |
|---|---|---|
| ① 数量未与篇幅挂钩 | 篇幅表只说「20–30 章：饱满」「50 章以上：太长」，**从不说"因此应该输出 N 个"** | 800 章 ÷ 25 ≈ 32 个的**推论从未被要求做** |
| ② 输出示例暗示"少数几个" | 示例只示范 `## 阶段一` 与 `## 阶段二`，第二个后面直接 `…` | 模型把"两个"当成量级参考 |
| ③ 子弧是**条件式** | 「**若**某阶段预估超过 30 章，**应**在内部拆出 1–3 个 5–15 章的小阶段」 | 条件句模型可跳过；实测**全部跳过** |
| ④ systemRole 反向拉低数量 | 「让每个阶段都能回答"我为什么接在前一个之后"，**而不是罗列平行区间**」 | 因果链天然短 → 体系天然**收敛**到少数几个阶段 |
| ⑤ 分类学缺失 | 「先判断每个阶段的**类型**（A/B/C）」只有 3 类 | 容易被读成"三个阶段" |

→ **结论**：这不是"模型不听话"，是**模板在同时做两件矛盾的事** —— 篇幅表要求"单段别太长"，
而示例与 systemRole 要求"少而连贯"。模型选择了后者。

### 7.2 指导意见（7 条，按落地优先级）

#### 指导 1 ★ 预算先行：把"数量"变成**推导结果**，而不是模型的主观判断

每个生成步骤**开头强制一行推算**，再写内容：

```
【篇幅预算】全书 800 章；按 25 章/中弧 ⇒ 约 32 个中弧；按 100 章/大弧 ⇒ 约 8 个大弧。
本步必须输出 8 个大弧，其内含中弧总数约 32 个。
```

这条**单条就能消灭"4 个弧光"**。它把「合理数量」这种主观措辞换成**算术**。

#### 指导 2 ★ 嵌套用「数量映射」表达（作者已定：大弧套中弧）

```
大弧数   ≈ 总章数 ÷ 100        （800 章 → 8 个大弧）
中弧数   = 大弧章数 ÷ 25
小弧数   = 中弧章数 ÷ 8（每个中弧 2–4 个）
```
并要求**逐个大弧显式写出「本大弧含 N 个中弧」**——这既是自查，也让层级**机械可验证**。

#### 指导 3 把"条件式"改成"必然式"

- 旧：「**若**某阶段超过 30 章，应拆出小阶段」→ 实测被跳过
- 新：「**每个大弧必须至少含 2 个中弧**，否则视为不合格输出」

#### 指导 4 示例必须**明示"不代表数量上限"**

输出格式示例写成 `## 大弧 1 … ## 大弧 2 … ## 大弧 N（共 N 个）`，并在示例后加一句：
「以上仅示范书写格式，**N 由第 1 步的篇幅预算决定，不是 2**」。

#### 指导 5 ★★ 角色先解决"是不是角色"，再解决"有几个角色"

**实测证据**（只读作者项目 `characters_arch`，2181 字 / 6 条）：
其中「**副本规则化身**」「**主神意志**」被当作角色收进去了 —— 而它们是**机制与意志**，
不是人。这正是作者说的"甚至还包含了副本的角色"。

→ **这是分类问题，不是数量问题**。模板应加硬约束：

```
只收录：有名有姓（或固定代号）、有独立动机与选择、可对话或对抗的**人格化个体**。
不要收录：规则、机制、环境化身、空间、组织、势力 —— 这些归**世界观**（写稿阶段它们
不进角色卡，也不会被当成"出场角色"）。
```

★ 比"拆核心/弧光两层"更根本：**先保证收进来的是人**，再谈数量。

#### 指导 6 数量与篇幅挂钩，且**上限随篇幅走**

`builtin-prompt-templates.ts:443` 的「短篇 3-4 人 / 中长篇 4-6 人」→ 改为公式：

```
核心角色数量 ≈ 总章数 ÷ 100，下限 3，上限 12   （800 章 → 约 8 个）
```

**弧光角色不在这里生成** —— 由对应章纲的 `newCharacterCandidates`（P1 已实现
`5933a50`/`9504097`）按需产出，**天然绑定所属弧光**，无需新字段（见 §3 建议 1）。

#### 指导 7 ★ 单向引用，禁止下游回头改上游

依赖链上每一层只能**引用**上游已固化的**名字**，不得新增或改写上游事实：

| 层 | 只允许引用 | 禁止 |
|---|---|---|
| 弧光 | 世界观第 4 维的**空间名**、角色的**姓名** | 新建地图节点、新造角色 |
| 情节大纲 | 弧光的**弧名**、角色的**姓名** | 重新定义弧光边界、增删角色 |
| 蓝图 | 大纲的**章号段** | 改大纲 |

违反时**只报告不自动修**（沿用 `consistency-preflight` 的「**证据非禁令**」纪律）。

**通用实现手段**：把"上游已定事实"以**清单形式**注入下游（而不是让模型自己去上游长文里找）。
这与分析的建议 1 同向，但适用范围更广。

### 7.3 关于"地图区域"的明确建议：**不要再建"地图节点"实体**
