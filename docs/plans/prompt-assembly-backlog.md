## 0. 背景速览：这批任务从哪来

作者在实际使用中撞到一连串问题，逐层追下来形成本台账：

1. **单次请求包体过大 → 工作流失败**（最痛）。
   作者原话：「我用 deepseek 写都失败了，到底发了什么东西能达到租约请求上限 65536 Tokens，这么离谱么」。
   → 直接引出 **P1（Prompt 逐字去重）**，见 `docs/design/prompt/p1-literal-dedup.md`。
   **P1 已完成**（Phase 0/1/2 落地），本台账不再重复 P1 细节。
2. 追查组装逻辑时发现**两类更上游的问题**：
   - **蓝图提到但 roster 里没有的角色**不会进 Prompt（作者在面板看到蓝图设了角色，以为是 bug）。
   - **参考作品（referenceWorks）没有被当作「参考作品」专门组织**（疑似设计遗漏，不是 bug）。
3. 由此衍生出 **P2 角色卡 AI 生成增强**、**P5 地图/区域架构**等特性诉求。
4. 另有两项**去重/配置整合**类任务（P3 / P4），源自「P1 只做逐字重复，语义级重复另立项」的拆分决定。

> ★ **新增台账（AC 系列）**：[`architecture-consistency-design.md`](../design/architecture/architecture-consistency-design.md)
> （作者问「可以做故事架构五层一致性校验么」的评估）。

> **硬性要求**（backlog 原有）：AI 只提建议，**作者逐条确认才落盘**；不得削弱/删除作者要求。

### 缘起

同上，属「语义级」议题的 A 类：**配置层面的整合**。
现状是多个配置项（如 `globalGuidance`、`writingStyle`、`coreOutline` 等）之间存在**语义重叠**，
但各写各的，作者需要手动维护一致性。

### 目标

让 AI 提出**配置整合建议**（例如「这两条全局要求其实是一件事，建议合并为一条」），
作者**人工确认**后，**替换**成整合后的配置。

### 硬性要求（作者明确）

流程必须是 **AI 建议 → 人工确认 → 替换配置** 三段式。
**不得**让 AI 直接改配置 —— 作者必须逐条确认。

### 风险与边界

- 配置是**权威约束**（`novel_config` 是「作者确认的小说配置（权威约束）」，见内置模板注释）。
  替换必须**可回滚**、**可对比**（建议做 diff 预览）。
- 不得吞掉作者原意；整合只能**合并表述**，不能**削弱或删除**要求。

### W1（系统级）内置模板升级：检测 / 提示被遮蔽的全局覆盖 —— ✅ 已实施（2026-10-11）

**问题（不是单机偶发，是升级路径缺陷）**
`promptCatalog.resolve` 的优先级是 `project > global > builtin`。而全局模板目录
（`VELA_HOME/prompts/`，本机为 `~/.ai-novel-writer-dev/generations/<uuid>/prompts/`）
里存的是**用户首次保存时的内置模板副本**。于是：

> **任何从旧版升级的用户，都拿不到新版内置模板的任何改进** —— 内置模板更新了，
> 全局副本仍是旧文本，且优先级更高，静默胜出。

本机实测（2026-10-11）：20 个从 `~/.vela` 迁移来的全局模板遮蔽了内置版本，
导致世界观永远只有 3 维、角色数量写死"中长篇 4-6 人"、模型把判据抄成 JSON 字段。
**已用两个不同模型复现同一结果**，是这个问题最硬的旁证。

**落地实现（按原建议的方案 1 + 2）**

| 位置 | 内容 |
|---|---|
| `PromptTemplate.builtinRevision?: string` | 覆盖文件里记录**保存当时的内置模板摘要** |
| `src/services/prompt-builtin-revision.ts` | `promptBuiltinRevision()`：稳定摘要，只覆盖用户**不可编辑**的部分（name / description / content / systemRole / taskGuidance / variables / requiredContextVariables）。**不含 `key` / `writingLanguage` / `systemSuffix`** —— 前两者是身份；后者渲染时始终取内置版本、覆盖改了也不生效，它的变化无需提醒 |

### O1 情节大纲：为什么是 10 章，能不能按弧生成

**为什么是 10（原设计意图，按代码反推）**
`PLANNING_ACTION_CHAPTER_LIMIT = 10`（`plot-outline-contract.ts:8`）是**双端硬契约**：
服务端 `assertPlanningActionRange` 会直接拒绝 >10 的范围。它是一条
**分批 + 可断点续写**的流水线设计：

- 每章大纲的目标字数是 `targetUnits`（默认 600，上限 1000）；
  10 章 ≈ 6000 字，正好落在一个可在单次输出预算内完成、且作者能中途检查的粒度。
- 批次之间有**显式水位线**：`synopsis_covered_to` + `planningContinuation.remainingRange`；
  「继续」按钮就是顺着这个水位线开下一批。
- 它是**契约**而不只是默认值：把 845 章一次性交给模型，输出必然被截断，
  而截断后的 JSON/Markdown 无法可靠续接。

**续写的一致性与连续性会不会受影响** —— 机制上是设计好的，风险点明确：
- 每一批都会重新注入**完整弧光结构**（`resolveStageStructureGuide`），
  所以"故事该讲什么"不会漂。
- 续写会带上**已完成大纲的尾部**作为种子，所以"上一批讲到哪"不会断。
- **真正的风险**不是批次大小，而是**弧光本身的质量**：弧光若只给 5 个大弧
  （现状），大纲就只能拿到"宏观分期"，每批 10 章之间缺少"本弧还剩什么没讲"的约束。

**结论**：
1. **不建议直接把上限改大** —— 那是把输出截断风险从"小概率"变成"必然"，属负收益。
2. **"按弧生成"值得做，但形态应是"按弧切片"而不是"按弧一次生成"**：
   把上限从"固定 10 章"改为"**当前弧内的一段，且不超过 10 章**"，
   并在每批注入「本弧目标 / 本弧已完成 / 本弧剩余」的进度上下文。
   这样既保留分批的安全边界，又让批次与叙事单元对齐。
3. **前置条件**：弧光必须先能稳定产出**三层结构**（G1 已实施，待作者实机验证），
   否则"按弧切片"切不出可用的边界。

**成本**：方案 2 需要改 `plot-outline-contract` 的范围校验（允许"弧内区间"）、
对话框 UI（选择"按弧"而非手填章号）、以及每批的弧进度注入。**属独立一轮**，
建议排在作者验证完三层弧光之后。

**2026-10-18 更新（作者定方向，核实后方案改了形态）**

作者原话：「按弧分配、按章生成 + 弧位块按章定位」。核实代码后，三处前提被修正：

1. **现行已是一次一章**，不是 10 章一批一次（`plotOutlineRequestContract`「本次只写第 N 章」；
   `validPlotOutlineEntry` 从契约上禁多章）。所以**不需要**改范围校验，上面"成本"里那两项（契约 + UI）**可以省掉**。
2. **连贯性没坏**：每章都带 `confirmedPrefix`（本批起点之前全部条目 + 本批已接受）。
   真正的缺口是**规划性**——`withProjectedArcGuide(..., from, to, ...)` **传批范围不传章号**，
   导致第 1 章与第 10 章看到同一份弧位，逐章贪心。
3. **形态从"按弧切片"进一步精确为"按弧分配 + 按章生成 + 事件进度线"**：
   进度上下文不再是一句散文（「本弧剩余 3 条」），而是**代码算出的水位区间**
   `[floor(k·M/N), ceil(k·M/N)]`，模型在既有 `覆盖：` 行后写 `#E<n>` 声明水位。
   四条不变量 EV-1..4（终态完备 / 不超前 / 不拖后 / 不回退）。

⇒ 全部机制见 [`o1-arc-event-progress-design.md`](../design/architecture/o1-arc-event-progress-design.md)。
**仍然不改批次大小、不改 cursor、不新增请求**，因此**不再需要"独立一轮"**，可拆成三步增量落地。

### 目标

审稿 prompt 中世界观只保留一份（预计 user 32,442 → ~26,200）。

### 需先定的问题（设计稿前置）

| # | 问题 | 备注 |

| 1 | 保留哪一份 | 材料块是**准入单元**（`materialDecisions` 的 `promptHash` 依赖它）⇒ 倾向**保留材料块、模板侧留空**；但模板 `consistency_check` 的 `requiredContextVariables` 若含 `world_building`，留空会触发**兜底注入**（红线 16）到正文末尾 ⇒ 两者须一起处理 |

## P8（高）· 番茄向正文的**质量闸门**：字数 / 番茄味 / AI 味（2026-10-17 实机发现）

### 缘起

作者 2026-10-17 用首章 trace（`20261017-041520-240-正文-ch1-f0b4235e.md`）实测，指出三个问题：**字数达不到标准、AI 味不少、番茄味不太足**。要求先挑一个小口子开刀，通用型架构（四层契约 / 平台画像层）留作最终目标。

### 根因（一句话）

**这份 prompt 里所有「可判定」的约束都没有判定权；唯一有判定权的是字数下限，而那个下限接错了线。**

| 抱怨 | 根因 | 锚点 |
|---|---|---|
| 字数不够 | `shouldAutoContinue` 在 `finishReason='stop'` 时比**退回线** `minimum`(1750) 而非**合格线** `aimLow`(2125)；实出判定值 1767 ≥ 1750 ⇒ 不续写 ⇒ 静默落库。全链路零处引用 2125 | `generate-draft.command.ts:1545-1546`；`draft-units.ts:10-11` |
| AI 味 | 实际生效的去 AI 腔禁令仅 4 条**举例式黑名单**（点名"这一切才刚刚开始"），换措辞即通过 | trace:935 冒号归纳+对称复述；trace:985 定性解释+三连排比；trace:830-834 |
| 番茄味 | 番茄 KPI 全写在 `global_guidance`（距生成点约 100 行、无校验器），且与自称"最高优先级"的【真人叙事】互斥；唯一承载调性的【文风要求】槽因 `writing_style=''` 被整段裁掉 | trace:738-780；trace:774-779；`project_core.writing_style` |

### 一条必须纠正的旧结论

上一轮交接称 `systemSuffix` 由 `BasePromptBuilder.build()` 追加进 **system**。**错**：`prompt-builder.ts:29-57` 的 `build()` 返回的是 user 消息体，systemSuffix 追加在其末尾；第 2 次调用的 system 只有 1129 字符（trace:488-513）。⇒ **所有硬规则都在 user 体里竞争 recency**，没有谁拥有 system 级权重。这也解释了为什么 `:1066`「不要超过目标」能压过 `:837`「请写到约 2125–2500」。

### 目标

三项指标机械可查地达标：字数落 `[2125, 2500]`；对话占比 `[25%, 40%]`；AI 味 L1/L2 扫描 0 命中。

### 设计稿 + 取证

- 设计稿：`docs/design/prompt/p8-fanqie-flavor-draft-quality-design.md`（含三处补丁的完整可粘贴文本、会撞的测试清单、§9 实施记录、§10 复验 #1）
- 取证：`docs/research/2026-10-17-fanqie-draft-quality-evidence.md`（5 份并行报告 + 独立校验；6 条可载荷结论 5 VERIFIED / 1 数值 PARTIAL，无一条被推翻）

### 落点（已实施）

## P9（高）· **平台文风层**：从「写死在 prompt 里」到「可选择的文风资料库」（2026-10-17）

### 缘起

作者明确：后续希望做出**平台文风资料库**，或者直接**按平台选择加载文风**。本轮 P8 的实机复验证明"写在 prompt 里的风格规则"只能定方向、定不了达标（对话占比仅 6.40% → 9.34%），因此需要把平台口味从 prompt 文本提升为一等配置。

### 结论（一句话）

**基础设施已经存在，缺的不是架构，是一个"平台画像"的装配点。** 写作 Skill 机制（分阶段 / 绑定 / 冻结 / 打包 / 每轮注入）天生就是装平台文风的容器；缺的是 `.vela-pack` 的 `platform` 字段与小说配置的"平台"下拉。

### 关键依据

| 事实 | 位置 |
|---|---|
| 写作 Skill 分四阶段（planning/drafting/review/refinement），来源 builtin/user/project | `src/shared/writing-skills.ts` |
| Skill 注入到**每轮**请求第一条 user 消息头部，自带「只能补充创作方法，作者事实优先」降级声明 | `base-command.ts:71-118` `injectWritingSkillIntoTask` / `injectWritingSkillIntoSession` |
| 工作流启动时冻结 Skill 快照（一轮不漂移） | `workflow-store.ts:605-607` |
| 已有按阶段绑定的 UI | `src/components/settings/SkillSettings.tsx` |
| 已有打包容器（prompts + skills），但 manifest 无 platform 字段 | `src/shared/user-settings-pack.ts` |
| 覆盖优先级 builtin < global < project | `src/services/prompt-catalog.ts` |

### 为什么不能沿用现有三条路

| 路 | 为什么不走 |
|---|---|
| 项目 `taskGuidance` | **续写轮不携带**（P8 的 D6）：首稿失败后全章由续写重写时规则全部丢失——本轮正是如此 |
| `writing_style` 变量 | 被内置【文风适用边界】`:1055`「无需逐条强行兑现」豁免 |
| 内置模板 `systemSuffix` | 全局唯一一份，不含平台分支；起点/文学向项目也会被番茄规则约束 |

**剩下唯一"每轮都注入且不被豁免"的通道就是写作 Skill。**

### 落点（S1–S5，按成本排序）

1. **S1（零代码，建议先做）**：把番茄口径压成 1–2KB 的 `stage: drafting` Skill，手工绑定，跑一章看对话占比能否从 9.34% 抬到 15%+。这一步同时验证"平台文风用 Skill 承载"这个核心假设。
2. **S2** 修 P8 的 D6：续写轮补上模板正文 / taskGuidance / systemSuffix 的规则摘要。
3. **S3** 平台 KPI 后置校验：生成后跑纯函数 `lintDraftAgainstPlatformProfile`，检查对话占比 / 段长分布 / 末句类型 / 比喻数，**只提示不阻断**。
4. **S4** `.vela-pack` manifest 加 `platform` 字段（fanqie/qidian/literary/general，缺省 general，**绝不静默回落 fanqie**）+ 小说配置加"平台"下拉。

## P11（高）· **计划的有效期与事实登记**：蓝图吃的是「计划」却被当作「事实」（2026-10-18 实机发现）

## W5 · 世界状态的只读可视化（2026-10-22 作者提出 · 待议）

> **作者原话**：「以后可能需要世界状态的可视化管理。」
> **定位**：**只读视图**。不新建事实源、不新增写回路径、不动 schema（W3 的差分落库是唯一的写入口）。

### 缘起（为什么现有界面不够）

作者现在能看到的只有**当前值**：角色管理页显示 `cs_location` / `cs_condition` / `cs_key_items`… 的最后一次写入。它不显示这个值**怎么演变来的** —— 第 3 章末是 6 枚药，第 5 章剩 2 枚，中间花在哪、哪一章算错的，界面上无处对照。

于是「一致性」只能靠人眼逐章比对正文，而比对用的基准本身不可见。W3 做完后库里会有「每章的差分」，但**差分不等于视图**：不呈现，作者仍然只能靠翻章节。

### 现状：数据已经在库里，缺的是读

| 数据 | 位置 | 粒度 | 能否画时间轴 |
|---|---|---|---|
| 角色状态现值 | `characters.cs_*`（8 字段）+ `cs_provenance` + 更新章号 | 当前值 | ❌ 只有最后一格 |
| 日序 | `summary_snapshots.story_day_offset` / `story_day_label`（M10） | 每快照 | ✅ |
| 连续性事实 | `summary_snapshots.continuity_facts`（JSON：`category` / `entities` / `characterRefs`） | 每快照 | ✅（需按实体聚合） |
| 角色身份决定 | `character_cast_decisions`（`register` / `revoke` 追加日志） | 追加型 | ✅ |
| 状态差分 | **W3 产出**（尚未落地） | 每章 | ✅ ← W5 的前置 |

### 目标（三档，按成本递增）

| 档 | 内容 | 依赖 |
|---|---|---|
| V1（最小） | **单角色时间轴**：选中一个角色，按章列出「该章结束时它的状态 + 支撑原文片段」 | W3 差分落库；日序可读 |
| V2 | **章节断面**：选一章，列出本章所有角色的状态（谁在哪、伤到什么程度、持有什么） | V1 + 实体对齐（判据 CX 的登记表） |
| V3 | **漂移高亮**：某字段在相邻两章之间发生「无正文支撑的跳变」时标出来 | V2 + 判据 CJ 的待裁决队列 |

### 明确不做

- ❌ **不在这里编辑状态**。要改走角色管理页（那里已有 `cs_provenance` 区分 author / derived）。视图一旦可编辑，就成了第五个事实源。
- ❌ **不做全局世界地图 / 资源图**。属 P5 评估范围，且已判定动态地图节点会成第三个空间事实源。
- ❌ **不用折线图代替待裁决**。冲突必须能被逐条处置，画成曲线不算完成。

### 验收（将来真做时）

1. 任取一章，视图给出的每个状态值都能点回**具体原文片段**（quote 能唯一定位）；
2. 状态来源（author 手设 / derived 派生 / 未定）**在界面上可区分** —— 这是 §6.4 的可见化；
3. **没有任何写路径**：视图层不出现 UPDATE / INSERT。
