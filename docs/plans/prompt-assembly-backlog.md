1. **生成命令**：需要一个「从蓝图角色生成待确认角色卡」的命令

4. **归属语义**：作者明确要求 —— **副本/主线**的归属通过「notes / arc」**文本承载**，

- 蓝图里有、roster 里没有的角色，能在不离开当前流程的前提下走完「生成 → 审核 → 落卡」。

- 导入类命令有**卡上限**（如 `import-novel.command.ts:208` 的 8 张上限），新命令要明确自己的上限策略。

### W1（系统级）内置模板升级：检测 / 提示被遮蔽的全局覆盖 —— ✅ 已实施（2026-10-11）

**问题（不是单机偶发，是升级路径缺陷）**
`promptCatalog.resolve` 的优先级是 `project > global > builtin`。而全局模板目录
（`VELA_HOME/prompts/`，本机为 `~/.ai-novel-writer-dev/generations/<uuid>/prompts/`）
里存的是**用户首次保存时的内置模板副本**。于是：

> **任何从旧版升级的用户，都拿不到新版内置模板的任何改进** —— 内置模板更新了，
> 全局副本仍是旧文本，且优先级更高，静默胜出。

本机实测（2026-10-11）：20 个从 `~/.vela` 迁移来的全局模板遮蔽了内置版本，
导致世界观永远只有 3 维、角色数量写死"中长篇 4-6 人"、模型把判据抄成 JSON 字段。
**已用两个不同模型复现同一结果**，是这个问题最硬的旁证。

**落地实现（按原建议的方案 1 + 2）**

| 位置 | 内容 |
|---|---|
| `PromptTemplate.builtinRevision?: string` | 覆盖文件里记录**保存当时的内置模板摘要** |
| `src/services/prompt-builtin-revision.ts` | `promptBuiltinRevision()`：稳定摘要，只覆盖用户**不可编辑**的部分（name / description / content / systemRole / taskGuidance / variables / requiredContextVariables）。**不含 `key` / `writingLanguage` / `systemSuffix`** —— 前两者是身份；后者渲染时始终取内置版本、覆盖改了也不生效，它的变化无需提醒 |

| `PromptSettings.TemplateItem` | 加载时比对；不一致（含**更早版本写入、根本没有戳**的存量覆盖）→ 头部琥珀色「内置已更新」徽标 + 展开区说明，并把「恢复默认」指为采用新版的途径 |

### O1 情节大纲：为什么是 10 章，能不能按弧生成

**为什么是 10（原设计意图，按代码反推）**
`PLANNING_ACTION_CHAPTER_LIMIT = 10`（`plot-outline-contract.ts:8`）是**双端硬契约**：
服务端 `assertPlanningActionRange` 会直接拒绝 >10 的范围。它是一条
**分批 + 可断点续写**的流水线设计：

- 每章大纲的目标字数是 `targetUnits`（默认 600，上限 1000）；
  10 章 ≈ 6000 字，正好落在一个可在单次输出预算内完成、且作者能中途检查的粒度。
- 批次之间有**显式水位线**：`synopsis_covered_to` + `planningContinuation.remainingRange`；
  「继续」按钮就是顺着这个水位线开下一批。
- 它是**契约**而不只是默认值：把 845 章一次性交给模型，输出必然被截断，
  而截断后的 JSON/Markdown 无法可靠续接。

**续写的一致性与连续性会不会受影响** —— 机制上是设计好的，风险点明确：
- 每一批都会重新注入**完整弧光结构**（`resolveStageStructureGuide`），
  所以"故事该讲什么"不会漂。
- 续写会带上**已完成大纲的尾部**作为种子，所以"上一批讲到哪"不会断。
- **真正的风险**不是批次大小，而是**弧光本身的质量**：弧光若只给 5 个大弧
  （现状），大纲就只能拿到"宏观分期"，每批 10 章之间缺少"本弧还剩什么没讲"的约束。

**结论**：
1. **不建议直接把上限改大** —— 那是把输出截断风险从"小概率"变成"必然"，属负收益。
2. **"按弧生成"值得做，但形态应是"按弧切片"而不是"按弧一次生成"**：
   把上限从"固定 10 章"改为"**当前弧内的一段，且不超过 10 章**"，
   并在每批注入「本弧目标 / 本弧已完成 / 本弧剩余」的进度上下文。
   这样既保留分批的安全边界，又让批次与叙事单元对齐。
3. **前置条件**：弧光必须先能稳定产出**三层结构**（G1 已实施，待作者实机验证），
   否则"按弧切片"切不出可用的边界。

**成本**：方案 2 需要改 `plot-outline-contract` 的范围校验（允许"弧内区间"）、
对话框 UI（选择"按弧"而非手填章号）、以及每批的弧进度注入。**属独立一轮**，
建议排在作者验证完三层弧光之后。
