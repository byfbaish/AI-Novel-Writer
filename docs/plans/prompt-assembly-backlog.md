## P1（高）· 蓝图角色 ↔ 角色卡 roster 同步

> 📄 **详细设计稿**：[`p1-blueprint-roster-sync.md`](./p1-blueprint-roster-sync.md)（2026-10-10，设计待审）
> 关键发现：蓝图→角色的 durability 骨架**已存在**（`blueprint_character_sync_operations` +
> `newCharacterCandidates` 契约 + `character-proposal:stage` 通道），缺的是**触发时机与 UI 入口**。

### 缘起

作者提问（原话）：

> 「你说蓝图提到但 roster 里没有的角色不会进，但是面板看到蓝图设置有角色的啊，是 bug 么？」

追查结论：**不是 bug，是设计边界，但体验上确实是缺口。**
蓝图（chapter blueprint）里可以写明本章登场的 `characters`，但**只有已经在角色卡 roster 里的角色**
才会被组装进 Prompt。蓝图里凭空出现、roster 里没有的名字，**生成时会被静默忽略**。

代码现状（`generate-draft.command.ts` 约 `:769`）：

```
'如需其设定参与生成，请先为该角色创建角色卡。'
```

即：系统**知道**这个角色缺卡，但也只给了一句提示，没有提供「一键补卡」的路径。

### 关键既有资产（**务必复用，不要另造轮子**）

- **AI 生成角色图谱**：`architecture.command.ts` 的 `character_dynamics` 步骤
  （`:1129` 定义 operation `character-architecture`，`:1139` 解析模板 `character_dynamics`，`:1158` 执行）。
- **角色卡提议批量流（character-proposal）**：这是**已经跑通的全链路**，包含
  生成 → 暂存 → 人工选择 → 审批落库：
  - 分享契约：`shared/character-proposal.ts`（`CharacterProposalBatch` 等）
  - 解析/校验：`shared/character-proposal-parser.ts`
  - 预览/默认选择：`services/workflows/character-proposal-preview.ts`、
    `services/character-proposal-choices.ts`
  - IPC 通道：`character-proposal:stage`（暂存）、`character-proposal:approve`（审批）
    （`services/workflows/blueprint-character-sync.ts:21`、`architecture.command.ts:1374/:1395`）
- **蓝图→角色同步入口**：`services/workflows/blueprint-character-sync.ts`（**已存在**，需确认当前触发点）。

### 目标

让「蓝图里设定了角色但 roster 没有」这种情况有**顺畅的落地路径**：
蓝图里的新角色可以走 `character-proposal` 流 → 人工确认 → 落成角色卡 → 下次生成即参与组装。

### 4 个缺口（作者原话归纳，逐条落实）

1. **生成命令**：需要一个「从蓝图角色生成待确认角色卡」的命令
   （可复用 `character_dynamics` 或新写一个更聚焦的 delta 生成器，参照 `import-novel.command.ts`
   的「受限补卡 delta 生成器」`:249` 的做法与限制）。
2. **审核列表**：生成出的角色卡要进入可审核的列表（复用 `character-proposal` 的预览/选择 UI）。
3. **UI 入口**：在**蓝图/角色卡管理界面**给出入口（这是作者最直接的需求 —— 见 P2）。
4. **归属语义**：作者明确要求 —— **副本/主线**的归属通过「notes / arc」**文本承载**，
   不要为归属新增结构字段。（作者原话：「副本和区域地图其实是一回事……这个可以作为评估项，放在后续」。）

### 验收

- 蓝图里有、roster 里没有的角色，能在不离开当前流程的前提下走完「生成 → 审核 → 落卡」。
- 落卡后，该角色在后续章节生成中**确实进入 Prompt**（可用逐字计数断言验证，参照 P1 的测试手法）。
- 不破坏 `CHARACTER_AUTHOR_ROSTER_NOT_READY` 既有语义（作者 roster 未就绪时的既有报错路径要保持）。

### 风险与边界

- **ADR 0020** 硬约束：只能改措辞/组织，**绝不删除作者事实或红线**。
- 角色卡的 `characterId` 是**冻结名单的精确 ID**（见 `finalize-chapter.command.ts:290` 的合同），
  补卡时不得凭名字推断身份、不得改名。
- 导入类命令有**卡上限**（如 `import-novel.command.ts:208` 的 8 张上限），新命令要明确自己的上限策略。

- 在**设置里提供开关**，由作者显式开启。
- 理由：语义去重有**误删作者关键信息**的风险（AI 判定「这段和上文重复」可能删错），
  必须由作者掌握开关权。

### 风险与边界

- **ADR 0020**：不得因去重删除作者事实/红线。去重前应有**保守策略**
  （例如：只提示、不自动删；或只对「非作者原文」段做去重）。
- 与 P1 共用「逐字计数」测试工具，但**不能**用逐字断言验收语义去重（语义重复是逐字不同的）。
- 建议先做**只读检测**（报告「疑似语义重复段」）再考虑自动处理。

## P4（中）· 任务 #7 · A 类「配置整合」（AI 建议 → 人工确认 → 替换）

> 📄 **详细设计稿**：[`p4-prompt-config-merge.md`](./p4-prompt-config-merge.md)（2026-10-10 v1）
> **作者指定的靶子**：用户级 Prompt 设定（设置 → 提示词模板），因为**全局与项目两级最容易重复**；
> 作者认为大纲蓝图等"会重复的比较少"（判断正确，但结构上它们同样可两级编辑，设计上不排除）。
> ★ **必须先读设计稿 §0.0（本项最关键的一条）**：**全局与项目不是叠加，是覆盖**——
> `prompt-catalog.ts:239-251` 的 `peek`/`resolve` 是**短路返回**（项目命中即返回，全局被整个丢弃），
> 且有既有测试固化（`prompt-catalog.test.ts:95-103`）。
> → 作者设想的「全局 AAAAA + 项目 AAAB → 实际效果 AAAAAB」**不成立**；
>   **实际效果是 `B`，全局那份一个字都不进 prompt。**
> → 这个纠正决定整个方案形态，**P4 开工前必须先确认**。
> **方案主体**：Phase 0「当前实际生效」展示（零 AI）→ Phase 1 重复检测（零 AI）
> → Phase 2 AI 优化按钮（diff + 建议存哪 + 确认落盘）→ Phase 3 显著位置推荐。
> **硬性要求**（backlog 原有）：AI 只提建议，**作者逐条确认才落盘**；不得削弱/删除作者要求。

### 缘起

同上，属「语义级」议题的 A 类：**配置层面的整合**。
现状是多个配置项（如 `globalGuidance`、`writingStyle`、`coreOutline` 等）之间存在**语义重叠**，
但各写各的，作者需要手动维护一致性。

### 目标

让 AI 提出**配置整合建议**（例如「这两条全局要求其实是一件事，建议合并为一条」），
作者**人工确认**后，**替换**成整合后的配置。

### 硬性要求（作者明确）

流程必须是 **AI 建议 → 人工确认 → 替换配置** 三段式。
**不得**让 AI 直接改配置 —— 作者必须逐条确认。

### 风险与边界

- 配置是**权威约束**（`novel_config` 是「作者确认的小说配置（权威约束）」，见内置模板注释）。
  替换必须**可回滚**、**可对比**（建议做 diff 预览）。
- 不得吞掉作者原意；整合只能**合并表述**，不能**削弱或删除**要求。
