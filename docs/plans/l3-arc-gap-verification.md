## 1. 批评一核实：剧情树**是只读投影**，不是设计空间

### 1.1 证据：面板自己声明了

作者截图 #1 里，面板正下方写着：

> 「AI 只读归纳现有大纲、蓝图、定稿与叙事计划；**剧情树不会反写项目事实**。」

**代码完全吻合**，`src/components/editor/NarrativeThreadEditor.tsx`：

```ts
// :123 源头必须是已有实体
'请先添加章节蓝图、定稿或叙事线索，再生成剧情树。'

// :134 结果只是一个"快照"
'剧情树快照保存失败' / '剧情树快照清除失败'

// :140 源变则快照作废
'剧情资料在生成期间已更新，本次结果未保存，请重新生成。'
```

**→ 数据流是单向的：`blueprints` + `drafts` + `threads` →（AI 归纳）→ 树快照。**
**树本身不是可编辑的规划结构，它是"把已有内容换个视角展示"。**

### 1.2 作者的判断，用代码语言转述

作者原话：

> 「这个树是根据已有章节蓝图生成的，也就是说通过修改章节蓝图我确实可以在前10章完成一个副本剧情的闭环，
> 但是这种剧情走向就需要作者严格精细的把控，没有可以方便管理规划的空间，不太符合工程化工作流的创作思路。」

**精确对应**：

| 作者说 | 代码事实 |
|---|---|
| "树是根据已有蓝图生成的" | `:123` 源必须含 `blueprints` |
| "通过修改蓝图我确实可以闭环" | `blueprints.chapter_number` 是主键，逐章可改 |
| "需要作者严格精细的把控" | **没有上层结构**，闭环只能靠逐章手工对齐 |
| "没有可以方便管理规划的空间" | 树**不可编辑**（只读快照，`清除/刷新`两个操作而已） |
| "不符合工程化工作流" | 缺**声明式**的上层结构，只剩**命令式**的逐章微调 |

**→ 结论：作者要的是"声明式的弧"（我声明 ch1-12 是一个副本、目标是什么），
现状给的是"命令式的逐章"（你一章一章改蓝图去凑）。这是两种范式，不是同一件事的粗细之分。**

## 2. 批评二核实：叙事线索**只能表达伏笔，无法表达剧情**

### 2.1 证据：字段一共只有 5 个

`src/shared/narrative-thread.ts:18-24`：

```ts
export interface NarrativeThreadPlanInput {
  title: string
  type: string
  targetStartChapter: number   // "计划埋设 / 开始章"
  targetEndChapter: number     // "预计回收 / 结束章"
  authorIntent: string
}
```

**这是全部字段。** 对照 `seven-layer-skeleton-assessment.md` 里分析的 L3 定义：

| 分析的 L3 字段 | `narrative_thread_plans` | 结果 |
|---|---|---|
| `chapters: 1-12` | ✅ `targetStartChapter` / `targetEndChapter` | **有** |
| `foreshadowing_planted` / `paid` | ✅ event: `planted` / `progressing` / `resolved` | **有** |
| `space: 副本世界/无声公寓` | ❌ | **无** |
| `goal` | ❌（`authorIntent` 是"为何埋这伏笔"，非"本弧要达成什么"） | **无** |
| `conflict` | ❌ | **无** |
| `climax: ch10-12` | ❌ | **无** |
| `active_characters` | ❌ | **无** |
| `exit_characters` | ❌ | **无** |
| `rules` | ❌ | **无** |

### 2.2 作者的判断，用代码语言转述

作者原话：

> 「至于伏笔和叙事线索的设定，我更倾向于这只是用来设计伏笔的，并不能用来设计完整的剧情。」

**→ 代码支持：8 个 L3 必需字段里，它只有 2 个，且这 2 个恰好是"伏笔"专属的。**

作者截图 #2 里那条：

> 「沈晚语音中的电流声与信号中断 · 情感伏笔/异常信号线索 · **埋设 1 · 预计回收 60**」

**这条完美暴露了局限**：一个跨 **59 章**的伏笔，结构上只记了"第 1 章埋、第 60 章收"。
**中间 58 章它完全无感知** —— 不知道这期间角色在哪、故事在哪个副本、有没有高潮。

**→ 结论：它是"伏笔台账"（记账用），不是"剧情骨架"（设计用）。
前文说它"已是半个 L3"是高估 —— 准确说法是：
它实现了 L3 的"伏笔字段族"，而 L3 的"骨架字段族"为零。**

## 3. ★ 批评三核实：角色弧光**单独设计必然脱节**（这是结构性缺陷）

### 3.1 证据：角色卡 `arc` 是**孤立的自由文本**

`characters` 表（`baseline-schema.ts:80`）：

```sql
arc TEXT DEFAULT '',   -- 弧光
```

生成路径（`character-card-generation.command.ts:82`）：

```ts
...(optionalText(record.arc) ? { arc: optionalText(record.arc)! } : {}),
```

**就是"有就带上，没有就空着"** —— **没有任何机制把它与大纲/章节/弧绑定。**

### 3.2 角色与章节的唯一关联是"逐章点名"

搜索 `chapterInfo.characters` 的全部用法，结果一致：

```ts
:329  characters: chapterInfo.characters,
:635  characters: [...chapter.characters],
:692  this.chapterInfo.characters.join(' '),
:760  this.chapterInfo.characters,
:889  this.chapterInfo.characters,
:957  ...this.chapterInfo.characters,
```

**→ 角色只通过"本章点名"与单章关联。** 而 `chapterInfo.characters` 的来源是
`blueprints.characters`（逐章数组）。

**→ 所以：角色的出场范围 = 逐章蓝图里点名的并集。没有"归属范围"的概念。**

### 3.3 作者的判断，用代码语言转述

作者原话：

> 「自顶向下设计小说架构的话，**弧光是跟随大纲走的**，怎么会在这种地方单独设计呢，
> 因为**非常容易跟大纲脱节，甚至冲突**，只有一些伏笔是可以强行圆。」

**→ 完全正确，而且比"容易脱节"更严重 —— 是"结构上无法不脱节"：**

| 角色卡 `arc` 文本 | 大纲（蓝图） |
|---|---|
| 人在"角色图谱"页手写/AI 生成 | 人在"情节大纲"页生成 |
| **独立存储、独立编辑** | **独立存储、独立编辑** |
| 无外键、无章节绑定 | 无外键、无弧绑定 |

**→ 两条平行线，永不同步。** 作者改了角色的成长线，大纲里的章节不会跟着动；
反之亦然。**"冲突"是必然的，不是偶然的。**

### 3.4 但作者说对了一半：**伏笔确实可以"强行圆"**

> 「只有一些伏笔是可以强行圆。」

**这句话点出了伏笔与其他结构的本质差异**：

- **伏笔是"延迟兑现"**——第 1 章埋、第 60 章收，中间不需要连续一致，
  作者可以在第 60 章回头补一句"其实那就是信号中断"，**圆的成本低**；
- **弧光是"连续演变"**——角色的成长必须每章累积，**中间任何一章脱节都会露馅**，
  不能事后强行圆。

**→ 所以 `narrative_thread_plans` 只做伏笔是"合理的最小实现"；
但它不能扩展成 L3，因为 L3 要管的是"连续结构"，不是"延迟兑现"。**

**这是作者比前文分析更深刻的地方。**

## 4. 修正后的现状盘点（诚实版）

| 层 | 应有的实体 | 本项目现状 | 缺什么 |
|---|---|---|---|
| **L0** 故事内核 | premise + 配置 | ✅ 有（`project_core.premise` 等） | — |
| **L1** 世界框架 | 世界规则 + **空间骨架** | ⚠️ 有世界设定，**无空间骨架** | 空间节点定义 |
| **L2** 人物体系 | 角色卡 + **归属范围** | ⚠️ 有角色卡，**无 `space_scope` / `active_in`** | 归属绑定 |
| **L3** 叙事弧 | 弧（空间/目标/高潮/角色进出） | ❌ **只有"伏笔"字段，无骨架** | **整个骨架层** |
| **L4** 事件单元 | 事件（规则/目标/奖励） | ⚠️ 有 `draftShortOutlinePrompt`（只整理不承接） | **显式实体** |
| **L5** 章节 | 章节蓝图 | ✅ 有（`blueprints`） | 无弧/事件归属 |
| **L6** 场景 | 场景 | ❌（AI 写正文时隐式处理） | 不必须 |

**→ 修正结论：项目在 L3 上是"接近空白"，而非前文说的"半个"。**
**真正缺的是"弧"这个**声明式结构**——它要能回答"这一段在哪个空间、要达成什么、高潮在哪、谁进出"。**

## 5. 为什么"必须补弧"（用作者的话论证）

作者说「不符合工程化工作流的创作思路」。**这句话指出了根本**：

| | 命令式（现状） | 声明式（作者要的） |
|---|---|---|
| 作者做什么 | 逐章改蓝图，手工凑出闭环 | 声明"ch1-12 是无声公寓弧，目标 X，高潮 ch10-12" |
| 系统做什么 | 什么都不做（只展示） | **检查**：蓝图是否覆盖弧的范围？**注入**：生成时告知 AI 当前弧 |
| 出错时 | 靠作者自己发现"这章好像不对劲" | 系统提示"第 8 章不在任何弧内" |
| 800 章规模 | **不可维护**（要手工对齐 800 次） | **可维护**（27–80 个弧） |

**→ 作者的诉求不是"更细的伏笔管理"，而是"把逐章命令式改成声明式"。**
**这与前文把 `narrative_thread_plans` 当作 L3 起点的建议，方向上是错的。**

## 6. 修正后的落地判断（待作者确认）

### 6.1 前文 §6.2 的"第 0/1 步"要**撤回**

前文建议"把 `narrative_thread_plans` 当起点、扩展 L3 字段"。
**经本次核实，这个建议不成立** —— 因为：
- 它的字段是"伏笔专属"的（`targetStart/EndChapter` + `authorIntent`）；
- L3 需要的是"骨架专属"字段（`space`/`goal`/`climax`/`active_characters`）；
- **两者语义不同，硬合并会让"伏笔"和"弧"互相污染**（作者 §3.4 已指出这个区别）。

**→ 正确做法：L3 弧应是**独立的新实体**，而不是 `narrative_thread_plans` 的扩展。
两者关系：**弧 ⊃ 伏笔**（一个弧内可以有多条伏笔/线索，但弧不等于伏笔）。**

### 6.2 新建议的顺序

```
第 1 步（先做）：定义「叙事弧」独立实体
                —— 字段对齐分析里的 L3（space/goal/conflict/climax/active_characters/exit_characters）
                —— 与 narrative_thread_plans 建立"包含"关系（可选外键）

第 2 步：定 L4（事件单元）与 blueprints 的关系（前文 §4.4 的架构决策，仍需拍板）

第 3 步：弧 → 生成上文的注入
          ⚠️ 触碰收据契约（main-generation-owner.ts:543/561）+ 110 用例 —— 同 P3 教训

第 4 步：P5 地图 → 弧的 space 子视图（前文 §3 已被作者认可）

第 5 步：角色卡加 space_scope / active_in
          ⚠️ 同时处理 arc 文本的"脱节"问题 —— 要么绑定到弧，要么明确标注为"仅参考"
```

### 6.3 一个必须先回答的设计问题（本次新发现）

> **角色的 `arc`（弧光）字段，未来怎么办？**

三种可能：
1. **绑定到 L3 弧**：角色的弧光 = "在弧1里从 A 变成 B"，随之有结构约束；
2. **保留为自由文本**，但**明确标注"不参与生成约束"**（避免作者误以为它有效）；
3. **删除**，改为在弧里描述"本弧内角色的变化"。

**→ 现状是"有字段、无约束"，这最危险**：作者以为写了弧光 AI 会遵守，实际不会。
