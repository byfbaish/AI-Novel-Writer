# 「故事弧」环节设计提案（作者设想的具体化）

> 缘起：作者指出「我觉得就是在现在的故事架构里，少了这一个环节」，
> 并给出初步设想：**世界观里设 L5 地图空间信息（大区域 + 副本）；故事弧据其他信息生成；情节大纲受故事弧约束**。
> 本文把该设想**落到确切的数据流与改动点上**，供讨论。
> 日期：2026-10-11 · 分支 `dev_byf`

---

## 0. 先纠正我自己：作者对"声明式 vs 命令式"的反驳是对的

我在 `seven-layer-skeleton-assessment.md` 里把这件事框架成"声明式 vs 命令式"的范式之争。
**作者指出这不是重点**：

> 「剧情弧的层级在大纲之上，是用来约束大纲的，**只要大纲按照剧情弧的内容来设计，跟现在的命令式一脉相承**」

**→ 接受。** 我的框架错了，因为：
- 大纲**继续用现有的做法生成**（AI 逐章产蓝图，命令式不变）；
- 弧的作用是**给大纲一个上游输入**，而不是替换它的生成方式。

**弧的价值 ≠ 换范式，弧的价值 = 给大纲一个它现在没有的依据。**

前文说"命令式不可维护、要改成声明式"是**过度推论**；
作者说"跟现在一脉相承"才是准确的——**弧只是往上游又加了一层输入**。

## 1. 作者设想的数据流（转述）

```
L1 世界观（现有环节，扩展）
    ├─ 核心规则 / 阶层断层 / 深层危机      ← 现有三维度
    └─ ★ 空间结构（大区域 + 副本）          ← 新增，作者说的"L5 地图空间信息"
              │
              │  弧引用空间节点
              ▼
★ L3 故事弧（新增环节）
    ├─ 名称 / 起止章节
    ├─ space: 引用 L1 的空间节点（如"无声公寓"）
    ├─ 目标 / 冲突 / 高潮位置
    ├─ 活跃角色 / 退场角色
    └─ 伏笔埋收（可与现有 narrative_thread_plans 关联）
              │
              │  大纲受弧约束
              ▼
L5 情节大纲（现有环节，加约束）
    └─ 生成时知道"本段处于哪条弧的什么位置"
              │
              ▼
L4 章节蓝图（现有，不变）
    └─ 逐章命令式生成，但上游多了弧的依据
```

**关键：整条链上唯一"新"的实体是弧。世界观是扩展，情节大纲是加输入，蓝图完全不动。**

## 3. 设计细节：三个必须定清楚的问题

### 3.1 ★ 世界观加"空间结构"——但它不像其他三个维度

**现状**：世界观模板（`builtin-prompt-templates.ts:508-520`）明确要求**三个维度，每个"自带冲突点"**：

```
1. 【核心规则与体系漏洞】
2. 【阶层断层与资源战场】
3. 【隐喻与深层危机】
（要求）每个设定都必须"自带冲突点"，能直接驱动情节。
```

**问题**：**空间结构是"客观地点"，不该"自带冲突点"**。
"无声公寓在第三层"是一个地理事实，不是冲突。

**两个选项**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 作为第 4 维度**（并入世界观文本） | 在世界观末尾加 `### 4.【空间结构】`，写明大区域与副本清单 | 与世界观的"每项自带冲突"要求**语义冲突**；且它会被 `worldbuilding` 的一段文本承载，**难以被弧结构化引用** |
| **B. 独立为结构化清单**（推荐） | 空间节点作为**结构化数据**（名称/类型/父节点/描述），存 DB | 需要新表；但**弧可以直接外键引用**，且地图可视化有天然数据源 |

**→ 我倾向 B**，理由是作者自己的诉求：分析里说"P5 地图是弧的 space 字段可视化"——
**如果空间只是世界观里的一段散文，地图就无从可视化。**
（这条需要作者确认：你要的"大区域和副本"是**散文描述**还是**可选清单**？）

### 3.2 ★ 弧"根据其他信息生成"——具体是哪些信息？

作者说"故事弧根据其他信息来生成"。**需要明确"其他信息"是什么。** 我的理解是：

| 弧字段 | 来源 |
|---|---|
| `space` | ← L1 空间结构（**引用**，非自由填写） |
| `active_characters` / `exit_characters` | ← L2 角色图谱 |
| `goal` / `conflict` | ← L0 故事前提（核心冲突链） |
| `climax` / 起止章节 | ← L0 故事前提（悬念骨架）+ 作者指定 |
| 伏笔埋收 | ← 可与现有 `narrative_thread_plans` **关联**（`弧 ⊃ 伏笔`） |

**→ 即：弧 = 把 L0/L1/L2 的信息"按时间切片"，切成若干段。**
**这正是它作为"中间层"的意义**：不是新造信息，而是**把已有信息组织成阶段**。

#### 3.2.1 弧的字段清单（草案，供逐条增删）

结合外部文档的 L3 建议字段 + 本项目已有实体，我整理成下表。
**"来源"一栏决定了这个字段是"AI 生成"还是"引用已有"还是"作者输入"** —— 这一栏是本次最需要作者审的。

| 字段 | 含义 | 来源 | 必填？ |
|---|---|---|---|
| `title` | 弧名（如"无声公寓篇"） | AI 生成 + 作者改 | ✅ |
| `from_chapter` / `to_chapter` | 起止章 | **作者输入或 AI 建议后确认** | ✅ |
| `space` | 所在大区域 / 副本 | **引用 L1 空间结构**（3.1-B 才可行） | ✅ |
| `goal` | 本弧要达成的目标 | ← L0 故事前提（核心冲突链）切片 | ✅ |
| `conflict` | 本弧的主要阻力 | ← L0 故事前提 + L2 角色对立 | ✅ |
| `climax_chapter` / `climax_event` | 高潮位置与事件 | ← L0 悬念骨架 + 作者指定 | ✅ |
| `active_characters` | 本弧活跃角色 | ← L2 角色图谱（**引用 `characters.name`**） | ✅ |
| `entry_characters` / `exit_characters` | 本弧登场/退场角色 | ← L2 + 作者 | ⭕ |
| `thread_ids` | 本弧涉及的伏笔 | **引用 `narrative_thread_plans`**（弧 ⊃ 伏笔） | ⭕ |
| `summary` | 本弧一句话概要 | AI 生成 | ✅ |

**★ 与外部文档的差异（需要作者判定）**：

外部文档建议在**角色卡**上加 `space_scope`（角色归属范围）、`active_in`（绑定到弧）。
**我认为不必** —— 因为：`characters` 表是**全局名单**，一个角色可以跨多个弧活动；
把"某角色在某弧活跃"写在**弧**这一侧（`active_characters`）比写在角色那一侧更自然，
**且避免"改一个角色要动 N 条弧"的反向依赖**。
（本项已在 `l3-arc-gap-verification.md §6.3` 记为待决问题 3。）

#### 3.2.2 ★ 弧"根据其他信息生成"的执行形态（本次新增的具体化）

作者说"故事弧根据其他信息来生成"。**落到代码上，它就是一个新的架构步骤**，与现有四步同构：

```
新增第 5 步：story_arc
  输入：premise + charactersArch + worldbuilding（含空间结构）+ 总章数 + 卷规划（若有）
  输出：一份"弧清单"（每条弧含上表字段）
  契约：类比 PLOT_OUTLINE_PROTOCOL —— 但由于弧是"一次成一批"，不需要逐章 cursor
```

**关键设计点：弧的输出格式用 JSON 而非自由文本。**
理由：弧需要被**结构化引用**（章节区间、`space` 外键、角色名单），
如果像 `worldbuilding` 那样存成一段散文，**下游就无法定位"第 8 章属于哪条弧"** ——
这正是"地图无法可视化"的同源问题（§3.1-A 的代价）。

**→ 所以：`story_arc` 是整个体系里**第一个"必须结构化存储"的架构资产**。**
这也解释了为什么它不能像其他四个一样，简单加进三处硬编码列表就完事 ——
它还需要一张表 + 一个编辑界面（列表/时间轴）。

#### 3.2.3 弧的粒度与"卷"（回答 §5 的问题 2、3）

- **一弧的合理跨度**：外部文档举例"一章一个副本"到"数十章一个副本"不等。
  作者的 800 章项目，若一弧 = 一个副本，**弧数量会很大**（分析里估 27–80 个）。
- **是否需要"卷"这一层**：**如果一弧本身已经带"起止章 + 目标 + 高潮"，那么"卷"就是若干弧的集合，
  可以直接由"阶段目标"表达，不必新增实体。** 我的倾向：**先不要"卷"，用"弧的上级分组"预留即可。**
- **→ 这一条建议作者先给个"典型项目里一弧大概多少章"的直观数字**，
  它直接决定 UI 是"列表"还是"甘特图"。

### 3.3 ★ 情节大纲"受弧约束"——怎么个约束法？

**现状**（已核实）：`synopsis` 是**按批次逐章生成**的（`architecture.command.ts:52-57` 的
`synopsisRange` + `PLOT_OUTLINE_PROTOCOL`），**当前不以任何"段"为前提**。

**★ 本次深挖到的关键结构事实（三处，直接决定可行性）**：

**事实 ①：大纲是"严格一章一条"的，不许分组。**

`plot-outline-contract.ts:150-161` 的 `validPlotOutlineEntry` 要求一份大纲条目**必须且只能**是
`## 第N章：标题` + 一行非空正文，并显式拒绝：

```ts
if (/```|~~~|大纲批次进度|后续概览|.../iu.test(text)) return false          // 拒绝进度行/概览
if (entries.length !== 1 || heading.grouped || heading.from !== chapter) return false  // 拒绝分组/多章
return !/^[\t ]*(?:#{1,6}[\t ]+|...第[^\r\n]*章|Chapters?\b)/imu.test(body)  // 正文里也不许再出现章标题
```

而 `validPlotOutlineAuthorPrefix`（`:229-240`）进一步要求：**范围内每一个章号都必须逐章连续存在**
（`entries.length !== range.to - range.from + 1` 即判非法）。

**→ 含义**：大纲已经是**章级最细粒度、不可再分组**的实体。
**"弧"不能是"大纲的上位分组"再交给大纲生成器去消化——因为生成器一次只写一章、且禁止写"这一段属于哪个弧"之类的元信息。**
弧若想约束大纲，**必须从"生成时的上游输入"或"生成后的外部校验"这两个方向进，不能从"大纲内部的层级"进。**
（这条正好印证作者说的"弧的层级在大纲之上"——**大纲这一层内部已经没有任何可插层级的空间了**。）

**事实 ②：大纲被"整篇"喂给蓝图，不是切片喂。**

`directory-workflow.ts:364-372`：

```ts
const parts: string[] = []
if (core.premise && core.premise.length > 50) parts.push(core.premise)
if (core.charactersArch && core.charactersArch.length > 50) parts.push(core.charactersArch)
if (core.worldbuilding && core.worldbuilding.length > 50) parts.push(core.worldbuilding)
if (core.synopsis && core.synopsis.length > 50) parts.push(core.synopsis)   // ← 全文，不切
context.data.architecture = parts.join('\n\n---\n\n')
```

然后 `directory.command.ts:341` 用 `.withNovelArchitecture(architecture)` 把**这一整坨**塞进
**每一个**蓝图批次（`MAX_BLUEPRINT_ITEMS_PER_BATCH = 5`，即每 5 章一批，批批都带全文大纲）。

**→ 含义（重要）**：**蓝图生成时"看得到全部大纲"，却"不知道自己这批属于哪一段"。**
这就是作者说的"**没有抓手**"最精确的位置 —— 不是缺信息，是**缺"你正在写的是哪一段"这个坐标**。
**→ 弧在蓝图这一步的落地形态，天然就是给这批蓝图附一个"本批所属弧"的标签，而不是再塞一遍结构。**

**事实 ③：对照——草稿阶段反而已经做了"切片"。**

`generate-draft.command.ts:102-141` 的 `synopsisForDraftChapter` 会把大纲**投影到当前章**：
按 `## 第N章` 标题切分，只保留命中本章的那一段（不可定位则原文保留，绝不猜删）。

**→ 含义**：**"把大纲投影到当前范围"这件事，项目里已经有现成的、且经过保守性设计的实现。**
弧如果要影响大纲/蓝图，**应当复用这套"投影"思路**（弧 = 一个更大的投影窗口），
而不是新造一套。

**结论：加弧之后的两种做法（修正版）**：

| 做法 | 说明 | 风险 | 本次评估 |
|---|---|---|---|
| **a. 生成时注入弧** | 生成第 N 章大纲/第 b 批蓝图时，告知"本段属于 arc X，目标是 Y，高潮在 ch10-12" | ⚠️ 触碰生成侧契约（与 P3 同源的收据校验问题） | 价值更大（真正"给抓手"） |
| **b. 生成后校验** | 大纲/蓝图照旧生成，之后**检查它是否覆盖弧的起止章、章号是否落在弧区间内** | 零运行时风险，但只是"报错"不是"引导" | 建议**先做** |

**★ 本次修正的一个更优路径（介于 a/b 之间）**：

> **c. 生成前"预检 + 提示"**——不动生成管线，但在**呼出生成前**根据"当前要生成的章号范围"
> 反查它落在哪条弧里，把这条弧的目标/空间/高潮位置**作为 `stepGuidance` 注入**
> （`stepAuthorInputs` 的 `architecture:step-guidance:<key>`，`architecture.command.ts:61` 已支持）。

- 它**不改任何契约**（`stepGuidance` 本来就是作者可填的输入，走的是同一条既有通道）；
- 它**真的把弧变成了"抓手"**（不是事后报错）；
- 代价：作者需要自己确认"这段指导是弧自动带出来的"（或在 UI 上标明）。
- **→ 建议：c 优于 b，且风险接近 b。** 先做 c，验证价值后再谈 a（改契约直接注入）。

## 4. 与既有实体的关系（避免重复造轮子）

## 6. 一句话总结

**作者的纠正成立：这不是"范式之争"，弧只是给大纲加一个上游依据，大纲的生成方式不变。
落地的最小形态是——世界观加"空间结构"、新增"故事弧"环节（弧 = 把 L0/L1/L2 信息按时间切片）、
情节大纲加弧约束。整条链上唯一的新实体是弧，蓝图完全不动。**

**★ 本次深挖补充的三条结论（2026-10-11 二稿）**：
