# 「故事弧」环节设计提案（作者设想的具体化）

> 缘起：作者指出「我觉得就是在现在的故事架构里，少了这一个环节」，
> 并给出初步设想：**世界观里设 L5 地图空间信息（大区域 + 副本）；故事弧据其他信息生成；情节大纲受故事弧约束**。
> 本文把该设想**落到确切的数据流与改动点上**，供讨论。
> 日期：2026-10-11 · 分支 `dev_byf` · **版本：v3**（经作者两轮纠正）
>
> **阅读提示**：v1 提"只读检测"、v2 提"结构化弧表（含章号+角色）"，均被作者纠正。
> **最新结论看 §0.1（不绑章号、不管角色）与 §3.2.3（弧 ≈ `plot_structure_guide` 的内容化）。**

---

## 0. 先纠正我自己：作者对"声明式 vs 命令式"的反驳是对的

我在 `seven-layer-skeleton-assessment.md` 里把这件事框架成"声明式 vs 命令式"的范式之争。
**作者指出这不是重点**：

> 「剧情弧的层级在大纲之上，是用来约束大纲的，**只要大纲按照剧情弧的内容来设计，跟现在的命令式一脉相承**」

**→ 接受。** 我的框架错了，因为：
- 大纲**继续用现有的做法生成**（AI 逐章产蓝图，命令式不变）；
- 弧的作用是**给大纲一个上游输入**，而不是替换它的生成方式。

**弧的价值 ≠ 换范式，弧的价值 = 给大纲一个它现在没有的依据。**

前文说"命令式不可维护、要改成声明式"是**过度推论**；
作者说"跟现在一脉相承"才是准确的——**弧只是往上游又加了一层输入**。

## 0.1 ★★ 作者的第二轮纠正：弧**不绑定章号、不管理角色**（v3，2026-10-11）

作者看了 v2 后进一步纠正，**我的 v2 字段表有一半是错的**：

> 「故事弧实际上只是描述一个**阶段性**的故事，它**并不需要明确指出在多少章到多少章**。
> 用多少章来解决这个故事，**是情节大纲要做的事情**。
> 重点是要把故事弧**管理起来**，至于什么角色和故事弧的相关性……**我觉得完全没有这个必要，按层级约束就好了**。
> 故事弧只是用来**约束情节大纲走向**的，**并不跨级管理**，
> 而在现有的设计下，**一个角色只要说清楚他参与了哪些事件、参与了什么副本就行。未参与的自然就退出了生命周期**。」

**→ 我错在两点：**

| # | 我的错误 | 作者的纠正 | 为什么作者是对的 |
|---|---|---|---|
| 1 | 给弧加 `from_chapter` / `to_chapter` / `climax_chapter` | **弧不管章号** | **章号是"展开"的结果，不是"设计"的输入。**假如弧绑定了章号，那弧和大纲就变成了**同层互相打架**的两套事实；而"用多少章讲完这个阶段"恰恰是**大纲该回答**的问题。**→ 不绑章号，弧才是真正的"上游"。** |
| 2 | 给弧加 `active_characters` / `entry` / `exit` | **弧不管理角色** | **作者的原话是决定性的**：「一个角色只要说清楚他参与了哪些事件、参与了什么副本就行。**未参与的自然就退出了生命周期**」。→ **角色相关性是"参与关系"的推导结果，不需要额外存一份。存了就必然和"参与关系"不同步。** |

**★ 第二条有一个我已经验证过的代码依据**：
`generate-draft.command.ts:1940-1990` 的 `readCharacterProfiles` **已经是"逐章按需注入"** ——
它拿 `chapterInfo.characters`（本章蓝图点名的角色）去 roster 里**按名匹配**，命中才注入档案，
未命中就记入 `missingNames` 提示（`:763-770`）。
**→ 也就是说"角色在场"这件事，系统已经在"章"这一级用它本来就该用的方式回答了。
在"弧"这一级再存一份 `active_characters`，纯属重复且必然漂移。**

**→ 结论：v2 的 §3.2.1 字段表已被 v3 大幅精简（见该节）。
弧的字段从 10 个降到 7 个，且**删掉的全是"跨级管理"的部分**。**

## 1. 作者设想的数据流（转述）

```
L1 世界观（现有环节，扩展）
    ├─ 核心规则 / 阶层断层 / 深层危机      ← 现有三维度
    └─ ★ 空间结构（大区域 + 副本）          ← 新增，作者说的"L5 地图空间信息"
              │
              │  弧以"副本名"弱引用空间（不做外键）
              ▼
★ L3 故事弧（新增环节）—— **v3 精简后的字段**
    ├─ 名称（如"无声公寓"）
    ├─ space: 所属副本 / 大区域（弱引用）
    ├─ 目标 / 冲突 / 转折事件
    └─ 伏笔（可选关联）
    ✗ 不含章号        ← 章号归大纲
    ✗ 不含角色名单    ← 角色归"参与关系"
              │
              │  大纲受弧约束（= 作为"阶段结构引导"注入）
              ▼
L5 情节大纲（现有环节，加约束）
    └─ **由大纲自己决定每个阶段占多少章**（弧不管）
              │
              ▼
L4 章节蓝图（现有，不变）
    └─ 逐章命令式生成，但上游多了弧的依据
```

**关键（v3）**：整条链上唯一"新"的实体是弧，且弧**只描述阶段、不绑定章号与角色**。
世界观是扩展，情节大纲是加输入，蓝图完全不动。
**→ 弧与既有数据的耦合面因此极小：它只影响大纲步骤的一个输入。**

## 3. 设计细节：三个必须定清楚的问题

### 3.1 ★ 世界观加"空间结构"——但它不像其他三个维度

**现状**：世界观模板（`builtin-prompt-templates.ts:508-520`）明确要求**三个维度，每个"自带冲突点"**：

```
1. 【核心规则与体系漏洞】
2. 【阶层断层与资源战场】
3. 【隐喻与深层危机】
（要求）每个设定都必须"自带冲突点"，能直接驱动情节。
```

**问题**：**空间结构是"客观地点"，不该"自带冲突点"**。
"无声公寓在第三层"是一个地理事实，不是冲突。

**两个选项**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 作为第 4 维度**（并入世界观文本） | 在世界观末尾加 `### 4.【空间结构】`，写明大区域与副本清单 | 与世界观的"每项自带冲突"要求**语义冲突**；且它会被 `worldbuilding` 的一段文本承载，**难以被弧结构化引用** |
| **B. 独立为结构化清单**（推荐） | 空间节点作为**结构化数据**（名称/类型/父节点/描述），存 DB | 需要新表；但**弧可以直接外键引用**，且地图可视化有天然数据源 |

**→ 我倾向 B**，理由是作者自己的诉求：分析里说"P5 地图是弧的 space 字段可视化"——
**如果空间只是世界观里的一段散文，地图就无从可视化。**
（这条需要作者确认：你要的"大区域和副本"是**散文描述**还是**可选清单**？）

### 3.2 ★ 弧"根据其他信息生成"——具体是哪些信息？

作者说"故事弧根据其他信息来生成"。**需要明确"其他信息"是什么。** 我的理解是：

| 弧字段 | 来源 |
|---|---|
| `space` | ← L1 空间结构（**引用**，非自由填写） |
| `active_characters` / `exit_characters` | ← L2 角色图谱 |
| `goal` / `conflict` | ← L0 故事前提（核心冲突链） |
| `climax` / 起止章节 | ← L0 故事前提（悬念骨架）+ 作者指定 |
| 伏笔埋收 | ← 可与现有 `narrative_thread_plans` **关联**（`弧 ⊃ 伏笔`） |

**→ 即：弧 = 把 L0/L1/L2 的信息"按时间切片"，切成若干段。**
**这正是它作为"中间层"的意义**：不是新造信息，而是**把已有信息组织成阶段**。

#### 3.2.1 ★★ 弧的字段清单（**v3 大幅精简** —— 作者纠正后）

**⚠️ 作者纠正了我对这个环节的两个根本性误解：**

> 「故事弧实际上只是描述一个**阶段性**的故事，它**并不需要明确指出在多少章到多少章**。
> 用多少章来解决这个故事，**是情节大纲要做的事情**。
> 重点是要把故事弧**管理起来**，至于什么角色和故事弧的相关性……**我觉得完全没有这个必要，按层级约束就好了**。
> 故事弧只是用来**约束情节大纲走向**的，**并不跨级管理**，
> 而在现有的设计下，**一个角色只要说清楚他参与了哪些事件、参与了什么副本就行。未参与的自然就退出了生命周期**。」

**→ 这两条纠正把我的 v2 字段表砍掉了一大半。逐条说明：**

| v2 里的字段 | 处置 | 原因 |
|---|---|---|
| `from_chapter` / `to_chapter` | ❌ **删除** | **作者明确否定**：用多少章是**大纲**的职责，不是弧的。弧只管"有什么事"，不管"占几章" |
| `climax_chapter` | ❌ **删除章号**，只留 `climax_event` | 同上，章号是下游的事 |
| `active_characters` | ❌ **删除** | **作者明确否定**：不跨级管理角色。角色相关性由"参与哪些事件/副本"自然表达 |
| `entry_characters` / `exit_characters` | ❌ **删除** | 同上（"未参与的自然就退出了生命周期"——**这是推导结果，不是要存的字段**） |
| `space` | ⭕ **保留但降级** | 保留为"副本名"，但它**是弧的一个属性**，不是要反查角色的索引 |
| `thread_ids` | ⭕ **保留可选** | 弧 ⊃ 伏笔（作者此前已认可） |
| `title` / `goal` / `conflict` / `summary` | ✅ **保留** | 这些才是"阶段性故事"的本体 |

**→ v3 的弧字段表（精简后）：**

| 字段 | 含义 | 必填？ |
|---|---|---|
| `title` | 弧名（如"无声公寓"） | ✅ |
| `space` | 所属副本 / 大区域（**弱引用**，不是外键约束） | ✅ |
| `goal` | 本阶段要达成什么 | ✅ |
| `conflict` | 本阶段的主要阻力 | ✅ |
| `turn` | 本阶段的转折/高潮**事件**（**不写章号**） | ✅ |
| `summary` | 一句话概要 | ✅ |
| `thread_ids` | 涉及的伏笔（可选，弧 ⊃ 伏笔） | ⭕ |

**★ 这个精简带来一个巨大的好处（v2 完全没想到）：**

**没有章号 ⇒ 弧不再是"时间轴上的切片" ⇒ 弧可以被自由增删改、重排、插队。**
一个"阶段性故事"就是一段**叙事意图**；它占多少章、落在哪几章，是**大纲**在展开时决定的。
**→ 这才是作者说的"把故事弧管理起来"真正的意思：管理的是"有哪些阶段故事"，而不是"每段占几章"。**

**★ 同时这也彻底解决了 v2 §3.2.3 那个"800 章 = 27–80 个弧"的粒度难题** ——
既然不绑定章号，就**不存在"弧太碎/太大"的问题**，粒度由作者需要多少个"阶段故事"决定。

#### 3.2.2 ★ 弧"根据其他信息生成"的执行形态（v3 修正）

作者说"故事弧根据其他信息来生成"。**落到代码上，它就是一个新的架构步骤**：

```
新增第 5 步：story_arc
  输入：premise + charactersArch + worldbuilding（含空间结构）
  输出：一份"阶段故事清单"（每条含上表字段）
  不含：任何章号、任何角色名单
```

**关键设计点（v3 修正）：**

 ~~输出必须用 JSON~~ → **仍然建议 JSON，但理由变了**：
v2 的理由是"要做外键引用、要做时间轴"，**那个理由随字段精简已经不成立了**。
v3 的理由只剩一条，但依然成立：**至少要能逐条增删改**（把"阶段故事管理起来"），
自由文本做不到"单独编辑第 3 条弧"。**如果作者觉得连这个都不需要，存成散文也不是不行。**

**→ 诚实地说：弧的存储形态现在是一个"体验问题"，不再是"技术必须"。
这让它的落地成本从 v2 的"新表 + 新步骤 + 新界面"降为"新步骤 + （可能的）轻量列表"。**

#### 3.2.3 ★★ 叙事弧在现有体系里的"位置"（v3 最关键的发现）

我在 `architecture-workflow.ts:279-355` 找到了一个**极其重要的既有事实**：

**`getPlotStructureGuide()` 已经在做"弧范式"的事情 —— 只不过它是"公式化"的。**

```ts
// architecture-workflow.ts:279-355
case 'kishotenketsu': 起 1~ch25 / 承 ch25+1~ch50 / 转 ch50+1~ch75 / 合 ch75+1~全书
case 'three_act':     第一幕 1~20% / 第二幕 20%~75% / 第三幕 75%~100%
case 'heros_journey': 十二阶段（按百分比切）
case 'multi_thread':  交汇节点在第 25% / 50% / 75% 章
```

**→ 这就是"约束情节大纲走向"的现成机制！**
它被注入到 `synopsis` 步骤（`architecture.command.ts:2284` 的 `.withPlotStructureGuide(...)`），
直接决定大纲怎么切段、怎么排节奏。

**→ 所以"故事弧"的真实定位是：**
**不是"从零发明一个新层"，而是"把 `plot_structure_guide` 从'公式化的百分比切片'
升级为'内容驱动的阶段故事切片'"。**

| | 现状（`plot_structure_guide`） | 加弧之后 |
|---|---|---|
| 切法 | 按**固定百分比**（三幕 20/55/25） | 按**作者定义的阶段故事** |
| 依据 | 一个结构模式枚举（`three_act`/`heros_journey`/…） | 这本书**独有的**若干阶段 |
| 谁决定 | 系统给公式，AI 填内容 | **作者定义阶段，AI 负责展开** |
| 变形能力 | ❌ 所有三幕小说切法一样 | ✅ 一本书一套自己的阶段 |

**★★ 这条发现把故事弧的落地成本降了一个量级：**
**它不需要"在大纲之上插一层"，它可以就是"喂给大纲步骤的一段更优质的 `plot_structure_guide`"。**
换句话说 —— **弧的第一步落地，很可能只是"让 `plot_structure_guide` 可由作者自定义"。**

这个方向同时天然满足作者的全部三条要求：
- ✅ **不绑定章号**（弧只描述阶段，大纲才定章号）—— 与 `plot_structure_guide` 同构（它就是"建议章节分配"而非强制）
- ✅ **不跨级管理角色**（`plot_structure_guide` 从不点角色名）
- ✅ **约束大纲走向**（它**本来就是**大纲步骤的输入）

**→ 这是一个"改一处、复用全部既有管线"的落点，比我 v2 设想的"新表+新界+新步骤"轻得多。**

### 3.3 ★ 情节大纲"受弧约束"——怎么个约束法？

**现状**（已核实）：`synopsis` 是**按批次逐章生成**的（`architecture.command.ts:52-57` 的
`synopsisRange` + `PLOT_OUTLINE_PROTOCOL`），**当前不以任何"段"为前提**。

**★ 事实 ①②③（下方）在 v3 下的意义**：这三条**原是为了论证"弧怎么标在章上"，
v3 里弧不再绑章号，它们的作用变成了"说明为什么 v2 那条路是错的"**。
**→ 保留它们，因为它们是"为什么不能绑章号"的代码级证据。**

**事实 ①：大纲是"严格一章一条"的，不许分组。**

`plot-outline-contract.ts:150-161` 的 `validPlotOutlineEntry` 要求一份大纲条目**必须且只能**是
`## 第N章：标题` + 一行非空正文，并显式拒绝：

```ts
if (/```|~~~|大纲批次进度|后续概览|.../iu.test(text)) return false          // 拒绝进度行/概览
if (entries.length !== 1 || heading.grouped || heading.from !== chapter) return false  // 拒绝分组/多章
return !/^[\t ]*(?:#{1,6}[\t ]+|...第[^\r\n]*章|Chapters?\b)/imu.test(body)  // 正文里也不许再出现章标题
```

而 `validPlotOutlineAuthorPrefix`（`:229-240`）进一步要求：**范围内每一个章号都必须逐章连续存在**
（`entries.length !== range.to - range.from + 1` 即判非法）。

**→ 含义（v3 版）**：大纲是**章级最细粒度、不可再分组**的实体。
**且它明文禁止输出任何"这一段属于哪个弧"的元信息。**
**→ 这从代码上证明了作者 v3 纠正的正确性：弧一旦绑了章号，它和大纲就都住在"章"这个坐标系里，
必然互斥或打架。所以弧必须待在"无章号"的上游——这正是 v3 精简后的形态。**

**事实 ②：大纲被"整篇"喂给蓝图，不是切片喂。**

`directory-workflow.ts:364-372`：

```ts
const parts: string[] = []
if (core.premise && core.premise.length > 50) parts.push(core.premise)
if (core.charactersArch && core.charactersArch.length > 50) parts.push(core.charactersArch)
