## 2. ⚠️ 隐藏成本一：世界观加第 4 维度 = **改 1 处模板 + 6 处 UI 字符串**

**修订版说**：世界观加第 4 维度"空间结构"，**"零新表、零字段、零数据模型改动"**。

**→ "零新表零字段"**成立**（确实只是往 `worldbuilding` 那段散文里多写一节）。**
**→ 但"零改动"**不成立** —— **"三个维度"这个描述被硬编码在 4 个 UI 位置**：**

| 位置 | 内容 | 需改 |
|---|---|---|
| `builtin-prompt-templates.ts:508` | 模板正文"构建以下**三个维度**" + 只列 1/2/3 | ★ 需加第 4 节 |
| `ArchitectureConfirmDialog.tsx:31` | `desc: '核心规则、阶层断层、深层危机'` + `descEn: '...'` | ★ 中英各 1 处 |
| `ArchFileViewer.tsx:55` | `desc: '核心规则、阶层断层、深层危机'` + `descEn: '...'` | ★ 中英各 1 处 |
| `sidebar-arch-files.ts:12` | `desc: '核心规则、阶层断层、深层危机'` | ★ 1 处 |
| `architecture-service.ts:21` | `desc: '核心规则 · 阶层断层 · 深层危机'` | ★ 1 处 |

**→ 真实成本：1 处模板 + 6 处字符串（4 个文件，其中 2 个含中英双语）。**
都是纯显示文案（我已逐一核实：全部是 `desc`/`descEn` 字段，**无逻辑依赖**），
所以是**低风险改动**，但**不是"零改动"**。

**★ 附：模板第 4 条【避免复述】也要同步** ——
它现在写"补全它未覆盖的维度（规则漏洞、阶层资源、终极灾祸）"，
加了第 4 维度后**必须把"空间结构"列进这个枚举**，否则 AI 可能在空间结构里复述核心设定。

### 2.1 ★ 一个更深的可行性问题：空间结构"该不该"放进世界观？

**修订版把空间结构定义成"世界观第 4 维度"，但这里有一个概念冲突我上一轮提过（`state-tracking-assessment.md §2.2`）：**

**现有世界观模板明确要求"每个设定都必须自带冲突点，能直接驱动情节"** ——
而**空间结构（一张地点清单）本身是中性信息，不带冲突**。

| | 世界观三维度 | 空间结构 |
|---|---|---|
| 性质 | 冲突装置（规则漏洞/阶层对立/终极灾祸） | **中性索引**（地点树） |
| 是否自带冲突 | ✅ 必须 | ❌ 不必 |
| 消费者 | 注入正文，制造戏剧张力 | **被弧引用、被 preflight 校验** |

**→ 所以把空间结构塞进"三维度"会**污染那一节的设计一致性**（AI 会被要求"给地点编冲突"）。**

**→ 我的建议（比修订版更稳）：**
**空间结构**不并入世界观正文三维度，而是作为**世界观的"第 4 节（索引节）"**，
在模板里**明确区别对待**：

```
1.【核心规则与体系漏洞】  ← 冲突装置
2.【阶层断层与资源战场】  ← 冲突装置
3.【隐喻与深层危机】      ← 冲突装置
4.【空间结构】            ← ★ 索引，不要求自带冲突（只需可引用的地点树）
```

**→ 这样既满足"第 4 维度"的可引用性，又不破坏"三维度自带冲突"的设计原则。**
**→ 成本不变（一样是改模板 + 6 处 UI 字符串），但语义更干净。**

## 3. ⚠️ 隐藏成本二：preflight 扩 3 条规则 = **需穿参，不是纯增量**

**修订版说**：preflight "扩为 3 条：弧引用的前弧/伏笔/空间是否存在"，
**"约 3 条正则检查"**、**"零新表、零字段、零数据模型改动"**。

**→ 规则本身确实能用正则写（这部分成立）。**
**→ 但"纯增量"不成立 —— 现有 preflight 的**输入签名里根本没有它要检查的东西**：**

```ts
// src/services/consistency-preflight.ts:11-25（现状）
export async function readConsistencyPreflight(
  session, blueprints,               // ← 只有蓝图
): Promise<...> {
  const exemptions = await ipc('db:consistency-exemption-list', ...)
  // 对每个蓝图：读"本章之前的定稿事实"
  const projections = await ipc('db:continuity-list-before', blueprint.chapterNumber, ...)
  return findBlueprintContinuityRisks(projections, blueprint, exemptions)
}
```

**→ 它现在**只看**："定稿事实（`projections`）vs 本章蓝图"。**
**→ 要检查"弧引用的空间是否存在"，它**必须多拿到两样**：① `worldbuilding`（空间定义）② 弧文本（空间引用）。**

| 要检查的 | 需要的新输入 | 从哪来 |
|---|---|---|
| 弧引用空间是否存在 | `worldbuilding` + 弧文本 | `db:project-core-get`（**已存在**，见下） |
| 弧引用的伏笔是否存在 | `narrative_thread_plans` | 已有 IPC（`narrative-thread-*`） |
| 弧引用的前弧是否存在 | **全部弧文本**（同一份即可） | 同上 |

**→ 好消息：`db:project-core-get` **已经存在**且被广泛使用**（`read-architecture.tool.ts:32` 等 10+ 处）
**→ 所以**不需要新 IPC**，只需在 preflight 里加一次 `project-core-get`。

### 3.1 ★ 关键判断：这 3 条规则**不该塞进现有函数**，应另开一个函数

**理由：三者是**架构内部**的引用完整性（弧↔空间↔伏笔），与"定稿事实 vs 蓝图"**无关**。**

| | 现有 `findBlueprintContinuityRisks` | 建议新增 `findArchitectureRisks` |
|---|---|---|
| 输入 | 定稿事实 + 蓝图 | **弧文本 + worldbuilding + 伏笔表**（**不含章号**） |
| 触发时机 | **逐章**（每次建章前） | **架构层**（弧生成后 / 手动触发） |
| 与章号关系 | 强依赖（查"本章之前"） | **无依赖**（纯跨层引用） |

**→ 好处：新函数**完全不用碰**现有两个调用点
（`ChapterCreationDialog.tsx:329`、`BatchChapterCreationDialog.tsx:207`），
**也不会让"逐章建章"多付一次 worldbuilding 读取的代价。**

**→ 这正是 `architecture-consistency-design.md` 里 AC3 的形态 —— 修订版说的"preflight 扩展"，
准确说应该是"AC 系列新增一个同构的架构级检查函数"，而非"给现有函数加规则"。**

**→ 真实成本：新建 1 个 ~60 行的纯函数 + 1 个 IPC 读取 + 1 个 UI 呈现点。仍属"低代码"，但不是"纯增量"。**

## 4. ⚠️ 隐藏成本三：角色知识"挂事实链" = **改三处，不是"加一维"**

**修订版说**：角色知识"挂事实链加 `known_by`，**不建矩阵（防爆炸）**"。

**→ 方向正确（这是 `state-tracking-assessment.md §2.1` 的原始建议）。**
**→ 但"加一维"这个说法**掩盖了三处实际改动**：**

| # | 改动 | 位置 | 说明 |
|---|---|---|---|
| 1 | **抽取器**：抽事实时判定"谁知道" | `finalized-continuity-facts.ts` | 现在按 `chapterNotes` 分句抽事实，**须新增"本句涉及谁"的判定** |
| 2 | **存储**：事实结构加 `known_by` | `finalized-continuity.ts:40-48` `FinalizedContinuityFact` | 加一个可选字段 + **schema 兼容**（老数据无此字段） |
| 3 | **查询**：生成时注入"该角色已知什么" | `generate-draft.command.ts` | 现在 `readCharacterProfiles` 只给角色卡，**须再加一路"知识注入"** |

**→ 真实成本：中（三处改动，跨 shared/service/命令层），不是"一维"。**
**→ 但**仍是第三类里最值得先做的**（唯一纯空白 P0），修订版判断没错。**

**★ 另有一个修订版没提的**难点**：`known_by` 的判定本身不可靠。**
"谁在场"能靠 `chapterInfo.characters` 拿到，但**"谁被告知、谁偷听、谁推断出来"**推不出来 ——
**这会直接导致 `known_by` 漏标** → 检查器误报"他不知道"。
**→ 建议：`known_by` 只标"**明示在场 + 明文告知**"（保守），宁可漏标不可错标，
并在检查器里**把"他可能只是没被告知"标成 INFO 而非 WARN。**（同 §3 的假阳性纪律）**

## 5. ⚠️ 落地次序：修订版的 ②③ 建议**对调**（AC1 应早于角色知识）

**修订版次序**：

```
① 弧层 prompt → ② 角色知识 → ③ AC1 层内一致性 → ④ AC2 层间引用 → ⑤ 合并决策
```

**→ 我的建议（把 ② 和 ③ 对调）：**

```
① 弧层 prompt（零代码）
② AC1 层内一致性（低代码，1 个纯函数 + 复用现有框架）
③ 角色知识（中，跨三层改动）
④ AC2 层间引用完整性（中）
⑤ 物品/场景/空间/时间线合并决策
```

**理由：**

| 维度 | AC1 | 角色知识 |
|---|---|---|
| 改动面 | 1 个纯函数（`characters_arch` 文本 ↔ `characters` 表） | **跨 3 层**（抽取器/存储/命令） |
| 依赖 | 无（两张表都在） | 依赖"事实链已经理解" |
| 能否立刻见效 | ✅ 能（现在就有散文↔角色卡不一致） | ⚠️ 要等抽取器改完才有数据 |
| 风险 | 低（纯文本比对） | 中（`known_by` 判定可能漏标） |

**→ AC1 是"低垂果实"：**改一个函数就能让"人物群像写了张三、但角色表没有张三"这种
**当下一眼可见**的不一致自动报出来。**它比角色知识更快见效、风险更低，适合排前面。**

**→ 唯一支持"角色知识先行"的理由**是它更痛（P0 纯空白）；
**但"痛"不等于"该先做"** —— 角色知识改动大、依赖抽取器、且判定不可靠，
**适合在 AC1 把"校验框架 + 假阳性纪律"跑顺之后再上。**
