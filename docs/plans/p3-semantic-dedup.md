## 0.0 先纠正一个会决定方案方向的技术误解 ★

作者的设想里有一句：

> 「在后续请求的时候，先在本地做校验，如果和上一次的 Prompt 头没有差别，
> **那就不用去做预请求**，直接从本地取上一次修改完的版本做替换。」

**这句话的前提不成立。** 我核实了这三点：

1. **「Prompt 头」本来就已经是本地字符串。** `composeInitialPrompt`
   （`generate-draft.command.ts:997-1000`）和 `draftAuthorMaterialBlock`（`:561-626`）
   都是**纯字符串拼接**，组装过程**没有任何 AI 调用**。
2. **续写/压缩请求已经复用了同一份头**。`draftAuthorMaterialBlock` 在续写
   （`:1609`）与压缩（`:1799`）时是**调用同一个函数**，`systemRole` 也是同一份
   （`:1662` 的 `params.systemRole`）。
   也就是说——**「保持一致」这件事今天就已经做到了**，靠的是"每次都重新拼一遍同样的字符串"。
3. 所以**重跑拼接的代价是零**：不是省钱的问题，因为它**压根不花钱**。

→ **结论**：作者真正想省掉的那个"预请求"，在当前架构里**不存在**。
但作者的核心直觉——**「中后期共通设定稳定，就该复用它，不该重新判定」**——是**完全正确**的，
只是它要解决的问题不是"省一次预请求"，而是**"别重新花钱重新问 AI 一遍"**（见 §0.1）。

> 🚨 **这一条如果不纠正，方案会做反**：会去实现一个"缓存拼接结果"的机制，
> 而真正的成本大头（LLM 语义判定）反而被漏掉。

## 0.1 成本账：钱花在哪，缓存才花得值

P3 与 P1 的根本区别是：**P1 的判定是零成本本地指纹，P3 的判定必须花钱（LLM 或 embedding）。**

所以"语义去重开不开"的决策，本质是一道成本算术题：

| 场景 | 不做去重 | 每次请求都重新判定 | **缓存判定结果（作者方案）** |
|---|---|---|---|
| 头内容**未变**（中后期常态） | 多带几段重复内容 | **每次都多花一次判定费** ← 最差 | 只花一次哈希比对（≈0）**← 作者方案胜** |
| 头内容**变了**（前期常态） | 多带几段重复内容 | 多花一次判定费 + 少带重复 | 多花一次判定费 + 少带重复 |

**这张表说明**：作者的直觉在成本上是**对的**，而且**恰好补上了 P3 最大的软肋**——
即"为了省几百 token，每轮多花一次 LLM 调用"这种**净亏**。把判定结果缓存下来、
只在头变化时重判，是这个方案能成立的**前提**，不是一个可选项。

**并且它自动实现了作者关心的"前期收益小、中后期收益大"的曲线**：
前期的头频繁变动 → 缓存频繁失效 → 每次都重判（无明显收益，但也不亏）；
中后期的头稳定 → 缓存长期命中 → 判定费趋近于零，只省不花。

## 0.2 作者方案的真实价值定位

把它翻译成准确的技术描述：

> **不是「省一次预请求」，而是「把一次 LLM 语义判定摊销到多次请求上」。**

- **收益来源**：LLM 判定费的**摊销**（省的是"判定"，不是"拼接"）。
- **收益曲线**：与头的**稳定性**正相关（作者的判断正确）。
- **前提条件**：头必须能被**确定性哈希**（否则缓存无法命中）。
- **失效条件**：头一变，缓存作废，重新判定。

> ⚠️ **v2 曾担心"头几乎每章都变导致缓存永不命中"。作者已给出正确处置，见 §2.2 ——
> 这不是缓存方案的缺陷，而是**拼装分层设计不合理**，应该修拼装，而不是给缓存打补丁。**

## 0.3 ★ P3 与 P4 的**实施次序依赖**（作者决策三的引申，必须先说清）

作者对决策三的判断是：

> 「实际上关于决策3，我觉得风险没有那么高，因为还有P4的改造在呢。等P4优化完之后，P3的价值才真正体现出来。」

**这个理由是成立的，而且它顺带解决了我在 §1.3 里对"删掉防漂移层"的顾虑——但前提是顺序对。**

关键事实：**P4 改的是配置本身，而配置就是 P3 的头。**

- P4 的产出是「**合并后的 `globalGuidance` / `writingStyle` / `coreOutline`…**」（backlog `:200-211`）。
- 这些字段**正是 P3 的 HEAD 的组成部分**（§2.1）。
- 所以：**P4 一动配置，P3 的 `headHash` 就变**（§2.3 的失效条件）。

**结论（这是一个此前双方都没说清的次序约束）**：

> **P4 必须在 P3 之前完成，或至少 P3 的缓存必须能识别"P4 改过配置"。**
> 若先上 P3、后上 P4，则 P4 上线当天 P3 的全部缓存失效、并触发一次全量重判。
> 这个代价**一次性、可接受**，但如果能排好序，就能省掉。

**为什么这还解决了我的顾虑**：作者说"风险没那么高，因为还有 P4"——
意思是 P4 会先把**配置层面的语义重叠**（`coreOutline` ↔ `premise` 那种）**从源头合并掉**，
那么留给 P3 的语义重复就只剩「**跨块的表述重叠**」（例如同一条要求写在全局要求里、
又写在执行合同 rules 里），**数量更少、边界更清楚、误判风险更低**。

→ **这个论证我接受。** 但它成立的条件是 **P4 真正落地**。
所以：**§1.3 里"保留 A 层防篡改"的建议不变**（那是安全边界，与 P4 无关），
而 **B 层（防漂移）的放开，风险确实因 P4 而下降** —— 我在此收回 v2 中"这是最需拍板的一条"的强调，
降级为"按 §1.3 的『可归因』方案改造即可"。

**⚠️ 但 P4 有它自己的硬约束**（backlog `:213-222`）：**不得让 AI 直接改配置**，必须三段式。
所以 **P3 不能顺手把"合并配置"也做了** —— 那是越界。P3 发现配置重叠时**只报告，交给 P4**。

## 1. 三项决策的逐条落实

### 1.1 决策一 · 「直接判定并删除 + 可查 log」→ 接受，但要加硬边界

作者：*「可以直接判定并删除，但是要做好结果可查的 log，方便后续改进。因为这个可以在设置里提供开关，所以我觉得风险是可控的。」*

**我接受，理由如下**（并且我承认 v1 稿在这一条上过于保守）：

- 作者的"开关 = 风险可控"论证是成立的 —— 开关在作者手里，且**默认关**。
- "结果可查的 log"补上了 v1 稿最担心的那个洞（**不可观测**）：
  只要每次删除都有完整记录，作者就能在出现问题时回溯、调整、关掉。

但**硬边界不能让步**（这些不是"保守"，而是 ADR 0020 的直接要求）：

| # | 硬边界 | 理由 |
|---|---|---|
| **B1** | **必删即记**：任何被删除的段落，必须有一条包含**原文全文**的日志。无日志 = 不允许删。 | 没有它"可查"就是空话；原文不记则事后无法判断删得对不对。 |
| **B2** | **保护区不参与自动删除**：作者原文段（`project_core.*` / `novel_config.*` / 作者本章指导 / 角色卡作者字段）**只报告、不删除**。 | ADR 0020「绝不删除作者事实或红线」。 |
| **B3** | **恢复路径（resume）不删**：resume 时必须复现首次的删除决策。 | 否则 `GENERATION_DRAFT_RECOVERY_AUTHOR_INPUT_CHANGED` 可能触发（§3.4）。 |
| **B4** | **删除是"改写进 prompt"，不是"改数据"**：不改 `chapter-materials.ts` 的构成、不改 `toWriterChapterInfo`。 | 守住 §3.2 / §3.3 的冻结护栏。 |
| **B5** | **降级不阻断**：判定失败（无网 / 无模型 / 超时 / 解析失败）→ **原样发送，不做去重**，并记一条"已跳过"。 | 去重是优化，不能变成生成失败的原因。 |
| **B6** | ★ **AI 只出「映射表」，不出「删除指令」**（2026-10-11 新增，见 §1.1.1） | 让每一条删除都能**指向作者原文的某一句**，可直接核对，与「必删即记」合流。 |

### 1.1.1 ★ 判定形态：**引用式判定**，而非「删/不删」的黑箱判定

这一条来自 2026-10-11 对作者真实项目的**段落级原文比对**（见 `p4-reassessment.md` §2.4.7），
它**改变了 P3 的核心机制**，必须写在这里而不是只留在 P4 文档里。

**实测事实**：AI 产的 `worldbuilding`（2413 字 / 16 段）与作者 `world_setting`（493 字）的重复形态是
**「复述」——同一事实换措辞说两遍**，例如：

- AI 段[3]："『第六条』曾存在后在 ch20 被直接刮平，导致所有持有该条信息的玩家暴毙"
  ↔ 作者 e 条："规则会变、会藏、会被抹（如 ch20 被刮平的「第六条」）"
- AI 段[9]："用于恢复理智值（SAN）（每章扣除 5 点，归零即淘汰）"
  ↔ 作者 d 条："理智值 SAN（100 起、每副本 −5、归零＝迷失淘汰）"

**→ 逐字去重（P1 指纹）对这两处完全无效**（措辞不同），这正是 P3 的靶心。

**但更重要的是**：这 16 段里 **纯复述只有 2 段（约 565 字）、复述+新增 1 段、纯新增/保留 10 段（约 1 500 字）**。
**如果让 AI 直接回答"这段删不删"，它会顺手把有价值的扩写也删掉**（因为扩写里也常"提到"作者的设定）。

**所以 P3 的 AI 调用必须改成「引用式」**：

```
❌ 旧设想：  输入段落 → 输出 { delete: true/false }
✅ P3 应采用：输入 [AI段列表(n)] + [作者条目列表(m)]
             → 输出 [ { aiSeg: i, defendsTo: j | null, overlap: "复述|扩写|新增" } ]
```

**好处（每一条都对应一个既有约束）**：

| 好处 | 对应约束 |
|---|---|
| 每一条删除都有"作者依据"作为凭证 | ADR 0020「必删即记」；B1 |
| 判定结果**可人工核对**（拿 i 和 j 两段对读即可） | 「结果可查的 log」；B1 |
| AI 的裁量空间被限制在"是否复述"，而非"是否有用" | B2 保护区零删除 |
| `overlap: 扩写|新增` 的段落**一律不删**，天然保住 §2.4.7 里那 1 500 字扩写 | 防止删过头 |
| 判定结果与缓存 key 解耦（见 §2.3） | §2.4 |

**→ 这一条同时回答了 backlog `:179` 的验收难题**：验收不靠"删了几段"（那是 P1 的逐字计数，P3 不能用），
而靠**「映射表里每条复述都能在作者原文里找到依据」**这个可核对性质。

**待办**：§2.3 的缓存 key 需要同步更新 —— 缓存的不再是"删完的结果"，而是**这张映射表**。

### 1.3 决策三 · 「promptHash 收据契约直接改掉」→ **部分接受，但必须保留核心**

作者的判断：

> 「promptHash 收据契约直接改掉吧，这个就不合理，对使用者的要求太高了，很容易造成Prompt膨胀。」

**我同意"当前形态对作者的约束过强"这个判断**，但**不能按"直接改掉"理解**。
必须把它拆成两层看清楚，因为其中一层**必须保留**：

| 层 | 作用 | 例子 | 该不该动 |
|---|---|---|---|
| **A · 防篡改** | 渲染层不能"夹带任意内容"发给模型 | `main-generation-owner.ts:1239` 的 `'smuggle'` 用例：`${reconciledPrompt}\n\n夹带内容` → 拒绝 | **必须保留** |
| **B · 防漂移** | 作者改了配置后，用旧收据重发 → 拒绝 | `test.ts:924`：`composed + '改目标'` → 拒绝 | **可以放开** |

**作者说的"对使用者要求太高"，指的是 B 层。B 层确实过强**——
它假定"收据里的 prompt 必须与最终发送的 bytes 完全一致"，
而 P3 的去重天然要改 bytes。

**但 A 层的存在意义不是"为难过作者"，而是"渲染层不能自由构造发给模型的 prompt"**。
若直接删掉整个契约，任何渲染层代码（或注入的第三方代码）都能自由拼 prompt 发给模型，
**这是安全边界，不是流程洁癖**。

**→ 处理方式（已按 §1.3 落地，不再作为"待拍板"项）**：

把契约从「**byte 精确**」改为「**可归因**」：

- 收据里不再存「prompt 的哈希」，而是存「**组装后的头原文 + 去重决策**」；
- 发送前校验：**发送内容 = 头原文 经过 决策 变换后的结果**（可重放验证）；
- 这样：P3 的删除是**在收据里声明的决策**，不是"擅自改 bytes"，**A 层护栏保留**，
  同时 **B 层的过强约束被解除** —— 作者的诉求达成。

> ⚠️ **代价必须说清**：这条改动会动 `main-generation-owner.ts` 与 `generate-draft.command.ts`
> 的**收据生产/消费两侧**，是 P3 里**最大的一块工作量**。
> 并且 `main-generation-owner.test.ts` 里**有 9 处 `GENERATION_MATERIAL_PROMPT_MISMATCH` 断言**
> （`:918`、`:924`、`:1201`、`:1240`、`:1242`、`:1262`、`:1281`、`:1288`、`:1291`），
> **必须逐条判断**：哪些是 A 层（要保留、要改写断言）、哪些是 B 层（可以放开）。
> **不能一把删掉**——那是把安全护栏和流程约束一起扔了。

## 2. 头缓存方案设计（作者决策二）

### 2.1 结构：怎么定义"Prompt 头"

先把 prompt 切成两半：

| 半 | 内容 | 是否稳定 | 是否进缓存 |
|---|---|---|---|
| **头（HEAD）** | 共同设定：`architecture` / `novel_config` 事实 / `globalGuidance` / 文风 / 角色档案 / 后续计划边界 | **相对稳定**（中后期几乎不动） | ✅ |
| **尾（TAIL）** | 本章个性化：章节蓝图 JSON / 本章已写正文 / 篇幅合同 / 对账块 / 续写指令 | **每章必变** | ❌ |

**用作者的话说**：头 = 「共同设定那些，不包含章纲等个性化生成特定的内容」。

### 2.2 ★ 头提纯：作者已给出正确处置 —— **修拼装，不给缓存打补丁**

v2 曾把这一条列为"关键风险 + 待拍板（H1/H2）"。作者的回答是：

> 「关于决策4的方案。如果有一个项目每一章都必变的话，那它就不应该放在共同设定的头部，
> 我认为是拼装逻辑设计不合理，应该放到后续拼装里去。」

**这个判断是对的，而且它比 v2 的选项设计更根本。** 我核实了代码，确认问题性质：

`draftAuthorMaterialBlock`（`:561-626`）当前是**平铺的线性拼接**——所有块按固定顺序摞在一起，
**没有区分"稳定"与"每章变"**：

```
【本章蓝图】{ json }                  ← 每章必变
【全局写作要求】{ globalGuidance }      ← 稳定
【文风要求】{ writingStyle }            ← 稳定
【文风适用边界】{ 固定文本 }             ← 稳定（字面常量）
【小说配置事实】{ novelConfigFacts }    ← 稳定
{ chapterMaterials }                 ← ⚠️ 混合：作者资料/角色档案/后续计划稳定，定稿原文每章变
{ reconciliation }                   ← 每章变
{ authorItems }                      ← 每章变
```

**问题的性质**：`chapter-materials.ts` 其实**早就分类清楚了**，只是拼装层把它拍平了：

- `REQUIRED_SOURCE_ID` 段（`:519-533`）：【作者资料】+【后续计划边界】→ `category: 'author'`，**稳定**
- `finalizedMaterial(...)` 段（`:535-549`）：【定稿原文 · 第N章 · draft X】→ `category: 'finalized-history'`，**每章必变**
- `sourced` 段（`:525-529`）：【有来源的历史与候选】→ **每章变**
- `category: 'reference'` 段（`:652-656`）：参考作品 → 稳定

→ **"每章必变"的部分是有明确标记的**（`finalized-history` / 候选）。
**所以这不是要重新设计分类，而是要在拼装层把这个已有的分类用于分层。**

**修正后的方案（取代 v2 的 H1/H2 二选一）**：

> **不是把 finalized 段"删掉"或"提纯缓存"，而是把 prompt 重组为"头 + 尾"两段：
> 稳定的块留在头，每章变的块统一挪到尾部（与本章蓝图、已写正文、篇幅合同并列）。**

| 段 | 所属 | 依据 |
|---|---|---|
| 【全局写作要求】/【文风要求】/【文风适用边界】 | **头** | 字面稳定 |
| 【小说配置事实】 | **头** | 来自 `novel_config`（P4 才改） |
| 【作者资料】/【后续计划边界】 | **头** | `category: 'author'`，`chapter-materials.ts:519-524` |
| 【定稿原文 · 第N章】 | **尾** | `category: 'finalized-history'`，`:535-549` |
| 【有来源的历史与候选】 | **尾** | `:525-529` |
| 【本章蓝图】/`reconciliation`/`authorItems`/篇幅合同/已写正文 | **尾** | 每章必变 |

**收益**：头因此变得**真正稳定** —— 中后期不动配置时，`headHash` 跨章不变，缓存长期命中。

**这个方案的额外好处（重要）**：它**不是**"为了缓存而改结构"。
「稳定的在前、变化的在后」本身就是**更好的拼装设计**：
- 对**模型**：头部约束稳定，指令层级更清晰（与 provider 前缀缓存也天然友好）。
- 对**P1**：P1 的 I1 不变量（逐字 1 次）**不受影响**（只是重排与归类，不改内容）。
- 对**审计**：头/尾可分别校验，§5 的验收更好写。

**⚠️ 必须先验证的两件事（实施前的门槛）** —— **我已核实，结论比预期好得多**：

**验证 1 · `chapterMaterials.text` 能否按 category 分段取出 → ✅ 能，且改动极小。**

`chapter-materials.ts:770` 的最终拼装是：

```ts
text: [requiredBlock, sourced, ...sourcedBlocks, gap].filter(Boolean).join('\n\n')
```

其中：
- `requiredBlock`（`:739-741`）：来自 `REQUIRED_SOURCE_ID`，即【作者资料】+【后续计划边界】→ **稳定**；
- `sourced`（`:525-529`）：【有来源的历史与候选】→ **每章变**；
- `sourcedBlocks`（`:742-744`）：`selection.included` 里除 required 外的所有段，
  **每段都带 `category`**（`selection.included[].category`，`generate-draft.command.ts:974-976` 就在用它）→
  可按 `category === 'finalized-history'` 分流；
- `gap`（`:752-755`）：覆盖缺口提示 → 每章变。

→ **四个组成部分在拼装函数里本来就是分开的变量，只是最后被 `join` 掉了。**
只要让 `ChapterMaterialBundle` **同时暴露这四个部分**（或直接暴露"稳定段/变化段"两个字符串），
**P3 就能在不改 `chapter-materials.ts` 任何内部逻辑、不动任何 hash 的前提下完成分层**。

**这是一个纯"多返回两个字段"的改动，风险极低** —— 远低于 v2 设想的 H1。

### 2.3 缓存流程

⚠️ **2026-10-11 修订**：判定产物从"删完的文本"改为"**映射表**"（§1.1.1 / B6）。
缓存**同时存**映射表与由它推导出的文本 —— 存映射表是为了"可查"，存文本是为了"快"。

```
组装 prompt
   │
   ├─ 切出 HEAD(原始) 与 TAIL
   │
   ├─ headHash = hash(HEAD原始 + 版本号 + 保护区指纹)
   │
   ├─ 命中？ 是 → 取缓存的 mapping[] → 应用到本次 HEAD → HEAD'
   │         否 → 调 LLM → 得 mapping[]（引用式映射表）
   │                → 持久化 {headHash → mapping[]} + 人可读决策日志
   │                → 应用 mapping[] → HEAD'
   │
   └─ prompt = HEAD' + TAIL
```

**缓存键（key）必须包含**：

1. `headHash` —— 头原始文本的哈希（变更即失效）；
2. **去重版本号** —— 算法/阈值改了必须让旧缓存全失效（否则用旧算法的结果跑新逻辑）；
3. **保护区分辨率** —— 作者原文变了（哪怕头哈希没变）也要失效。

**缓存值（value）**：`{ headHash, headOriginal, mapping[], headDeduped, algorithmVersion, createdAt }`。

> **为什么要存 `mapping[]` 而不是只存 `headDeduped`**（修订理由）：
> 只存结果 → 事后只能看"少了什么"，**看不出"为什么少"**；
> 存映射表 → 每一条删除都带着 `defendsTo`（作者原文依据），
> **日志可以直接打印成"删了这段，依据是作者第 X 条"** —— 这正是作者要的"结果可查的 log"（B1）。
> `headDeduped` 只是 `mapping[]` 的一个派生缓存，可以不存、每次重算（重算零 AI 成本）。

**存放位置**：随项目走（项目目录下），与既有诊断日志同族。
**不放进 `novel_config` / 数据库结构字段**——否则又变成"配置"，与 P4 的边界就糊了。

### 2.4 缓存与"直接删除"的关系

两者是**正交**的两个机制，不要混在一起设计：

- **缓存**决定「**要不要重新问 AI**」（省判定费）；
- **删除**决定「**问到了之后做什么**」（改 prompt）。

并且缓存**天然强化了可复现性**：同一 `headHash` 必然得到同一 `mapping[]`，
所以同一份头在多次请求中**删除结果完全一致** —— 这正好满足 §1.1 的 **B3（恢复路径可复现）**。
**缓存不只是省钱，它是"删除决策可复现"的实现手段。** 这一点很关键。

**另一个副作用（修订新增）**：因为缓存的是 `mapping[]` 而不是 `headDeduped`，
**作者改了 `worldbuilding` 原文但 HEAD 未变时**（例如作者手动编辑了推演结果），
映射表里的 `aiSeg` 索引会错位 → 所以 **`headHash` 必须包含被判定侧（AI 推演段）的指纹**，
不能只哈希作者侧。这是 §2.2 分层时必须一并确认的一点。

## 5. 验收

### 5.1 通用（每个 Phase）

1. **开关默认关**：不设 config 时 P3 完全不生效。
2. **降级不阻断**：判定失败时 prompt 原样发送，且有一条"已跳过"记录（B5）。
3. **回归**：`npx vitest run <相关文件>` 全绿 → `npx tsc --noEmit` EXIT=0 →
   全量扫描失败集与基线（18 个 ABI `NODE_MODULE_VERSION 145 vs 127`）**逐条 diff 一致**。

### 5.2 删除的验收（**不能用逐字计数**，backlog `:179`）

⚠️ **2026-10-11 修订：新增第 1 条（引用可核对）** —— 这是引用式判定带来的**更好的验收抓手**。

1. ★ **引用可核对**：映射表里每一条 `overlap: '复述'` 的条目，其 `defendsTo` 必须能在作者原文里
   定位到对应条目；构造"故意乱指"的映射，断言**被拒绝**。
   —— **这替代了"删了几段"的计数式验收**，成为 P3 的主验收指标（backlog `:179` 明确禁止用 P1 的逐字计数）。
2. **必删即记**：断言"删除发生 ⟺ 存在含原文全文的决策日志"（B1）。
3. **保护区零删除**：断言 `被删段集合 ∩ 保护区集合 = ∅`（B2）。
4. **`overlap != 复述` 的不删**：断言映射表里标为 `扩写` / `新增` 的段落**一律未被删除**（B6 的衍生约束）。
5. **其余内容逐字节不变**：断言"除被删段外，prompt 其余部分与未开启时逐字节相同"。
   —— 这是"删除是精确的、不是重写"的可证明形式。
6. **缓存一致性**：同一 `headHash` 两次请求 → 删除结果**完全一致**（§2.4）。
7. **未删不误伤**：构造语义相近但不重复的用例，断言**不被错删**。

### 5.3 缓存的验收

1. **命中不重判**：第二次同头请求**不产生**新的判定调用（断言调用次数）。
2. **变更即失效**：改 `globalGuidance` 一个字 → `headHash` 变 → 重新判定。
3. **版本号失效**：改去重算法版本号 → 旧缓存全失效。
4. **省下的量可测**：给出"前 N 章 / 后 N 章"的判定调用次数对比（验证作者的收益曲线假设）。

   → 而 P3 的**复杂度是常态化的**（每章都要跑判定、维护缓存、处理失效）。

3. **"风险还高"——对，而且风险点在最不该动的地方**。
   P3 的硬前置是**收据契约改造**（§1.3），那是 `main-generation-owner.ts` 的**安全边界**
   （防篡改 A 层必须保留）。**为 2.8–4.7% 的收益去动安全边界，不划算。**

### 8.4 ★ 如果仍要压这部分体积，有**成本低一个数量级**的替代方案

> **不要"智能去重"，直接"少注入"。**

P3 的思路是"把重复的挑出来删掉"；但既然这些是**固定的架构文本**，
更直接的做法是在**架构阶段就把注入策略定下来**：

| 方案 | 做法 | 成本 | 收益 |
|---|---|---|---|
| **A · 架构层去重（推荐）** | 在**架构生成时**（`architecture.command.ts`）就让 AI 不要复述已配置的字段，**从源头不产生重复** | **低**（改提示词合同，零运行时开销） | 同上 2.8–4.7%，但**无运行时成本、无缓存、无判定** |
| **B · 注入开关** | 既然作者手写了 `world_setting`，提供"推演侧只注入新增部分"或"完全用作者版" | 低 | 可到 20–47%（判定域全免） |
| **C · P3 语义去重** | 运行时 AI 判定 + 缓存 + 映射表 | **高** | 2.8–4.7% |

**A 和 B 的共同点：把问题解决在"产生时"而不是"消费时"。**
架构文本是**一次性生成、永久复用**的 —— 在生成时管住它，成本只在架构阶段发生一次。

### 8.5 建议

- **P3 暂缓**，不进入实施。保留本文档作为"已充分评估后决定不做"的记录。
- 若作者仍想压缩这部分体积 → **优先做 §8.4 的 A（架构层去重）**，它是零运行时成本的同类收益。
- **P3 的 §1.1.1「引用式判定」与 §2.4.7 的逐段比对结论仍然有效**，
  它们是**未来任何"处理 AI 推演文本"的改动**都必须遵守的约束（别删扩写、只删复述）。
- 释放出的精力建议投向**真正随规模增长的开销**（如 `chapter-materials` 的历史材料累积、
  或 pending 的 P4 零 AI 部分「当前实际生效」展示）。

## 9. ★ §8.4 方案 A 的**落地锚点已定位**（2026-10-11 续）

### 9.1 现场：约束存在，但**只管住了一半**

`src/services/builtin-prompt-templates.ts:474-530` 的 `world_building` 模板，
`content` 结尾的【要求】第 3 条（`:524`）：

> 「严格遵循故事前提、主角档案中的作者明确设定和全局写作要求；
> **无需机械复述与世界无关的角色事实**，但不得制造相反设定。」

**问题在加粗那半句**：它只约束了「**与世界无关的角色事实**」不要复述 ——
**却没约束「世界设定本身」**。

→ 所以 AI 的推理是：`core_setting`（= 作者的 `world_setting`）**正是"世界相关"的**，
   那它当然要"展开"；而展开时把它顺手重写一遍，**没有任何条款禁止**。

**这正是 §2.4.7 里那 565 字复述的来源。**

### 9.2 改法（方案 A 的具体形态）

**不动运行时、不动收据契约、不动测试。只改一个提示词模板的一句话。**

把 `:524` 从：

```
3. 严格遵循故事前提、主角档案中的作者明确设定和全局写作要求；无需机械复述与世界无关的角色事实，但不得制造相反设定。
```

改为（示意，措辞待作者定）：

```
3. 严格遵循故事前提、主角档案中的作者明确设定和全局写作要求。
   ★【核心世界观设定】已由作者给出，**它是权威版本、会原样随本章注入**；
   你的任务是**补全它没有覆盖的维度**（规则漏洞、阶层资源、终极灾祸），
   **不要复述或改写在【核心世界观设定】里已经写明的条目**。
   世界设定同样不需要机械复述；任何情况下都不得制造与作者设定相反的设定。
```

**为什么这条比 P3 好**：

| 维度 | 方案 A（改提示词） | P3（运行时语义去重） |
|---|---|---|
| 运行时成本 | **0** | 每章一次 AI 判定 |
| 缓存/失效管理 | **不需要** | 需要（且前期频繁失效） |
| 收据契约 | **不动** | **必须动**（安全边界） |
| 测试改动 | **0** | 6 处顺序断言 + 9 处 MISMATCH 断言 |
| 风险 | **低**（生成质量回归，可肉眼看） | **高**（误删 + 安全边界） |
| 覆盖面 | **只对新生成的项目生效**（存量项目需重新推演） | 对存量也生效 |

### 9.3 ⚠️ 方案 A 的**唯一代价**（必须如实说明）

**它只对"重新推演的世界观"生效，改不了存量。**

作者真实现有项目的 `worldbuilding` 已经是 2413 字（含 565 字复述），
改提示词**不会**让它自动变短 —— 除非作者**重新执行一次「世界观构建」**。

**→ 所以这是"面向新项目/新推演"的修复，不是"存量清理工具"。**

若作者希望**同时清理存量**，那才需要 P3 或一个**一次性的"重新推演"引导**
（提示作者"你的 `world_setting` 更新过，要不要重新推演 `worldbuilding` 以应用新约束"）。

### 9.5 ★ 项目内**已有现成范式**可对齐（这条让方案 A 更像"补一致"而非"新发明"）

搜索 `builtin-prompt-templates.ts` 里的「复述」用法，发现约束**已经存在**，
只是**没有覆盖到 `world_building` / `premise` / `synopsis` 这三个模板**：

| 位置 | 已有约束 | 覆盖对象 |
|---|---|---|
| `:273` | 「禁止逐章列大纲或**复述 coreOutline**，全文不超过 600 字」 | 扩写 `globalGuidance` 时 |
| `:304` | 「globalGuidance 只写跨章节长期有效的执行规则，禁止逐章列大纲、分配章节区间或**复述 coreOutline**」 | 同上 |
| `:322` | `"…禁止逐章列大纲、分配章节区间或**复述 coreOutline**"` | 同上（JSON schema 描述） |

| — | **无** | ❌ `premise` 模板 |

**→ 系统的设计原则其实已经明确**：**"字段 A 的生成任务里，不得复述已存在的字段 B"**。

`core_setting`（作者的 `world_setting`）或 `premise`，却没有任何"别复述它们"的条款。

**→ 所以方案 A 的正确定位不是"新增功能"，而是「补齐一致性」**：

**这大幅降低了方案 A 的风险** —— 它不是引入新机制，而是**把项目自己已经确立的约束推广完整**。
