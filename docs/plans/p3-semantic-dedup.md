## 0.0 先纠正一个会决定方案方向的技术误解 ★

作者的设想里有一句：

> 「在后续请求的时候，先在本地做校验，如果和上一次的 Prompt 头没有差别，
> **那就不用去做预请求**，直接从本地取上一次修改完的版本做替换。」

**这句话的前提不成立。** 我核实了这三点：

1. **「Prompt 头」本来就已经是本地字符串。** `composeInitialPrompt`
   （`generate-draft.command.ts:997-1000`）和 `draftAuthorMaterialBlock`（`:561-626`）
   都是**纯字符串拼接**，组装过程**没有任何 AI 调用**。
2. **续写/压缩请求已经复用了同一份头**。`draftAuthorMaterialBlock` 在续写
   （`:1609`）与压缩（`:1799`）时是**调用同一个函数**，`systemRole` 也是同一份
   （`:1662` 的 `params.systemRole`）。
   也就是说——**「保持一致」这件事今天就已经做到了**，靠的是"每次都重新拼一遍同样的字符串"。
3. 所以**重跑拼接的代价是零**：不是省钱的问题，因为它**压根不花钱**。

→ **结论**：作者真正想省掉的那个"预请求"，在当前架构里**不存在**。
但作者的核心直觉——**「中后期共通设定稳定，就该复用它，不该重新判定」**——是**完全正确**的，
只是它要解决的问题不是"省一次预请求"，而是**"别重新花钱重新问 AI 一遍"**（见 §0.1）。

> 🚨 **这一条如果不纠正，方案会做反**：会去实现一个"缓存拼接结果"的机制，
> 而真正的成本大头（LLM 语义判定）反而被漏掉。

## 0.1 成本账：钱花在哪，缓存才花得值

P3 与 P1 的根本区别是：**P1 的判定是零成本本地指纹，P3 的判定必须花钱（LLM 或 embedding）。**

所以"语义去重开不开"的决策，本质是一道成本算术题：

| 场景 | 不做去重 | 每次请求都重新判定 | **缓存判定结果（作者方案）** |
|---|---|---|---|
| 头内容**未变**（中后期常态） | 多带几段重复内容 | **每次都多花一次判定费** ← 最差 | 只花一次哈希比对（≈0）**← 作者方案胜** |
| 头内容**变了**（前期常态） | 多带几段重复内容 | 多花一次判定费 + 少带重复 | 多花一次判定费 + 少带重复 |

**这张表说明**：作者的直觉在成本上是**对的**，而且**恰好补上了 P3 最大的软肋**——
即"为了省几百 token，每轮多花一次 LLM 调用"这种**净亏**。把判定结果缓存下来、
只在头变化时重判，是这个方案能成立的**前提**，不是一个可选项。

**并且它自动实现了作者关心的"前期收益小、中后期收益大"的曲线**：
前期的头频繁变动 → 缓存频繁失效 → 每次都重判（无明显收益，但也不亏）；
中后期的头稳定 → 缓存长期命中 → 判定费趋近于零，只省不花。

## 0.2 作者方案的真实价值定位

把它翻译成准确的技术描述：

> **不是「省一次预请求」，而是「把一次 LLM 语义判定摊销到多次请求上」。**

- **收益来源**：LLM 判定费的**摊销**（省的是"判定"，不是"拼接"）。
- **收益曲线**：与头的**稳定性**正相关（作者的判断正确）。
- **前提条件**：头必须能被**确定性哈希**（否则缓存无法命中）。
- **失效条件**：头一变，缓存作废，重新判定。

⚠️ **一个必须提前说清的坏消息**：见 §2 —— 在**当前**的组装方式下，头**几乎每章都会变**
（因为 `chapterMaterials.text` 里含上一章正文）。所以这个缓存的收益
**在现有架构下会小于作者的预期**。但这不是方案的问题，而是**切分粒度**的问题，
可以修（§2.2）。**这一条我建议单独拍板，因为它可能要动 `chapter-materials.ts`。**

## 1. 三项决策的逐条落实

### 1.1 决策一 · 「直接判定并删除 + 可查 log」→ 接受，但要加硬边界

作者：*「可以直接判定并删除，但是要做好结果可查的 log，方便后续改进。因为这个可以在设置里提供开关，所以我觉得风险是可控的。」*

**我接受，理由如下**（并且我承认 v1 稿在这一条上过于保守）：

- 作者的"开关 = 风险可控"论证是成立的 —— 开关在作者手里，且**默认关**。
- "结果可查的 log"补上了 v1 稿最担心的那个洞（**不可观测**）：
  只要每次删除都有完整记录，作者就能在出现问题时回溯、调整、关掉。

但**硬边界不能让步**（这些不是"保守"，而是 ADR 0020 的直接要求）：

| # | 硬边界 | 理由 |
|---|---|---|
| **B1** | **必删即记**：任何被删除的段落，必须有一条包含**原文全文**的日志。无日志 = 不允许删。 | 没有它"可查"就是空话；原文不记则事后无法判断删得对不对。 |
| **B2** | **保护区不参与自动删除**：作者原文段（`project_core.*` / `novel_config.*` / 作者本章指导 / 角色卡作者字段）**只报告、不删除**。 | ADR 0020「绝不删除作者事实或红线」。 |
| **B3** | **恢复路径（resume）不删**：resume 时必须复现首次的删除决策。 | 否则 `GENERATION_DRAFT_RECOVERY_AUTHOR_INPUT_CHANGED` 可能触发（§3.4）。 |
| **B4** | **删除是"改写进 prompt"，不是"改数据"**：不改 `chapter-materials.ts` 的构成、不改 `toWriterChapterInfo`。 | 守住 §3.2 / §3.3 的冻结护栏。 |
| **B5** | **降级不阻断**：判定失败（无网 / 无模型 / 超时 / 解析失败）→ **原样发送，不做去重**，并记一条"已跳过"。 | 去重是优化，不能变成生成失败的原因。 |

### 1.2 决策二 · 提示词头缓存 → 接受，见 §2

### 1.3 决策三 · 「promptHash 收据契约直接改掉」→ **部分接受，但必须保留核心**

作者的判断：

> 「promptHash 收据契约直接改掉吧，这个就不合理，对使用者的要求太高了，很容易造成Prompt膨胀。」

**我同意"当前形态对作者的约束过强"这个判断**，但**不能按"直接改掉"理解**。
必须把它拆成两层看清楚，因为其中一层**必须保留**：

| 层 | 作用 | 例子 | 该不该动 |
|---|---|---|---|
| **A · 防篡改** | 渲染层不能"夹带任意内容"发给模型 | `main-generation-owner.ts:1239` 的 `'smuggle'` 用例：`${reconciledPrompt}\n\n夹带内容` → 拒绝 | **必须保留** |
| **B · 防漂移** | 作者改了配置后，用旧收据重发 → 拒绝 | `test.ts:924`：`composed + '改目标'` → 拒绝 | **可以放开** |

**作者说的"对使用者要求太高"，指的是 B 层。B 层确实过强**——
它假定"收据里的 prompt 必须与最终发送的 bytes 完全一致"，
而 P3 的去重天然要改 bytes。

**但 A 层的存在意义不是"为难过作者"，而是"渲染层不能自由构造发给模型的 prompt"**。
若直接删掉整个契约，任何渲染层代码（或注入的第三方代码）都能自由拼 prompt 发给模型，
**这是安全边界，不是流程洁癖**。

**→ 我的建议（这是 §5 最需要作者拍板的一条）**：

把契约从「**byte 精确**」改为「**可归因**」：

- 收据里不再存「prompt 的哈希」，而是存「**组装后的头原文 + 去重决策**」；
- 发送前校验：**发送内容 = 头原文 经过 决策 变换后的结果**（可重放验证）；
- 这样：P3 的删除是**在收据里声明的决策**，不是"擅自改 bytes"，**A 层护栏保留**，
  同时 **B 层的过强约束被解除** —— 作者的诉求达成。

> ⚠️ **代价必须说清**：这条改动会动 `main-generation-owner.ts` 与 `generate-draft.command.ts`
> 的**收据生产/消费两侧**，是 P3 里**最大的一块工作量**。
> 并且 `main-generation-owner.test.ts` 里**有 9 处 `GENERATION_MATERIAL_PROMPT_MISMATCH` 断言**
> （`:918`、`:924`、`:1201`、`:1240`、`:1242`、`:1262`、`:1281`、`:1288`、`:1291`），
> **必须逐条判断**：哪些是 A 层（要保留、要改写断言）、哪些是 B 层（可以放开）。
> **不能一把删掉**——那是把安全护栏和流程约束一起扔了。

## 2. 头缓存方案设计（作者决策二）

### 2.1 结构：怎么定义"Prompt 头"

先把 prompt 切成两半：

| 半 | 内容 | 是否稳定 | 是否进缓存 |
|---|---|---|---|
| **头（HEAD）** | 共同设定：`architecture` / `novel_config` 事实 / `globalGuidance` / 文风 / 角色档案 / 后续计划边界 | **相对稳定**（中后期几乎不动） | ✅ |
| **尾（TAIL）** | 本章个性化：章节蓝图 JSON / 本章已写正文 / 篇幅合同 / 对账块 / 续写指令 | **每章必变** | ❌ |

**用作者的话说**：头 = 「共同设定那些，不包含章纲等个性化生成特定的内容」。

### 2.2 ⚠️ 头必须"提纯"，否则缓存永远不命中（关键设计点）

**这是本稿新增的一处、也是作者方案落地前必须解决的一处。**

我核实 `draftAuthorMaterialBlock`（`:561-626`）的构成：

```
【本章蓝图】{ json }              ← TAIL（每章必变）
【全局写作要求】{ globalGuidance }   ← HEAD
【文风要求】{ writingStyle }        ← HEAD
【文风适用边界】{ 固定文本 }         ← HEAD
【小说配置事实】{ novelConfigFacts } ← HEAD
{ chapterMaterials }              ← ⚠️ 混合！见下
{ reconciliation }                ← TAIL
{ authorItems }                   ← TAIL
```

**问题在 `chapterMaterials.text`**：它是 `assembleChapterMaterials`
（`generate-draft.command.ts:941-959`）的产物，`finalized` 参数传的是
`finalizedSources`（含**上一章定稿正文**，`:928-932`）。
即：**`chapterMaterials.text` 里混着"上一章正文"，它每章必变。**

→ **若把头定义为"去掉蓝图和已写正文"，`chapterMaterials.text` 仍是每章必变 → 缓存每章都失效 → 收益归零。**

**解法（两条路，需作者选）**：

| 路径 | 做法 | 代价 |
|---|---|---|
| **H1 · 提纯** | 把头定义为"**从 `chapterMaterials.text` 里剔除 finalized 段之后**的部分"（即只保留作者资料 / 角色档案 / 后续计划边界） | 需动 `chapter-materials.ts` 的段落隔离，**有可能触碰 hash 与覆盖缺口日志**（§3.3），且是 P1 明确克制没动的区域 |
| **H2 · 保守** | 头只取**本来就独立于 chapterMaterials 的那部分**（`globalGuidance` / 文风 / `novelConfigFacts` / `architecture`），**不动 `chapter-materials.ts`** | **改动面小、零风险**；但缓存覆盖的头部体积**较小**，收益打折 |

**我的建议：先 H2，量出真实收益，再决定要不要做 H1。**
理由：H2 零风险且能立刻验证"缓存到底省了多少"；H1 要动 P1 刻意绕开的区域，
**在没有数据前不该动**（这与 P1 §3.4 的"没有数据不动手"是同一条纪律）。

### 2.3 缓存流程

```
组装 prompt
   │
   ├─ 切出 HEAD(原始) 与 TAIL
   │
   ├─ headHash = hash(HEAD原始 + 版本号 + 保护区指纹)
   │
   ├─ 命中？ 是 → 取缓存的 HEAD(去重后)  →  HEAD' = 缓存值
   │         否 → 调 LLM 判定 → 得 HEAD' →  持久化 {headHash → HEAD'} + 决策日志
   │
   └─ prompt = HEAD' + TAIL
```

**缓存键（key）必须包含**：

1. `headHash` —— 头原始文本的哈希（变更即失效）；
2. **去重版本号** —— 算法/阈值改了必须让旧缓存全失效（否则用旧算法的结果跑新逻辑）；
3. **保护区分辨率** —— 作者原文变了（哪怕头哈希没变）也要失效。

**缓存值（value）**：`{ headHash, headOriginal, headDeduped, decisions[], algorithmVersion, createdAt }`。

**存放位置**：随项目走（项目目录下），与既有诊断日志同族。
**不放进 `novel_config` / 数据库结构字段**——否则又变成"配置"，与 P4 的边界就糊了。

### 2.4 缓存与"直接删除"的关系

两者是**正交**的两个机制，不要混在一起设计：

- **缓存**决定「**要不要重新问 AI**」（省判定费）；
- **删除**决定「**问到了之后做什么**」（改 prompt）。

并且缓存**天然强化了可复现性**：同一 `headHash` 必然得到同一 `HEAD'`，
所以同一份头在多次请求中**删除结果完全一致** —— 这正好满足 §1.1 的 **B3（恢复路径可复现）**。
**缓存不只是省钱，它是"删除决策可复现"的实现手段。** 这一点很关键。

## 5. 验收

### 5.1 通用（每个 Phase）

1. **开关默认关**：不设 config 时 P3 完全不生效。
2. **降级不阻断**：判定失败时 prompt 原样发送，且有一条"已跳过"记录（B5）。
3. **回归**：`npx vitest run <相关文件>` 全绿 → `npx tsc --noEmit` EXIT=0 →
   全量扫描失败集与基线（18 个 ABI `NODE_MODULE_VERSION 145 vs 127`）**逐条 diff 一致**。

### 5.2 删除的验收（**不能用逐字计数**，backlog `:179`）

1. **必删即记**：断言"删除发生 ⟺ 存在含原文全文的决策日志"（B1）。
2. **保护区零删除**：断言 `被删段集合 ∩ 保护区集合 = ∅`（B2）。
3. **其余内容逐字节不变**：断言"除被删段外，prompt 其余部分与未开启时逐字节相同"。
   —— 这是"删除是精确的、不是重写"的可证明形式。
4. **缓存一致性**：同一 `headHash` 两次请求 → 删除结果**完全一致**（§2.4）。
5. **未删不误伤**：构造语义相近但不重复的用例，断言**不被错删**。

### 5.3 缓存的验收

1. **命中不重判**：第二次同头请求**不产生**新的判定调用（断言调用次数）。
2. **变更即失效**：改 `globalGuidance` 一个字 → `headHash` 变 → 重新判定。
3. **版本号失效**：改去重算法版本号 → 旧缓存全失效。
4. **省下的量可测**：给出"前 N 章 / 后 N 章"的判定调用次数对比（验证作者的收益曲线假设）。
