# P1 设计稿 · `user_guidance` 拆解与缓存分区

> 目标读者：作者（审阅者）。本稿只做**设计与判据论证**，不含实现。
> 依据代码：`generate-draft.command.ts`、`builtin-prompt-templates.ts`、`ChapterCardEditor.tsx`（均为 dev_byf 当前状态）。

---

## 0. 结论先行（TL;DR）

方案文档 §13 把第 6 项排为 P1，理由是「`user_guidance` 占 prompt 约 36%，上浮到缓存区可省钱省延迟」。
**我按代码逐条核对后，发现这个前提站不住**，如实报告：

| §13 原假设 | 代码事实 |
|---|---|
| `user_guidance` 是一个能装大量通用规范的**大字段**，占 36% | 它是**章节蓝图里的单章字段**（`ChapterCardEditor` 一个 3 行 textarea），语义是「本章微操」，典型 1–2 句 |
| 它排在可变后缀区，是「最大单一变量段」 | 它确实在**最末尾**（systemSuffix 里），但**体量小**，不是体积大头 |
| 把它拆开上浮能省钱 | **拆不动**：它的内容按定义就是逐章变化的，没有可上浮的稳定部分 |

**因此 P1 的正确形态不是「拆 `user_guidance`」，而是「诊断真正的体积大头，然后针对真问题下手」。**
本稿给出真实归因，并给出 3 个候选方向供你选。

## 1. 现状还原：prompt 究竟长什么样

单次写稿请求 = `system` + `user` 两条消息（`generate-draft.command.ts:797-814` 构建，`BasePromptBuilder.build()` 渲染）。

### 1.1 `system` 消息（`template.systemSuffix` + 执行合同）

```
systemRole（角色定位，短）
systemSuffix:
  【不可偏离的作者事实】
    - 小说配置：{novel_config JSON}          ← promptOnlyConfigKeys 已剔除 7 个字段
  【文风适用边界】
  ★【作者对本步骤的额外指导（如有，最高优先级）】★：
    {{user_guidance}}                        ← ★ 就是我们讨论的这个字段
  【具体生成要求】 ……
  （+ appendRequiredPromptContext 兜底）
```

### 1.2 `user` 消息（`template.content` 逐变量替换）

```
【全书设定池】 {{architecture}}
【本章信息】   {{chapter_info}}          ← JSON，含 userGuidance 等 8 个字段
【后续章节大纲预告】{{future_blueprints}}
【全局写作要求】{{global_guidance}}
【网文创作法则】…（静态长文）
【文风要求（如有）】{{writing_style}}
【参考作品（如有…）】{{reference_works}}
```

### 1.3 两个关键事实（决定优化空间）

**事实 A — `user_guidance` 被注入了两遍。**

- 第一遍：`system` 尾部的 `★【作者对本步骤的额外指导】★`（`:810` 显式 `withUserGuidance`）；
- 第二遍：`user` 的 `【本章信息】` JSON 里含 `userGuidance` 字段（`toWriterChapterInfo` `:322-333` 把它带进去了），
  并且 `【本章执行合同】` 里又把它拆成 `- 作者本章指导: …` 一行（`:482`、`:484`）。

同一段作者文字在单次 prompt 里**出现 3 处**。这是本轮唯一能确定性拿到的收益——**纯去重，零风险**。

**事实 B — `user_guidance` 不是 36%，`architecture` + `chapter_materials` 才是。**

`architecture`（`readArchitecture()`，经第 2 项去重后）承载 premise/worldbuilding/synopsis；
`:517-524` 还会把 `authoredConfigFacts`（coreOutline/worldSetting/goldenFinger/protagonistProfile）
作为【作者资料】注入 `chapterMaterials`。这两块才是体积主力。

> **§13 的 36% 从何而来**：我复核了当时的量算——那是把 `globalGuidance + user_guidance + 执行合同的静态长文`
> 合起来按「逐章可变」归类后得到的比例，不是 `user_guidance` 单字段的占比。是我在写 §13 时表述不准，
> 这里更正。**据此，P1 需要重新定义。**

## 2. 为什么「拆解 `user_guidance`」技术上不成立

§13 原方案想做的事是：把 `user_guidance` 里「通用写作规范」上浮到缓存命中区、「本章微操」留在后缀区。

**这条路走不通，因为它假设了字段里混有两类内容，而实际上作者 UI 只提供了一个文本框，且提示语明确写入的是「本章」语义：**

> `（写稿时会作为最高优先级注入 AI — 可覆盖蓝图）`
> 占位符：`我想在这章加入一个意外的背叛… / 让反派在这章露出破绽… /（不填则完全按蓝图走）`
> —— `ChapterCardEditor.tsx:1182-1196`

作者往这个框里写的**按定义就是本章专属指导**。它逐章变化是设计意图，不是缺陷。
把「逐章变化」的东西上浮到「跨章稳定」的缓存前缀区，**逻辑上自相矛盾**。

即便强行做内容级启发式切分（用正则/小模型判断哪些句子是「通用规范」），也会因为：
- 误判会把本章专属指导污染进跨章前缀 → **后面所有章节的缓存全部失效**，比现在更差；
- 违背 ADR 0020「不删减作者事实」的精神（重排作者原文顺序、拆分语义单元属于事实改写）。

**结论：§13 的第 6 项按原描述应当废弃或重写。** 下节给出替代方案。

## 3. 真实问题清单与候选方向

### 3.1 已确认的真实问题（按收益/风险排序）

| # | 问题 | 证据 | 性质 |
|---|---|---|---|
| **R1** | `user_guidance` 三处重复注入 | `system` 尾部 + `【本章信息】` JSON + `【本章执行合同】` 行 | 纯冗余，可删 |
| **R2** | `【本章信息】` 的 JSON 序列化本身臃肿 | `JSON.stringify(writerChapterInfo, null, 2)` 带缩进和 key 名；`userGuidance` 已在别处单独出现 | 体积优化 |
| **R3** | `architecture` ↔ `【作者资料】` 字段级重复**尚未处理** | 第 2 项只做了**逐字段落**去重；`coreOutline` 与 `premise` 语义重叠但措辞不同，仍双份 | 语义级，风险高 |
| **R4** | 缓存前缀被 `chapter_info` / 合同截断 | `withChapterInfo` 之后的内容每章都变，但其后还有 `future_blueprints`、`user_guidance` 等 | 结构问题 |

### 3.2 三个候选方向

#### 方向 A（推荐）· 消除 R1：`user_guidance` 单点注入

**做法**：确立「`user_guidance` 只在一个位置出现」这一不变量。保留 `system` 尾部那份（作者语义上最贴近「最高优先级指导」的定位，且已与执行合同解耦），
从 `【本章信息】` JSON 与 `【本章执行合同】` 的 `作者本章指导` 行中移除。

**收益**：确定性 100%（同一段文字从 3 份降到 1 份）。若作者写了 500 字指导，单次省约 1000 字。
**风险**：低。但要处理 `【本章执行合同】` 的语义——它原本把 `必需事件 / 章节钩子 / 作者本章指导` 并列为「作者本章任务」，
移除后需要确认「作者指导」的执行约束力没有被削弱（**这是本方向唯一的实质风险点，见 §4**）。

#### 方向 B · 消除 R2：`chapter_info` 压缩

**做法**：`【本章信息】` 改用紧凑序列化（去缩进），或改成结构化清单（`- 标题: X\n- 关键事件: Y`）而非 JSON。
**收益**：确定性中等（每个 key 名 + 缩进约省 15–25%）。
**风险**：中。JSON 是给模型看的强结构信号，改成缩进/清单可能影响模型对字段边界的理解，**需实测**。

#### 方向 C（暂缓）· 处理 R3：语义级跨段去重

**做法**：用 AI 判定 `coreOutline`/`worldSetting` 与 `premise`/`worldbuilding` 的语义重叠并合并。
**收益**：可能是最大的一块（第 2 项实测 26% 冗余，逐字去重只吃掉了其中一部分）。
**风险**：**高**。改写作者原文 = 触碰 ADR 0020 红线；且需要额外 AI 调用（预请求），正是被打入 P3/P4 的那类。
**建议**：**本期不做**。它和方案文档第 7/8 项（A 类固化 / B 类预请求去重）是同一件事，应在那两项里统一设计，不要在这里偷做。

## 4. 推荐方案：方向 A 详细设计

### 4.1 不变量（Invariant）

> **每次写稿请求中，`user_guidance` 的作者原文恰好出现 1 次，且位于 `system` 末段。**

### 4.2 需要改的点

| 位置 | 现状 | 改为 |
|---|---|---|
| `toWriterChapterInfo()` `:322-333` | 把 `userGuidance` 放进 `WriterChapterInfo` | **移除该字段**（`WriterChapterInfo` 类型同步去掉 `'userGuidance'`） |
| `chapterExecutionContractText()` `:479-485` | `executionItems` 含 `作者本章指导` | **移除该项**，只保留 `必需事件` + `章节钩子` |
| `template.systemSuffix` | `★【作者对本步骤的额外指导】★：{{user_guidance}}` | **保持不动**（唯一注入点） |
| `draftAuthorMaterialBlock()` `:512-563` | `JSON.stringify(material.chapterInfo)` 会带出 `userGuidance` | 随 `WriterChapterInfo` 类型变更自动消失 |
| `recoveryChapterSource()` `:565-576` | `userGuidance` 用于恢复对账 | **保留**（恢复路径需要它做 hash 对账，不属 prompt 组装） |

### 4.3 语义保全（这是关键，必须解决）

移除 `【本章执行合同】` 里的 `- 作者本章指导: …` 行后，**「作者指导 → 必须执行」这个约束链会不会断？**

**现有约束链**（`:489-497` 的 `rules`）写的是：
> 【作者本章任务】按作者原文含义遵循：明确要求在本章发生的事件与收束须由正文动作或结果落实……

它约束的是「作者本章任务」整体，而任务清单 = `必需事件 + 章节钩子 + 作者本章指导`。
**如果清单里不再有「作者本章指导」，这段 rules 就管不到它了** —— 这是真实风险。

**两种保法（择一，建议 ①）**：

- **① 收紧 rules 措辞**：把 `【作者本章任务】` 的第一句改为显式覆盖 system 段的指导，例如
  「按作者原文含义遵循**上文★额外指导★与下列条目**：……」。
  → 零新增体积，约束链重建，**推荐**。
- **② 保留清单行、只删 JSON**：即只做 `【本章信息】` JSON 的去重（3 份降 2 份）。
  → 更保守，但收益减半。

### 4.4 验收标准

1. `user_guidance` 在单次请求的所有消息里 `match(/原文片段/g)` 恰好 **1** 次（这是可写成断言的硬指标）。
2. `【本章信息】` / `【本章蓝图】` 的 JSON 中**不再出现** `"userGuidance"` key。
3. `【本章执行合同】` 的 `作者本章任务` 段仍然约束作者指导（用「措辞覆盖」测试验证，而非仅测存在性）。
4. 全部既有测试通过；失败集与基线逐条 diff 一致。
5. `tsc --noEmit` EXIT=0。

### 4.5 工作量与影响面

- 主改：`generate-draft.command.ts`（约 4 处，均是小范围）；
- 连带：**至少 6 个测试会红**，需要同步（我已定位）：
  - `:1519`、`:1571` 断言 `- 作者本章指导: …` 存在；
  - `:1524`、`:4255` 断言 system **不含** 作者文字（现在含了，方向反转）；
  - `:4243`/`:4257` 相关；
  - `:4288` 首章注入用例。
- 预计净收益：**单次请求省 1 份作者指导全文**，纯减法，无新依赖。
