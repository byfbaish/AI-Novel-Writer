**这份报告是迄今为止三份外部材料里**最贴合我们当前进度**的一份 ——

### 评价总表

| 报告主张 | 与我们的关系 | 评价 |
|---|---|---|
| ① 弧的核心是"可验证的因果-时序结构"，不是"一段描述" | **完全一致** | ✅✅ **命中要害，应该吸收进 Prompt 设计** |
| ② 弧要分类型（因果驱动 / 目标驱动 / 探索） | **新增且有用** | ✅ 这是一个我们**没想过**的真洞见 |

## 1. ✅ 报告最值钱的一句：**"结构定了，逻辑推进就定了；结构没定，AI 给你漂亮废话"**

这与作者第四轮的纠正**是同一件事**：

| 来源 | 表述 |
|---|---|
| **作者第四轮** | 「真正要关注的是，同级弧是有**因果、时序**等事件推进逻辑的」 |
| **本报告** | 「弧生成的核心不是'让 AI 写一段弧的描述'，而是'让 AI 输出一个**可验证的因果-时序结构**'」 |
| **我们文档 §2.2** | 「为每一个同级弧说明它**为什么接在前一个弧之后**……答不出来就是断链」 |

**→ 三者在说同一个设计意图。报告的贡献是：它把"怎么把因果写进 Prompt"具体化了。**

### 1.1 ★ 报告独有的真洞见：**弧要分三种因果类型**（这是我们没想过的）

报告的 §1 是整个文档里**最有价值的一节**，因为它指出了我们 §2.2 的一个疏漏：

**我们写的推进要求是**单一模板**："逐弧交代因果/时序"——
但报告指出，**不是所有弧都走因果链**，套一个模板会让"探索型弧"（比如休整区、日常）被强行加上伪因果。**

| 弧类型 | 特征 | 该给的 Prompt 结构 | 命中我们文档哪里 |
|---|---|---|---|
| **A 因果驱动型** | A→B→C 链式 | 每事件标 `前置事件 + 因果说明` | ✅ §2.2 现在写的正是这个 |
| **B 目标驱动型** | 目标→尝试→结果→再尝试 | `目标-尝试-结果` 三元组 | ❌ 我们**没有** |
| **C 探索型** | 空间/人物并列遭遇 | `探索路径 + 节点发现` | ❌ 我们**没有**，且**误把它当因果弧会写坏** |

**→ 这是本报告应该被吸收的**唯一硬增量**：**
**§2.2 的推进要求不应是一句话，而应是"先判断弧类型，再套对应结构"。**

**★ 但要提醒：报告举的例子（arc1 因果型 / arc2 目标型 / 休整区探索型）恰好对应我们文档 §3.1 示例
里的"大弧 1/2/3" —— 也就是说，这一层判断**不需要新字段**，
只需要在生成 Prompt 里加一句"先判断本弧属于哪种类型，再按对应结构组织"。** 与"无字段"定性不冲突。

## 2. ❌ 报告的手段与作者已定形态**正面冲突**（必须先说清楚）

报告全篇建立在**三个技术假设**上，而这三个假设**本项目一个都不成立**：

| 报告假设 | 本项目的现实 | 结论 |
|---|---|---|
| 弧有 `state_in` / `state_out` 且**必须相等衔接** | 我们**没有**弧级 state 表；作者明确"弧不绑章号、不管角色" | ❌ 无法实现 |
| 有 `character_knowledge`（角色知识状态表） | **完全没有**（`state-tracking-assessment.md §2.1` 已确认这是唯一纯空白） | ❌ 表不存在 |
| 有 `item_state`（独立道具表） | **没有**（只有 `characters.cs_key_items` 文本字段） | ❌ 表不存在 |
| 有 `foreshadowing_state`（伏笔状态表） | ✅ **有**（`narrative_thread_plans` + 四态 confirmations） | ✅ 唯一成立 |

**→ 报告的六项"结构验证"里，有四项的校验对象在本项目**根本不存在**。**
所以它的验证机制不是"可落地性打折"，而是**建立在一个我们没打算建的抽象之上**。

### 2.1 ★ 最根本的冲突：**YAML 固定字段 vs 作者的"不需要字段"**

报告 §3/§4/§5 给了三套完整的 YAML schema（arc 骨架 18 个字段、event 10 个字段、chapter 9 个字段）。
**这与作者的原话直接矛盾：**

> 作者：「**不需要什么字段不字段的**，故事弧跟情节大纲其实相似度非常高，**基本上属于 Prompt 约束**」

**→ 而且本项目**已经有先例证明这个判断是对的**：**

| 现有模块 | 输出格式 | 是否有独立表 |
|---|---|---|
| `synopsis`（情节大纲） | **纯文本** `## 第N章`（`plot-outline-contract.ts`） | ❌ 无（存在 `project_core.synopsis` 一段文本里） |
| `chapter_blueprint`（章节蓝图） | **JSON 严格数组**（`builtin-prompt-templates.ts:638`） | ✅ 有 `blueprints` 表 |
| 角色卡提取 | **JSON 严格对象**（`:996`/`:1176`） | ✅ 有 `characters` 表 |

**→ 规律很清楚：**需要**逐条被下游消费/校验**的（蓝图、角色卡）才上 JSON + 表；
只需要**作为上下文注入**的（大纲、世界观）就是纯文本。**

**弧属于后者**（作者已定性：它**约束**大纲，不被逐条消费），**所以它就该是纯文本。**
报告的 YAML 方案会把弧从"上游引导文本"升级成"需要维护的结构化实体"——
**这正是作者三次纠正要避免的方向。**

## 3. ⚠️ 报告的三步流水线：**第 3 步已是现状，第 1/2 步是"要不要拆"的问题**

报告主张：

```
Step 1：弧骨架生成
Step 2：弧内事件链生成
Step 3：章级拆分（交给现有情节大纲模块）  ← 报告自己说"交给现有模块"
```

### 3.1 ✅ 报告对第 3 步的判断是**准确的**（我们有代码佐证）

`architecture.command.ts:2262` 的 `executeChapterOutline` 确实是**分批、可断点续写、
带 checkpoint 的循环**（`while (outline.cursor.kind !== 'complete')` +
`saveNavigation()` 存 `synopsis_covered_to` / `synopsis_body_hash`）。
**它本来就是一个"把结构逐章展开"的成熟模块** —— 报告说"交给现有模块"完全正确。

### 3.2 ⚠️ 但第 1/2 步"要不要为弧单开两步"，报告的论证**不成立**

报告的理由是："一条 prompt 同时做，AI 容易在骨架还没立稳时就跳进细节。"

**→ 这个担心本身合理，但本项目已有两种现成的应对方式，不需要为此新建两个生成步骤：**

| 现成机制 | 位置 | 作用 |
|---|---|---|
| **Step 冻结 + 单步重生成** | 架构阶段的分步管线 | 弧作为**一步**生成，可单独重新生成（同 worldbuilding） |
| **Step guidance 注入** | `architecture:step-guidance:synopsis` | 作者可在生成前追加"先立骨架再展开"的指令 |
| **map-reduce 分批** | `executeChapterOutline` 已有的批处理 | 长结构的"一段一段写"能力已存在 |

**→ 建议：弧生成保持"一步产出整段结构文本"，但**在 Prompt 内部用**分节指令**
模拟报告的三段（先定类型 → 再列事件链 → 再标推进关系），而不是拆成三个 DB 步骤。**

**★ 理由：拆步会增加 3 倍的管线改动（每步都要 checkpoint/指纹/UI 卡片），
而收益（"骨架立稳"）用 Prompt 内分节就能拿到 90%。**

## 4. ❌ 报告的验证机制：**方向对，但项目已有更好的等价物**

报告的"三层验证"（结构脚本 / AI 语义 / 人工）里，**前两层本项目已经在别处实现了，
而且做得比报告设想的更严谨**（见 `state-tracking-assessment.md §1.2`）：

| 报告提议 | 本项目现状 | 差别 |
|---|---|---|
| 结构验证：事件 causes 拓扑有序 | ❌ 无（弧不结构化） | 报告方案需要先上 YAML，代价大 |
| **语义验证：AI 检查"因果是否合理"** | ⚠️ **部分**：`consistency-preflight.ts` 已有一条确定性规则 | 报告想扩到 6 条，但对象表不存在 |
| **人工审核** | ✅ 有（`consistency_exemptions` 允许作者标"不算矛盾"） | 我们已有**豁免机制** |
| **"每条事实必须能溯源到原文"** | ✅✅ **已强制实现** | `finalized-continuity-facts.ts:22` `evidenceExcerpt()` |
| **"陈旧检测"** | ✅✅ 已实现 | `continuity_projection_meta.stale_from_chapter` |

**→ 报告的验证哲学（"可溯源、可检测陈旧、可人工豁免"）本项目**已经全有**，
只是**它作用在"已写正文"上，而报告想让它作用在"未写弧"上。**

**★ 这里有一个**真正的机会**，但报告没说准：**
把现有的 `consistency-preflight`（现在只有 1 条规则、只检查 `character-state`）
**扩成一组"弧级/章级结构规则"** —— 例如：
- "弧声明的因果链里，前置弧是否真的存在"（**同级弧引用完整性**）
- "弧声明的'伏笔回收'，`narrative_thread_plans` 里是否真有这条"（**跨层引用完整性**）

**→ 这才是"可验证"在本项目的**正确落点**：不新建 YAML，而是让已有的 preflight 去**读弧文本 + 比对已有表**。**

## 5. ⚠️ 报告最不可行的一点：**人工 30–45 分钟/弧**

报告给出"骨架 5-10 分 + 事件链 10-15 分 + 章拆分 5 分 + 正文 10-15 分 = 30-45 分钟/弧"。

**→ 问题：它假设的是"逐弧手审"的工作流。**
我们面对的是**800 章 / 约 20–40 个弧**的长篇 —— 若逐弧手审 30 分钟，
仅弧设计就要 **10–20 小时**，且这还没算正文。**这与"AI 代写"的整个前提矛盾。**

**→ 本项目的人工介入哲学是不同的（更省人力）：**
- **不逐弧审**，而是**审"结构模板 + 抽样弧"**（第一弧、最后一个弧、一个探索型弧）。
- 用 `consistency_exemptions` 做**一次性豁免规则**，而非逐条确认。
- 让 `stale_from_chapter` 机制**自动标记**"弧改了 → 哪些章受影响"，只审受影响的。

**→ 报告的"审核耗时"数字对**单弧验证**有价值，但对**长篇工作流**的假设是错的。**

## 6. ★ 综合建议：**吸收 §1（分型）与 §2 的哲学，拒绝 §3/§4/§5 的 YAML 形态**

### 6.1 应该吸收的（写进 `arc-nesting-design.md` 与生成 Prompt）

| # | 吸收项 | 落到哪 |
|---|---|---|
| **A** | **弧的三种类型**（因果/目标/探索），生成时**先判型、再套结构** | §2.2 从"一句话"扩成"先判型" |
| **B** | **因果的两种写法**：链式（causes 前置）vs 三元组（目标-尝试-结果） | §2.2 的两种子结构 |
| **C** | **"结构定了推进就定了"** 的表述 | 已有（§2.2），可引用报告强化 |
| **D** | **"先立骨架再展开"的顺序感** | Prompt 内分节指令（非拆步） |

### 6.2 应该拒绝的（与作者定性冲突）

| # | 拒绝项 | 理由 |
|---|---|---|
| **E** | YAML 固定字段 schema | 作者已定"不需要字段"；弧 = 整段文本（同 synopsis） |
| **F** | `state_in`/`state_out` 相等校验 | 本项目无弧级 state 表；且与"不校验章号"边界同源 |
| **G** | `character_knowledge` / `item_state` 表 | 表不存在；引入= 另一次大规模建表（应走 `state-tracking-assessment.md` 的独立议题） |
| **H** | 弧拆成 3 个 DB 步骤 | 管线成本 3×，收益可用 Prompt 内分节拿到 |
| **I** | 逐弧 30–45 分钟人工审核 | 与长篇工作流不兼容 |

### 6.3 ★ 一个**可以两边都满足**的折中（推荐）

**报告想让"因果结构"可验证，我们想让"弧保持纯文本" —— 这两者可以同时满足：**

> **弧仍是一段纯文本（Markdown），但 Prompt 里规定**写作格式**：
> 每个同级弧必须用固定的小标题分节 —— `目标` / `类型` / `因果` / `时序` / `转折`。
> → 于是它**既是自由文本**（作者整段编辑，无字段、无表），
> **又是半结构化**（`## 弧 N` 下的 `- 因果：` 行可用正则提取，供 preflight 做引用完整性检查）。**

**→ 这样：**
- **作者定性的"整段文本、无字段"** ✅ 保持
- **报告的"可被脚本检查"** ✅ 也拿到（因为格式有约定，文本可解析）
- **成本**：只加一条 Prompt 格式约定 + 一条 preflight 规则（"弧声明的伏笔是否真实存在"）

**★ 这就是我对本报告的**最终裁决**：**
**要它的"结构"，不要它的"schema"；用 Markdown 约定的格式替代 YAML 字段。**

## 7. 结论表

| 问题 | 报告答案 | 本评估裁决 |
|---|---|---|
| 有没有必要设计弧生成 Prompt？ | 有，但是三步 | ✅ **有必要**；但**一步**（内部 Prompt 分节），非三步流水线 |
| 因果怎么放？ | 因果型用 `causes` 字段 | ⚠️ **用文本行**（`- 因果：因为X所以Y`），**不用字段** |
| 时序怎么放？ | `time` 字段 + 单调递增校验 | ⚠️ 文本行 + **不校验**（同章号边界） |
| 逻辑推进怎么放？ | 目标型用 attempts 三元组 | ✅ **吸收**（含"先判型"） |
| 怎么验证？ | 脚本 + AI + 人工三层 | ⚠️ **复用现有 preflight**（不新建 YAML） |
| 人工审什么？ | 逐弧 30-45 分钟 | ❌ **改为抽样式 + 豁免制** |

**一句话总结：**
**报告的正确性在**哲学层**（"结构定推进"），错误在**手段层**（YAML + 三步 + 逐弧审）。
它论证的方向——"弧必须携带可读的因果/时序结构"——正是作者第四轮的原话；
但它把这个结构**用字段来实现**，而本项目（以及作者的定性）要求它**用文本格式来实现**。
**我们的折中方案（Markdown 约定格式 + 复用 preflight）能同时满足"可读、可查、无字段"三个约束。**
