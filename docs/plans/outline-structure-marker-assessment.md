# 大纲要不要加「标记行」——结合本项目正文生成链路的评估

> 评估对象：外部报告《大纲要不要结构化：这份大纲的回答》
> （作者 2026-10-11 提供，主张在大纲中加 `【状态：X】` `【空间：X】` `【角色：X,Y】`
> `【因果：A→B】` `【伏笔：…】` 等标记行，并把它当作正文生成的硬约束）
> 评估方法：**先读链路再判断** —— 本项目"正文到底读了大纲的什么"是判断的唯一依据。

---

## 1. 结论先行

| 判断 | 内容 |
|---|---|
| **诊断** | ✅ **准确**。这份大纲作为给机器用的输入，确实缺少显式的状态/空间/知识锚点，报告举的例子（走廊门数=4、第六条全文、电梯停1楼）都能在原文里核到。 |
| **处方** | ❌ **层级错了**。本项目在"大纲"与"正文"之间**已经有一层结构化产物（章节蓝图 JSON）**，而正文**并不直接读整份大纲**、只读**本章那一段**。因此"给大纲加标记行"不会自动成为正文的硬约束，反而会造出第二个事实源。 |
| **真正缺的** | 报告说的 5 个缺口里，**只有 1 个是本项目真正空白的**（角色知识），而它**早已立项**（backlog **S1**）。其余 4 个已由既有机制覆盖或属于校验层议题。 |
| **可采纳** | 报告的核心诉求（"把状态/空间/知识显式化"）成立，但**落点是事实层与校验层，不是大纲**。另有 1 条**零成本**的现成能力见 §5，已顺手接上。 |

## 2. 先看事实：正文生成到底读了大纲的什么

这是全部判断的基础。`generate-draft.command.ts` 的 `readArchitecture()` 注入给正文的是：

```
premise  +  worldbuilding  +  synopsisForDraftChapter(synopsis, 本章号)
```

而 `synopsisForDraftChapter`（同文件 :102）做的是**把大纲投影到当前这一章**：

> 逐行扫描，只保留命中本章（或其章组）标题之下的行；标题层级不一致、章序不严格递增、
> 或定位不到唯一一章时**整份原样返回**（宁可不切，也不丢作者事实）。

所以：

| 事实 | 含义 |
|---|---|
| 正文拿到的是**本章那段散文大纲** | 大纲里的状态/空间/因果**确实会进正文的上下文** —— 报告担心的"AI 要自己推断"在这一点上是成立的 |
| 但它**不是一条独立通道** | 除大纲外还并行注入了：**本章章节蓝图（JSON）**、后续章节蓝图（作为边界）、本章出场角色卡（含 `currentState`）、连续性事实、伏笔台账 |
| `keyEvents` 会被**逐项核对** | `freezeChapterGoals(chapterNumber, blueprint.keyEvents, authorSources)` → `buildChapterGoalReviewPrompt`：审稿时对每个 keyEvents 项要求**正文逐字引文**并给出 completed/unmet/unknown |

**关键推论**：报告建议的 `【角色：X,Y,Z】` = 蓝图的 `characters`；`【章末钩子】` = 蓝图的 `suspenseHook`；
`【因果：A→B】` ≈ `keyEvents` 的顺序；`【弧光：X】` ≈ 蓝图的 `role/purpose`。
**这些字段已经以 JSON 形式存在，而且已经有 schema 校验与回归测试。**

蓝图契约（`src/shared/blueprint-semantic-contract.ts`）实际字段：

```
chapterNumber, title, role, purpose, keyEvents, characters[],
newCharacterCandidates[], relationships[], suspenseHook
```

## 3. 逐条核对报告的 5 个缺口

| # | 报告说缺什么 | 本项目现状 | 判定 |
|---|---|---|---|

| 2 | **空间节点** | 弧光结构里要求写「空间：X」，世界观第 4 维【空间结构（地图与区域）】就是那本空间名册。**但没有强制/校验**，实测副本名缺失（见 §4） | ⚠️ 已覆盖，缺的是**校验**（AC2/AC3 已立项） |
| 3 | **角色知识**（谁知道什么） | **纯空白** | ✅ 报告说对了。但 backlog **S1「角色知识状态」**早已立项，且标注为"唯一纯空白 + P0 项" |
| 4 | **因果链** | `keyEvents` + 章节目标逐项核对（要求逐字证据）+ 蓝图 `purpose/role` | ✅ **已覆盖**，不需要在大纲再标一遍 |
| 5 | **弧光归属** | 蓝图无弧字段；弧光结构是散文 | ⚠️ 真缺口，属 **AC3**（弧加入后一致性校验） |

→ **5 条里只有 1 条（角色知识）是真正空白，而且早已立项。** 报告的价值在于**独立地指向了同一个空白**，
这是对既有判断的一次外部确认，而不是新发现。

## 4. 用作者的真实产出反证：缺的不是"标记"，是"命名与数值一致"

对作者已生成的 30 章大纲（845 章项目，分批 1-5 / 6-15 / 16-25 / 26-30）做机械核对，
发现的问题**全是"内容一致性"，加标记行一条也治不了**：

| 现象 | 证据 | 报告的方法能治吗 |
|---|---|---|
| **第二副本没有名字** | 第 16 章起进入新副本（规则措辞从「不得」变「禁止」、主体从「住户」变「读者」），但**全文从未命名**；"白板走廊"只作为描述出现 1 次 | ❌ 需要的是**命名约定 + 校验**，不是标记格式 |
| **同一空间两个名字** | 弧光用「休整区」，大纲用「白色空间」（大纲中「休整区」出现 0 次） | ❌ 同上 |
| **SAN 与国运值取同一个数** | 第 10 章「SAN 从 100 掉到 95」；第 11 章「牌子…只写一个数字：95。他的国运值。」 | ❌ 这是数值设计问题 |
| **两份规则清单的"第 N 条"撞车** | 无声公寓第六条＝门牌让位；新副本第六条＝主体切换、第七条＝禁止带走物件、第八条＝不得回应书写声 | ❌ 标记行反而会让"第六条"出现两次而更混乱 |

**反过来说**：报告夸的部分（钩子密度、物品追踪、伏笔「待验」标记贯穿 15 章）
在大纲里**本来就成立** —— 说明这些不是靠格式约束获得的，而是靠叙事质量。

## 5. ★ 已存在的"标记行"能力（报告不知道，作者今天就能用）

本项目**已经**有一个面向作者的标记行机制，只是输入面不在大纲：

```
【第N章必现】具体要求
```

- 解析处：`src/shared/chapter-goal-review.ts:29`（`/^\s*【第(\d+)章必现】\s*(\S(?:.*\S)?)\s*$/u`）
- 它把该行变成**该章审稿的强制核对项**：审稿时必须给出**正文逐字引文**并判定
  completed / unmet / **unknown**；`unknown` **不阻断定稿**（"清单不是定稿许可"）。
- UI 里已有说明：角色卡「备注」、小说设定「世界观设定」两处的输入提示都写了这个用法
  （`CharacterEditor.tsx:424`、`NovelConfigEditor.tsx:476`）。
- 注入来源：`review-revision-context.ts:149`
  `freezeChapterGoals(chapterNumber, keyEvents, [core.worldSetting, ...authorNotes])`

**本次已顺手接上大纲**（1 行）：把 `core.synopsis` 也加入 `authorSources`。
于是作者**在大纲里给某一章写一行 `【第3章必现】沈舟必须亲手摸到第五条刮痕`，
它就自动成为第 3 章审稿的必现项** —— 不需要给大纲定任何新格式：
普通正文行不受影响，没写标记的章节行为完全不变。

> 这是报告诉求的"标记行"在本项目里**唯一不需要新契约**的落法：
> 标记是可选的、作者写的、只影响审稿清单，**不影响大纲的散文形态与切片逻辑**。

## 6. 为什么"大纲标记行作为正文硬约束"这个处方不该采纳

| 理由 | 依据 |
|---|---|
| **层级重复** | 蓝图已经是"每章的机器契约"，且正文同时读蓝图与本章大纲段。再往大纲塞一套标记 = 同一信息两个来源，两套事实迟早打架（本项目已有"第三个空间事实源"的警惕） |
| **下游不直连** | 正文只拿本章那一段大纲，**不拿整份**。整份大纲的标记行既不会被逐章核对，也不会变成硬约束 |
| **散文步骤加格式契约 = 已连踩 4 次** | ① 弧光子弧被示例锚定 ② 世界观维度听枚举 ③ 小弧数被示例锚定 ④ B 型中弧抄 A 型字段名。**"示例即形态"是这四条的共同机制** |
| **会与切片逻辑冲突** | `synopsisForDraftChapter` 要求"标题层级一致 + 章序严格递增 + 唯一命中"。标记行若被写成 `##` 级标题（模型很容易这么做），会直接破坏切片，退回"整份注入" |
| **作者会手改大纲** | 作者刚手动分批生成并会继续改。格式契约意味着**每改一次都可能违约**，校验会持续误报 |
| **数据已有替代** | 报告的"硬约束"诉求，已由 `keyEvents` 逐项核对 + 证据引文实现，且符合本项目「**证据非禁令**」纪律（只报告、不自动改） |

## 8. 一句话总结

**报告的诊断对（大纲是散文、机器锚点不显式），处方错层（标记行该加在"事实层/校验层"，
而正文的每章机器契约已经是章节蓝图）；它指出的 5 个缺口里 4 个已被现有机制覆盖或已立项，
唯一真空白（角色知识）也早有台账。真正值得做的不是改大纲格式，而是：
① 把已存在的 `【第N章必现】` 标记接进大纲（已完成，零成本）；
② 按既有次序推进 S1 / AC2 / AC3；③ 单独评估"非角色状态"是否值得建表。**
