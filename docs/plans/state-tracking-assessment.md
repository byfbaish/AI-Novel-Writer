# 「状态管理」分层评估：外部报告 vs 本项目现状

> 缘起：作者给出一份外部报告《状态管理的收益/可落地性分析：从"够用"到"世界模拟"的分层》，
> 要求**结合本项目**做评估并列入下一阶段改善计划。
> 本文逐层核对该报告的 13 类状态在**本项目里已经存在什么、缺什么、值不值得补**。
> 日期：2026-10-11 · 分支 `dev_byf` · 上游文档：`story-arc-proposal.md`

---

## 0. 结论先行：这份报告的**分层框架是对的，但"现状判断"严重低估了本项目**

报告把状态分成四层，按"收益/可落地性"排序。**这个框架我完全接受**，
它的判断标准（"不追踪就会导致读者跳戏/作者翻前文/AI 写崩"）也精准。

**但它有一个前提性错误：它像是在对一个"没有状态管理"的系统提建议。**

本项目**已经有一套成熟的"定稿后处理 → 连续性事实 → 章节投影"链路**，
报告列为 **P0 的 4 项里，有 3 项已实现或部分实现**，报告甚至没有提到这套机制的存在。

### 核对总表（13 类状态）

| 报告层级 | 状态类型 | 报告建议 | **本项目现状** | 差距 |
|---|---|---|---|---|
| P0 | 物品/道具 | 建表 | ⚠️ **部分**：`characters.cs_key_items`（在场角色携带） | 缺**独立道具表**（无持有者历史、无位置） |
| P0 | 时间线 | 章级快照 | ⚠️ **部分**：`chapter-time-continuity.ts` 只有**提示词约束**，无结构化数据 | 缺**时间锚点数据** |
| P0 | 伏笔/钩子 | 状态机 | ✅ **已实现**：`narrative_thread_plans` + `narrative_thread_confirmations`（`planted/progressing/resolved/abandoned` 四态） | **报告的四层规划里唯一完整命中的** |
| P0 | 角色知识 | 角色×知识点矩阵 | ❌ **完全没有**（本机 `character-roster.ts` 无 knowledge 字段） | ★ **真空** |
| P1 | 空间/位置 | 空间节点表 | ⚠️ **部分**：`characters.cs_location`（角色在哪） | 缺**空间节点表本身**（= 故事弧的 §3.1） |
| P1 | 规则状态 | 规则表+版本 | ❌ 无（规则只在 `worldbuilding` 散文里） | ★ 真空 |
| P2 | 关系网络 | 关系表 | ⚠️ **部分**：`characters.relationships` 自由文本；蓝图 `relationships` 字段 | 缺**结构化 + 变化时点** |
| P3 | 势力/组织 | 组织表 | ❌ 无 | 真空（但**收益确属最低**） |
| P3 | 事件/副本进度 | 事件表 | ⚠️ **部分**：剧情树快照（只读）；=`故事弧`要解决的正是这个 | 依赖故事弧 |
| P4 | 经济/资源 | 数值表 | ❌ 无（`keyItems` 里当文本写） | 真空，但**确实顺手可做** |
| — | 情绪/心理 | 不做 | ⚠️ `characters.cs_mental_state` **已存在** | 报告说"不做"，本项目**做了**且没出问题 |
| — | 世界底层规则 | 放世界观 | ✅ 一致（`worldbuilding` 散文） | 无 |
| — | 读者情绪/弹幕 | 不做 | ✅ 一致（本就无） | 无 |

**→ 关键发现：真正"完全空白且报告判定为 P0"的只有两类：
`角色知识状态`（报告称"最容易被忽略、最容易出矛盾"）和 `规则状态`。**
其余要么已实现、要么是故事弧的连带产物、要么收益本就低。

## 1. ★ 本项目已有一套报告没看到的机制（必须先说清楚）

报告逐条提议"建表"，但本项目在**定稿之后**已经跑着这样一条链：

```
定稿（finalize）
  → 抽取 continuity_facts（分段、分类、带原文证据）
  → 抽取 character_state_candidates（角色状态候选）
  → 存 summary_snapshots（按章、按 draft 绑定）
  → 生成 continuity projection + generation watermark
  → 下一章生成时作为"已定稿来源"注入
  → 审校时跑 consistency preflight（确定性矛盾检测）
```

### 1.1 关键代码资产

| 能力 | 位置 | 说明 |
|---|---|---|
| **连续性事实（分类）** | `src/shared/finalized-continuity.ts:5-9` | 已有 4 个类别：`character-state` / `timeline` / `open-thread` / `plot` |
| **事实抽取器** | `src/shared/finalized-continuity-facts.ts` | 从章节要点 + 定稿原文抽事实，**每条必须能定位到原文证据**（`evidenceExcerpt`） |
| **章级快照表** | `baseline-schema.ts:320-334` `summary_snapshots` | 含 `continuity_facts`、`character_state_candidates`、`projection_generation` |
| **投影水位线** | `baseline-schema.ts:609-615` `continuity_projection_meta` | `stale_from_chapter` —— 已有"陈旧检测" |
| **豁免表** | `baseline-schema.ts:622-628` `consistency_exemptions` | 已允许作者标注"这条不算矛盾" |
| **确定性矛盾预检** | `src/shared/consistency-preflight.ts:84-119` | 已实现一条**结构化规则**：定稿里死亡的角色又被排进蓝图 → 报警（带原文证据 + 建议） |
| **时间承接约束** | `src/shared/chapter-time-continuity.ts` | 已有一套完整的"同日/跨日/时点换算"提示词契约 |
| **角色状态字段** | `src/shared/character-roster.ts:44-52` | `location` / `powerLevel` / `physicalState` / `mentalState` / `keyItems` / `recentEvents` |
| **字段级来源** | `character-roster.ts:55-60` | `{kind:'author'}` / `{kind:'derived', source}` / `{kind:'legacy'}` —— **区分作者手填与 AI 派生** |

### 1.2 这套机制的设计水平**高于**报告的提议

报告三种模式（结构化字段 / 自由文本+AI校验 / 事件溯源），本项目**三种都在用，且组合得更严谨**：

| 报告模式 | 本项目对应 | 本项目做得更好的地方 |
|---|---|---|
| A 结构化字段 | `characters.cs_*` | **带字段级 provenance**（谁是作者、谁是 AI 推的） |
| B 自由文本+AI校验 | `chapter_notes` → `continuity_facts` | **每条事实强制带原文 evidence，AI 不能凭空断言** |
| C 事件溯源 | `narrative_thread_confirmations` / `summary_snapshots` | 已经"记录谁在什么时候知道了/埋了什么" |

**→ 尤其是"evidence 强制绑定原文"这一条，比报告的"AI 定期扫描是否矛盾"强一个量级**：
报告的模式 B 明确标了缺点"校验依赖 AI，可能漏检"，而本项目用**原文证据锚定**规避了这一点。

## 2. 逐条评估（只评"报告判 P0/P1 但本项目有差距"的）

### 2.1 ★ 角色知识状态（报告：P0 / "最容易被忽略"）—— **本项目真空，且报告判断正确**

**报告说**：`character_id, knowledge_id, learned_chapter, source` 矩阵。
**本项目现状**：`character-roster.ts` 里**没有任何 knowledge 字段**。
`cs_recent_events` 是"最近发生了什么事"，**不等于"他知道了什么"**。

**为什么这条是真缺口**：报告举的例子精准 ——「沈舟在 ch1 不知道铃铛，ch3 突然会用」。
这类矛盾**用现有机制抓不到**：
- `consistency-preflight.ts:97` 只检测 `category !== 'character-state'` 就 `return []`，
  即**只认"死亡终态 vs 出场"这一条**；
- 而"某人知道了他不可能知道的事"属于**信息流矛盾**，当前**无任何检测**。

**→ 评估：同意报告，这是最高优先级的真缺口。但落地形态要改。**

**⚠️ 报告方案的问题**：`character × knowledge_item` 建表会**爆炸**。
800 章 × N 个角色 × M 个知识点 = 大量行，且"知识点"边界模糊（谁知道"规则7条"？是知道全部还是知道其中有第4条？）。

**→ 本项目更合适的形态（建议）**：
把知识挂在**已有的事实抽取链路**上，而不是新建矩阵：

- `finalized-continuity-facts.ts:6-9` **已经会把事实分类**，其中 `open-thread` / `plot` 就是"信息类事实"；
- 只需**给事实加一个 `known_by: characterId[]` 维度**（谁在场、谁被告知），
  复用现有 `factEntities`（已经从原文抽出了实体）；
- 查询时反向："第 8 章要写 X 知道 Y 吗"→ 查 `facts` 里 `statement` 命中 Y 且 `known_by` 含 X 的记录。
- **这样零新表、零新抽取器，只是给已有事实加一维。**

**→ 这条应列为下一阶段**第一优先**（因为它是唯一"纯空白 + P0"的）。**

### 2.2 ★ 规则状态（报告：P1）—— 真空，但**报告低估了它的难度**

**报告说**：`rule_id, layer, number, content, effective_from, effective_to, status`。
**本项目现状**：规则**只是 `worldbuilding` 散文里的一段**（模板 `builtin-prompt-templates.ts:508-520`
的【核心规则与体系漏洞】维度）。

**⚠️ 报告方案的问题**：它假设规则是"客观、可编号、稳定"的。
但**本项目的世界观模板明确要求"每个设定都必须自带冲突点"** ——
即世界观里的"规则"本身是**叙事装置**，不是法条。
把它结构化会与既有的"自带冲突"设计**打架**（这就是 `story-arc-proposal.md §3.1` 里
"空间结构不像其他三个维度"的**同类问题**）。

**→ 评估：这条应当**与故事弧的"空间结构"一起决策**。**
如果作者选择"世界观扩展为结构化维度"（§3.1-B），那规则表可以顺带做；
如果选 A（并入散文），则规则表**没有数据源**，先不做。
**→ 不建议单独立项，建议挂在故事弧之后。**

### 2.3 时间线（报告：P0）—— 本项目"有约束无数据"

**报告说**：章级快照 `chapter, story_time_start, story_time_end, duration`。
**本项目现状**：`chapter-time-continuity.ts` 是一套**很精细的提示词契约**
（同日默认、跨日换算、时点归属、不确定时保留不确定），**但没有任何结构化时间数据**。

**→ 评估：同意报告，是真缺口。但优先级低于"角色知识"。**
理由：
- 现有的**提示词契约已经能防住大部分时间错乱**（"不得写成昨天/昨夜"是硬指令）；
- 结构化时间锚点的主要价值是**"可查询/可校验"**，而当前没有任何校验器消费它；
- **→ 所以它更像"为未来的校验器准备数据"，而非解决当下的痛点。**

**→ 建议：先做 `角色知识`；时间线可与它共用同一条事实抽取链路**
（事实已有 `timeline` 分类，`finalized-continuity-facts.ts:7`），成本会低很多。

### 2.4 物品/道具（报告：P0）—— 部分已有，报告方案**过重**

**报告说**：`item_id, name, location, holder, state, last_seen_chapter`。
**本项目现状**：`characters.cs_key_items` 已经在追踪"该角色身上有什么"，
且**走的是带 evidence 的抽取链路**（`character-proposal-parser.ts:376`）。

**→ 评估：报告的"独立道具表"是**过度设计**。**
理由：本书的道具（A4纸、圆珠笔、铃铛、钥匙）**绝大多数时候是"跟着人走的"**，
而"人"已经有了 `cs_location` + `cs_key_items`。
真正缺的是**"道具脱离角色之后的状态"**（铃铛被丢在房里 → 谁都不持有）。
**→ 建议：只在 `cs_key_items` 上补一个"当前不在任何人身上"的表达约定，不建新表。**
（这条与故事弧的"空间结构"有重叠 —— 道具的位置本质是"在哪个空间节点"。）

### 2.5 关系网络（报告：P2）—— 部分已有，报告自己也说"只追踪关键关系"

**本项目现状**：`characters.relationships` 自由文本 + 蓝图 `relationships` 字段（`{from,to,relation}`）。
**→ 评估：与报告一致，属"够了"。** `story-arc-proposal.md §3.2.1` 已建议
把"弧内角色变化"写在弧上，而不是新建关系表。
**→ 不单独立项。**

### 2.6 空间/事件/势力/经济 —— **全部归入故事弧**

| 报告项 | 本项目处置 |
|---|---|
| 空间/位置（P1） | = `story-arc-proposal.md §3.1` 的"空间结构"，**已在故事弧方案内** |
| 事件/副本进度（P3） | = 故事弧的 `goal/climax` + 状态，**已在故事弧方案内** |
| 势力/组织（P3） | 报告自评收益最低，**暂不做** |
| 经济/资源（P4） | 报告说"顺手做"，但本项目无强需求，**暂不做** |

**→ 这四项不要与故事弧并行立项，否则会打架。**

### 2.7 情绪/心理 —— **报告说"不做"，但本项目已经做了，且没出问题**

`characters.cs_mental_state` 已存在并参与派生。
**→ 评估：报告这条判断偏保守，但不构成"要新增"的理由。保持现状即可。**

## 3. 与故事弧的关系（作者要求"当前目标集中在故事弧上"）

**这条是本文最重要的定位结论：**

```
状态管理  ⊃ 故事弧
```

- **故事弧 = 状态管理里"空间/事件"两类的落地形态**（报告 P1 空间 + P3 事件）。
- 报告里 **P0 的四项（物品/时间线/伏笔/角色知识）与故事弧是**并列关系**，不是从属**。
- **→ 所以：故事弧继续按原方案推进，不受本文影响；
  报告里与故事弧重叠的部分（空间/事件），不要在故事弧之外另立项目。**

### 3.1 唯一需要与故事弧**对齐**的一处

报告的时间线 + 空间节点 + 弧的起止章，**三者共用同一个"章节区间"坐标系**。
`story-arc-proposal.md §3.2.1` 已定义 `from_chapter / to_chapter`。
**→ 建议：未来的时间锚点、空间快照，都以"弧 + 章"为坐标系，而不是各自建表。**
（否则会出现"弧说第 10 章高潮，时间线说第 10 章是次日"这种两套事实。）

## 4. 建议列入下一阶段的改善计划

**原则**：① 不与故事弧并行立项的重叠项一律并入故事弧；
② 只做"纯空白 + 高收益"的；③ 复用已有抽取链路，不新建平行系统。

### 阶段 A（与故事弧并行，不冲突）

| # | 项 | 依据 | 落地形态 | 成本 |
|---|---|---|---|---|
| **A1** | ★ **角色知识状态** | 报告 P0，本项目唯一"纯空白"的 P0 | 给 `finalized-continuity-facts` 的**事实加 `known_by` 维度**，复用现有抽取链路 | 中（**零新表**） |
| **A2** | 时间锚点 | 报告 P0，已有提示词契约但无数据 | 复用同一事实链路（已有 `timeline` 分类），补"章级时点"字段 | 中低 |

### 阶段 B（挂在故事弧之后）

| # | 项 | 依据 | 说明 |
|---|---|---|---|
| **B1** | 空间结构（= 故事弧 §3.1） | 报告 P1 | **已在故事弧方案内**，不另立项 |
| **B2** | 规则状态表 | 报告 P1 | **依赖 B1 的决策**：选结构化才做 |
| **B3** | 事件/副本进度 | 报告 P3 | **= 故事弧的 `goal/climax` 状态**，不另立项 |

### 阶段 C（暂缓 / 不做）

| # | 项 | 理由 |
|---|---|---|
| C1 | 独立道具表 | 报告方案过重；`cs_key_items` 已覆盖 90% |
| C2 | 势力/组织表 | 收益最低 |
| C3 | 经济/资源表 | 无强需求 |
| C4 | 情绪/心理表 | **已有 `cs_mental_state`**，无需新增 |
| C5 | 关系网络表 | 已有自由文本，报告自评"只追踪关键关系" |

### ★ 一个**报告没提、但我认为更值得做**的项（阶段 A 补充）

**扩大 `consistency-preflight.ts` 的检测规则集。**

现状：它只检测**一条**规则（`consistency-preflight.ts:97`：`category !== 'character-state'` 直接跳过），
即"死亡角色又被排进蓝图"。

**但基础设施全都齐了**：事实有分类（`character-state`/`timeline`/`open-thread`/`plot`）、
有原文证据、有豁免表、有增量水位线（`stale_from_chapter`）。
**→ 扩充规则（如"已知死亡角色仍有对白""伏笔超期未收""时间倒流"）
的成本，远低于新建一套状态系统，收益却很高。**

**建议列为 A3**（纯增量、零新表、复用全部现有设施）。

## 5. 一句话总结

**报告的分层框架正确、判断标准精准，但它低估了本项目 ——
本项目早已有一条"定稿→连续性事实（带原文证据）→章节投影→确定性预检"的成熟链路，
报告列为 P0 的四项里，伏笔已完整实现、物品与时间线已有部分基础。**

**真正值得做的只有两件：
① `角色知识状态`（唯一纯空白的 P0，且现有机制永远抓不到"他知道了不该知道的事"）；
② `扩大 consistency-preflight 的规则集`（基础设施全齐，纯增量）。**

**空间/事件两类状态 = 故事弧本身，不要另立项。
→ 故事弧照原计划推进；状态管理只在 A1/A2/A3 三处与它并行，且共用同一"弧+章"坐标系。**
