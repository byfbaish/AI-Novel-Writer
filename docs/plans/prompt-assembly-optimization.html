一、问题定性：一个表象，三条独立根因

表面报错是渲染端的安全闸 MAIN_SNAPSHOT_REGRESSION（generation-runtime.ts:190）， 但它只是下游症状。真正的因果链是：

1
提示词被重复组装
同一份设定（前提/世界观/大纲/文风/全局要求）在 prompt 里各出现 2 次，膨胀出 13394 字节冗余（占 26%）。
2
输入体量逼近上限，模型行为失稳
inputUpperBoundTokens=51500 → reservationLiabilityTokens=117548；小模型在超长、重复的上下文里更容易违反篇幅/指令合同。
3
产物超出篇幅合同
「短细纲」只应 500 units，却写出 8881 字；正文 8921 字，远超 draftTargetUnitRange(3000) 的 2100–3900。
4
进入补救链路 → 投影判废
触发 condenseDraftIfNeeded 惩罚链 → 渲染端 accept() 拒绝 → 整条运行判废，报 MAIN_SNAPSHOT_REGRESSION。
结论 MAIN_SNAPSHOT_REGRESSION 不是模型错误，也不是存储错误，而是提示词组装把设定重复注入这一上游缺陷的放大表现。 修组装，比在下游给投影闸加豁免更根本。

2.2 为什么去重失效

readArchitecture()（generate-draft.command.ts:1704）这样去重：

const duplicates = exactParagraphs(authoredConfigFacts)
if (core?.premise)      parts.push(withoutExactParagraphDuplicates(core.premise, duplicates))
if (core?.worldbuilding) parts.push(withoutExactParagraphDuplicates(core.worldbuilding, duplicates))
if (core?.synopsis)      parts.push(withoutExactParagraphDuplicates(synopsisForDraftChapter(...), duplicates))

而 exactParagraphs（:143）是逐段精确字符串匹配：

new Set(values.flatMap(v => v.split(/\r?\n\s*\r?\n/u).map(p => p.trim()).filter(Boolean)))
失效机制 旧项目里 project_core.premise / worldbuilding / synopsis 是带 # 标题与多级 ## 的 markdown 大纲， 而 novel_config.coreOutline / worldSetting 是被剥离 markdown 的纯文本。 两边切段后字符串永不相等 → 命中 0 段 → 一字未删 → 两处各出一遍。

对照证据（同一 prompt）：golden_finger / core_outline / world_setting / protagonist_profile 各只出现 1 次 —— 它们几个字段的 markdown 形态恰好一致，去重生效。 这恰好证明机制判断成立。

三、根因 B — 参考作品在写稿阶段缺位

用户提问：「没有被当作『参考作品』专门组织，是设计错误还是功能不完善？」

定性：功能不完善（写稿阶段缺专门组织），不是 bug，也不丢数据
阶段参考作品的组织方式状态
架构阶段 有专属 builder 方法 withReferenceWorks()（prompt-builder.ts:319）→ 变量 reference_works；模板里有专门块 【参考作品风格（如有，调性与节奏可参考以下作品）】{{reference_works}} （builtin-prompt-templates.ts:381-382 / 452-453） 已组织
写稿阶段
first_chapter_draft / next_chapter_draft		 模板 variables 里没有 reference_works， requiredContextVariables 也不含它；ChapterPromptBuilder 没有 withReferenceWorks 方法 → 参考作品只靠"意外"进 prompt： 它未被列进 promptOnlyConfigKeys，于是被 JSON.stringify(novelConfigFacts) 带进 {{novel_config}}，以 "referenceWorks": "..." 的原始 JSON 字段塞在 【不可偏离的作者事实】里 缺位

后果：参考作品在写稿时既没有语义定位（"参考作品的调性与节奏"）也没有边界声明， 只以 JSON 字段形态出现。模型无法区分它是"可借鉴调性"还是"必须兑现的作者事实" —— 这与同一块里那些真正不可偏离的设定混在同一权威层级，既不精确也不安全。

已定改造（写稿阶段对齐架构阶段）

  1. ChapterPromptBuilder 增加 withReferenceWorks(works: string)，复用架构侧同名语义。
  2. generate-draft.command.ts 把 referenceWorks 加入 promptOnlyConfigKeys， 从 JSON blob 中摘出（避免同一内容既在 JSON 又在专块各出一遍）。
  3. first_chapter_draft / next_chapter_draft 模板各加一块 【参考作品（仅供调性与节奏借鉴，不是必须兑现的作者事实）】{{reference_works}}。
  4. 变量声明与 requiredContextVariables 同步；空值时整块省略或留空提示。

四、根因 C — 日志把「预留」写成「请求」

用户现场日志：短细纲：租约请求上限 65536 Tokens（单次上限 65536，累计 65536/67108864）， 由此怀疑「到底发了什么东西能达到 65536 token」。

真相：那个 65536 是「预留额度 reservation」，不是「本次要生成的量」
指标值含义
requestedOutputTokens1712 本次实际请求的输出量（短细纲只求 500 units）
reservedOutputTokens65536 为不可知模型能力预留的额度上限，被 model-capability-unknown （用户把输出上限设为 65536）× output-allocation-ceiling 顶格
inputUpperBoundTokens51500 输入上界 —— 真正的压力来源
reservationLiabilityTokens117548 预留负债合计 = 输入上界 + 预留输出

日志台词 generate-draft.command.ts:339-341 打印的是 receipt.budget.requestedOutputTokens 的位置，却写成了「租约请求上限」，并把 maxRequestedOutputTokensPerAttempt 当作「单次上限」并列， 读者极易把 65536 误读成「这一次要写 6.5 万 token」。

【用户自定义创作指导】占 18420 字节（36%），内容是整份创作指令： 文风 / 毒点红线 / 设定禁忌 / 节奏控制 / 移动端段律 / 伏笔规则 / 命名规则 / 参考作品拆解 / 避坑清单。 而它同时与下列三块大面积重合：

六、去重升级方案（规范化指纹）

6.1 核心思路

把 exactParagraphs 的逐字节比较升级为规范化指纹比较，让"同内容不同 markdown 形态"也能判重。

// 规范化：NFKC → 去 markdown 行首符号 → 折叠空白 → 统一大小写
function normalizeForFingerprint(text: string): string {
  return text
    .normalize('NFKC')
    .replace(/^[ \t]*#{1,6}[ \t]*/gmu, '')      // 去 # 标题前缀
    .replace(/^[ \t]*[-*+>][ \t]+/gmu, '')      // 去列表/引用前缀
    .replace(/[*_`~]/g, '')                      // 去行内强调符
    .replace(/[\s\p{P}\p{S}]+/gu, '')            // 折叠空白与标点
    .toLowerCase()
}

6.2 两级判重（安全优先）

  1. 段级：把 authoredConfigFacts 的段落做上述规范化，建指纹集合； 对 core.premise / worldbuilding / synopsis 逐段比对指纹，命中即剔除。
  2. 整块级兜底：若某字段规范化后整体等于某个 authoredConfigFacts 字段（或互为子串且长度占比 > 阈值）， 整块不注入 architecture，只保留一处权威表述。
硬约束（必须遵守） 去重只针对逐字重复的内容。规范化仅用于判等，注入给模型时保留原文 （不改写、不截断、不摘要）。任何"长度不同但语义相近"的段落一律不去重 —— 宁可多花预算，不得丢失作者事实（ADR 0020 / S07 容量准入 / "必要原文不得静默截除"）。

七、配置优化：可固化 / 不可固化（B 类默认关闭）

用户的构想：用一个「AI 优化配置」功能处理重复描述，分两类 ——

A 类 · 可固化

继承性重复，例如：

  • 系统级 与 用户级配置
  • 正文生成时：大纲级 与 细调级
  • 作者设定 prompt 与 写文 prompt

流程：AI 提出合并后的权威表述 → 用户逐条确认 → 替换原配置（落库）。

B 类 · 不可固化

当次上下文里的临时重复（本次预请求才发现、不宜写回配置）。

流程：当次预请求（extra call）优化重复描述 → 再拼装正式生成 prompt。 结果不落库、只对本次生成生效。

已定策略（用户确认，选项 a） B 类默认关闭，设置项里可开。
理由：预请求后的结果不太可控，收益确定性不高；不能强求默认开启， 只给「预算有限、愿意尝鲜」的用户提供开关，零意外消耗。

7.1 A 类固化的实现要点

  • 必须用户确认：不能自动改写作者配置。AI 产出的是「建议」，落库前需人工逐条勾选。
  • 可回溯：固化动作要留版本/来源标记，允许撤销回原配置。
  • 不越权：固化不得删除作者事实与红线，只能合并重复表述。

7.2 B 类预请求的实现要点

  • 默认关闭，设置项 promptOptimization.volatileDedup.enabled 控制。
  • 预请求的产物不写回任何配置，仅在本次拼装时生效。
  • 预请求本身计入预算（不能白烧 token）；预算不足时跳过预请求而不是静默截断。
  • 预请求失败必须优雅回退到未优化的原始拼装。
  • 预请求的输入也要走 §6 的规则化去重兜底（规则层零成本、先做）。
实施次序建议 先做确定性强、零额外消耗的规则化去重（§6）。B 类 AI 预请求作为可选增强后置 —— 因为它引入额外 LLM 调用与不确定性，收益依赖模型质量，不宜与规则层耦合。

八、日志与文案纠正

位置现状建议
generate-draft.command.ts:339-341 「租约请求上限 {requestedOutputTokens} Tokens（单次上限 {maxPerAttempt}，累计 {cum}/{max}）」 区分三者：
本次实际请求 = requestedOutputTokens；
预留上限 = reservedOutputTokens（并注明来源：模型能力未知 / 输出分配上限）
同处的「累计 x/y」 容易被读成「已用 y 中的 x」 明确为「本运行累计预留 / 运行总额度」，并区分 requested 与 reserved 两条线

九、拼装架构升级

9.1 保持「稳定前缀 → 可变后缀」（缓存友好）

generate-draft.command.ts:644-647 的注释已明确这个目标。当前 builder 链：

  .withArchitecture(architecture)

  .withWritingStyle(writingStyle)
  .withNovelConfig(novelConfigFactsJson)
  .withWordNumber(targetChars)
  .withChapterInfo(writerChapterInfo)
  .withCharacterStates('')
  .withFutureBlueprints('')
  .withFilteredContext('')

9.2 建议的改进

  1. 规约化：一个约束只在一处表达。
    • 设定事实 → 只进【全书设定池】/【不可偏离的作者事实】
    • 全局规范 → 只进【全局写作要求】
    • 文风 → 只进【文风要求】
    • 参考作品 → 只进新的【参考作品】块
    • 本章微操 → 只进【作者对本步骤的额外指导】（保持最高优先级语义）
  2. 拆解 user_guidance：把"可固化的通用创作规范"从"本章微操"里分离出来 —— 前者并入全局规范（经 A 类固化确认），后者留在 user_guidance。
  3. 变量命名对齐：withReferenceWorks 在架构侧已存在，写稿侧补齐同名方法，减少认知差。
  4. 去重前置：在 builder 之前对输入各来源做一次统一的「来源归并 + 指纹去重」， 而不是在每个字段内部各写一套 withoutExactParagraphDuplicates。

十、角色卡缺口提示

用户发现蓝图里的「老猫」「首席分析师」「异邦幸存者」等角色没进 prompt，怀疑是 bug。

定性：数据缺口，非组装 bug readCharacterProfiles() 按 chapterInfo.characters 命中 —— 本案例命中 2 张（沈舟、沈晚）， 注入内容包含完整 gender/age/appearance/personality/background/abilities/motivation/arc/notes 与 7 条 relationship。「老猫」根本不在 roster 里（characters 表 6 人）， 所以不是"提到却没查"，而是"根本没有卡可查"。

建议：软提示而非静默跳过

  • 当 chapterInfo.characters 中的名字在 roster 里查无此卡时， 在生成日志里给一条软提示：「本章提到『老猫』，但角色名册里没有对应卡片，将不注入其档案」。
  • 不阻断生成（避免误伤别名、龙套等合理情况）。
  • 可选：在章节蓝图编辑界面标一个弱警示图标，引导作者补卡。

十一、已决事项汇总（第 1、2 条）

第 1 条 · 分隔符提示语 —— 已修复 ✅

问题：ChapterCardEditor.tsx:1134 标签写「出场关键人（逗号分隔）」 （en: comma-separated），但同一控件用 join('、') 以顿号显示， 解析器 split(/[,，、\s]+/) 两者都吃。

真相：数值层是数组（ChapterBlueprint.characters: string[]）； AI 生成走 blueprintSemanticGenerationContract，要求"至少含一个唯一非空角色名的字符串数组"。 所以顿号完全是 UI 显示层 join 出来的，不是 AI 写出来的，也没有任何数据损坏。 ChapterCreationDialog.tsx:502 早已写作「用逗号或顿号分隔」，只有编辑器标签没跟上。

改法（1 行）：标签 → 「出场关键人（顿号或逗号分隔）」/ en Key characters (separated by 、 or ,)；解析器与 join('、') 保持不变。 tsc --noEmit EXIT=0。

第 2 条 · 参考作品的组织 —— 已定性并定方向 ✅

定性：功能不完善（写稿阶段缺专门的参考作品组织），不是 bug、不丢数据。 架构阶段有专属 withReferenceWorks + {{reference_works}} 块； 写稿阶段两者都缺，只能靠未过滤的 novel_config JSON 把 referenceWorks 带进去， 以原始 JSON 字段形态混在【不可偏离的作者事实】里。

方向：①ChapterPromptBuilder 补 withReferenceWorks； ②referenceWorks 加入 promptOnlyConfigKeys 从 JSON 摘出； ③写稿模板加【参考作品（仅供调性与节奏借鉴，不是必须兑现的作者事实）】块； ④变量声明同步。详见 §三。

P1 · 第 6 项为何排第一

  • user_guidance 是 prompt 中体量最大且逐章变化的段（约 36%）。它目前排在 builder 链的可变后缀区，导致其后所有内容每章都无法命中前缀缓存。
  • 拆解逻辑：把其中「作者全局写作规范」部分（跨章稳定）上浮到 withGlobalGuidance 之后的缓存区，「本章微操」保留在后缀区。
  • 风险点：拆分判据若由启发式规则判断，可能误判「本章微操」为「通用规范」→ 破坏作者意图。建议改为显式字段（作者侧拆成两个输入框）或仅在模板层面分离呈现，不做内容级自动切分。必须先出判据方案再动手。

P2 · 蓝图场景 → AI 角色卡（可行性评估已通过）

结论：可做，约 70–80% 后端与契约可复用 现有闭环：directory 蓝图 → commitDirectoryBlueprintRange → retryDirectoryCharacterSync → syncBlueprintCharacterCandidates → character-proposal:stage（{kind:'directory'}）→ generation-character-proposal-proof.ts 转成待定提案。 角色卡数据结构 CharacterRosterEntry 已是权威定义，project_core.characters_arch 只是它的派生投影。

缺口（4 处，即真正要写的新代码）

  1. 缺「按场景富化生成」的 prompt / command：现有 directory 路径只携带 name + role（BlueprintNewCharacterCandidate）， 不带该角色在本章的剧情上下文。需要新增一个「读本章蓝图剧情 + 该书总体蓝图 → 产出完整角色卡 JSON」的生成命令。
  2. 缺审阅列表：listPendingFinalized()（character-proposal-service.ts）目前只返回 import 与 finalized-generation 两种来源，directory / generation 提案没有对应的 UI 列表 → 作者看不到、批不了。
  3. 缺入口按钮：CharactersView.tsx 角色卡管理界面没有「从蓝图 AI 生成」的入口。
  4. 缺「副本 / 主线」语义：CharacterRole 枚举只有 protagonist / antagonist / supporting / minor， 没有「活跃于某个副本」还是「加入主线」的概念。方案：先写进 notes / arc 字段（零 schema 改动）， 确有必要再评估新增字段。

  • P3（B 类预请求去重）：放在 P2 之后，因为它是「锦上添花」而非「堵漏」。默认关闭 + 设置开关的策略已经确定，实现路径清晰、风险低，所以排在中段。
