## 1. 为什么需要这份章程

2026-10-24 的核查结论：**规则不缺，缺两个闭环。**

| 闭环 | 缺什么 | 后果 |
|---|---|---|
| **入口闭环** | 规则写在 `docs/README.md`，但那个文件只在「我要找文档」时才会被打开；根目录又没有常驻指令文件（`/AGENTS.md` 被 `.gitignore:58` 忽略） | 新会话 agent 开工前**从不读规则**，凭习惯把设计稿写到 `docs/plans/` 或根目录 |
| **反馈闭环** | 唯一的检查脚本 `scripts/check-doc-links.mjs` **只查断链**，不查状态行、索引登记、命名、放置位置 | 违规可以无限累积；规则是否被遵守**无人知道** |

**本文件的定位**：把"人记得住的约定"变成"agent 开工必读 + 脚本可查"的两件东西。规则条文继续留在 `docs/README.md`，本文件负责**四层模型（§2）、单一事实源（§3）、完成定义（§6）、开工流程（§7）与反例（§8）**。

## 2. 四层文档模型：谁进上下文、什么时候进

> 判断标准只有一条：**不读它，agent 一定会悄悄犯错吗？** 会 → 允许常驻；不会 → 下沉，按需读。

| 层 | 承载物 | 谁读 | 进上下文的方式 | 长度约束 |
|---|---|---|---|---|
| **L0 常驻宪法** | `AGENTS.md`（**入库**，2026-10-25 起）· 本文件 | 每个新会话 | AGENTS.md **全文常驻**；本文件按 §7 只读 §4/§6 | AGENTS.md **≤ 60 行**，超出必须下沉 |
| **L1 索引** | [`docs/README.md`](../README.md) | 找文档 / 放文档时 | 只读 §1 那张表 + §3 决策树 + §4 对应小节的**行** | 已 300 行；加行前先问「这行能不能并进既有行」 |
| **L2 任务级** | `docs/design/<主题>/*-design.md` · `docs/handoffs/` | 做某一件事时 | 只读**当前任务相关的 1–2 份**，不整目录通读 | 单稿不限；设计是树，靠头部 `> 上级稿` 串 |
| **L3 长期沉淀** | `docs/adr/` · `docs/plans/prompt-assembly-backlog.md` | 改契约 / 决策 / 排期前 | 按编号或条目**检索**，不通读 | ADR 一篇一决定；台账一节一项 |

**反模式（明确禁止）**：
- ❌ 把 L2 的内容塞进 L0（AGENTS.md 变成 200 行的"项目百科"）——agent 会略读，等于没写。
- ❌ 把 L3 的结论抄进 L1（README 变成"为什么"的集散地）——README 只回答"打开哪个文件"。
- ❌ 为了"看得全"而新建一份汇总稿——汇总稿必然腐烂，**索引 + 检索**才是可持续的。

## 3. 单一事实源纪律

**一条事实只活一份。** 同一规则在 README、本文件、AGENTS.md 各写一遍的结果是：更新时必漏一处，然后 agent 不知道该信哪个。

| 事实 | 权威处 | 其他处只能 | 已知重叠（2026-10-24 实测） |
|---|---|---|---|
| 放置决策树（放哪） | `docs/README.md` §3.1 | 指路，不复述条目 | 本文件 §4 只讲判定原则与高频误判 |
| 状态行写法 | `docs/README.md` §3.2-3 | 指路 | 本文件 §5 只补"允许的取值"与脚本识别范围 |
| 命名约定 | `docs/README.md` §3.3 | 指路 | 本文件 §5 只给正则，不重列表 |
| 检查命令 | `AGENTS.md` 命令块 | 指路 | 本文件 §9 只讲**判定规则**与基线纪律 |
| 待办优先级 | `docs/plans/prompt-assembly-backlog.md` 顶部表 | 指路 | 任何设计稿不得另立优先级表 |
| 长篇文章的生产链定级 | `design/architecture/long-form-readiness-review.md` §1.1 | 指路 | 创作侧见 `long-form-craft-alignment-assessment.md`，两者互补不互抄 |
| 术语（continuity / story bible / …） | `design/architecture/industry-alignment-and-stage-goals.md` §2 | 指路 | 设计稿**必须用右侧的词**，不自造概念 |

**执行方式**：改一张表的条目时，顺手 `grep` 它的标题关键词，确认没有第二处在复述。这步 30 秒，能省掉一次"两份文档打架"。

## 4. 放置决策树：三个高频误判

**判定表见 [`docs/README.md`](../README.md) §3.1，本节不复制。** 这里只说三个真实发生过、且脚本抓不到的误判：

| # | 误判 | 为什么错 | 正确落点 |
|---|---|---|---|
| 1 | 把**评估稿 / 设计稿**写进 `docs/plans/` | `plans/` 只剩台账与冻结子树；冻结子树被 `vite.config.ts` 与 `donor-delta.json` 按字面路径引用，混放会让"哪份是台账"失去唯一性 | `docs/design/<主题>/<主题>-assessment.md` |
| 2 | 为"实施记录"**新开一份文件** | 状态从此分散在 ≥2 个文件，收口时必漏改（2026-10-22 的教训：只改了顶部状态行，路线图表没标 ✅，读者以为没做完） | 写进**原设计稿**的「实施记录」小节，只改头部 `> 状态：` 行 |
| 3 | 把**一次性排查结论**当成设计稿入库 | 结论有日期、会过时；设计稿是"现行方案"，混进排查记录后没人敢归档它 | 跨会话交接 → `docs/handoffs/YYYY-MM-DD-主题.md`；长期有效的结论 → 台账条目或 ADR |

## 5. 命名 / 状态行 / 归档

### 5.1 命名

一律 **小写 ASCII**（数字、连字符、点），不含中文与空格。五类具体格式见 `docs/README.md` §3.3；脚本用这条正则校验：

```
^[a-z0-9][a-z0-9.-]*\.md$
```

目录自带的 `README.md` 是索引件，不套用本条。

### 5.2 状态行

每份 `docs/design/` 下的设计稿，头部必须有状态行。两种写法都合法（脚本都认）：

```markdown
> 状态：已实施（2026-10-24）
> **状态**：✅ 已落地（2026-10-24，M17）
```

**受控词表（2026-10-31 起由脚本 `C1b` 强制）**——状态行里必须出现且只出现一个：

| 取值 | 含义 |
|---|---|
| 待裁定 | 方案已写，未获作者批准 |
| 已裁定 | 批准了，但没开工 |
| 已实施 / 已落地 | 有代码 |
| 已搁置（原因） | 明确不做，**必须写原因**，否则下一轮会被重新提出 |
| 已结项 | 全部收口，不再改动 |

**必须带日期**（`YYYY-MM-DD`）。词表用「含受控词」而非「以受控词开头」判定：真实写法大量是
「期 1 已落地（2026-10-30 · M24…）」「P15 已实施 · P16 已实施」，强制前缀只会逼人改一堆本来读得懂的句子；
而「含」已经足够把 `草案 v1，待作者多轮评审`、`部分否决`、`已列入待办` 这类**完全脱离词表**的写法拦下来。

> **为什么现在才强制**：这个词表 2026-10-25 就写在这里，但**从来没有脚本校验过**。
> 2026-10-31 打开校验时实测：`docs/design/` 85 份带状态行的稿子里，**30 份取值不在词表、12 份缺日期、4 份同时出现多个受控词**
> ——这些是「规则存在但无人执行」的存量。首次暴露 46 条，其中 1 条当场修掉（本方案自己的稿子），
> 余 45 条进基线，合计 `C1` 33 + `C1b` 45 = **78 条**，只对新增判红。**基线只许缩小**，不许再往里写。
>
> **2026-11-02：存量已清零**（`docs/agents/doc-placement-baseline.json` 现为 `items: []`）。处理口径记在这里，
> 因为它决定了 76 份稿子顶上那行是怎么来的：
> ① `C1b` 的 43 份**只补受控词与日期、不改结论**，原句里的限定语（「部分否决」「待评审」「已撤销」）原样保留；
> ② `C1` 的 33 份原本没有状态行，按「文档自身写明的结局 → 词表」补，并在行尾标注 **`状态行 2026-11-02 回溯补登`**，
> 让读者知道这行是后加的，不是作者当初的判断；
> ③ 补登一律以**文档正文里的实施记录 / 裁定节**为准，不按索引里的一行摘要猜 —— 这一条当场捞回 4 份写错的状态
> （`p7-review-material-dedup-design` 正文写着「已实施」、`phase2-keyevents-bprime-implementation-plan` 段一/段三已落地、
> `layered-generation-assessment` §10 G1 已落地、`outline-setting-compatibility-guard-design` §9 R5 已落地）。
> **这正是上一段警告的那件事**：脚本只能保证词在表里，判断得靠正文。

**状态变化只改这一行**，不新建文件、不新开"v2 稿"。跨版本演进（如 `arc-prompt-v2` → v7）是**验证件**，属于例外，但每份仍要有状态行。

> **⚠️ 这一层只能防「词表失控」，防不了「说法与事实不符」。** 2026-10-30 的实例：`e704a697` 提交信息写
> 「P2-2 期 2 完成」（改 24 个文件），而主稿写着「期 2 未开工」、子稿写着「只写文档未改代码」——
> 三处都**有**状态行、词也都在表里，脚本一个字都不会报。把这种漂移判红，需要「登记表 + 证据锚」，
> 属 B 档（见 [`harness-and-docs-reorganization-plan.md`](../design/harness/harness-and-docs-reorganization-plan.md)），本层不承诺。
> 当前能做的只有一件事：**收口时别漏位置** —— 见 §9 的 `--status-of`。

### 5.3 归档

| 判定 | 动作 |
|---|---|
| 被新稿取代 | 移到 `docs/design/archive/`，原位置留指针 |
| 交接快照超过 30 天且无引用 | 移到 `docs/handoffs/archive/` |
| 已完成且不再被引用 | 移到 `docs/design/archive/` |

**`docs/design/archive/` 于 2026-10-24 建立**——在此之前 `docs/README.md` §2.5③ 就指向它，而目录并不存在，规则等于空文。

归档四步（缺一步就会断链）：

1. `git mv` 移动文件；
2. 原位置留一行指针：`> 已归档（YYYY-MM-DD）→ archive/<文件名>`（写成行内代码，不要写成本仓库不存在的示例链接）；
3. `grep` 全库改引用（相对路径会变）；
4. 跑 `node scripts/check-doc-links.mjs` 与 `node scripts/check-doc-placement.mjs`。

**不能归档**：`docs/adr/` 既有条目、现行设计稿、唯一台账、`novel-quality-*` 冻结子树。

## 6. 完成定义（Definition of Done）

代码改完 ≠ 任务完成。提交前逐条勾：

```
[ ] pnpm check:fast 通过（typecheck + 两个文档检查，约 30s）
[ ] 跑了受影响的测试文件（不只是改动所在模块的测试）
[ ] 改了行为 → 对应设计稿的 §实施记录 + 头部 > 状态： 行已同步
[ ] 收了某一期 → 所有写着该期状态的位置都改了（顶部/分期表/台账/路线图）
    —— 别靠记忆：node scripts/check-doc-placement.mjs --status-of "<期名>"
[ ] 新增设计稿 → 已在 docs/README.md §4 对应小节登记一行
[ ] 改了行为且跑过全量 → pnpm check:full（含 lint 与全量测试，慢，不强制每次）
[ ] 新增 TODO → 已追加到台账，没另建台账
[ ] 文档里的图是 Mermaid，且每张图有一句读法
```

理由：文档腐烂的根源不是"忘了写"，是"写完了但没人知道该写"。把文档同步和测试并列写进完成条件，才有执行力。

**从「规则」到「闸门」**：上面这份清单原来是"人记得就做"。2026-10-31 起，第一条由 `.git/hooks/pre-commit`
自动执行（`pnpm hooks:install` 安装，`pnpm install` 时也会自动装）。**只跑快档**——理由见 §9。

## 7. 新窗口 agent 的开工与收尾

### 第 0 步：复述本轮授权（R01 闸门，2026-11-07 作者定）

**动手前先公开写下一句**：`本轮授权：<只读 / 只计划 / 可改码 / 可提交 / 可推送>`，可多选。规则四条：

1. **作者没明说 ⇒ 按最窄（只读）执行**。默认拒绝，不做善意推断（"他大概是让我改"不算授权）。
2. **每一类越界动作都要单独出现在这句里**：改码 ≠ 可提交 ≠ 可推送 ≠ 可改状态行。缺哪一项，哪一项就不许做。
3. **中途要扩大范围 ⇒ 先问一句，得到答复再动手**。「先做再解释」按越权处理，不因结果正确而豁免。
4. **复述与作者原话不符 ⇒ 以作者原话为准**，立即停手重述，不得按自己的理解继续。

**为什么默认取最窄**：2026-11-07 上一窗口把「只做计划」做成「计划未批先执行」——代码已改、状态行已改，作者回看时**无法完整撤回**。授权是唯一能挡住「不可逆动作发生在确认之前」的东西，所以它必须 fail-closed。

**已知它治不了什么**：这是一条**自证式**闸门——Agent 可以不复述就动手，脚本抓不到。它的效力来自作者能一眼看出「这句复述在不在、范围对不对」。所以复述必须写在**可见的回复正文**里，不能写进内部思考。

### 开工五步（约 3 分钟，在第 0 步之后）

1. 读 `AGENTS.md`（本机常驻宪法；若不存在，见 §7.1）。
2. 读本文件 **§4 放置决策树** 与 **§6 完成定义**。
3. `git status --short` + `git rev-parse --short HEAD` + `git log --oneline -5`：确认基准与脏状态，别在未知分支上动手。
4. 读 `docs/plans/prompt-assembly-backlog.md` **顶部优先级表**（当前该做什么以此为唯一口径）。
5. 只读**当前任务相关的 1–2 份**设计稿；不要整目录通读（上下文成本的主要浪费就在这里）。

### 收尾三步

1. 状态行 + 索引 + 台账（对照 §6 清单）。
2. 跨会话任务写 `docs/handoffs/YYYY-MM-DD-主题.md`：分支、基准 SHA、做了什么、**未验证事项**。
3. 跑 §9 的两个脚本。

### 7.1 AGENTS.md 不存在时（2026-10-25 起）

`AGENTS.md` **已入库**（见 [`adr/0025`](../adr/0025-track-agents-md-and-copilot-channel.md)），新克隆的机器上**直接存在**，不再需要重建。
只有它被误删时才按本节处理：以本文件为准，按 §2 的 L0 三件（项目地图 / 命令集 / 硬规则）重建一份 ≤60 行的 `AGENTS.md`，
并在首行写 `<!-- charter-version: <本文件的 charter-version> -->`。两处版本号不一致时脚本会报 C7。

## 9. 体检脚本与基线纪律

```bash
pnpm check:fast                                        # 闸门档：typecheck + 两个文档检查（~30s，pre-commit 跑这个）
pnpm check:full                                        # 全档：check:fast + lint + 全量测试（慢，作者手动跑）
pnpm check:docs                                        # 只跑两个文档检查

node scripts/check-doc-links.mjs                       # 断链
node scripts/check-doc-placement.mjs                   # 报告（退出码恒 0）
node scripts/check-doc-placement.mjs --strict          # 有「新增」违规时退出 1（CI / pre-commit 用）
node scripts/check-doc-placement.mjs --update-baseline # 重写基线（只许缩小）
node scripts/check-doc-placement.mjs --status-of "期 2" # 列出所有写着这个状态的文档（收口用，退出码 0）
```

| 码 | 检查 | 处理口径 |
|---|---|---|
| C1 | `docs/design/` 缺 `> 状态：` 行 | 存量进基线 |
| C1b | 状态行**取值不在受控词表**（§5.2）或**缺日期**或**同时出现多个受控词** | 硬拦新增（2026-10-31 新增校验；存量 76 条已于 2026-11-02 清零，基线为空） |
| C2 | 设计稿未在 `docs/README.md` §4 登记 | 存量进基线（**新增必须当场登记**） |
| C3 | 文件名不符合小写 ASCII 规则 | 存量进基线 |
| C4 | 文档里链接的相对**目录**不存在 | 存量进基线 |
| C5 | 放在禁放区（根目录白名单外的 md / `plans/` 下的设计稿） | 存量进基线 |
| C6 | 断链 | 与 `check-doc-links.mjs` 同源，**不允许进基线** |
| C7 | 本机 `AGENTS.md` 与本文档的 `charter-version` 不一致 | 修正后消除 |

**基线纪律**（`docs/agents/doc-placement-baseline.json`）：

1. 基线**只允许缩小**。修复一条就重跑 `--update-baseline` 收窄。
2. **新增违规不得写入基线**。写进去等于把违规洗白；要么修，要么在台账登记"暂缓 + 理由 + 期限"。
3. 基线文件本身的变化必须在提交信息里说明（"基线 41 → 33"），否则没人知道违规是在减少还是被藏起来。
4. **例外说明（2026-10-31）**：`C1b` 上线时基线是 `33 → 79`（+46），随后当场修掉方案稿自己那条 ⇒ **78**。
   这不是洗白新增，而是**把一条 2026-10-25 就存在、却从未被校验的规则打开后暴露的存量**。此后 78 只许变小。

**为什么不默认阻断**：首次运行必然命中存量违规，硬阻断会把正在进行的文档改造卡死。`.github/workflows/pr-ci.yml` 若要接，接 `--strict`（只对新增判红）。

**为什么 `pnpm check:fast` 不含全量测试**：本机单进程全量跑测是 20 分钟起步，且 2026-10-31 实测连续三次
跑不到汇总（文件列表打完就没有下文）。把它放进 pre-commit，第一天就会被 `--no-verify` 绕过——
闸门一旦被绕，就退化成"写在文档里的规则"，正是本机制要消灭的东西。**快的用闸门拦，慢的留给手动。**

## 11. 提请裁定的材料口径（2026-11-06 作者定，最高优先）

> **一条事实只活一份**：本节是「裁定材料怎么写」的**权威正文**；AGENTS.md 硬规则 10、交接稿、台账、看板卡只写一句指针，不复制四段模板与理由。**事故现场的作者原话记录不在此限**（那是事实记录，不是规则正文）。
> 适用范围：**所有 harness、所有裁定形态**（对话内口头提请、看板卡、交接稿、复核意见），不限于 D8。

### 11.1 硬规则与四段模板

**向作者提请裁定，材料必须先用产品语言把问题讲清；代码、行号、符号名只作证据，不作叙述主线。** 这里的产品语言 = **作者能看到的界面动作与结果**（点了什么、屏幕上变成什么、接下来还能不能做），不是实现术语。四段缺一段就不算裁定材料，退回重写：

| 段 | 要回答 | 反例 |
|---|---|---|
| ① 实际操作流程 | 作者本来在做什么，依次点了什么，走到哪一步 | 直接从「某个守卫命中」开头 |
| ② 卡点 | 这一步**不符合什么操作流程／操作预期**；期望什么、实际什么 | 只说「冲突 / 张力」，不说谁被卡住 |
| ③ 想怎么改 | **产品意图**（要保住哪条流程、给作者什么能力），不是实现手段 | 直接给「撤回半句 / 放宽红线」二选一 |
| ④ 现行方案改下去会造成什么结果 | 每个选项分别落到作者以后会遇到什么、会失去什么 | 用「风险不对称 / 超出边界」这类工程判断代替后果 |

末尾给**明确的建议**（不是把选项摆回去让作者挑），以及「若采纳，下一步动哪几处」。

### 11.2 为什么（作者 2026-11-06 原话提炼）

- **甩代码会消灭产品视角**：作者看代码只能判断「技术上合不合理」，这个判断与 Agent 大致相同 ⇒ 双方判断趋同，**没有人从产品角度审视它是不是对的**，于是目标一步步漂移，最后走进死胡同。
- **技术服务于产品，关键时刻要向需求让步**：只从技术看，根本不会诞生「解耦」这类选项 —— 选项空间被现有实现框死，等于「螺丝壳里做道场，庙越做越窄」。
- **产品视角能一眼分辨伪冲突**：C1 从产品看是「续写、重写两条流程线，根本不冲突」；C2 从产品看是「按钮该按 type 解耦」。这两条在代码视角下容易被读成同一个问题，因而不容易被单列出来。

### 11.3 事故复盘：D8（本节存在的理由）

| 环节 | 实际发生 |
|---|---|
| 起因 | 方案把「一个未完成状态只能有一种解释」当前提，写成 A（整批重来）/ B（接着写）单选；作者裁 A、B 整节作废（设计稿 §3.2 / §8）。**同一个决策点只有一颗按钮、检查点里只有一份未完成状态**，该前提在实现里成立，但「续写 + 重写两条线并存」这个产品选项从一开始就没被列进选项表 |
| 放大 | 裁定 4 又把 C（重置）当作要关闭的按钮钉死，而不是一条独立的创作流程；§9:256「重置后的拦截也得改通」悬着没撤 ⇒ 除根因（裁定 1 的 A/B 单选）之外，重来这条线连一个自己的合法状态都没有 |
| 后果一（伪裁定 C1） | 作者点「重置情节大纲检查点（从全书起点重来）」或清空上游后再生成，被防误删守卫拦住；系统要求他恢复刚丢弃的检查点、或**清空数据库中已生成的情节大纲**（`architecture.command.ts:3344` 原文）⇒ **合法创作流程变成死胡同** |
| 后果二（伪裁定 C2） | 情节大纲候选与世界观候选共用一颗「断点续写」按钮（数据层与行为层其实已按 type 分流，只差 UI 层），改文案被迫「按 kind 改字符串」、连带浏览器断言 ⇒ 被当成「要不要放宽并行红线」的结构裁定 |
| 两轮审核为何没拦住 | 两轮审查的**主体**都是「方案内部自洽 + 与代码/标准一致」；03:20 豆包还核了行业归类、两个常量的唯一定义处与守卫的两条现存入口，但**两轮都接受了 A/B 单选前提，没把「问题定义」单列一问**。清单 / 行号核查只能保证说法自洽，判断得靠读产品流程的人 |
| 怎么发现的 | 作者明确要求「不要从代码角度解释，从产品角度讲：实际过程中遇到什么卡点、不符合什么操作流程、想怎么改、现行方案会造成什么结果」；换了口径，两处伪裁定当场显形 |

**结论**：C1 / C2 不是待裁项，是**耦合制造出来的伪问题**。v3 任务书回炉，代码零改动。

### 11.4 规避方案（写材料 / 审方案时各过一遍）

1. **动笔前先问**：「这件事在作者的实际操作流程里，是哪一步卡住了？」答不上来 ⇒ 还没到产品层，不许提请裁定。
2. **出现「非此即彼」就亮黄灯**：先查是不是把「一个入口承载多个意图」压成单选。两条流程线可以并存、按钮可以按 type 拆开时，就不该有 A/B 裁定。
3. **别把现状当铁律**：实现约束（并行红线 / ABI / 缓存）与产品约束分开写。红线本身可以成立，但「因为共用按钮所以只能改字符串」是耦合债，不是边界。
4. **审核也要查前提**：复核方案时，除核「行号 / 说法与代码是否对得上」，必须单列一问「这份材料要解决的问题，在产品流程里定义对了吗」。
5. **与「复核只跑一轮」的关系**（规则在 `docs/agents/task-board-channel.md` §5.2「复核要收敛」与 §5.4「质量边界」，**不是本文件 §5.4**）：那一轮约束的是**对同一份方案反复打磨**；作者指出**需求前提错了**属方案回炉，不是第三轮挑刺，不受「还能更好不进本轮」限制。**门槛：只有作者本人能触发这个例外** —— 复核者仍只能用 `unmet` / `regression` 打回，不得以「前提错了」绕过 AGENTS.md 硬规则 9；作者改前提按新卡 / 方案回炉处理，不计复核轮次。

## 12. 规则分档（2026-11-07 作者定）

> **一条事实只活一份**：本节是「规则该占多少注意力」的**权威正文**；`AGENTS.md` §0 只放速查表与三问，全量登记在 [`rule-registry.md`](./rule-registry.md)。改档位只改台账那一行 + 本节判据，不许在注入层或交接稿里另立一套。

### 12.1 问题：红线等重 = 没有红线

2026-11-07 核查两件事，指向同一个根因：

- **事故**：上一窗口把「只做计划」做成「计划未批先执行」，改了代码、改了状态行。回查发现**没有任何一条规则禁止这件事**——不是被忽略，是从没写过。
- **症状**：40 余条规则全部 `★★` / `★` 等重，无档位。读者无法判断哪条该先看 ⇒ 关键的没被看见，冗长的被略读。

同时还有一个自欺：**「上限 60 行」被当成可以商量的数字**。上一轮讨论的是「加到 70 行塞进 5 条红线」，这等于承认上限可破——上限一破，下一条红线进来时还会破第二次。

**真实用意**：60 行不是篇幅指标，是**准入闸门**。它逼你每次想加一条就先删一条。所以正确的动作永远是**降档**，不是扩容。

### 12.2 判据：按失败形态分，不按主题分

「这条重不重要」是主观判断，「违反了会怎样」是客观事实。只用后者：

| 档 | 准入（两条同时成立） | 形态 | 落点 | 容量 |
|---|---|---|---|---|
| **T0 不变量** | ① 后果**不可逆或静默**（数据丢失 / 错提交 / 越过授权 / 方向漂移）② **每次会话都可能触发** | 一句祈使句，**不写原因、日期、事故编号** | `AGENTS.md` §2 | **≤ 8 条** |
| **T1 触发型** | 有明确触发条件（「动 X 前」），但不是每次会话都该占注意力 | 条件 + 一句动作 + 指针 | 记忆注入层 / 通道手册 | 受 8,000 字符滚动 |
| **T2 判据型** | 要用它得先有判断力（边界、反例、为什么） | 全文 | `notes/*.md` | 无 |
| **T3 证据型** | 一次复盘、一次交接 | 全文 | `docs/handoffs/`、ADR | 无 |

**降档三问**（加任何规则前逐条答，任一答否 ⇒ 进不了 T0）：

1. **违反了，作者当天能自己看出来吗？** 能（报错 / 测试红 / 界面明显不对）⇒ 交给脚本闸门，不占 T0 的注意力。
2. **每次会话都有机会被违反吗？** 只在「加列 / 改模板 / 收口一期」才有机会 ⇒ T1。
3. **删掉原因只留一句话，作者还能照着执行吗？** 不能 ⇒ 它是知识点，不是规则 ⇒ T2。

### 12.3 两条附加约束

1. **T0 必须配闸门**。合法的闸门形态有三种：**脚本**（C1b / C7 / `check:fast`）· **强制读入点**（常驻文件本身）· **fail-closed 的默认值**（不声明就按最窄执行，见 §7 第 0 步）。三种都没有 ⇒ 台账标 🕳 并进缺口表。**没有闸门的 T0 只是愿望。** 依据 §2 反模式与 harness 讲义 L08：「文档可以被忽略，原语不能被绕过」。
2. **T0 上限 8 条，不许扩容量**。要加第 9 条，先证明现行 8 条中有哪条的失败形态已不成立。**任何"这次特殊、先加一行"都属于破线**，按 §12.1 的结论处理：降档或删一条。

### 12.4 篇幅上限改为双约束

只卡行数会被「压成一行长段」绕过（2026-11-07 实测：`AGENTS.md` 60 行里含一段 380 字无换行说明）。

> `AGENTS.md` 硬顶 = **≤ 60 行 且 ≤ 4,500 字符**。两者任一超出即须下沉，不得以另一项有余量抵扣。
