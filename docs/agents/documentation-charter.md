# 文档章程（Documentation Charter）

> 状态：已生效（2026-10-24）· `charter-version: 2026-10-24`
> 适用范围：本仓库 `docs/` 下全部文档，以及本机 `AGENTS.md`
> 关系：**索引与放置表**在 [`docs/README.md`](../README.md) · **贡献流程**在 [`CONTRIBUTING.md`](../../CONTRIBUTING.md) · **交付流程**在 [`delivery.md`](./delivery.md)。本文件只写**纪律与闭环**，不复述那三份的内容。
> 缘起：新会话 agent 反复把文档放错位置（实证见 §8）。规则本身早就有，缺的是**入口**与**反馈**——见 §1。

---

## 1. 为什么需要这份章程

2026-10-24 的核查结论：**规则不缺，缺两个闭环。**

| 闭环 | 缺什么 | 后果 |
|---|---|---|
| **入口闭环** | 规则写在 `docs/README.md`，但那个文件只在「我要找文档」时才会被打开；根目录又没有常驻指令文件（`/AGENTS.md` 被 `.gitignore:58` 忽略） | 新会话 agent 开工前**从不读规则**，凭习惯把设计稿写到 `docs/plans/` 或根目录 |
| **反馈闭环** | 唯一的检查脚本 `scripts/check-doc-links.mjs` **只查断链**，不查状态行、索引登记、命名、放置位置 | 违规可以无限累积；规则是否被遵守**无人知道** |

**本文件的定位**：把"人记得住的约定"变成"agent 开工必读 + 脚本可查"的两件东西。规则条文继续留在 `docs/README.md`，本文件负责**四层模型（§2）、单一事实源（§3）、完成定义（§6）、开工流程（§7）与反例（§8）**。

## 2. 四层文档模型：谁进上下文、什么时候进

> 判断标准只有一条：**不读它，agent 一定会悄悄犯错吗？** 会 → 允许常驻；不会 → 下沉，按需读。

| 层 | 承载物 | 谁读 | 进上下文的方式 | 长度约束 |
|---|---|---|---|---|
| **L0 常驻宪法** | `AGENTS.md`（本机，不入库）· 本文件 | 每个新会话 | AGENTS.md **全文常驻**；本文件按 §7 只读 §4/§6 | AGENTS.md **≤ 60 行**，超出必须下沉 |
| **L1 索引** | [`docs/README.md`](../README.md) | 找文档 / 放文档时 | 只读 §1 那张表 + §3 决策树 + §4 对应小节的**行** | 已 300 行；加行前先问「这行能不能并进既有行」 |
| **L2 任务级** | `docs/design/<主题>/*-design.md` · `docs/handoffs/` | 做某一件事时 | 只读**当前任务相关的 1–2 份**，不整目录通读 | 单稿不限；设计是树，靠头部 `> 上级稿` 串 |
| **L3 长期沉淀** | `docs/adr/` · `docs/plans/prompt-assembly-backlog.md` | 改契约 / 决策 / 排期前 | 按编号或条目**检索**，不通读 | ADR 一篇一决定；台账一节一项 |

**反模式（明确禁止）**：
- ❌ 把 L2 的内容塞进 L0（AGENTS.md 变成 200 行的"项目百科"）——agent 会略读，等于没写。
- ❌ 把 L3 的结论抄进 L1（README 变成"为什么"的集散地）——README 只回答"打开哪个文件"。
- ❌ 为了"看得全"而新建一份汇总稿——汇总稿必然腐烂，**索引 + 检索**才是可持续的。

## 3. 单一事实源纪律

**一条事实只活一份。** 同一规则在 README、本文件、AGENTS.md 各写一遍的结果是：更新时必漏一处，然后 agent 不知道该信哪个。

| 事实 | 权威处 | 其他处只能 | 已知重叠（2026-10-24 实测） |
|---|---|---|---|
| 放置决策树（放哪） | `docs/README.md` §3.1 | 指路，不复述条目 | 本文件 §4 只讲判定原则与高频误判 |
| 状态行写法 | `docs/README.md` §3.2-3 | 指路 | 本文件 §5 只补"允许的取值"与脚本识别范围 |
| 命名约定 | `docs/README.md` §3.3 | 指路 | 本文件 §5 只给正则，不重列表 |
| 检查命令 | `AGENTS.md` 命令块 | 指路 | 本文件 §9 只讲**判定规则**与基线纪律 |
| 待办优先级 | `docs/plans/prompt-assembly-backlog.md` 顶部表 | 指路 | 任何设计稿不得另立优先级表 |
| 长篇文章的生产链定级 | `design/architecture/long-form-readiness-review.md` §1.1 | 指路 | 创作侧见 `long-form-craft-alignment-assessment.md`，两者互补不互抄 |
| 术语（continuity / story bible / …） | `design/architecture/industry-alignment-and-stage-goals.md` §2 | 指路 | 设计稿**必须用右侧的词**，不自造概念 |

**执行方式**：改一张表的条目时，顺手 `grep` 它的标题关键词，确认没有第二处在复述。这步 30 秒，能省掉一次"两份文档打架"。

## 4. 放置决策树：三个高频误判

**判定表见 [`docs/README.md`](../README.md) §3.1，本节不复制。** 这里只说三个真实发生过、且脚本抓不到的误判：

| # | 误判 | 为什么错 | 正确落点 |
|---|---|---|---|
| 1 | 把**评估稿 / 设计稿**写进 `docs/plans/` | `plans/` 只剩台账与冻结子树；冻结子树被 `vite.config.ts` 与 `donor-delta.json` 按字面路径引用，混放会让"哪份是台账"失去唯一性 | `docs/design/<主题>/<主题>-assessment.md` |
| 2 | 为"实施记录"**新开一份文件** | 状态从此分散在 ≥2 个文件，收口时必漏改（2026-10-22 的教训：只改了顶部状态行，路线图表没标 ✅，读者以为没做完） | 写进**原设计稿**的「实施记录」小节，只改头部 `> 状态：` 行 |
| 3 | 把**一次性排查结论**当成设计稿入库 | 结论有日期、会过时；设计稿是"现行方案"，混进排查记录后没人敢归档它 | 跨会话交接 → `docs/handoffs/YYYY-MM-DD-主题.md`；长期有效的结论 → 台账条目或 ADR |

## 5. 命名 / 状态行 / 归档

### 5.1 命名

一律 **小写 ASCII**（数字、连字符、点），不含中文与空格。五类具体格式见 `docs/README.md` §3.3；脚本用这条正则校验：

```
^[a-z0-9][a-z0-9.-]*\.md$
```

目录自带的 `README.md` 是索引件，不套用本条。

### 5.2 状态行

每份 `docs/design/` 下的设计稿，头部必须有状态行。两种写法都合法（脚本都认）：

```markdown
> 状态：已实施（2026-10-24）
> **状态**：✅ 已落地（2026-10-24，M17）
```

允许的取值（`docs/README.md` §3.2 第 3 条的定义，此处只列全集）：

| 取值 | 含义 |
|---|---|
| 待裁定 | 方案已写，未获作者批准 |
| 已裁定 | 批准了，但没开工 |
| 已实施 / 🚧 期 N 已落地 | 有代码 |
| 已搁置（原因） | 明确不做，**必须写原因**，否则下一轮会被重新提出 |
| 已结项 | 全部收口，不再改动 |

**状态变化只改这一行**，不新建文件、不新开"v2 稿"。跨版本演进（如 `arc-prompt-v2` → v7）是**验证件**，属于例外，但每份仍要有状态行。

### 5.3 归档

| 判定 | 动作 |
|---|---|
| 被新稿取代 | 移到 `docs/design/archive/`，原位置留指针 |
| 交接快照超过 30 天且无引用 | 移到 `docs/handoffs/archive/` |
| 已完成且不再被引用 | 移到 `docs/design/archive/` |

**`docs/design/archive/` 于 2026-10-24 建立**——在此之前 `docs/README.md` §2.5③ 就指向它，而目录并不存在，规则等于空文。

归档四步（缺一步就会断链）：

1. `git mv` 移动文件；
2. 原位置留一行指针：`> 已归档（YYYY-MM-DD）→ archive/<文件名>`（写成行内代码，不要写成本仓库不存在的示例链接）；
3. `grep` 全库改引用（相对路径会变）；
4. 跑 `node scripts/check-doc-links.mjs` 与 `node scripts/check-doc-placement.mjs`。

**不能归档**：`docs/adr/` 既有条目、现行设计稿、唯一台账、`novel-quality-*` 冻结子树。

## 6. 完成定义（Definition of Done）

代码改完 ≠ 任务完成。提交前逐条勾：

```
[ ] 跑了受影响的测试文件（不只是改动所在模块的测试）
[ ] npx tsc --noEmit 通过
[ ] 改了行为 → 对应设计稿的 §实施记录 + 头部 > 状态： 行已同步
[ ] 收了某一期 → 所有写着该期状态的位置都改了（顶部/分期表/台账/路线图）
[ ] 新增设计稿 → 已在 docs/README.md §4 对应小节登记一行
[ ] node scripts/check-doc-links.mjs 无断链
[ ] node scripts/check-doc-placement.mjs 无「新增」违规
[ ] 新增 TODO → 已追加到台账，没另建台账
[ ] 文档里的图是 Mermaid，且每张图有一句读法
```

理由：文档腐烂的根源不是"忘了写"，是"写完了但没人知道该写"。把文档同步和测试并列写进完成条件，才有执行力。

## 7. 新窗口 agent 的开工与收尾

### 开工五步（约 3 分钟）

1. 读 `AGENTS.md`（本机常驻宪法；若不存在，见 §7.1）。
2. 读本文件 **§4 放置决策树** 与 **§6 完成定义**。
3. `git status --short` + `git rev-parse --short HEAD` + `git log --oneline -5`：确认基准与脏状态，别在未知分支上动手。
4. 读 `docs/plans/prompt-assembly-backlog.md` **顶部优先级表**（当前该做什么以此为唯一口径）。
5. 只读**当前任务相关的 1–2 份**设计稿；不要整目录通读（上下文成本的主要浪费就在这里）。

### 收尾三步

1. 状态行 + 索引 + 台账（对照 §6 清单）。
2. 跨会话任务写 `docs/handoffs/YYYY-MM-DD-主题.md`：分支、基准 SHA、做了什么、**未验证事项**。
3. 跑 §9 的两个脚本。

### 7.1 AGENTS.md 不存在时

`.gitignore:58` 让 `/AGENTS.md` 不入库（仓库不发布内部 agent 指令）。新克隆的机器上它不存在，此时**以本文件为准**：按 §2 的 L0 三件（项目地图 / 命令集 / 硬规则）重建一份 ≤60 行的本机 `AGENTS.md`，并在首行写 `<!-- charter-version: <本文件的 charter-version> -->`。两处版本号不一致时脚本会报 C7。

## 8. 反例库（2026-10-24 实测，不是假想）

| # | 反例 | 实际后果 |
|---|---|---|
| 1 | 规则只写在 `docs/README.md` | 新窗口 agent 不读它，继续乱放——**这是本次补章程的直接原因** |
| 2 | 归档规则指向 `docs/design/archive/` | 该目录**根本不存在**，规则等于空文 |
| 3 | 索引自称"完整索引即本节" | 实测漏了 **8 篇**设计稿（P1-1 四格、能力形状提案、P1-2 卷末交接、卷单元结构、W8）；读者信了索引就找不到 |
| 4 | 状态行规则写了，但没有检测 | 首次跑脚本：**33 份**设计稿没有 `> 状态：` 行 |
| 5 | "实施记录"另开文件 | 状态分散，收口时漏改路线图表（2026-10-22 已发生过一次） |

反例 3 与 4 已在本次修复/登记；反例 2 已建目录；反例 1、5 由 §2、§4 与脚本共同兜住。

## 9. 体检脚本与基线纪律

```bash
node scripts/check-doc-placement.mjs                  # 报告（退出码恒 0）
node scripts/check-doc-placement.mjs --strict         # 有「新增」违规时退出 1（CI 可用）
node scripts/check-doc-placement.mjs --update-baseline # 重写基线
```

| 码 | 检查 | 处理口径 |
|---|---|---|
| C1 | `docs/design/` 缺 `> 状态：` 行 | 存量进基线 |
| C2 | 设计稿未在 `docs/README.md` §4 登记 | 存量进基线（**新增必须当场登记**） |
| C3 | 文件名不符合小写 ASCII 规则 | 存量进基线 |
| C4 | 文档里链接的相对**目录**不存在 | 存量进基线 |
| C5 | 放在禁放区（根目录白名单外的 md / `plans/` 下的设计稿） | 存量进基线 |
| C6 | 断链 | 与 `check-doc-links.mjs` 同源，**不允许进基线** |
| C7 | 本机 `AGENTS.md` 与本文档的 `charter-version` 不一致 | 修正后消除 |

**基线纪律**（`docs/agents/doc-placement-baseline.json`）：

1. 基线**只允许缩小**。修复一条就重跑 `--update-baseline` 收窄。
2. **新增违规不得写入基线**。写进去等于把违规洗白；要么修，要么在台账登记"暂缓 + 理由 + 期限"。
3. 基线文件本身的变化必须在提交信息里说明（"基线 41 → 33"），否则没人知道违规是在减少还是被藏起来。

**为什么不默认阻断**：首次运行必然命中存量违规，硬阻断会把正在进行的文档改造卡死。`.github/workflows/pr-ci.yml` 若要接，接 `--strict`（只对新增判红）。

## 10. 复核节奏

| 时机 | 动作 |
|---|---|
| 每次提交前 | 跑两个脚本（§6 已列） |
| 每次大版本 / 每季度 | 跑脚本 → 清新增 → `--update-baseline` 收窄 → 若 `docs/design/` 新增主题子目录，在 README §4 建一节 |
| 每份新设计稿入库时 | 头部状态行 + 索引一行 + 台账条目（若产生待办） |
| 每次推翻既有决定时 | 新增 ADR（只增不改）+ 在被推翻文档打作废标记 + 指向新 ADR |
